## 1. Google Material 3 — adaptive layout, navigation, foldables, motion, type

m3.material.io is an Angular SPA; every page returned an empty shell to curl (see "Pages that failed"). The M3 rules below are therefore taken from Google's official implementation docs that state they map to the M3 guidance: Android Developers adaptive-layout pages and the `material-components-android` docs on GitHub (Motion.md, Typography.md). Material's own bidirectionality page could not be read; RTL mirroring rules come from Android + Apple (section 5).

| # | Rule / pattern | Documented detail | Source URL | Implication for AWJ |
|---|---|---|---|---|
| 1 | Width window size classes | Compact < 600dp; Medium 600–<840dp; Expanded 840–<1200dp; Large 1200–<1600dp; Extra-large >= 1600dp. Compact/medium/expanded "map to" M3 layout guidance; large/XL added for desktop and connected displays. | https://developer.android.com/develop/ui/compose/layouts/adaptive/use-window-size-classes | Use these as CSS breakpoints in px (1dp ≈ 1 CSS px): 600/840/1200/1600. Tailwind 3 defaults (640/768/1024/1280/1536) don't line up with them; we'd need custom screens. |
| 2 | Height size classes | Compact height < 480dp (99.78% of phones in landscape); Medium 480–<900dp; Expanded >= 900dp. Phone landscape: width medium but height compact, so "two pane layouts are not practical". | same | A landscape phone (e.g. 844×390) must not get the two-pane invoice editor just because width ≥ 600. Gate two-pane on width AND height. |
| 3 | Classes ≠ device type | Size classes are "explicitly not determined by the size of the device screen"; not for `isTablet` logic; they change at runtime (fold, rotate, split-screen). | same | Drive layout from viewport/container size (CSS media/container queries), never from user-agent sniffing. A foldable that unfolds mid-task must keep form state. |
| 4 | Design order | Optimize for expanded width first, then decide what makes sense for medium; test at the compact, medium and expanded breakpoints. | same | For dense ERP screens: design the 840–1200 layout first, then phone, then the 600–840 medium case explicitly (tablets in portrait, unfolded foldables). |

| 7 | Canonical: feed | Grid of equivalent items; becomes one column when compact; adaptive columns with a minimum item width (sample: `GridCells.Adaptive(minSize = 180.dp)`). | same | Dashboards/KPI cards and the storefront only. Not for financial lists, which should stay tables or list-detail. |

| 9 | Foldables: postures | HALF_OPENED gives **tabletop** (horizontal fold) and **book** (vertical fold). Controls near the fold are hard to reach; text over the fold is hard or impossible to read. Split content top/bottom (tabletop) or left/right (book). | https://developer.android.com/develop/ui/compose/layouts/adaptive/foldables/learn-about-foldables | On the web this is mainly about avoiding centered modals across a hinge (Viewport Segments API is experimental; inference). | 10 | Foldables: continuity | Folding/unfolding restarts the app; it must "preserve and restore its state seamlessly". | 11 | Touch target | Touch targets of "at least 48dpx48dp. Larger is even better." Mouse/trackpad targets may be smaller. | https://developer.android.com/guide/topics/ui/accessibility/apps | 48px on touch layouts (POS, station app, phone lists). Dense desktop tables can go below this, but must still meet WCAG 2.5.8 (24px or spacing). |
| 12 | Easing tokens | Standard `cubic-bezier(0.2,0,0,1)`; standard-decelerate `(0,0,0,1)`; standard-accelerate `(0.3,0,1,1)`; emphasized-decelerate `(0.05,0.7,0.1,1)`; emphasized-accelerate `(0.3,0,0.8,0.15)`; linear. Emphasized is a two-segment path. **Standard** = "utility focused" motion; **emphasized** = "common, M3-styled" motion. | https://github.com/material-components/material-components-android/blob/master/docs/theming/Motion.md | A data tool should mostly use the standard curves. Keep emphasized for sheets/panes entering. These can become CSS custom properties. |
| 13 | Duration tokens | 16 tokens: Short1–4 = 50/100/150/200ms; Medium1–4 = 250/300/350/400ms; Long1–4 = 450–600ms; ExtraLong1–4 = 700–1000ms. "Duration should increase as the area/traversal of an animation increases." | same | Menus/tooltips ~100–200ms, sheets/panes ~250–400ms. Nothing above 400ms in daily ERP work; respect `prefers-reduced-motion`. |
| 14 | Springs (newer system) | Six spring attributes (fast/default/slow × spatial/effects), e.g. fast spatial damping 0.9 / stiffness 1400; slow spatial 0.9 / 300. | same | CSS can't express springs natively. Don't adopt them; use the easing+duration tokens. |
| 15 | Type scale roles | 15 baseline roles: Display L/M/S 57/45/36sp; Headline L/M/S 32/28/24; Title L/M/S 22/16/14 (M and S are Medium weight); Body L/M/S 16/14/12; Label L/M/S 14/12/11 (Medium). The newer "Emphasized" scale makes the same sizes heavier. | https://github.com/material-components/material-components-android/blob/master/docs/theming/Typography.md | Dense ERP mostly needs Title S/M, Body M/S, Label M/S. Arabic needs larger sizes and line-height than Latin; 11–12px Arabic labels are risky (see Apple's +2pt advice, §5). |
| 16 | Bidi text in strings | RTL text can contain LTR runs (numbers, embedded Latin). App-generated mixes (text that starts with a number, phone numbers, trailing punctuation) can render wrongly without direction hints. Fix: wrap the inserted string with direction marks (`BidiFormatter.unicodeWrap`). Use start/end, not left/right. | https://developer.android.com/training/basics/supporting-devices/languages | Web equivalent: `<bdi>` or `dir="auto"` / `unicode-bidi: isolate` around interpolated invoice numbers, SKUs, IBANs and phone numbers in Arabic sentences. Use logical CSS (`ms-`/`me-`, `start`/`end`). |

**Do not copy (M3):** Android-only APIs (`NavigationSuiteScaffold`, `WindowSizeClass`); springs; the feed layout for financial data; percentage device statistics (they describe Android devices, not our users); M3 Expressive shapes and colours, which conflict with DESIGN_SYSTEM.md's single-accent, dense look.

## 2. WCAG 2.2 (W3C Recommendation, 12 December 2024 edition)

WCAG 2.2 adds 9 success criteria and **removes one**, 4.1.1 Parsing. It is backward compatible: conforming to 2.2 means conforming to 2.1/2.0. New criteria were added at the end of their guidelines, so the numbering doesn't group them by level.

**About "4.6 removed":** no item 4.6 exists in WCAG 2.2. The removed item is **SC 4.1.1 Parsing**, now labelled "(Obsolete and removed)": assistive technology no longer parses HTML directly, so the criterion "no longer has utility". Authors bound by 2.0/2.1 policies may still need to test and report 4.1.1. (Source: https://www.w3.org/TR/WCAG22/#comparison-with-wcag-2-1 and the 4.1.1 entry.)

## 3. Radix UI Primitives

Radix is an unstyled, low-level primitive library. Components follow the WAI-ARIA Authoring Practices and are tested with common assistive technologies. They are uncontrolled by default but can be controlled, and can be adopted incrementally. RTL comes from a global `Direction.Provider` or a per-component `dir` prop.

| # | Rule / pattern | Documented detail | Source URL | Implication for AWJ |
|---|---|---|---|---|
| 1 | A11y baseline | Follows WAI-ARIA Authoring Practices; handles "aria and role attributes, focus management, and keyboard navigation". | https://www.radix-ui.com/primitives/docs/overview/accessibility | Keep using Radix for dialogs, menus, popovers, selects and tabs instead of custom ones. That is the cheapest route to 2.1.1/4.1.2. |
| 2 | Labels are the app's job | Radix gives labelling abstractions (Label primitive), but "Ultimately it's up to you to provide those labels". | same | Icon-only row actions and filter triggers still need `aria-label` (Arabic and English). |
| 3 | Focus management | Focus moves with interactions, e.g. AlertDialog focuses **Cancel** when opened. | same | Matches safe defaults for destructive ERP confirms (void, delete, post). Don't override autofocus to the destructive button. |
| 4 | Dialog behaviour | "Focus is automatically trapped within modal"; Esc closes; Title/Description handle announcements. Controlled via `open`/`onOpenChange`, uncontrolled via `defaultOpen`; `modal` prop. | https://www.radix-ui.com/primitives/docs/components/dialog | Every dialog needs a `Dialog.Title` (visually hidden if needed). Control from state when a server 409/422 must keep the dialog open. |
| 5 | Controlled vs uncontrolled | "Components are uncontrolled by default but can also be controlled." | https://www.radix-ui.com/primitives/docs/overview/introduction | Use controlled mode where URL/state must persist (tabs synced to `?tab=`, sheets tied to selection in list-detail). |
| 6 | DirectionProvider | Wrap the app in `Direction.Provider dir="rtl"` "to ensure all of the primitives adjust their behavior based on the dir prop". | https://www.radix-ui.com/primitives/docs/utilities/direction-provider | Radix does **not** read `<html dir>` itself. AWJ must render `Direction.Provider` with the next-intl locale direction at the root of each app (ERP, station app, storefront). |
| 7 | Direction affects keyboard | DropdownMenu: "Supports submenus with configurable reading direction"; ArrowRight/ArrowLeft opens/closes a SubTrigger "depending on reading direction". | https://www.radix-ui.com/primitives/docs/components/dropdown-menu | Without the provider, Arabic users press ← to open a submenu and nothing happens (inference from the doc). Test arrow keys in Tabs, RadioGroup, Menubar and Slider in RTL. |
| 8 | asChild composition | Parts accept `asChild`; Radix clones the child and passes behaviour and props. If you change the element, you must keep it accessible (e.g. a Tooltip trigger must stay focusable). | https://www.radix-ui.com/primitives/docs/guides/composition | Use `asChild` to put Tooltip/Dialog triggers on Next `<Link>` or our `Button`. Never use `asChild` on a `div`. |
| 9 | Own components must spread props + forward ref | Custom children must spread all props and forward refs, or Radix "will break". `asChild` nests, e.g. Tooltip.Trigger + Dialog.Trigger on one button. | same | Audit shared `Button`/`IconButton` for `{...props}` and `forwardRef` (React 18; React 19 passes ref as a prop). |
| 10 | Portals | Content (menus, tooltips, popovers) renders in a Portal. Dialog Portal has a `container` prop. | https://www.radix-ui.com/primitives/docs/components/dialog | Portaled content leaves the subtree, so inherited `dir` and theme CSS scope can be lost (see shadcn RTL note below). |

**Known RTL limitations (documented and inferred):** (a) Direction must be given explicitly through the provider or `dir`; `<html dir>` alone is not enough for Radix behaviour (documented). (b) Portaled content may not pick up direction-dependent CSS animations; shadcn recommends passing `dir` to Popover/Tooltip content (documented, §4). (c) Radix doesn't flip icons; that is the app's job (inference).

## 4. shadcn/ui

shadcn/ui is "not a component library. It is how you build your component library": you copy component source into your repo and own it (Open Code, Composition, Distribution through a CLI and a flat-file registry schema). Theming uses semantic CSS variables. RTL is now first-class but tied to the newer styles and CLI transforms.

| # | Rule / pattern | Documented detail | Source URL | Implication for AWJ |
|---|---|---|---|---|
| 1 | Copy-owned model | "The top layer of your component code is open for modification"; edit the button code directly instead of wrapping. | https://ui.shadcn.com/docs | AWJ owns its components (no `components.json`), so RTL/density fixes go straight into `web/src/components/ui`. Upstream updates are manual merges. |
| 2 | Registry | The CLI can run your own registry to distribute components, hooks, pages and config, with namespaces and authentication. | https://ui.shadcn.com/docs/registry | Option for sharing one UI kit across `web/` and `storefront/` (inference; not needed now). |
| 3 | Styles | `style` "cannot be changed after initialization". "The default style has been deprecated. Use the new-york style instead." The theming page now shows `"style": "base-nova"`. RTL page names new styles `base-nova`, `radix-nova`. | https://ui.shadcn.com/docs/components-json ; https://ui.shadcn.com/docs/theming | "new-york" is still documented but newer "nova" styles exist; the docs mix generations. Don't anchor AWJ's design on any shadcn style. DESIGN_SYSTEM.md governs. |
| 4 | CSS-variable theming | Semantic pairs: base token = surface, `-foreground` = content on it (`primary`/`primary-foreground`). Tokens in `:root` and `.dark`. | 11 | Amount cell example | Formats with `Intl.NumberFormat("en-US", {currency:"USD"})` and `text-right` on header and cell. | same | Don't copy literally: use `text-end`, locale-aware formatting from halalas, and `tabular-nums`. Keep digits Latin where AWJ requires it (inference). |

| 13 | Sidebar structure | Composition: `SidebarProvider` › `Sidebar` (Header sticky, Content scrollable, Footer sticky, Group, Menu, MenuSub, Rail) + `SidebarInset` + `SidebarTrigger`. ## 5. Apple Human Interface Guidelines — Right to left, Layout (optional)

Fetched through Apple's JSON content endpoint (the HTML page is JS-rendered). Apple's guidance is the most explicit official list of what to mirror and what not to mirror.

| # | Rule / pattern | Documented detail | Source URL | Implication for AWJ |
|---|---|---|---|---|
| 1 | Text alignment | Align to the interface direction. A **paragraph (3+ lines)** aligns to its own language, not the context. One- and two-line blocks follow the context. All list items use one consistent alignment. | https://developer.apple.com/design/human-interface-guidelines/right-to-left | English notes or descriptions inside an Arabic invoice: use `dir="auto"` on multi-line note fields. Table columns keep one alignment. |
| 2 | Never reverse a number's digits | Digits in a number (e.g. "541", phone, card number) "always appear in the same order". | same | Amounts, invoice numbers, VAT numbers and IBANs are LTR runs inside RTL. Isolate them (`<bdi>`/`dir="ltr"`). Consistent with AWJ's phone-input rule. |
| 3 | Numeral systems vary | Arabic text may use Western or Eastern Arabic numerals, which vary by country and region. Number-centric apps should decide per locale. | same | AWJ has chosen 0–9 for phones. A deliberate numerals policy (per tenant or locale) is a "configurable policy" candidate (inference). |
| 4 | Flip progress/order controls | Flip sliders and progress indicators. Reverse sequences of numerals that show progress or order, but never flip the numerals themselves. | same | Progress bars (import, tank level), steppers (7-step import wizard), and pagination run right-to-left in Arabic. |
| 5 | Flip navigation controls | Back points **right** in RTL. Next/previous in ordered lists flip. | same | Breadcrumb separators, "back" arrows, pagination chevrons, and carousel arrows flip. |
| 6 | Don't flip true directions | A control meaning "to the right" always points right. | same | Text-align-right buttons in the print-template editor, and "move column right", keep their physical arrows. |
| 7 | Don't flip images, logos, universal marks | Don't flip photos or artwork. Never flip logos. Keep universal marks like the **checkmark** unflipped. | same | Don't apply a blanket `rtl:-scale-x-100` to all icons. Product photos, the ZATCA QR, and brand logos stay as they are. |
| 8 | Real-world objects | Generally don't flip icons of real objects; "clocks work the same everywhere". Right-handed tools stay unflipped. | same | Clock/history, calendar, printer, fuel pump, and search (magnifier) icons stay unflipped. |
| 9 | Flip icons that show text or motion | Flip icons that represent text or reading direction (aligned bars), and forward/backward motion (e.g. speaker sound waves). | same | List/align-start icons, "indent", "reply/forward", and "send" flip. |
| 10 | Script balance | Arabic next to all-caps Latin can look too small; "increase the RTL font size by about 2 points". | same | Mixed Arabic/English badges and buttons (VAT, SKU, POS): consider a slightly larger Arabic size or avoid all-caps Latin. |
| 11 | Size classes, not device | Lay out by size class, not device type or orientation. Keep functionality the same across sizes; on larger spaces you may switch "from a tab bar to a sidebar". | https://developer.apple.com/design/human-interface-guidelines/layout | Agrees with M3 #3/#8: bottom bar on phone, sidebar on wide screens, same features. |
| 12 | Safe areas & Dynamic Type | Respect safe areas so hardware features like the Dynamic Island don't block content.
