# تشخيص: بقية مسار Manual Retry بعد #652 — دفعة الإنتاج `a2abffb0-3740-4e40-99cf-0e029b5b1030`

**وضع القراءة فقط — لا تعديل كود، لا PR. كل ما يلي من قراءة الكود الحالي (يطابق `origin/main` عند `eedaee9`) + `render.yaml`/`deploy/DEPLOY.md`.**

---

## 1) السبب الجذري المؤكَّد لـ `document_retry_file_unavailable`

الكود المسؤول (`DocumentRetryService.php:62-64`):
```php
if ($file->purged_at !== null || ! $this->stored($file)) {
    return $this->rejected($locked, $actor, self::CODE_FILE_UNAVAILABLE, 'ملف المستند غير متاح لإعادة المحاولة.');
}
```
`stored()` يستدعي `DocumentStorageService::exists($profile, $objectKey)`.

**الدليل الحاسم من `render.yaml` و`deploy/DEPLOY.md`:**
```yaml
- key: DOCUMENT_DURABLE_STORAGE_ENABLED
  value: "false"
- key: DOCUMENT_STORAGE_DRIVER
  value: local
```
و`DEPLOY.md` نفسه يحذّر صراحةً: *"قرص حاوية Render المحلي مؤقت وقد يفقد الملفات عند إعادة البناء أو استبدال الحاوية. هذه مخاطرة مؤقتة مقبولة خلال مرحلة التطوير."*

**الاستنتاج:** كل ملفات مركز المستندات في الإنتاج اليوم تُخزَّن على القرص المحلي للحاوية (S3/R2 مؤجَّل بقرار مشروع صريح، غير متعلق بالـ Retry إطلاقاً). نشر PR #652 استبدل حاوية Render — قرصها المحلي القديم (وملف هذه الدفعة عليه) اختفى مع الحاوية القديمة. `DocumentStorageService::exists()` يُعيد الآن `false` عن حقّ، لأن جسم الملف **غير موجود فعلياً**، لا لأي خلل في منطق Retry.

`purged_at` مستبعد عملياً: الاحتفاظ الافتراضي 365 يوماً (`DOCUMENT_RETENTION_DAYS`) والدفعة عمرها أيام. **التوصية:** استعلام واحد يحسم الشك المتبقي:
```sql
SELECT purged_at, storage_profile, object_key FROM document_files
WHERE id = (SELECT document_file_id FROM document_processing_runs WHERE document_batch_id = 'a2abffb0-3740-4e40-99cf-0e029b5b1030' AND stage='extraction');
```

## 2) أي حالة/خاصية للملف تسبّبت به — وليست `scan_status`

`scan_status = pending` **لا علاقة له إطلاقاً** بهذه البوّابة. البوّابة تفحص وجود البايتات الخام فقط (`purged_at`, `storage->exists()`) — شرط تقني بحت لازم لقراءة الملف وترميزه base64 قبل إرساله لـ Gemini (`DocumentExtractionService::base64File()`)، لا علاقة له بحالة الفحص الأمني أو الإسناد.

---

## 3) مقارنة مع `DocumentFileScanAdmissionService::authorize()` والإسناد الثابت

الإسناد (`DocumentFileScanExceptionAdmission`) **صفّ في قاعدة البيانات** — لم يتأثر بفقدان القرص المحلي إطلاقاً (Postgres مُدارة منفصلة تماماً عن الحاوية). لو وصل التنفيذ إلى بوّابة `scanAdmission->authorize($file)` (السطر 92)، كان سيُعاد استخدام الإسناد القائم بنجاح تماماً كما في التشغيل الأصلي — **لكن الكود لا يصل إليها إطلاقاً** لأن بوّابة `stored()` الأسبق (السطر 62) ترفض أولاً. لا تعارض بين البوّابتين؛ الترتيب صحيح.

---

## 4) هل يطلب Retry خطأً دلالات CLEAN/معاينة بدل دلالات معالجة؟ — لا

تحقّقتُ من الفصل الثلاثي فعلياً في الكود:

| الفحص | أين | يتحقق من |
|---|---|---|
| وجود البايتات | `DocumentRetryService::stored()` + `DocumentStorageService::exists()` | وجود الكائن في التخزين — تقني بحت، لا صلة بالأمان |
| جواز المعالجة | `DocumentRetryService` → `scanAdmission->authorize($file)` | الإسناد الثابت (PENDING مسموح إن وُجد إسناد صالح) |
| جواز المعاينة/التنزيل | `DocumentIntakeController::assertDownloadable()` (منفصل تماماً): `if ($file->scan_status !== CLEAN ...) throw ValidationException` | **`scan_status === CLEAN` حرفياً — لا شيء غيره** |

**لا تصحيح مطلوب هنا.** الفصل قائم وصحيح فعلاً؛ لا Retry يتسرّب إلى معاينة، ولا معاينة تتساهل مع PENDING مُسنَد. الإصدار #652 لم يمسّ أياً من هذه الحدود ولا حاجة لمسّها الآن.

## 5) تتبّع كل بوّابة لاحقة (بافتراض ملف موجود فعلياً — دفعة مستقبلية سليمة)

| # | البوّابة | الحالة المُتحقَّق منها لهذه الدفعة | الخلاصة |
|---|---|---|---|
| نسخة (version) | `updated_at` مطابق | يُرسَل من الواجهة تلقائياً | آمن |
| مرحلة/حالة | `stage=extraction`, `status=failed` | مطابق | يمرّ |
| **ملف/تخزين** | `purged_at`/`stored()` | **هنا الرفض الحالي** | — |
| **حد دورات retry اليدوي** | `manualRetryCycleCount()` مبني على أحداث `retry_queued` **المقبولة** فقط | لم يُقبَل أي retry لهذا الـ run قط (كل الرفضات السابقة `limit_reached` ثم `file_unavailable`) → العدّاد = **0** | مساحة كاملة (0 < 3 الافتراضي) — لا خطر تصادم مع الإصلاح السابق |
| بوّابة الشبكة | `DocumentProviderNetworkGate::allowsExternalRequests()` | ثابتة من env، نجحت أصلاً في التشغيل الأصلي | متوقَّع أن تمرّ |
| جاهزية السياسة/المزوّد | `policy->enabled()` + `configuration->isOperationallyReady()` | صفوف DB لم تتأثر بفقدان القرص | متوقَّع أن تمرّ |
| إسناد الفحص + الحجر + حجم الملف | `scanAdmission->authorize()` + `!QUARANTINED` + `allowsFile()` | إسناد قائم بالفعل، الدفعة `failed` لا `quarantined` | متوقَّع أن تمرّ (انظر §3) |
| `claim()` + `process()` | إعادة ضبط `attempt_count=0`، محاولة مزوّد جديدة | — | يصل Gemini فعلياً لأول مرة بعد استعادة الملف |

**لا بوّابة أخرى في المسار تشكّل خطراً.** كل بوّابة بعد `stored()` إما ثابتة من env/DB غير متأثرة بفقدان القرص، أو أثبتها التشغيل الأصلي الناجح فعلياً، أو أثبتها إصلاح #652 (حد الدورات) مع دليل عدّاد فعلي = 0 لهذا الـ run تحديداً.

## 6) هل يُتوقَّع عائق إضافي بعد إصلاح `file_unavailable`؟

**لا، بثقة عالية.** المسار كامل ومُثبَت خطوة بخطوة أعلاه. لا يوجد "إصلاح كود" لبوّابة `stored()` نفسها بمعنى تغيير منطقها — لأنها **صحيحة بالفعل**؛ المشكلة بيانات مفقودة فعلياً لا خطأ منطقي.

---

## 7) هل تبقى الدفعة القديمة قابلة لإعادة المحاولة فعلياً، أم تحتاج البنية دفعة جديدة؟

**تحتاج دفعة جديدة.** لا يوجد مسار API لاستبدال ملف دفعة موجودة (`document-batches/{id}/files` هو الرفع الوحيد، ولا يوجد "reupload" على ملف/دفعة فاشلة). فرض نجاح Retry على ملف بايتاته غائبة فعلياً يعني إما:
- تلفيق نجاح باستخراج فارغ/وهمي — **يخالف صراحةً** "لا تلفيق"، أو
- تجاوز بوّابة `stored()` بالكامل — **يخالف صراحةً** عدم إضعاف الفحوصات.

كلاهما مرفوض بنص التكليف. **رفض `file_unavailable` لهذه الدفعة بالذات هو السلوك الصحيح والنهائي، لا عائق يُصلَح.** الحل الوحيد المتّسق مع البنية: رفع المستند من جديد كدفعة جديدة.

## الخلاصة قبل أي Build

- **السبب الجذري لـ `document_retry_file_unavailable` مؤكَّد:** فقدان الملف من القرص المحلي المؤقت لحاوية Render عند استبدالها بنشر #652 — مخاطرة معمارية موثّقة صراحةً ومقبولة مؤقتاً في `render.yaml`/`DEPLOY.md`، لا علاقة لها بمنطق Retry.
- **كل البوّابات اللاحقة فُحصت** (نسخة، مرحلة/حالة، حد الدورات اليدوي، شبكة، سياسة/مزوّد، إسناد فحص+حجر+حجم، claim/process) — كلها إما مُثبَتة سابقاً بالتشغيل الأصلي الناجح، أو غير متأثرة بفقدان القرص، أو مُصلَحة فعلياً في #652 مع عدّاد فعلي = 0 لهذا الـ run.
- **لا عائق إضافي متوقَّع** بعد توفّر ملف حقيقي (دفعة جديدة).
- **الحل يحافظ على CLEAN-only للمعاينة/التنزيل** لأنه لا يمسّ ذلك المسار إطلاقاً — الفصل الثلاثي (وجود بايتات / جواز معالجة عبر الإسناد / CLEAN للمعاينة) قائم وصحيح فعلاً في الكود الحالي، ولا حاجة لتغييره.
- **الدفعة الحالية بعينها لن تنجح بعد أي نشر** — ملفها غير قابل للاستعادة عبر أي إصلاح كود يحترم القواعد المفروضة؛ تحتاج إعادة رفع كدفعة جديدة.

## خطة PR واحد نهائي (اختياري تماماً — لا خلل يُصلَح، بل وضوح تشغيلي فقط)

بما أن **لا خلل منطقي بقي في مسار Manual Retry**، لا يوجد "إصلاح" حقيقي مطلوب لإغلاق القضية. الخيار الوحيد المتبقّي ضمن نطاق Document Center Manual Retry حصراً، إن أراد الفريق PR ختامياً صغيراً لتحسين قابلية التشخيص المستقبلي (بلا أي تغيير سلوكي):

1. **فصل سبب `document_retry_file_unavailable` في البيانات الوصفية لحدث الحوكمة** (`purged` مقابل `missing_from_storage`) — إضافة مفتاح واحد لقائمة `$allowed` في `app/Models/DocumentGovernanceEvent.php:120`، وتمرير القيمة من `DocumentRetryService::rejected()`. **لا تغيير في شرط الرفض نفسه ولا في الاستجابة للمستخدم.**
2. اختبار واحد يثبّت أن `purged_at` و`missing_from_storage` يُسجَّلان بشكل مختلف في `document_governance_events.metadata`.

هذا PR **ليس ضرورياً لإغلاق المشكلة** — المشكلة مغلقة فعلاً من ناحية الكود. أُوصي بعدم البناء الآن، وبدلاً منه: تأكيد الفرضية عبر استعلام `document_files.purged_at`/`object_key` أعلاه، ثم رفع المستند من جديد على دفعة جديدة والتحقق أن Retry الحقيقي ينجح end-to-end (يُنتج `document_provider_attempt` جديداً ويصل `needs_review`) — وهو ما يُثبت أن #652 وحده كافٍ.
