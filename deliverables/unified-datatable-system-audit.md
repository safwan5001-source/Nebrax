# تدقيق نظام DataTable الموحّد في نبراس

> **حالة الوثيقة:** تدقيق ما قبل التنفيذ. ستُحدَّث في نهاية المهمة بنتائج الترحيل والاختبارات وطلب الدمج.

## نطاق التدقيق ومنهجيته

شمل التدقيق جميع مكوّنات القوائم والجداول في `web/src`، بما في ذلك صفحات التشغيل والمالية والمخزون والموارد البشرية والوقود والمنصة، ومكوّنات التقارير والمستندات. جرى تتبّع استعمال `DataTable` و`ReportDataTable` و`ReportResultsTable` وبدائية `<table>`، ثم مراجعة تطبيقات ممثلة ومسارات API الخلفية للمنتجات والفواتير والمشتريات وسجل القيود والتقارير والمخزون. لذلك يفرّق هذا التقرير بين **توحيد العرض** وبين **سلطة البيانات الخادمية**، ولا يستنتج سلامة الفلترة أو العزل من الواجهة وحدها.

| طبقة التدقيق | النتيجة | القرار |
|---|---|---|
| القوائم التشغيلية | 45 تطبيقاً تستعمل `DataTable` بالفعل، لكن بدرجات مختلفة من النضج | توسيع الأساس الحالي؛ لا إنشاء DataTable موازٍ |
| التقارير | 7 تطبيقات تستعمل طبقة تقارير متخصصة فوق TanStack | إبقاؤها طبقة متخصصة مع إعادة استعمال واجهات أعمدة مشتركة حيثما أمكن |
| الجداول المتخصصة | 50 تطبيقاً تستخدم جداول HTML/بدائيات `Table` | لا تُهاجَر آلياً؛ كثير منها تفاصيل مستند أو طباعة أو محرر أو لوحة تشغيلية |
| الواجهة | Next.js وTypeScript وTanStack وRTL و`next-intl` | أي تعديل يلتزم بالمكوّنات والرموز والترجمة القائمة |
| الخلفية | Laravel هو السلطة لعزل المستأجر والفرع وRBAC | لا تُعامل عناصر الواجهة أو الأعمدة المخفية كضوابط أمنية |

## جرد تجارب الجداول الرئيسية

### القوائم التشغيلية المبنية فوق `DataTable`

| المجال | المسارات أو المكونات المكتشفة | النمط السائد | حالة البحث/الفرز/الترقيم | القرار المبدئي |
|---|---|---|---|---|
| المبيعات | `invoices`، `quotes`، `recurring-invoices`، `returns`، `credit-notes`، `debit-notes`، جلسات POS | `DataTable`؛ فلاتر موحّدة في معظمها | الفواتير خادمية؛ عروض الأسعار والمرتجعات والاعتمادات متفاوتة ومحلية غالباً | ترحيل تحسينات الأساس تلقائياً؛ لا تغيير API بلا عقد مثبت |
| المشتريات | `purchases`، `purchase-returns`، `supplier-payments`، `procurement-list` | `DataTable` مع `ListToolbar` في الأغلب | المشتريات خادمية؛ بقية القوائم محلية أو بلا ترقيم ظاهر | إثبات الفرز الخادمي في المشتريات؛ إبقاء البقية ضمن الترحيل المرحلي |
| المنتجات والمخزون | `products`، `inventory`، `inventory-openings`، `stock-permits`، `stocktaking`، `warehouses` | المنتجات هي المثال الأكثر نضجاً؛ المخزون يستخدم الغلاف القديم | المنتجات خادمية مع تصدير مخصص؛ معظم قوائم المخزون محلية | اعتماد المنتجات كمرجع؛ توحيد الغلاف القديم بلا تغيير عقد التصدير |
| الأطراف والعملاء | `partners`، `suppliers`، `contacts`، `appointments`، `crm` | `DataTable` وفلترة متقدمة | محلي في معظم الحالات؛ الموردون يستخدمون الغلاف القديم | إبقاء سلوك المصدر، وتوحيد طبقة العرض فقط |
| المالية | `expenses`، `payments`، `receipt-vouchers`، `cash-and-bank`، `employee-custodies`، `financial-alerts` | `DataTable` مع بطاقات جوال في أغلب الصفحات | محلي؛ الفرع يمر عبر `BranchViewToggle` حيث ينطبق | لا تغيير منطق المحاسبة أو المصدر ضمن هذه المهمة |
| الحسابات | `journal-entries`، `manual-journals`، `cost-centers`، `assets` | `DataTable` مع شريط موحّد | سجل القيود والقيود اليدوية محليان حالياً | الأولوية لسجل القيود: توسيع عقد قراءة خادمي مع حفظ عزل الفرع |
| الموارد البشرية | `hr`، `leave-manager`، `requests-manager`، `org-structure-manager` | `DataTable` | لا توحيد كامل للشريط أو الترقيم بعد | خارج الترحيل الأول؛ يحافظ الأساس على توافقه |
| الوقود والمنصة | قوائم AVI/RFID والعقود والأجهزة والمبيعات والورديات، و`platform/tenants` | `DataTable` | المنصة تشير إلى حالة خادمية؛ الوقود متفاوت | لا مخاطرة بتحويل واجهات تشغيلية متخصصة في هذا الطلب |

| الفئة | المكوّنات الحالية | خصائص مميزة | قرار التوحيد |
|---|---|---|---|
| تقارير عامة ومالية | `ReportDataTable` و`ReportResultsTable` و`StructuredFinancialStatement` | بحث محلي في نتيجة التقرير، إظهار/إخفاء وترتيب وتغيير حجم الأعمدة، كثافة، تذييل إجماليات، بطاقات جوال، طرق عرض محفوظة محلية | تظل طبقة تقارير رفيعة ومتخصصة؛ لا تُحشَر في CRUD DataTable |

| تفاصيل المستندات والطباعة | سطور فاتورة/شراء/سند، وثائق ضريبية، قوالب طباعة، معالجات الاستيراد | جداول ثابتة/تحريرية أو قابلة للطباعة، وليست قوائم بيانات مستقلة | استثناء مقصود من الترحيل |
| لوحات تشغيلية متخصصة | dashboard، delivery notes، Document Center، POS report، صفحات وقود محددة، صفحات إعدادات | إجراءات متسلسلة، شاشات مدمجة أو جداول تحكم صغيرة | استثناء مقصود حتى يثبت أن تحويلها لا يغير سير العمل |

## ما هو قائم وقابل لإعادة الاستعمال

`DataTable` التشغيلي في `web/src/components/data-table.tsx` هو الأساس القانوني الحالي. يستخدم TanStack Table ويغطي العرض المكتبي والبطاقات المحمولة، حالات التحميل/الخطأ/الفراغ، الفرز المحلي، الفرز الخادمي الاختياري، والاختيار الاختياري للصفوف. يعرض الجدول أفقياً داخل حاويته ولا يضغط الأعمدة، وتلتزم خلايا المبالغ بمكوّنات الصفحة ومنسّق `formatRiyal`.

`ListToolbar` هو الغلاف الحديث للبحث والفلاتر والترتيب وعداد النتائج. ويستعمل عقد `DataExplorerState` وصيغة الرابط المشتركة: `q` و`sort` و`page` و`per_page` و`f.<key>`. وتستخدم قائمة المنتجات هذا العقد كاملاً، مع debounce للبحث ونتائج خادمية وفرز خادمي وتصدير خادمي لا يقتصر على الصفحة المرئية. القائمتان الماليةان للفواتير والمشتريات تطبقان كذلك البحث والفلاتر والتقسيم والفرز في الخادم، مع بقاء رؤوس الأعمدة غير موصولة بعد بالفرز الخادمي.

طبقة التقارير مستقرة ومختلفة عمداً: `ReportDataTable` تدير layout الأعمدة والكثافة والتذييل الإجمالي والترقيم المحلي داخل نتيجة تقرير مكتملة، بينما يضيف `ReportResultsTable` بطاقات جوال وتفضيلات طرق العرض المعزولة بالمستأجر والمستخدم والتقرير في `localStorage`.

## أدلة API وسلامة العزل

| المورد | سلوك القائمة في الخلفية | العزل والصلاحية ذوا الصلة | أثره على قرار الواجهة |
|---|---|---|---|
| المنتجات | `ProductListFilters` هو مصدر حقيقة مشترك للقائمة والتصدير؛ يدعم pagination والفرز، ويحمل العلاقات لتفادي N+1 | `Product::query()` يخضع لنطاق المستأجر، والتصدير المحدد لا يكشف معرفات مستأجر آخر | لا تصدير محلي بديل ولا تغيير لعقد الفلاتر |
| الفواتير | بحث وفلاتر ومدى مبالغ وفرز وقائمة مقسمة خادمياً | `scopeToActiveBranch()` يقصر `branch=all` على الفروع المسموحة؛ المسارات محمية بـ RBAC | يمكن وصل رؤوس الأعمدة بعقد `serverSort` بلا فرز صفحة محلية |
| المشتريات | نفس نمط الفواتير تقريباً، مع فلاتر التصنيف | `scopeToActiveBranch()` وRBAC على القائمة وإجراءات المسودة | يمكن وصل رؤوس الأعمدة بعقد `serverSort` بلا تغيير السلوك المالي |
| سجل القيود | يعيد كل القيود المرئية، مرتبة بالتاريخ؛ لا يدعم pagination أو البحث أو الفلاتر أو الفرز المطلوب حالياً | نطاق الفرع مستمد من `JournalLine` ويتضمن المركزية ويقيّد `branch=all` بالمسموح للمستخدم | يحتاج عقد قراءة خادمي محدود ومختبَر قبل إعلان الفرز/التقسيم خادميين |
| التقارير | تُرجع نتائج محسوبة لنطاق التاريخ والفرع ولا تتبع CRUD pagination | `ReportService` هو المصدر؛ الفرع اختياري للتجميع المقصود | تظل طبقة تقارير متخصصة من دون فرض خصائص CRUD |
| المخزون | قائمة أرصدة القراءة تعيد البيانات كاملة؛ التصدير يعيد تطبيق `InventoryBalanceFilters` خادمياً | نطاق المستأجر على المنتجات؛ لا كتابة محاسبية في هذا المتحكم | لا تُفبرك pagination أو export من واجهة الصفحة المرئية |

## حدود الترحيل الآمن

الترحيل الأول يجب أن يوسع الأساس القائم لا أن يعيد تصميم التطبيق. ستبقى جداول الطباعة وسطور المستندات والمحررات والجداول التحليلية والتفاصيل المضمنة خارج التحويل التلقائي، لأن تحويلها إلى قائمة CRUD قد يكسر الطباعة أو الإدخال أو تسلسل التشغيل. كما تبقى التقارير على طبقتها المتخصصة؛ إعادة استعمال مكوّن تخطيط الأعمدة لا يعني دمج عقود النتائج أو فرض إجراءات صفوف عليها.

لا يغيّر هذا العمل محرك القيود أو RBAC أو تصنيف الفرع أو تنسيق العملة. وكل فرز أو تصفية أو تصدير يخضع في النهاية للتحقق الخادمي ونطاق المستأجر وصلاحيات الفرع، ولا يعد إخفاء عمود أو زر إجراء ضابط وصول.

## خطوات التنفيذ المعتمدة بعد التدقيق

1. استخراج مكوّن تخطيط الأعمدة المحايد من طبقة التقارير، وإتاحته اختيارياً للجداول التشغيلية مع أعمدة أساسية محمية وحالة محفوظة اختيارياً لدى المستهلك.
2. تعزيز `DataTable` القائم فقط: ظهور الأعمدة الاختياري، الرأس الثابت الاختياري، والتحديد القابل للاستعمال في بطاقات الجوال عند وجود عملية جماعية حقيقية.
3. توحيد النصوص الداخلية لعناصر البحث والفلاتر وشرائح الفلاتر عبر مجموعة `nebrax` في `next-intl`، وإكمال اختيار متعدد في حوار الفلاتر المتقدمة من دون فرضه على APIs لا تقبله.
4. جعل `DataExplorerToolbar` القديم طبقة توافق رفيعة فوق `ListToolbar` الجديد، فتنتفع صفحات المخزون والموردين والإشعارات الدائنة/المدينة من العرض الموحّد بلا ترحيل سلوك بياناتها.
5. ترحيل الفواتير والمشتريات إلى `serverSort` على الأعمدة التي يقرّها المتحكم بالفعل، ثم توسيع سجل القيود بعقد قراءة خادمي محدود يدعم البحث والفلاتر والفرز والترقيم مع حفظ فرع السطور.
6. إضافة اختبارات عزل/فلترة لسجل القيود، واختبارات واجهة للأساس الموسع، ثم تشغيل الاختبارات والبناء وفحوصات Git وفتح PR غير مدموج.

## التنفيذ المنجز

تم توسيع الأساس التشغيلي الموجود في `web/src/components/data-table.tsx` بدلاً من إنشاء نظام ثانٍ. أضيف **تحكم اختياري بظهور الأعمدة** عبر حالة مضبوطة من المستهلك، مع أعمدة محمية من الإخفاء وتسميات قابلة للترجمة. كما أصبح تثبيت رأس الجدول اختيارياً، وأصبح التحديد—عند تفعيله لعملية جماعية حقيقية—متاحاً في البطاقة المنظمة على الجوال بدلاً من اقتصاره على سطح المكتب.

نُقل مكوّن ترتيب/ظهور الأعمدة من طبقة التقارير إلى `components/data-explorer/column-layout-menu.tsx` باعتباره مكوّناً محايداً. بقيت إعادة ترتيب الأعمدة متاحة للتقارير كما كانت، بينما يستدعي `DataTable` القائمة في وضع إظهار/إخفاء فقط، فلا يُنشئ حالة ترتيب أعمدة تشغيلية جديدة بلا حاجة. وتُحفظ تفضيلات الأعمدة في `localStorage` بمفتاح معزول حسب إصدار العقد والمستأجر والمستخدم والجدول؛ ففشل التخزين لا يمنع قراءة البيانات أو تغيير العرض.

| طبقة التغيير | الملفات/النطاق | الأثر المطبق |
|---|---|---|
| DataTable | `data-table.tsx` و`table-layout.ts` | ظهور أعمدة اختياري، حماية أعمدة الهوية/الإجراءات، رأس ثابت اختياري، تحديد متاح في بطاقات الجوال |
| عناصر البحث والفلترة | `search-bar` و`quick-filters` و`active-filter-chips` و`advanced-filter-dialog` | إزالة النصوص العربية الثابتة، ترجمة عربية/إنجليزية، دعم `multiSelect` بمشغّل `in` صريح |
| الغلاف المتوافق | `data-explorer-toolbar.tsx` | طبقة توافق رفيعة فوق `ListToolbar`؛ تستفيد أربع صفحات قديمة من الواجهة الموحدة بلا تغيير عقد البيانات |

## دليل تبني الشاشات اللاحقة

تعتمد شاشة تشغيلية جديدة `DataTable` و`ListToolbar` و`DataExplorerState` الموجودين. لا تُفعَّل الخصائص لمجرد توحيد الشكل؛ بل تُمرر فقط إذا كان المورد وعقد API يدعمانها. في القائمة الخادمية يمرر المستهلك `serverSort` مع allowlist لمعرّفات الأعمدة نفسها المعتمدة في المتحكم، ويعيد الصفحة إلى 1 عند تغيير الفرز أو البحث أو الفلاتر. لا يجوز أبداً فرز الصفوف المحمّلة محلياً فوق صفحة خادمية.

```tsx
const storedColumns = useDataTableColumnVisibility('domain-list');
const columnVisibility = {
  ...storedColumns,
  protectedColumnIds: ['number', 'actions'],
  labels: { actions: t('actions') },
};

<DataTable
  columns={columns}
  data={response.data}
  serverSort={{ value: state.sort, onChange: setSort, columns: ['number', 'date', 'total'] }}
  columnVisibility={columnVisibility}
  stickyHeader
  mobileRecord={toMobileRecord}
/>
```

لا تمرر `selection` إلا عند وجود إجراء جماعي معرّف (كتصدير العناصر المحددة). ولا ينبغي إعطاء الفلاتر أو الأعمدة المخفية معنى تفويضياً: **واجهة المستخدم تعرض ما تسمح به API فقط**. ويبقى تصدير القوائم الكبيرة خادمياً مع إعادة تطبيق فلاتر المورد؛ لا يصدّر `DataTable` إلا CSV صغيراً من الصفوف المحمّلة عندما يصرح المستهلك بذلك.

## سلامة سجل القيود

تغيير سجل القيود **قراءة فقط**. لا توجد هجرة ولا كتابة مباشرة في `journal_entries` أو `journal_lines`، ولا تغيير لمسار `LedgerService::post()` أو `LedgerService::reverse()`. تبدأ كل شروط البحث والفلترة من `visibleEntries()` القائم، ولذلك يبقى `TenantScope` قائماً ويبقى نطاق الفرع مشتقاً من سطور القيد. تبقى قيمة القيد معرّفةً بمجموع المدين بالهللات داخل SQL ثابت ومربوط، ويحّول مرشح الريال إلى هللات من دون `float`.

حافظت الاستجابة على التوافق الرجعي: الطلب القديم إلى `/api/journal-entries` من دون `per_page` يعيد `data` كاملاً كما سبق. أما الواجهة الجديدة فترسل `per_page` فتتلقى `data` و`meta` بالصيغة التي تستخدمها `Pagination` في بقية الموردين. حارس المسار بقي `accounts.view` ولم يُنقل إلى واجهة المستخدم.
