# S10b-1 — ميزانية استعلامات كتالوج Runtime + إصلاح N+1 في وسائط قائمة المنتجات

**الحالة:** منفَّذة. إصلاح خادم داخلي بلا تغيير في شكل أي استجابة؛ لا هجرة؛ لا أثر محاسبي.

## الاكتشاف
اختبار الميزانية الجديد (عدد استعلامات SQL لطلب دافئ بـ3 صفوف ثم 20) كشف **N+1 حقيقياً** في `GET commerce/v1/products` (القائمة التي يجلبها Runtime الجوال لكل `ProductList`/البحث/التصنيف): `21 → 38` استعلاماً بزيادة 17 صفاً — استعلام `product_media` لكل منتج (`ProductMediaGalleryService::resolveGallery` يُستدعى في `toResource` لكل صف). التصنيف (`productCategory`) كان محمَّلاً مسبقاً أصلاً.

## الإصلاح
`ProductMediaGalleryService::resolveSharedGalleries()` يجلب المعارض المشتركة لكل منتجات الصفحة **باستعلام واحد** بالترتيب نفسه (`sort_order, created_at, id`) وتفريغ التكرار نفسه، والمتحكّم يمرّرها لـ`toResource` (مع الرجوع للاستعلام المنفرد إن غابت — مسار التفاصيل لم يتغيّر). اختبار تكافؤ يثبت أن الدفعة = الاستعلام المنفرد لكل منتج (المحتوى والترتيب).

## الميزانية (`CommerceCatalogQueryBudgetTest`، 8)
عدد الاستعلامات **ثابت** عند زيادة الصفوف: القائمة العادية، البحث، الترتيب بالشعبية، الأحدث، الترشيح بالتصنيف، شجرة التصنيفات، والقائمة مع وسائط. طفرة تعطيل الإصلاح تُفشل 5 اختبارات؛ وحزمة الكتالوج/الوسائط/الواجهة العامة (375) خضراء.

## حدود معلنة (لم تُعالَج)
- مسار `availability->forWarehouse` لكل صف حين يُهيَّأ مخزن تنفيذ لقناة الجوال لم يُقَس (يحتاج إعداد مخزن في الاختبار) — يستحق ميزانية لاحقة.
- بناء الواجهة كسولاً (slivers على مستوى الصفحة) وميزانية أداء Flutter (QA-04) ما زالا مفتوحين.
