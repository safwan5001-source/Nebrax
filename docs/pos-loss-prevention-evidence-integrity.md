# POS Loss Prevention — Phase 4: Evidence Integrity

> مؤشرات المراجعة والاستثناءات تساعد في ترتيب أولوية المراجعة والتحقيق، ولا تُثبت وحدها
> وجود مخالفة.

يوثّق هذا الملف **كيف** تقوّي Phase 4 جودة الدليل القائم من Phase 1–3 دون إنشاء مصدر
حقيقة موازٍ: حماية إعادة الإرسال (idempotency)، سلسلة الدليل العابرة للكاشير، تسلسل مصدر
«ساعات العمل»، سبب عدم بناء محرك سلة خادمي جديد، وتأجيل سلامة الأحداث دون اتصال.

## 1) Idempotency — حماية إعادة الإرسال والتكرار

### المشكلة

قبل Phase 4 لم توجد آلية `idempotency_key` عامة لتدقيق POS (مؤكَّد بالتدقيق، انظر
`docs/pos-loss-prevention-phase-4-gap-matrix.md` §٥). عميل السلة (`web/`) يرسل تدقيق
الأحداث الحسّاسة (`item_remove`, `price_override`, ...) وطلبات الاعتماد عبر HTTP
fire-and-forget؛ فقدان الاستجابة بسبب شبكة غير مستقرة يدفع العميل لإعادة المحاولة، وبلا
حماية كانت إعادة المحاولة تُنتج **حدثاً مكرَّراً** (يضخّم معدلات الاستثناءات المشتقّة
زوراً) أو تستهلك **اعتماد Approval مرتين** (تُفشل إعادة المحاولة الثانية برسالة "استُهلك
مسبقاً" رغم أنها نفس الطلب فعلياً).

### التصميم

عمودان إضافيان فقط على `pos_session_events` (هجرة `2026_08_31_010000`، إضافية بحتة، لا
تُعاد كتابة بيانات تاريخية):

| العمود | النوع | الغرض |
|---|---|---|
| `client_event_id` | `string(100)`, nullable | معرّف يولّده العميل محلياً (ليس بالضرورة UUID — شكل حر مقصود، العميل قد يستخدم `crypto.randomUUID()` أو عدّاداً محلياً). `NULL` = مسار الخادم القديم بلا تغيير سلوك. |
| `client_event_payload_hash` | `string(64)`, nullable | SHA-256 لحمولة الطلب (ترتيب مفاتيح ثابت `ksort` متكرر، `JSON_UNESCAPED_UNICODE`) — يميّز «نفس الطلب أُعيد إرساله» عن «مفتاح أُعيد استخدامه بحمولة مختلفة». |

قيد فريد `(tenant_id, client_event_id)` (يتجاهل `NULL`، فلا يتصادم مع الأحداث القديمة أو
الأحداث بلا `client_event_id`).

### التدفق (`PosAuditService`)

يُطبَّق على مسارين فقط — الاثنان الوحيدان اللذان يستقبلان طلبات عميلية معرَّضة لإعادة
إرسال شبكي وينتجان أثراً قابلاً للتكرار الضار:

1. `recordClientObservedCartEvent()` (`app/Services/Pos/PosAuditService.php:141-190`) —
   أحداث السلة الحسّاسة (`item_remove`, `price_override`, `discount_*`, `cart_cancel`, ...).
2. `requestApproval()` (`app/Services/Pos/PosAuditService.php:253-339`) — طلب اعتماد
   Override جديد.

منطق الفحص متطابق في الاثنين:

```
clientEventId = normalizeClientEventId(input.client_event_id)   // trim، فراغ⇒null، حدّ 100 حرف
if clientEventId != null:
    hash = hashClientPayload(rawInput)   // يُحسب مرة واحدة من المدخلات الخام
    existing = SELECT * FROM pos_session_events WHERE client_event_id = clientEventId
    if existing == null:
        // مفتاح جديد فعلاً — تابع المسار العادي، خزّن clientEventId + hash مع الحدث
    elif existing.client_event_payload_hash == hash:
        return existing   // إعادة إرسال حقيقية — لا كتابة جديدة، لا استهلاك اعتماد ثانٍ
    else:
        throw PosIdempotencyConflictException   // نفس المفتاح بحمولة مختلفة — تعارض حقيقي
```

**نقطتان معماريتان حاسمتان:**

- **الفحص يسبق أي أثر جانبي.** في `recordClientObservedCartEvent()` يُستهلك اعتماد
  Override (إن كانت السياسة `approval_required`) **بعد** فحص idempotency لا قبله — إعادة
  محاولة بنفس المفتاح يجب ألا تستهلك اعتماداً مرتين ولا تفشل برسالة "استُهلك مسبقاً" رغم
  كونها نفس الطلب.
- **الهاش يُحسب مرة واحدة من المدخلات الخام** ويُستعمل للفحص والتخزين معاً. الخطأ الأول
  المُصلَح أثناء البناء كان حساب الهاش من المدخلات الخام للفحص، ثم إعادة حسابه من مدخلات
  مطبَّعة (`resolveReason()` يقصّ/يطبّع `reason_note`) للتخزين — فيختلف الهاشان لنفس
  الطلب فعلياً ويُبطل idempotency بصمت. الإصلاح: هاش واحد محسوب مبكراً، يُمرَّر صراحة إلى
  كل من الفحص والتخزين.

### الاستجابة عند التعارض

`PosIdempotencyConflictException` (استثناء جديد صغير، `app/Services/Pos/
PosIdempotencyConflictException.php`) — يلتقطه `PosAuditController` في نقطتي الدخول
(`recordCartEvent`, `requestApproval`) ويُترجَم لاستجابة **409 Conflict** (لا 422 — ليس
خطأ تحقق مدخلات، بل تعارض حالة حقيقي يستحق كوداً مختلفاً يميّزه العميل).

### ما لا يغيّره هذا التصميم

- **لا يُنشئ طابور تزامن أو مزامنة عدم اتصال.** هذا حماية من **إعادة إرسال HTTP فورية**
  (نفس الجلسة، نفس الطلب، شبكة غير مستقرة) — ليس بنية عدم اتصال (§6 أدناه).
- **العميل اختياري تماماً بإرسال `client_event_id`.** غيابه = السلوك القديم حرفياً (لا
  فحص، لا كسر توافق رجعي). كل استدعاءات العميل القائمة اليوم بلا هذا الحقل تستمر بالضبط
  كما كانت.
- **الأحداث القديمة (`client_event_id IS NULL`) صالحة كما هي** — لا حاجة لأي backfill.

## 2) سلسلة الدليل العابرة للكاشير (`cross_cashier_refund`)

### لماذا لم يكن ممكناً قبل Phase 4 (مؤكَّد بالتدقيق)

مسار مرتجع POS المقفل بالجلسة (`PosReturnService`) **لا يمكن أن ينتج حالة عابرة للكاشير
أصلاً بالتصميم**: `assertSourceMatchesSession`
(`app/Services/Accounting/PosReturnService.php:99-115`) يفرض أن يتم المرتجع في نفس
الجلسة المفتوحة التي تمت فيها الفاتورة الأصلية، و`requireOpenForCheckout` يفرض
`session.opened_by === actor`. فمرتجعات شاشة POS نفسها كاشير واحد دوماً — لا حاجة لقاعدة
هنا، ولا وجود لها.

السيناريو الحقيقي هو `POST /returns` العام (`ReturnController`) الذي لا يمنع إرجاع فاتورة
POS من خارج جلستها الأصلية، وكان يحمل خللاً حقيقياً قبل هذا الطور:
`ReturnController::store()` لم يكن يحقن `created_by` من المستخدم الحالي، فبقي
`return_documents.created_by` **دائماً `NULL`** على هذا المسار.

### السلسلة المبنية

```
Invoice.created_by                    ← خادمي بحت، من PosController::checkout()
                                          ($data['created_by'] = $request->user()?->id)
        │  (return_documents.original_id/original_type)
        ▼
ReturnDocument.created_by              ← أُصلِح في هذا الطور: ReturnController::store()
                                          يحقن الآن $request->user()->id (نفس نمط checkout)
        │
        ▼  (ReturnService::postSalesReturn، فقط للمسار غير المقفل بجلسة POS)
PosSessionEvent
  type = return_recorded_external
  payload.original_sale_actor_id = Invoice.created_by
  payload.return_actor_id        = ReturnDocument.created_by
  payload.return_number, original invoice/session ids, branch
```

**شرط الإطلاق الصريح:** `ReturnService::postSalesReturn()` يُصدر هذا الحدث فقط حين
`$type === 'sales' && $source instanceof Invoice && $source->pos_session_id !== null &&
($data['pos_session_id'] ?? null) === null` — أي: الفاتورة أصلها POS، والمرتجع **ليس**
عبر المسار المقفل بجلسة (ذاك يُصدر `return_recorded` من `PosSessionService::recordReturn`
كما في السابق، بلا تغيير). لا ازدواج بين المسارين.

### قاعدة `cross_cashier_refund`

تقارن `original_sale_actor_id` بـ `return_actor_id` من الحدث أعلاه. **لا تُطلَق أبداً** إن
كان أيّهما `null` — فاتورة POS قديمة سابقة لهذا التوثيق، أو أي حالة استثنائية لا يُعرَف
فيها المنفّذ الأصلي، **لا تُنتج نتيجة إيجابية كاذبة**. هذا التحفّظ الصريح موثَّق في
الـ Gap Matrix (تصنيف B — هجين لكنه دفاعي) ولا يُعاد فتحه بلا مصدر بيانات جديد.

## 3) تسلسل مصدر «ساعات العمل» (`outside_operating_hours`)

ثلاثة مصادر محتملة فُحصت بالتدقيق قبل أي كود؛ اثنان مرفوضان صراحة وواحد مقبول:

| المصدر | لماذا مرفوض/مقبول |
|---|---|
| `Branch.working_hours` | نص حر غير مهيكل — غير قابل للتفسير الآلي الموثوق. اعتماده كان يعني تخمين نمط لا مصدراً معتمَداً. **مرفوض.** |
| `pos_sessions.shift_id` | يختاره **العميل** عند فتح الجلسة (`$data['shift_id']` من جسم الطلب في `PosSessionController::open`) — قابل للتلاعب الذاتي من الكاشير نفسه. **مرفوض** كمصدر دليل. |
| `User → Employee → Shift` | حقل تديره الموارد البشرية (`Employee.shift_id`)، لا يستطيع الكاشير تغييره بنفسه، مع حساب عبور منتصف الليل الآمن الجاهز أصلاً في `Shift::netMinutes()`. **المصدر الوحيد المقبول** (تسلسل هرمي مستوى ١: «جدول موظف معتمَد»). |

### التنفيذ (`PosEmployeeScheduleResolver`)

غلاف رقيق فوق `Employee`/`Shift` القائمين — **لا نظام جدولة جديد** (ممنوع صراحة في المهمة
والـ Gap Matrix، تصنيف C):

- `resolveMany(userIds)`: يحلّ ورديات عدة مستخدمين دفعة واحدة (بلا N+1)، ويُسقط أي مستخدم
  بلا `employee_id`، أو موظف بلا `shift_id`، أو وردية معطّلة/محذوفة. **لا وردية محلولة =
  غياب تام من نتيجة `resolveMany`** — لا افتراض نمط ٩–٥.
- `covers(shift, at, timezone, graceMinutes)`: يفحص مرساتَي «اليوم» و«الأمس» بتواريخ
  تقويمية فعلية (لا `modulo` يدوي) فتُحسب الورديات الليلية العابرة لمنتصف الليل بلا أخطاء
  حدّية، مطابقاً لمنطق `Shift::netMinutes()` القائم.

### المنطقة الزمنية

`PosExceptionDetectionService::outsideOperatingHoursCounts()` يقرأ `tenants.timezone` عبر
`TenantContext` (نفس نمط `PosLpDigestService` من Phase 3)، لا `config('app.timezone')`
(الذي يفترض UTC افتراضياً). **خطأ أُصلِح أثناء البناء:** أول تنفيذ كان يستخدم
`config('app.timezone')` خطأً؛ صُحِّح لجلب `Tenant::find($tenantId)->timezone` مع سقوط
احتياطي صريح فقط عند غياب المستأجر نفسه (حالة استثنائية لا يُفترض حدوثها في مسار مُعزَّل
بالمستأجر أصلاً).

### السماحية (Grace period)

`PosSettings::outsideHoursGraceMinutes($tenant)` — إعداد `pos_loss_prevention` قابل
للضبط لكل مؤسسة (افتراضه 30 دقيقة)، يُضاف قبل بداية الوردية وبعد نهايتها قبل وسم أي نشاط
حسّاس بأنه خارج ساعات الدوام. يحمي من نتائج إيجابية كاذبة حول حدود الوردية الطبيعية
(تأخر تسليم/استلام، إغلاق متأخر بسبب عميل أخير).

### الأحداث الحسّاسة المفحوصة

مرتجع/استرداد، فتح درج، اعتماد (override)، خصم، إلغاء — نفس فئة الأحداث الحسّاسة
المستخدمة في قواعد Phase 2 الأخرى، لا قائمة موازية.

### من لا يحصل على إشارة إطلاقاً

مستخدم بلا `employee_id`، أو موظف بلا `shift_id`، أو وردية معطّلة — **لا إشارة له
إطلاقاً**، ليس إشارة بثقة أدنى وليس تخميناً افتراضياً. هذا خيار تصميم متعمَّد يمنع ترقية
غياب البيانات إلى دليل.

## 4) لماذا لا يوجد تعزيز أدلة سلة (cart-evidence-hardening) بمعنى "منع خادمي"

المهمة تسأل صراحة عن ترقية تعديلات السلة الحسّاسة (`item_remove`, `price_override`,
`discount_change`, `cart_cancel`) نحو دليل خادمي حيث يكون ذلك ممكناً تقنياً. التدقيق
(Gap Matrix، السؤال ٨) يخلص إلى: **لا يوجد مسار ممكن تقنياً بلا محرك سلة خادمي كامل.**

السبب البنيوي: السلة اليوم حالة **عميلية محلية بحتة** (`localStorage` + حالة React) حتى
لحظة `checkout`؛ الخادم لا يملك تمثيلاً حياً لسلة قيد التعديل، فقط `cart_id` (بصمة هوية
مُصدرة من `createCart()`، انظر `PosAuditService.php:109-127`) وتيار Telemetry لاحق يصف ما
فعله العميل محلياً *بعد وقوعه*. "منع" حذف صنف مثلاً يتطلب أن يكون الخادم هو من يملك حالة
السلة الحقيقية قبل/بعد ليقرر السماح أو الرفض **قبل** أن يرى العميل نتيجة الحذف على شاشته
— وهذا محرك سلة خادمي كامل (state machine + تزامن + أداء زمن حقيقي)، خارج نطاق هذا الطور
تماماً وشرط توقّف صريح في المهمة (§22).

**ما فُعل بدلاً من ذلك (الحد الأقصى الدفاعي الممكن اليوم):**

- تعزيز **هوية/جلسة/وقت** الحدث نفسه عبر idempotency (§1 أعلاه) — يمنع تضخّم الدليل
  عرضياً (إعادة إرسال شبكي)، لا يمنع الفعل نفسه.
- قواعد اكتشاف هجينة صريحة الثقة (`override_then_cancel`,
  `repeated_cancel_before_checkout`) تدمج طرفاً خادمياً (`override_consumed`) بطرف عميلي
  موسوم `client_observed` — نفس سابقة `item_removal_rate` المعتمَدة في Phase 2، لا نمط
  جديد.
- التصنيف `client_observed` نفسه **لم يتغيّر** ولن يتغيّر بلا محرك سلة خادمي حقيقي — أي
  ادّعاء عكس ذلك يكون كذباً على مستوى الثقة، وهو ما يمنعه المبدأ الحاكم لكل هذه السلسلة.

## 5) تأجيل سلامة الأحداث دون اتصال (Offline/Delayed)

التدقيق (Gap Matrix، السؤال ٦) يؤكد: **لا بنية مزامنة عدم اتصال قائمة في POS اليوم** — لا
طابور، لا فصل `observed_at`/`received_at`، لا طبقة مزامنة أجهزة؛ فقط مسودات سلة
`localStorage` و Telemetry فوري fire-and-forget مباشر عبر HTTP.

بناء طبقة مزامنة عدم اتصال جديدة **ممنوع صراحة** في هذا الطور (§9/§21 من المهمة) — ليس
لأنه غير مفيد، بل لأنه نظام مستقل كامل (طابور محلي على الجهاز، إعادة تشغيل مرتّبة زمنياً،
حل تعارضات، حالة اتصال) يستحق مهمة معمارية منفصلة بمواصفاتها الخاصة، لا إضافة جانبية على
Phase 4. **إن وُجدت لاحقاً**، حماية idempotency المبنية هنا (`client_event_id` +
`client_event_payload_hash`) هي **بالضبط** الأساس الذي ستحتاجه طبقة المزامنة لإعادة تشغيل
أحداث متأخرة بأمان دون تكرار — لا إعادة كتابة متوقعة.

## الخلاصة المعمارية

كل تعزيز في هذا الملف يتبع نفس القاعدة الحاكمة لكل السلسلة: **يشير إلى الدليل القائم أو
يُلحق به، ولا ينسخه ولا يبدّل تصنيف ثقته بلا مصدر بيانات خادمي حقيقي جديد.** لا مصدر حقيقة
موازٍ، لا تخمين يُقدَّم كحقيقة، ولا "منع" يُدَّعى حيث لا يوجد مسار خادمي فعلي يملك السلطة
لمنعه.
