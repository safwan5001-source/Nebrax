# AWJ-ERP-UX-H1 — ERP-Wide UX & Accessibility

**المشروع:** أَوْج AWJ ERP  
**نوع الوثيقة:** ميثاق مسار عمل وخطة تدقيق وتحسين (Charter & Roadmap)  
**الإصدار:** 1.0  
**التاريخ:** 2026-10-14  
**الحالة:** معتمد من حيث التوجه العام — **التنفيذ لم يبدأ**  
**الارتباط:** مسار مستقل عن `AWJ-PLATFORM-UX-H1`، ويُحضَّر بالتوازي دون دمج نطاقي العمل.

## 1. الغرض

تعميم منهجية تحسين تجربة المستخدم وإمكانية الوصول المتبعة في لوحة إدارة المنصة `/platform` على واجهات نظام أَوْج ERP بالكامل، مع مراعاة اختلاف متطلبات المحاسبة والمبيعات والمشتريات والمخزون ونقاط البيع وغيرها من الوحدات التي يثبت وجودها في النظام.

**الهدف:** واجهة ERP متسقة، واضحة، سريعة، قابلة للوصول، وتعمل بالعربية والإنجليزية وعلى مختلف الشاشات، دون الإخلال بالصحة المحاسبية أو الأمان أو سلوك العمليات الحالي.

> لا يعني هذا المسار نسخ إصلاحات `/platform` إلى بقية ERP تلقائيًا، ولا إعادة تصميم شاملة دفعة واحدة.

## 2. المبادئ غير القابلة للتفاوض

1. سلامة البيانات والصحة المالية والمحاسبية والضريبية والمخزنية أولًا.
2. الحفاظ على `Tenant Isolation`، والصلاحيات، والمصادقة، وأمان البيانات.
3. الحفاظ على `Backward Compatibility` وعقود API والسلوك التشغيلي الحالي.
4. عدم تغيير المنطق المحاسبي أو القيود أو الضرائب أو حركات المخزون ضمن مهام UX.
5. عدم تغيير قاعدة البيانات أو واجهات API أو قواعد العمل خارج نطاق مهمة صريحة ومعتمدة.
6. اعتماد تصميم أَوْج الحالي مرجعًا، مع أولوية **الوضوح والكثافة والسرعة والثقة والاتساق** على الإبهار البصري.
7. تنفيذ إصلاحات صغيرة قابلة للاختبار والمراجعة والتراجع، كل مجموعة مستقلة في PR محدد.
8. لا دمج أو نشر أو إصدار إنتاجي دون موافقة صريحة منفصلة من مالك المشروع.
9. لا تُعتبر المهمة مكتملة بمجرد كتابة الكود؛ يلزم دليل اختبارات ومراجعة وحالة دمج وتحقق مناسب بعد الدمج والنشر إن تم.

## 3. نطاق التدقيق والتحسين

| المجال | المراجعة المستهدفة |
|---|---|
| UI/UX | اتساق الصفحات والتنقل والأزرار والجداول والنماذج وكثافة المعلومات |
| Responsive | الجوال والتابلت والشاشات الصغيرة وتجنب القص والتمرير الأفقي غير المقصود |
| Accessibility | التسميات الدلالية، التركيز ولوحة المفاتيح وقارئات الشاشة وتكبير النص |
| RTL / LTR | العربية والإنجليزية وعكس الاتجاه وتنسيق النص والأرقام |
| Design System | اتساق المكونات والألوان والخطوط والمسافات والحالات |
| Translations | النصوص المفقودة والمفاتيح التقنية وملاءمة طول النصوص |
| Forms | وضوح الحقول والتحقق من المدخلات ورسائل الخطأ وعدم فقدان البيانات |
| Tables | البحث والفرز والتصفّح والكثافة وقابلية القراءة وأمان الإجراءات |
| States | التحميل، الفراغ، الخطأ، الاسترجاع وإعادة المحاولة |
| Performance | استجابة الواجهة وحجم التحميل وعمل التفاعلات دون تغيير منطق المعاملات |

**الوحدات المستهدفة:** تُحصر من المستودع أولًا، ثم تُرتب بحسب كثافة الاستخدام والمخاطر. تشمل الوحدات المذكورة في التوجه: المحاسبة، المبيعات، المشتريات، المخزون ونقاط البيع، **إذا كانت موجودة فعليًا**، إضافة إلى بقية الوحدات المثبتة. لا تُفترض جاهزية أي وحدة دون تحقق.

### خارج النطاق افتراضيًا

- إعادة كتابة ERP أو إعادة هيكلة واسعة للمكونات والبنية.
- إضافة ميزات وظيفية جديدة لمجرد تحسين UX.
- تغيير القيود المحاسبية واحتساب الضرائب والأسعار والأرصدة والجرد.
- توسيع أو تعديل الصلاحيات وحدود المستأجرين.
- تغيير نماذج البيانات أو API دون قرار مستقل ومبرر.
- تنفيذ تغييرات إنتاجية أو ترحيل بيانات ضمن مسار تدقيق الواجهة.

## 4. مراحل التنفيذ

### المرحلة 1 — Audit شامل دون تعديلات

- جرد صفحات ERP والوحدات والمكونات المشتركة المستخدمة فعلًا.
- جرد مسارات العمل الحرجة: إنشاء/تعديل/اعتماد/حفظ/إلغاء/طباعة وتصدير، بحسب كل وحدة.
- فحص التجربة على الأجهزة واللغات وأنماط العرض والحالات المختلفة.
- توثيق المشكلات بأدلة قابلة للتكرار وربطها بالملفات أو المسارات المتأثرة.
- تصنيف P0/P1/P2/P3 مع تقدير أثر كل مشكلة على العمل والأمن والعمليات.
- إخراج **Master UX Backlog** وقائمة أولويات، دون تعديل تطبيق أو قاعدة بيانات.

**مخرج المرحلة:** تقرير Audit + سجل الشاشات + سجل المشكلات + الأولويات وخطة PRs المقترحة.

### المرحلة 2 — المكونات المشتركة

- معالجة العيوب المثبتة في المكونات المستخدمة على نطاق واسع (الحقول، الأزرار، الشارات، الجداول، الحوارات والتنقل).
- تفضيل تغييرات اختيارية (`opt-in`) عند احتمال تضرر مستخدمين آخرين للمكون.
- حصر جميع أماكن الاستعمال والتأكد من عدم تغير السلوك الافتراضي.
- اختبار المكونات المتأثرة ومسارات العمل الحرجة قبل توسيع التطبيق.

**مخرج المرحلة:** PRs صغيرة مع اختبارات انحدار وتقارير أثر توافقية.

### المرحلة 3 — مراجعة وتحسين الوحدات

- ترتيب الوحدات بحسب المخاطر وكثافة الاستخدام، لا بحسب سهولة التجميل.
- تخصيص نطاق واضح لكل وحدة أو مجموعة شاشات مترابطة.
- مراجعة تدفق المهام وسهولة الوصول على الويب والجوال واللغتين.
- حماية العمليات المالية والبيانات والتصدير والطباعة والسجلات من أي تغيير غير مقصود.

**مخرج المرحلة:** تحسينات موضعية موثقة ومختبرة لكل وحدة على حدة.

### المرحلة 4 — التحقق النهائي

- تشغيل الاختبارات الوظيفية والانحدارية والمتعلقة بالصلاحيات والعزل.
- اختبار الاستخدام باللوحة والمحتوى الدلالي والتكبير وRTL/LTR.
- اختبار المتصفحات المستهدفة، وقارئ شاشة حقيقي عند الإمكان؛ تسجيل غير المنفذ بوضوح.
- مقارنة الصور والقياسات عند الحاجة، والتحقق من الأداء وحالات الخطأ.
- توثيق المخاطر المتبقية والبوابات غير المكتملة؛ لا إعلان اكتمال دون أدلة.

**مخرج المرحلة:** تقرير تحقق نهائي، ومصفوفة قبول، وقرارات صريحة بشأن المتبقي والاستثناءات.

## 5. درجات الأولوية

| الدرجة | التعريف العملي |
|---|---|
| P0 | خلل يؤدي إلى خطر مباشر على البيانات أو الأمن أو عمليات مالية حرجة؛ يُوقف التغيير المتأثر ويصعّد فورًا |
| P1 | عائق وظيفي كبير أو خلل إمكانية وصول يمنع مهمة أساسية بلا بديل مقبول |
| P2 | خلل واضح في تجربة أو وصول أو تجاوب يؤثر على سيناريو محدد، مع وجود بديل أو أثر محدود |
| P3 | تحسينات اتساق وتفاصيل عرض وغير ذلك من عيوب منخفضة الأثر |

التصنيف مبدئي ويُراجع بحسب أثر كل مشكلة وسياق الوحدة.

## 6. بروتوكول تنفيذ كل مهمة

1. قراءة أحدث تقرير تنفيذ/تسليم وسجل المشكلات المرتبط، دون إعادة استكشاف شامل.
2. تثبيت `Base SHA` من أحدث `origin/main` وإنشاء فرع جديد.
3. صياغة Scope محدد، ونتائج قابلة للقياس، ومناطق يمنع تعديلها.
4. تنفيذ أصغر إصلاح متوافق مع نظام التصميم.
5. تشغيل الاختبارات المرتبطة أولًا، ثم توسيعها وفق خطر التغيير؛ لا تخفيف لاختبارات المال والأمن وعزل المستأجرين.
6. توثيق Build وCI على Head النهائي، ومراجعة ملاحظات المراجع وإغلاقها بالأدلة.
7. فتح PR مستقل مع **Implementation Report** وشرح المخاطر والمتبقي.
8. مراجعة المالك قبل الدمج، وموافقة مستقلة قبل النشر. تظل حالة التحقق الإنتاجي مفتوحة حتى تُثبت إن نُشر.

### بيانات تقرير التنفيذ الإلزامية

- المشكلة والسبب الجذري ونطاق الإصلاح.
- ما أُنجز وما لم يُنجز والملفات المتغيرة.
- نتائج الاختبارات (مموهة/حقيقية) وBuild وCI والفحوصات غير المكتملة.
- مراجعات الكود والمخاطر والتوافق الخلفي.
- `Branch` و`PR` و`Base SHA` و`Head SHA` و`Merge SHA` إذا توفر.
- الخطوة التالية وحالة الجاهزية للدمج أو النشر.

## 7. بوابات القبول

**تدقيق المرحلة الأولى:** لا يُعتمد إلا بعد وجود جرد موثق للمكونات والوحدات والشاشات، وسجل مشكلات مصنف بأمثلة قابلة لإعادة الإنتاج، وخطة نطاقات قابلة للتنفيذ.

**قبول PR:** تحقق شروط النطاق والتوافق، ونجاح CI والاختبارات المطلوبة، وعدم وجود ملاحظات P0/P1 معلقة، ومعالجة أو توثيق ملاحظات P2 ذات الصلة، وموافقة المالك الصريحة على الدمج.

**قبول المسار ككل:** اكتمال الأعمال المتفق عليها والتحقق عبر البيئات واللغات والأجهزة، وتوثيق الباقي واعتماد استثناءاته صراحة؛ عدم مساواة “Merged” بـ“Deployed” أو “Production Verified”.

## 8. الأدوات والحوكمة

- **ChatGPT:** التخطيط والتحليل والتوثيق ومراجعة التقارير وتحديد الأولويات وكتابة مهام التنفيذ.
- **Claude Code:** تدقيق المستودع وتنفيذ التغييرات البرمجية متعددة الملفات عند الحاجة.
- **Cursor:** PRs صغيرة واضحة ومحددة إذا كان التنفيذ به أنسب.
- **Work/Codex:** عند الحاجة الفنية الحقيقية فقط؛ لا يُستهلكان تلقائيًا لإعادة فحص عمل معه تقرير واختبارات موثوقة.

تُحدد الأداة لكل مهمة وفق نطاقها والمخاطر والكلفة، مع عدم التضحية بالدقة.

## 9. الاعتماديات والحالة الحالية

- مسار `AWJ-PLATFORM-UX-H1` **منفصل** وما زال مفتوحًا؛ لا يُعد مغلقًا بمجرد دمج إصلاحات متتابعة.
- تجري متابعة عيوب H1-5 الخاصة بالمنصة؛ لا تُنقل هذه العيوب تلقائيًا إلى Backlog ERP الجديد.
- يجوز إعداد ميثاق ERP الجديد وخطة Audit بالتوازي، ولكن **التنفيذ الواسع يبدأ بعد ضبط التزامات P2 المتبقية في `/platform` أو بقرار أولوية صريح**.
- لا يُعد هذا المستند موافقة على إنشاء PR أو Merge أو Deploy.

## 10. القرار المعتمد والخطوة التالية

**القرار:** اعتماد التوجه والمنهجية العامة لمسار `AWJ-ERP-UX-H1`.

**الخطوة التالية المقترحة:** عند اكتمال الأولويات الحالية في `/platform`، تكليف Claude Code بـ**Audit فقط** لإنتاج جرد واقعي لوحدات ERP ومكوناته وتحديد أول دفعة عمل، دون تعديل كود.

---

**ملاحظة ضبط الوثائق:** هذا الميثاق يثبت الاتفاق الحالي؛ لا يدّعي إكمال Audit أو اختبارات لم تُجرَ، ولا يقرر قائمة وحدات نهائية قبل فحص المستودع. يُحفظ في المشروع ضمن `docs/plans/erp/` عند اعتماد إضافته للمستودع في PR توثيقي منفصل.
