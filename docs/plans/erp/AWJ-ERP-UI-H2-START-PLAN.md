> **r2:** يوسّع r1 بعد مراجعة المالك. r1 كان إغلاقاً لبقايا H1 واختبارات متصفحات؛ r2 أفقٌ شامل للتصميم وتجربة الاستخدام في كل وحدات ERP الموجودة فعلاً، وتبقى بقايا H1 (window.confirm، المتصفحات المتعددة، بوابة CI) داخله ضمن مسار الجودة.

## 1. النتيجة المطلوبة

مستخدم أَوْج يرى **نظاماً واحداً متسقاً** في كل الوحدات: الصفحة نفسها لها البنية نفسها، والجدول يتصرف بالطريقة نفسها، والنموذج يُملأ ويُتحقق منه بالطريقة نفسها، والحالة نفسها تبدو وتعني الشيء نفسه — على الكمبيوتر والهاتف، بالعربية والإنجليزية، فاتحاً وداكناً، وبالوصولية. ويُقاس ذلك بأدلة من المتصفح قبل الإصلاح وبعده، لا بالوصف.

## 2. نقطة البداية — ما أُنجز ولا يُعاد

**الاستنتاج الحاكم:** الأساس البصري والمكوّنات المركزية موجودة. فجوة H2 هي **الاتساق والتطبيق والتجربة على مستوى كل شاشة**، أي: هل تستعمل الشاشات الـ239 هذه المكوّنات والأنماط فعلاً وبالطريقة نفسها، وهل تدفّقات العمل نفسها سهلة؟

## 3. القرار الحاكم المطلوب أولاً: السطح المستهدف

v3 منفَّذة خلف `html[data-awj-ui="3"]`، والمسار القديم هو ما يراه المستخدم اليوم ما لم يُضبط `NEXT_PUBLIC_AWJ_UI_DEFAULT=3` في Railway.

| الخيار | الأثر |
|---|---|
| **أ (موصى به): التصميم والتحقق على v3** (البوابة مفعّلة)، مع فحص انحدار للمسار القديم في كل شريحة | الجهد يذهب إلى النظام الذي سيبقى؛ لا تحسين لمسار سيُزال |
| ب: الاثنان بالتساوي | ضعف الأدلة والوقت تقريباً، وتحسينات لمسار مؤقت |
| ج: القديم وحده | يتعارض مع v3 ويخلق انجرافاً جديداً |

مع الخيار أ: يصل أثر H2 للمستخدمين **عند تفعيل v3 افتراضياً**. التفعيل نشرٌ يملكه المالك ولا ينفّذه H2. **توصية:** أن يسبق التفعيل موجات الوحدات أو يرافقها، وإلا تبقى التحسينات خلف البوابة.

### 4.2 خارج النطاق (صراحةً)
- **`name_en` (D-ERP-UX-01)**، و**فجوة Cohort** في `nav-state`، وتقلّب `CreditNoteSourcePostgresTest`، وBL-001، وأي مشكلة backend أخرى. كلٌّ منها يُسجَّل «اعتمادية backend» ويُسلَّم لمالك backend، ولا يُعالَج داخل H2.
- أي تغيير في المحاسبة أو الضريبة/ZATCA أو الترقيم أو التسعير أو الأرصدة أو المخزون أو الهللات أو التقريب أو API أو قاعدة البيانات أو RBAC أو رؤية tenant/branch أو البنية التحتية.
- ميزات أو وحدات جديدة («قريباً» تبقى «قريباً»). إن احتاجت تجربةٌ بياناتٍ لا يعيدها الخادم، تُسجَّل `DESIGN_ONLY`/`GATED` ولا تُختلق.
- Storefront (واجهة المتسوق)، وتدفّقات checkout/payment، وbuilder persistence.
- `web/src/app/platform/**` و`web/src/components/platform/**` (مسار AWJ-PLATFORM-UX).
- إزالة بوابة v3 أو المسار القديم، والتفعيل الافتراضي ونشره (قرار مستقل).
- النشر للإنتاج.

## 5. منهج كل شريحة: دليل ← تشخيص ← إصلاح ← تحقق

1. **قبل:** فتح الشاشة الفعلية في المتصفح (Chromium/Playwright، بيانات `seed.sh`، البوابة مفعّلة) والتقاطها على المصفوفة القياسية أدناه، وتسجيل مسار المهمة الحقيقي (مثلاً: إنشاء فاتورة ← حفظ ← ترحيل)، وعدّ الخطوات والأخطاء.
2. **بحث بصري** (إلزامي في بروتوكول الأفق) في بداية كل موجة وحدات: زيارة منتجات مرجعية فعلياً ومشاهدة الشاشة المقابلة على Desktop/Mobile. المرشَّحة: Daftra (المرجع الوظيفي)، Microsoft Business Central، SAP Fiori، Odoo، Zoho Books/Inventory، Stripe Dashboard وLinear (أنماط الجداول والفلاتر)، Shopify Admin (Commerce)، Square/Toast/Foodics (POS). يُفصَل كلٌّ في `External Evidence` / `AWJ Decision` / `Rejected / Not Adopted`.
3. **إصلاح** بالمكوّن المركزي أولاً (قاعدة المكوّن الواحد في v3 §2A): لا نسخة محلية تنافس مكوّناً قائماً. المتغيّر الجديد يُضاف مركزياً ثم يُستهلك.
4. **بعد:** المصفوفة نفسها، والبيانات نفسها، والمسار نفسه. يُسجَّل الفرق في تقرير الشريحة مع اللقطات.

**المصفوفة القياسية للأدلة:** عربي 1440 فاتح · إنجليزي 1440 داكن · 1280×720 · 390 هاتف · 320 · تكبير 200% (عيّنة) · السمة Default دائماً وInk عيّنةً · دور `owner` ودور `staff` حيث تختلف الشاشة · البوابة القديمة (فحص انحدار فقط).

## 8. معايير القبول (كل شريحة كود)

1. لقطات **قبل/بعد** من المتصفح على المصفوفة القياسية (§5) في تقرير الشريحة.
2. **axe:** صفر انتهاك جديد على المسارات المتأثرة، وصفر تمرير أفقي عند 320، وترتيب عناوين سليم، وصفر مفتاح رسالة خام.
3. **لوحة المفاتيح:** المسار الأساسي كاملاً، والتركيز ظاهر، ولا حجب بالأشرطة اللاصقة.
4. RTL وLTR، وفاتح وداكن، وDefault (وInk عيّنةً).
5. **التوكنز:** لا hex/rgb أو `rounded-[..]` أو `shadow-[..]` أو نص < 12px جديد. **ratchet** `baseline.json` لا يرتفع، ويُخفَّض حيث أمكن.
6. **المكوّن الواحد:** لا نسخة محلية، والاستثناء مسجَّل.
7. **لا تغيير** لناتج رقمي أو محاسبي أو API، وتفحصه قائمة GOVERNANCE §5.
8. لا انحدار في المسار القديم (فحص اللقطات للمسارات المتأثرة).
9. Vitest كامل على الرأس النهائي، و`npm run build`، وWeb CI وCI أخضران.
10. مراجعتا Reviewer وAWJ Guardian على الرأس النهائي، و**إعادة قراءة كل خيوط المراجعة مباشرة قبل الدمج**، ثم `PRE_MERGE_REVIEW: PASS` ثم `POST_MERGE_REVIEW: PASS` بالـMerge SHA الحقيقي، وفحص CI على `main` قبل الشريحة التابعة.

## 11. سلطة الدمج والتوقف

- **مقترح بناءً على الموافقة المبدئية:** دمج تلقائي لكل شريحة **معتمدة النطاق** بعد اكتمال كل بوابات §8 دون انتظار، ثم الانتقال تلقائياً للتالية. **لا نشر.**
- **التوقف وطلب القرار** عند: الحاجة لأي بند خارج §4.2، أو قرار تصميم عالي الأثر خارج العقد المعتمد (A4)، أو P0 خارج الشريحة، أو تعارض مع ADR Commerce، أو فشل CI لا يخص الشريحة، أو تجاوز ميزانية CI.
- **مراجعة دورية:** تقرير قصير عند نهاية كل مرحلة (A، B، وكل موجة C) بالمنجز والمؤجَّل والقرارات.
