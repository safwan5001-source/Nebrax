## 2. فحص آلية القرارات الفردية والأقفال والمعاملات (قراءة فقط)

### 2.1 مسار `POST …/decisions` (الحالي)

`PartnerStatementReviewController::decide` (`throttle:60,1`، صلاحية `partner_statements.reconcile`، بوابة القدرة `accounting.partner_statements`) ← `PartnerStatementReviewService::decide`:

| # | الخطوة | الكلفة | ملاحظة |
|---|---|---|---|
| 1 | `matching->authorize`: RBAC (`reconcile` **و**`view`) + `assertReconciliationReadable` (نشاط الفاعل، `partners.view`، رؤية الطرف، الدور، فرع السياسة) | ثابتة | فشل ⇒ الرفض الموحَّد `PARTNER_UNAVAILABLE` (لا كشف وجود) |
| 2 | تحقق المدخلات؛ `run()` (التشغيلة مقروءة لنطاق الفاعل)؛ `line()`؛ صف `matches` للسطر | 3 استعلامات | |
| 3 | `DB::transaction` ← **قفل استشاري** `partner-statement-review:{tenant}:{recon}` ← `FOR UPDATE` على صف المقارنة ← فحص `status = draft` | قفلان | PG فقط (القفل الاستشاري يسقط على SQLite) |
| 4 | `matching->source()` ← `PartnerLedgerCandidates::for` ← `ReportService::partnerStatement` | **O(حجم دفتر الطرف في النافذة)** | يُقرأ **بعد** القفل (Codex #1915) |
| 5 | `digest->for()` | **O(N)**: يحمّل **كل** سطور الكشف (12 عموداً) ويحسب SHA-256 | |
| 6 | `assertFresh` (محرّك · سياسة · نطاق · بصمة دفتر · بصمة كشف) | مقارنات | `run_stale` 409 |
| 7 | `plan` (`planConfirm`/…) | **O(U)** للسطر الواحد | يبني `$byKey` من كل الوحدات |
| 8 | `warnings()` | استعلام | |
| 9 | `decisionsOf(recon)` | **O(D)**: يحمّل **كل** قرارات المقارنة | لحساب الفعّال والنسخة التالية وتعارض الوحدات |
| 10 | `sameDecision` ⇒ replay، وإلا فحص `unit_already_decided` بين السطور (O(claims × D)) | | |
| 11 | `PartnerStatementReviewDecision::create` ← مُشغّلات/قيود القاعدة | إدراج واحد | |

**الاستنتاج:** كلفة النداء الواحد O(L + N + D). إرسال N قراراً فردياً = O(N·(L+N+D)) — مع بحد الـthrottle: 1500 سطر ≥ **25 دقيقة** و2000 ≥ **33.3 دقيقة** (حساب 1500/60 و2000/60، غير مُقاس) قبل أي كلفة خادم، وبعشرات الآلاف من قراءات السطور/الدفتر. هذا يؤكد G3 ويُظهر أن الحلّ ليس «رفع الـthrottle» بل مسار جماعي بقراءات مرة واحدة.

### 2.2 أهلية السطر كما تُنفَّذ اليوم (`planConfirm`)

- `outcome ∈ {matched, amount_difference, date_difference}` و`unit_key` غير فارغ، وإلا `nothing_to_confirm`.
- سبب إلزامي لغير `matched`، **ولكل فرق مالي ≠ 0** (D-PS-16) — ثابت لا يُضبط.
- `net()`: الوحدة `active` وقابلة للمطابقة، ثم `settle()`: `difference = expected − setNet`؛ خارج `amount_tolerance_minor` ⇒ `difference_exceeds_tolerance` ما لم يُقرّ صراحةً.
- يخرج بـ`claims` (= unit_key) و`entry_ids` (قيود الوحدة مرتبة، من الدفتر المقيَّد ببصمة القرار).

**ما يعنيه «matched» فعلاً في المحرّك** (`PartnerStatementMatchingEngine`):
1. R1/R2 (مفتاح مرجع): `matched` حين |فرق المبلغ| ≤ التسامح و|فرق الأيام| ≤ تسامح التاريخ — أي **`matched` قد يحمل فرق أيام ≠ 0** ضمن التسامح (الافتراضي 3 أيام) و**فرق مبلغ ≠ 0 إن كان تسامح المقارنة > 0** (الافتراضي 0).
2. R3 (`matched_by_amount_date_unique`): بلا مرجع، مبلغ+تاريخ وحيدان من الجهتين — **أضعف قاعدة دليلاً**.
3. `base()` يضيف تحذير محرّك `kind_side_mismatch` إلى `warnings` المخزَّنة، و`decide` يحسب فوق ذلك `unit_proposed_for_another_line` — فعبارة «بلا تحذيرات» في العقد **تحتمل مصدرين** (يلزم تحديدها: §8-ي).

### 2.3 نقاط الكلفة المخفية عند إعادة الاستعمال الحرفي للمخطِّط (F3)

| النقطة | حرفياً ×N | الحلّ المقترح |
|---|---|---|
| `net()` يبني `$byKey` من كل `units` في كل نداء | N × U (مثلاً 2000×2000 ≈ 4 ملايين عملية مصفوفة) — **تقدير حسابي غير مُقاس** | خريطة `unitsByKey` تُحسب مرة واحدة وتُمرَّر |
| `entryIdsOf()` يمسح كل الوحدات + `in_array` | N × U | نفس الخريطة (`entry_ids` جاهزة لكل وحدة) |
| `warnings()` استعلام لكل سطر | **N استعلاماً** | استعلام واحد `whereIn(unit_key)` وتجميع في الذاكرة |
| تعارض الوحدات: كل claim × كل القرارات الفعّالة (`explode` داخل الحلقة) | N × D | فهرس claims مبنيّ مرة واحدة (hash set بـ`وحدة` و`وحدة@عضو`) |
| `decisionsOf` يحمّل كل القرارات | مرة واحدة (مقبول) | |
| `PartnerStatementReviewDecision::create` لكل سطر | N إدراجاً + أحداث نموذج | `insert()` مُجزَّأ 500 (سابقة `PartnerStatementMatchService::INSERT_CHUNK`: يضبط `id`/`tenant_id`/`created_at` يدوياً) |

**الاقتراح (قرار D-A4-04ط):** استخراج «التخطيط» (`planConfirm` + `net` + `settle` + `entryIdsOf`) إلى مكوّن نقيّ تستعمله `decide` والجماعي معاً. هذا **يحقق** روح العقد («لا منطق قرار ثانٍ») بصرامة أكبر من إعادة النداء، لكنه يمسّ مساراً حرجاً قائماً ⇒ شروطه: اختبار مكافئة (§7-أ) على بيانات متطابقة + Mutation على الدالة المشتركة. البديل (إبقاء النداء الحرفي) يبقى N استعلام تحذيرات وN×U CPU؛ يُقبل فقط إن أثبت القياس أنه ضمن العتبات.

### 2.4 الأقفال والترتيب — الجدول المرجعي

| المورد | من يقفله | النوع | ملاحظة للاعتماد الجماعي |
|---|---|---|---|
| قفل استشاري مراجعة المقارنة | `decide`، `markReviewed`، `reopen`، `close`، `void`، `replace` (نفس المفتاح عبر `lockReconciliation`) | `pg_advisory_xact_lock` | **الجماعي يأخذه مرة واحدة** ⇒ يتسلسل مع كل ما سبق |
| قفل استشاري المطابقة | `PartnerStatementMatchService::run` | مفتاح مختلف (`partner-statement-match:…`) | لا يتعارض مع المراجعة؛ تشغيلة جديدة أثناء الجماعي لا تؤثر (الجماعي مربوط بـ`run_id`) |
| صف المقارنة | `decide` وغيره | `FOR UPDATE` | مرة واحدة |
| قفل نطاق الطرف الواسع | `close` وما فوقه | استشاري | **لا يأخذه الجماعي** (لا يكتب مطالبات) |
| **صف `tenants` (مِرساة الأستاذ)** | `LedgerService` عبر `AccountingDateGuard::lockAnchor` (`lockForUpdate()` ⇒ `FOR UPDATE`)، و`close` | `FOR UPDATE` | **يتعارض مع `FOR KEY SHARE` الذي يأخذه FK عند إدراج القرارات** (F1) |
| صفوف الأم الأخرى (`users`، `lines`، `runs`، `recons`) | FK عند الإدراج | `FOR KEY SHARE` | لا تعارض عملي (تتعارض فقط مع حذف/تعديل مفتاح) |

**ترتيب القفل:** استشاري المراجعة ← صف المقارنة ← (عند الإدراج) `KEY SHARE` على الأم. `close` يأخذ استشاري المراجعة ← استشاري الطرف ← صف المقارنة ← المِرساة؛ فالجماعي والإغلاق يتسلسلان **على المقارنة نفسها** عند البداية، ولا دورة أقفال مع إغلاق **مقارنة أخرى** للطرف نفسه (لا تحتاج قفل مقارنتنا). يبقى `replace`/`void` عبر مقارنتين اختباراً إلزامياً (§7-ج) لا افتراضاً.

**F1 مُثبَت:** (§A.1) معاملة تُدرج 1500 صفاً بمفتاح أجنبي إلى `tenants` وتنام 3 ثوانٍ، وجلسة ثانية تطلب `SELECT … FOR UPDATE` على صف المستأجر بعد ثانية: **انتظرت 2.05 ث** (تساوي عمر المعاملة المتبقي)، مقابل **0.05 ث** لـ`FOR NO KEY UPDATE`. نتيجة عملية:
- الأقفال تُؤخذ **عند تنفيذ عبارة INSERT الأولى** لا عند `BEGIN`: كل ما يسبقها (قراءة الدفتر، البصمة، التخطيط) لا يجمّد الترحيل.
- فنافذة تجميد الترحيل = من أول INSERT حتى COMMIT. في التجربة الاصطناعية ≈ 13 / 60 / 78 ms لـ200/1500/2000 (§A.2) — منخفضة **إن** بُنيت كل الصفوف مسبقاً وأُدرجت متتالية.
- العكس صحيح: ترحيل قيد جارٍ يمسك المِرساة سيؤخر مرحلة الإدراج، والجماعي ممسك بقفلَي المقارنة طوال الانتظار ⇒ يجب `lock_timeout` قصير (§3.3).

### 2.5 ما يحرسه الجدول في القاعدة عند الإدراج (يؤثر على الكلفة والتوافق)

- **PostgreSQL:** `partner_stmt_decision_shape_chk` (شكل الإجراء/الوحدات)، `partner_stmt_decision_entry_ids_chk`، فهرس فريد `(tenant, reconciliation, line, revision)`، **مُشغّل `BEFORE INSERT FOR EACH ROW` للتأكد أن النسخة = 1 + MAX(نسخة السطر)** (استعلام جزئي لكل صف)، مفاتيح أجنبية: `tenant`، `line`، `created_by`، و`(tenant, reconciliation)` و`(tenant, run)`. مُشغّلات التحديث/الحذف/التفريغ تمنع التعديل (سجل append-only).
- **SQLite (CI):** مُشغّلات مكافئة للشكل والنسخة و`claim_entry_ids`.
- **لا مُشغّل على الجدول يقرأ حالة المقارنة**: كون المقارنة `draft` يفرضه الكود تحت القفل فقط (فجوة قائمة اليوم في المسار الفردي أيضاً، تغطيها اختبارات الخدمة).
- مُشغّلات المطالبات (`partner_statement_unit_claims`) تقرأ القرارات عند **الإغلاق** لا عند إدراج القرار.
- **أثر لتجربة الأداء:** مُشغّل النسخة هو الجزء الغالب من كلفة الإدراج (§A.2) وخطته تعتمد على إحصاءات الجدول — انظر تنبيه القياس §4.3.

## 3. تقييم الاعتماد الجماعي الذرّي: 200 / 1500 / 2000

### 3.1 الجدوى حسب الحجم

| الحجم | وضع الطلب | الحمولة | مرحلة الإدراج (اصطناعي) | الحكم |
|---|---|---|---|---|
| 200 | `line_ids[]` أو `exact` | ≤ ~8 KB معرّفات | ≈ 13 ms | **جدواه عالية**؛ المخاطر في الاستعلامات لا القفل |
| 1500 | `exact` | بلا معرّفات (بصمة + عدد) | ≈ 60 ms | **ممكن**؛ يعتمد على زمن قراءة الدفتر/البصمة/التخطيط (غير مُقاس) |
| 2000 (= `MAX_ROWS`) | `exact` | نفسه | ≈ 78 ms | **ممكن**؛ سقف طبيعي مضمون بالاستيراد ⇒ لا حاجة لتقسيم |

لا قيد في القاعدة يمنع: `unit_keys` وحدة واحدة لكل قرار `confirm`، و`claim_entry_ids` ≤ 5000 لكل صف (مفعول لوحدة واحدة ⇒ عملياً 1–بضعة قيود)، والمفتاح الفريد لا يتصادم لأن السطر يتلقى نسخة تالية.

### 3.2 التصميم المطلوب لتحقيق الأرقام أعلاه (مبدأ «الإدراج آخراً»)

1. `authorize` + تحقق مدخلات + (للمعرّفات) فحص أن كل `line_id` يخص هذه المقارنة — **قبل** المعاملة.
2. معاملة واحدة، `SET LOCAL lock_timeout` (قيمة: §8-ي)، قفل استشاري ← قفل صف المقارنة ← فحص `draft`.
3. قراءات **مرة واحدة**: `source()` (دفتر)، بصمة الكشف، صفوف `matches` للتشغيلة **بأعمدة محدودة** (دون `candidates`/`suggestions`/`unit` الثقيلة)، `decisionsOf`، استعلام تحذيرات واحد. `assertFresh` + `statement_changed` كما `decide`.
4. تخطيط **في الذاكرة** لكل سطر (المكوّن المشترك) وتجميع الأخطاء بأول فشل (كله أو لا شيء، `persisted: 0`).
5. إعادة حساب المجموعة وبصمتها ومقارنتها بـ`expected_count`/`expected_digest` (انحراف ⇒ `bulk_set_changed`).
6. بناء كل الصفوف كمصفوفات (uuid، `tenant_id`، الطابع الزمني) **ثم** `insert()` مُجزَّأ 500 متتالياً ثم COMMIT. لا أي حساب أو قراءة بين أول INSERT وCOMMIT.
7. الاستجابة: `{batch_id, count, replayed, sample}` — **لا** N قراراً (الحمولة صغيرة)؛ التفاصيل تُقرأ من `GET decisions`/`lines` القائمة.

### 3.3 نقاط تصميم حاسمة

- **`lock_timeout` على المسار:** بلا سقف، ترحيل قيد طويل أو إغلاق جارٍ يُبقي الجماعي ممسكاً بقفل المقارنة (فتتكدس قرارات المراجعين الآخرين). المقترح `SET LOCAL lock_timeout = '5s'` ورمز خطأ قابل للإعادة (`bulk_lock_busy`، 409، `persisted: 0`). **لا ينطبق على المسارات القائمة** (سلوكها لا يتغير).
- **حدّ READ COMMITTED (مقبول ومعلَن أصلاً):** ترحيل قيد يُثبَّت بين قراءة الدفتر والالتزام لا يمنعه قفل المراجعة؛ القِدم يظهر عند أي قراءة/`review` لاحق (`assertFresh`). الجماعي يوسّع النافذة (معاملة أطول) لكن بلا فقدان: القرارات تبقى مرتبطة ببصمة قديمة ويظهرها `decisions_on_other_runs`. لا يُقترح قفل المِرساة طوال التخطيط (يجمّد الترحيل لكل المستأجر — أسوأ).
- **التزامن مع التشغيلة الجديدة:** `run` يأخذ قفلاً استشارياً مختلفاً ⇒ قد ينشئ تشغيلة أثناء الجماعي؛ لا ضرر (الجماعي ثابت على `run_id`، وإن تغيّر الدفتر تتغير بصمته فيفشل `assertFresh` في الطلب التالي).
- **التشغيل المتزامن (sync):** الإنتاج على `QUEUE_CONNECTION=sync` ⇒ المسار طلب HTTP متزامن. حدود مهلة الوسيط/PHP **غير مُتحقَّق منها** هنا؛ تُقاس في القياس الطرفي (§4) وتدخل العتبة (HTTP p95).
- **الذاكرة:** صفوف `matches` للتشغيلة تحمل JSON ثقيلاً؛ التحميل بأعمدة محدودة شرط (غير مُقاس).

### 3.4 عدد الاستعلامات المتوقع (اشتقاق، غير مُقاس)

|---|---|---|
| authorize + run + line | ~(5–8)·N | ~5–8 مرة واحدة |

## 4. خطة قياس الأداء على PostgreSQL حقيقي

> **لم تُنفَّذ في هذا التقرير** (لا يوجد كود جماعي لقياسه). ما نُفِّذ فقط التجارب الاصطناعية في §A. هذه خطة + عتبات **مقترحة** تحتاج اعتماد المالك.

### 4.1 الشرط المسبق: سبايك غير قابل للدمج (D-A4-04هـ)

العقد يشترط القياس **قبل** الإذن بالتنفيذ، والقياس يحتاج الخوارزمية. الحل: فرع سبايك مؤقت يضم (أ) الخوارزمية المخططة (§3.2) و(ب) هجرة `batch_id` المرشَّحة و(ج) حزمة القياس أدناه — **لا يُدمج ولا يُنشر**؛ مخرجاته تقرير أرقام + قرار. هذا يتطلب موافقة صريحة لأنه يتجاوز «تحليل فقط».

### 4.2 مصفوفة البيانات

| المحور | القيم |
|---|---|
| عدد سطور الكشف N | 200 · 1500 · 2000 |
| وحدات الدفتر L (حجم دفتر الطرف في النافذة) | N · 5N |
| نسبة الأهلية | 100% · 70% (الباقي فروق/غامض/غائب) — لتأكيد أن القياس ليس أفضل حالة فقط |
| قرارات سابقة | لا شيء · 50% محسوم سابقاً (يُختبر مسار الرفض الذرّي وتكلفته) |
| الاستمرارية | PG على tmpfs (يعزل التنافس كما `pg-perf`) **و**على قرص حقيقي بـ`fsync` (يقيس WAL فعلياً) — قياس القرص غير مانع للدمج كما `perf-feed-lock-baseline` |
| حمل متزامن | C0 خامل · C1 ترحيل قيود على المستأجر نفسه (≈5/ث) · C2 قرارات فردية على مقارنة أخرى للمستأجر · C3 جماعي ثانٍ لمستأجر آخر · C4 قرارات فردية على المقارنة نفسها (تنتظر القفل) |
| الجولات | ≥ 20 لكل خلية بعد 3 جولات إحماء تُهمَل؛ تقرير p50/p95/max |

### 4.3 تنبيهات منهجية مستخلصة من التجارب الاصطناعية

1. **إحصاءات الجدول تغيّر النتيجة 3×**: على جدول فارغ الإحصاءات (مباشرة بعد `TRUNCATE`) كان إدراج 2000 صف ≈ 264 ms (النمو فوق الخطي ناتج على الأرجح عن مسح تسلسلي داخل مُشغّل النسخة)، وبعد تعبئة 20 ألف صف لمقارنة أخرى + `ANALYZE` صار ≈ 78 ms (§A.2). **أي قياس CI على قاعدة طازجة يعطي فشلاً كاذباً** ما لم يُعبَّأ الجدول ويُحلَّل قبل الجولات. شرط في الحزمة.
2. اختبار `lock_timeout` موروث من البيئة (`PGOPTIONS='-c lock_timeout=60s'`)؛ قياس التنافس يجب أن يُسجّل أيضاً حالة `lock_timeout` القصير للمسار (5 ث).
3. `Eloquent::create` لكل صف يضيف رحلة قاعدة بيانات وأحداث نموذج لكل سطر مقابل `insert()` مجزّأ؛ القياس يجب أن يكون على المسار المقترح فقط (والفرق بينهما نفسه يُقاس في السبايك).

### 4.4 ما يُقاس وكيف

| المقياس | الأداة |
|---|---|
| زمن المعاملة الكلي (BEGIN→COMMIT) ومراحله: authorize · انتظار القفل · قراءة الدفتر · البصمة · التخطيط · الإدراج · COMMIT | فواصل `microtime` في الحزمة (اختبار فقط، لا في كود الإنتاج) |
| **نافذة تجميد المِرساة** = أول INSERT→COMMIT | نفس الفواصل + مطابقة بـ`pg_stat_activity` |
| انتظار الأقفال لدى المتنافسين (مثلاً زمن ترحيل قيد متزامن) | قياس جداري لدى المتنافس + أخذ عيّنات `pg_stat_activity.wait_event_type='Lock'` كل 20 ms + `log_lock_waits=on` |
| الاستعلامات (العدد، والأبطأ) | `DB::listen` + `pg_stat_statements` (إن توفرت) |
| كلفة المُشغّلات/الـFK | `auto_explain` مع `log_nested_statements` |
| الذاكرة | `memory_get_peak_usage(true)` |
| حجم WAL للمعاملة | فرق `pg_current_wal_lsn()` |
| الجمود/الأخطاء | عدّ SQLSTATE `40P01` و`55P03` (يجب 0 و«متوقعة فقط» على التوالي) |

التنفيذ: مجموعة PHPUnit `ps-a4b0-perf` بنمط وظيفة `pg-perf` القائمة (`--fail-on-skipped --fail-on-risky`، خطوة تحقق من tmpfs، تلخيص ملخّص كما `scripts/ci-perf`)، وغياب `pcntl` فشل لا تخطٍّ.

### 4.5 العتبات المقترحة (**للاعتماد؛ ليست نتائج**)

أساسها: خط الأساس الاصطناعي لمرحلة الإدراج (§A.2) × هامش ≈ 5–6 للتجهيز في PHP، وسقوف قابلة للتحمل لطلب تفاعلي متزامن:

| المقياس | 200 | 1500 | 2000 |
|---|---|---|---|
| زمن المعاملة الكلي، p95 (خامل، ذاكرة دافئة) | ≤ 1.5 ث | ≤ 4 ث | ≤ 5 ث |
| نافذة تجميد المِرساة (أول INSERT→COMMIT)، p95 | ≤ 100 ms | ≤ 400 ms | ≤ 500 ms |
| زمن انتظار ترحيل قيد متزامن بسبب الجماعي، p95 / max | ≤ 100 / 250 ms | ≤ 400 / 800 ms | ≤ 500 / 1000 ms |
| الاستعلامات | الثابت المقيس + ≤ 15، و`Q(2000) − Q(200) ≤ 3` | | |
| الذاكرة القصوى | ≤ 128 MB عند N=2000 و L=5N (القيمة تُراجع مقابل `memory_limit` الفعلي) | | |
| `40P01` (جمود) | 0 في كل المصفوفة | | |
| الجماعي الثاني/الفردي المتزامن | ينتظر القفل ثم ينجح أو يفشل بـ409 قابل للتنفيذ، لا 500 | | |

**قاعدة التوقف (من العقد):** تجاوز أي عتبة يوقف الشريحة؛ **لا يُحلّ بالتقسيم إلى طلبات** (ذلك يخالف الذرّية). الخيارات عندئذٍ: تحسين، أو خفض السقف بقرار المالك (وهو أراد 1500 مدعوماً).

### 4.6 مخرجات القياس المطلوبة قبل الإذن

جدول p50/p95/max لكل خلية، تفصيل المراحل، لقطة `pg_locks`، عدد الاستعلامات، الذاكرة، WAL، ومقارنة مع خط أساس **القرار الفردي** (يُقاس بالحزمة نفسها لتأكيد التحسّن وللمعايرة).

## 5. دراسة `batch_id` (D-A4-04د)

### 5.1 لماذا هو أكثر من تجميل تدقيقي

| الحاجة | بلا `batch_id` | معه |
|---|---|---|
| إعادة الطلب بعد مهلة شبكة (F2) | وضع المعرّفات: يعمل عبر `sameDecision`. **وضع `exact`: مستحيل اشتقاقه** (المجموعة الأهلة صارت فارغة، والبصمة hash غير عكوسة) ⇒ خطأ مضلّل رغم نجاح الحفظ | `200 replayed` دقيق |
| عرض «اعتماد جماعي (N)» وتجميعه في التدقيق | غير ممكن إلا بالتخمين (فاعل+وقت متقاربان) | استعلام مباشر |
| تراجع الدفعة لاحقاً (ح) | غير ممكن | ممكن (مرشَّح) |
| إثبات أن المجموعة المنفَّذة = المعايَنة | لا أثر | إعادة حساب البصمة من الصفوف |

### 5.2 الخيارات

| الخيار | الوصف | التقييم |
|---|---|---|
| A | بلا `batch_id` | **مرفوض** لـF2؛ يقبل فقط إن اعتُبر replay في `exact` غير مطلوب (غير مستحسن) |
| **B** | عمود `batch_id uuid NULL` على `partner_statement_review_decisions`، **يُرسله العميل** (مفتاح idempotency) | **موصى به**: تغيير إضافي أدنى، سابقة مباشرة (`claim_entry_ids`) |
| C | جدول رأس `partner_statement_review_batches` + FK | تدقيق أغنى (وضع/عدّاد/بصمة)، لكنه جدول جديد + 4 مُشغّلات append-only + تعقيد؛ غير لازم الآن، ويمكن إضافته لاحقاً فوق B |
| D | وسم داخل `reason` أو في جدول الأحداث | **مرفوض**: `reason` جزء من `sameDecision` ويكسر مكافئة الفردي؛ وجدول الأحداث (`partner_statement_reconciliation_events`) أعيد تعريف دوال حراسه في 3 هجرات متتالية ⇒ هشّ، وله CHECK على قائمة إجراءات |

### 5.3 تصميم الخيار B (مقترح)

- **العمود:** `batch_id` UUID **nullable**، بلا قيمة افتراضية، بلا backfill (الفردي ⇒ NULL).
- **من يولّده:** العميل (UUID v4 عشوائي يُنشأ عند فتح المعاينة/تأكيد المستخدم). **مرفوض** اشتقاقه حتمياً من البصمة: إعادة اعتماد المجموعة نفسها بعد `clear` تُنتج المعرّف نفسه فتتداخل الدفعتان.
- **فهرس:** جزئي `(tenant_id, reconciliation_id, batch_id) WHERE batch_id IS NOT NULL` للبحث والتجميع.
- **قيد:** `batch_id IS NULL OR action = 'confirm'` (PG: CHECK؛ SQLite: مُشغّل — كسابقة `partner_stmt_decision_entry_ids`).
- **دلالة الـreplay (تحت القفل الاستشاري):** إن وُجدت صفوف بالـ`batch_id` في هذه المقارنة: نفس `run_id` وعدد الصفوف = `expected_count` وبصمة الصفوف المخزَّنة = `expected_digest` ⇒ `200 replayed` بلا كتابة؛ غير ذلك ⇒ `409 bulk_batch_id_reused`. لا وجود ⇒ مسار التنفيذ العادي. المعرّف غير مفرَد عبر المقارنات في القاعدة (مفرد منطقياً بنطاق المقارنة تحت القفل) — يكفي لأن كل الاستعلامات مقيَّدة بالمستأجر والمقارنة.
- **الفردي لا يتغير:** `decide` لا يكتب `batch_id`؛ تراجع فردي لاحق (`clear`) صف جديد بـNULL.

### 5.4 أثر الـMigration

| البند | التفصيل |
|---|---|
| DDL | `ALTER TABLE … ADD COLUMN batch_id uuid NULL` — على PostgreSQL ≥ 11 **تعديل بيانات وصفية فقط بلا إعادة كتابة**؛ يحتاج `ACCESS EXCLUSIVE` لحظياً (قد ينتظر خلف معاملات تلمس الجدول ⇒ يُنفَّذ بـ`lock_timeout` قصير). + فهرس جزئي (الجدول append-only صغير نسبياً؛ بناء عادي مقبول، ويُتحقق من الحجم عند التنفيذ) |
| SQLite (CI) | `Schema::table` يدعم إضافة العمود؛ الفهرس الجزئي والمُشغّل بـ`DB::unprepared` كسابقة `2027_01_02_000100` |
| الجداول/المُشغّلات القائمة | **لا مساس**: مُشغّلات عدم التعديل/الحذف/التسلسل تبقى صالحة (إدراج فقط)؛ لا إعادة تعريف دوال قائمة (تجنّباً لهشاشة الهجرات المتتابعة) |
| `down()` | يرفض إن وُجد صف بـ`batch_id` (سابقة `claim_entry_ids`: أثر تدقيق) |
| الترتيب عند النشر | **الهجرة أولاً ثم الكود**. الكود القديم مع المخطط الجديد سليم (عمود اختياري). التراجع عن الكود بعد الاستعمال يترك الأعمدة، والتراجع عن الهجرة ممنوع بعده |
| الحاجة لموافقة | **نعم** (العقد: «Migration يحتاج موافقة صريحة»). **لم تُكتب ولم تُنفَّذ هنا** |

### 5.5 التوافق

- API: حقل `batch_id` **إضافي** في `PartnerStatementReviewService::present` و`PartnerStatementReconciliationQuery::presentDecision` — بينهما اختبار تكافؤ يجب تحديثه معاً. مرشّح اختياري `batch_id` على `GET decisions`.
- الويب: أنواع TypeScript للقرار تتسامح مع حقل إضافي (لم يظهر فحص صارم من نوع zod `strict` في وحدة `partner-statements`)، ويُضاف الحقل اختيارياً.
- نموذج Eloquent: إضافة `batch_id` إلى `$fillable` فقط إن استُعمل `create` (المقترح `insert()` الخام يتجاوز).
- لا أثر على القيود/الأستاذ/ZATCA/المطالبات (القرارات لا تحمل قيماً مالية محاسبية).

### 5.6 أثر التدقيق

يضيف: تجميع الدفعة، عدّ، فاعل/وقت مشترك، إمكان إعادة حساب البصمة. **لا يحل:** ظهور الدفعة في `GET …/events` (جدول أحداث دورة الحياة فقط) — العرض يُشتق قراءةً من القرارات مجمَّعة بـ`batch_id` دون حدث جديد. يبقى لكل سطر صفّه بالقيم نفسها التي يكتبها `decide` (شرط العقد §6).

| C7 | ترحيل قيد بين قراءة الدفتر والالتزام (READ COMMITTED) | قرارات على بصمة قديمة | حدّ معلَن مقبول (`decisions_on_other_runs`)، نافذة قصيرة | اختبار يُظهر `run_stale` في الطلب التالي |
| C8 | مهلة شبكة ثم إعادة الطلب (F2) | ازدواج أو خطأ مضلّل | `batch_id` + replay | إعادة الطلب بعد نجاح |
| C9 | اعتماد حالة `STATUS_DRAFT` غير محروسة بالقاعدة | قرار على مقارنة غير مسودة عند خلل | الفحص تحت القفل (كاليوم) | اختبار `reviewed` ⇒ `persisted: 0` |

## 7. خطة الاختبارات اللازمة (إضافة إلى ما في العقد §7)

**أ. مكافئة وتكامل (SQLite + PG):** نتيجة الجماعي = `confirm` الفردي سطراً سطراً (الحقول كاملة بما فيها `claim_entry_ids` والنسخة) · اختبار تكافؤ للمخطِّط المشترك قبل/بعد الاستخراج (قرارات فردية قبل الاستخراج = بعده) · `present` مطابق للاستعلام (حقل `batch_id`) · الحدود 200 مقبول/201 مرفوض · `exact` عند 2000 · سطر ذو `clear` سابق يأخذ النسخة التالية.

**ب. ذرّية بحقن فشل:** عند السطر k، وآخر سطر، وجزء الإدراج الثاني والثالث؛ + قِدم التشغيلة · انحراف الأهلية · قرار قائم (أي تشغيلة) · بصمة/عدد مغايران · `reviewed` · تحقق مدخلات · `lock_timeout` — كلها `persisted: 0` وعدد صفوف القرارات قبل = بعد.

**ج. تزامن PostgreSQL (`pcntl_fork`، فشل لا تخطٍّ، على نمط `PartnerStatementReviewConcurrencyPostgresTest`):** جماعي × فردي على سطر · جماعي × جماعي · × `match` · × `review`/`reopen` · × `close` (مقارنة أخرى للطرف) · × `void/replace` عبر مقارنتين · **جماعي × ترحيل قيد: يُقاس انتظار الترحيل ≤ العتبة (F1)** · عدم وجود 40P01 · invariant: لا سطر بقرارين فعّالين · replay بعد نجاح متزامن.

**د. أداء (§4):** مجموعة `ps-a4b0-perf` + اختبار عدد الاستعلامات `Q(2000) − Q(200) ≤ 3` + تثبيت الإحصاءات قبل القياس.

**هـ. أمن وعزل:** 403 بلا `reconcile` · قدرة موقوفة/معطّلة · مستأجر آخر/مقيَّد/طرف مخفي ⇒ استجابة موحَّدة بايتاً ببايت لـ{مجهول، أجنبي، غير متاح} · عدم تسرب أعداد خارج النطاق · `rejectUnknown` (لا `reason`/`accept_difference`/`override`…) · `expected_digest` إلزامي.

**و. جدار ساكن:** لا استدعاء للخدمة إلا من المتحكّم · لا مجدول/Job/Listener · لا `LedgerService`/كتابة محاسبية · الإدراج عبر مسار واحد يضبط `tenant_id` · لا commit وسيط في ملف الخدمة.

**ز. Mutation (كل واحدة تُسقط اختباراً):** إزالة صفر الصافي · إزالة «بلا تحذيرات» (بمصدريه) · إزالة `matched` · تعطيل مقارنة البصمة/العدد · commit وسيط · إزالة `assertFresh` · إزالة فحص الصلاحية · قبول `reason`/`accept_difference` · إزالة فحص «قرار قائم» · **إزالة ضبط `tenant_id`** · **إلغاء قيد `reconciliation_id` على المعرّفات** · **تعطيل مقارنة `batch_id` في replay**.

## 9. التوصية النهائية

1. **GO مشروط**: الاعتماد الجماعي الذرّي ممكن ومعمارياً سليم، وهو الحلّ الصحيح لـG3 (تقدير 25–33 دقيقة تسلسلياً + كلفة O(N²) خادماً).
2. **لا بناء قبل**: القرارات الحاجزة د/هـ/ط/ي/و/ز.
3. **المسار المقترح:** (أ) قرارك على §8 ← (ب) سبايك قياس غير قابل للدمج على PostgreSQL (tmpfs + قرص) ← (ج) اعتماد العتبات من الأرقام الفعلية ← (د) PR الهجرة `batch_id` (إضافية، بموافقتك) ← (هـ) PR الخلفية (الخدمة + المتحكّم + الاختبارات + Mutation) ← (و) PR الواجهة (زر + حوار المعاينة) بعد البحث البصري المعتاد.
4. **أخطر نقطتين للتنفيذ:** (1) «الإدراج آخراً» + `lock_timeout` (F1)، (2) المخطِّط المشترك (F3) — إخفاقهما يعطي إما تجميد ترحيل أو منطق قرار ثانٍ.
5. **ما لم يُنفَّذ هنا:** أي كود أو هجرة على مخطط التطبيق، اختبارات التطبيق (لا تغيير كود ⇒ لم تُشغَّل المجموعة الكاملة)، أي قياس تطبيقي.

## ملحق A — التجارب الاصطناعية (بيئة الجلسة، PostgreSQL 16.15، `fsync=on`، `shared_buffers=128MB`، 4 أنوية)

> قاعدتان مؤقتتان (`scratch_lock`، `scratch_bulk`) خارج التطبيق، بمخططات يدوية، حُذفتا بعد التجربة. **ليست قياساً لأداء التطبيق**، وأرقامها أرضية دنيا لمرحلة الإدراج في قاعدة البيانات وحدها (دون PHP/Eloquent/الشبكة/قراءة الدفتر).

### A.1 تعارض الأقفال (F1)

الجدولان: `tenants(id)` و`decisions(tenant_id → tenants)`. الجلسة A: `BEGIN; INSERT … SELECT generate_series(1,1500); pg_sleep(3); COMMIT`. الجلسة B (بعد ثانية): `BEGIN; SELECT … FROM tenants … FOR UPDATE; COMMIT` (تحاكي `lockAnchor`).

| قفل الجلسة B | انتظار B | 
|---|---|
| `FOR UPDATE` (ما يفعله `LedgerService`) | **2.05 ث** (= المتبقي من معاملة A) |
| `FOR NO KEY UPDATE` (ضابط) | 0.05 ث |

### A.2 كلفة مرحلة الإدراج

جدول يحاكي `partner_statement_review_decisions`: الأعمدة نفسها، FK إلى `tenants`/`users`/`lines` وFK مركّب إلى المقارنة والتشغيلة، الفهرس الفريد `(tenant, reconciliation, line, revision)`، CHECK الشكل و`claim_entry_ids`، ومُشغّل `BEFORE INSERT FOR EACH ROW` للنسخة. معاملة واحدة، 4 عبارات `INSERT … SELECT` بحجم ≤ 500 (كـ`INSERT_CHUNK`)، 5 جولات لكل حجم. القيم بالميلي ثانية.

**أ) جدول مهيّأ الإحصاءات (20 ألف صف لمقارنة أخرى + `ANALYZE`) — الأقرب للواقع:**

| N | مرحلة الإدراج (الوسيط / المدى) | COMMIT |
|---|---|---|
| 200 | 12.9 / 11.9–18.4 | 0.7–1.3 |
| 1500 | 60.6 / 55.5–71.6 | 1.1–2.3 |
| 2000 | 78.0 / 76.2–87.3 | 2.2–2.8 |

**ب) جدول بلا إحصاءات (بعد `TRUNCATE` مباشرة) — تنبيه منهجي:**

| N | مرحلة الإدراج (الوسيط / المدى) |
|---|---|
| 200 | 13.9 / 13.5–17.1 |
| 1500 | 158.1 / 152.8–168.5 |
| 2000 | 264.4 / 248.6–267.5 |

**ج) ضابط: المُشغّل معطَّل (بلا إحصاءات):** 1500 ⇒ 44.5 (44.3–55.1) · 2000 ⇒ 58.2 (57.4–61.1) — ما يشير إلى أن مُشغّل النسخة هو الجزء الغالب من الكلفة وأن الأثر الفوق خطي في (ب) مرتبط بخطته مع غياب الإحصاءات (استنتاج لم يُتحقَّق منه بـ`EXPLAIN`).

**تحفظات:** قرص/ذاكرة الجلسة لا تمثل الإنتاج؛ `COMMIT` سريع هنا (ملاحظة: جولة واحدة بلغت 31–34 ms في (ب)/(ج)) ولا يعكس WAL/تخزين الإنتاج؛ النموذج لا يشمل مُشغّلات الجداول الأخرى ولا حمل متزامن.

### A.3 إعادة الإنتاج

سكربتات SQL مؤقتة (غير مُدرجة في المستودع): إنشاء المخطط أعلاه، ثم لكل N: `BEGIN; 4× INSERT … SELECT … FROM (select id,row_number() over(order by id) rn from lines) l WHERE rn BETWEEN … ; COMMIT;` مع `\timing on`، وتحضير الإحصاءات بـ`INSERT` 20 ألف صف لمقارنة أخرى (مع تعطيل المُشغّل أثناء التحميل) ثم `ANALYZE decisions`. ستُدمج النسخة المنقّحة في حزمة القياس عند اعتماد السبايك (§4.1).
