| # | الفجوة (مُتحقَّق منها في Base) | الأثر | المعالجة المقترحة |
|---|---|---|---|

### 2.3 عقد الأخطاء (يحكم رسائل الواجهة — **المفتاح هو `reason` لا `message`**)

|---|---|---|

**البنية:** مسار `/partner-statements` (قائمة) · `/partner-statements/import` (معالج) · `/partner-statements/[id]` (مساحة العمل بتبويبات). **مصدر الحقيقة للأزرار:** عقد القراءة (`status.close`, `status.void`, `readiness.can_mark_reviewed`) + `useCan` — لا استنتاج من الحالة وحدها (نمط COPS).

## 4. Mobile UX

مبدأ: **الجوال مسار عمل كامل لا نسخة مصغَّرة** — المراجعة تُبنى كـ«صف انتقاء» (triage) لا كجدول جنباً إلى جنب.

|---|---|---|
| القائمة | `DataTable` + فلاتر شريط | بطاقات `MobileRecordItem` (الطرف ← الدور/الفترة ← الحالة ← تقدّم المراجعة)؛ الفلاتر في `Sheet` سفلي + شرائح فلتر مرئية |

**قواعد الجودة:** أهداف لمس ≥44px؛ لا تفاعل hover وحده؛ الأرقام والمبالغ `dir=ltr` بأرقام 0–9 (قاعدة `INTL-PHONE`/`ltr-number`)؛ RTL أولاً؛ ترقيم 25–50 مع «تحميل المزيد»؛ لا تمرير أفقي للصفحة؛ حالات الفراغ/الخطأ/التحميل عبر `nebrax/states`؛ حفظ مسودة **سبب القرار** محلياً (بلا بيانات مالية) عند فقدان الاتصال؛ تحذير صريح عند 429 مع إعادة تلقائية. اختبارات Playwright بحجم جوال (Pixel/iPhone) ضمن كل شريحة، لا في A4e وحدها.

**بحث بصري (بروتوكول الأفق §UI):** هذه الوثيقة **لم تُجرِ** بحثاً بصرياً خارجياً (لا طُلب هنا ولا أُتيح). يلزم قبل A4b تحديداً (أعقد شاشة) فصلُ `External Evidence` / `AWJ Decision` / `Rejected` وفق البروتوكول، لمنتجات مرجعية للمطابقة المحاسبية (كشف بنكي/كشف مورد). **هذا شرط بوابة لـ A4b لا افتراض.**

## 5. RBAC Matrix

الصلاحيات الأربع **مستقلة ولا تُمنح لأي دور مخزَّن** (`owner`/`admin` عبر `*` فقط). كلها تستلزم `partner_statements.view` + `partners.view` + رؤية الطرف/الفرع + بوابة القدرة.

| القدرة | الصلاحية على المسار | شرط إضافي (الخادم) | مصدر الإتاحة للواجهة |
|---|---|---|---|
| رؤية القائمة/المساحة/السجل/التصدير | `partner_statements.view` | رؤية الطرف+الفرع، تشغيلة مقروءة | `can('partner_statements.view')` |
| رفع/معاينة/استيراد | `reconcile` | `partners.view` | `can('…reconcile')` |

| الاعتماد الجماعي (مشروط) | `reconcile` (+`view`) — **لا صلاحية جديدة ولا توسيع** | قواعد D-PS-16 + إعادة تحقق خادمي لكل سطر؛ لا يمسّ `close` ولا فصل المهام (المراجِع يُسجَّل عند `review` لا عند الاعتماد) | عقد N5 |

## 6. Settings Integration (PS-A4d)

### 6.1 القائم (يُعاد استعماله، لا نظام موازٍ)

- المفتاح: `Settings::DEFAULTS['partner_statements']['void_separation'] = 'strict'` في `tenants.settings` (JSON)، يُقرأ بـ`PartnerStatementVoidSeparation::effective()` — أي قيمة غير `flexible` حرفياً ⇒ `strict`.
- القاعدة (PostgreSQL وSQLite) تقرأ **صف المستأجر نفسه** وتفرض تطابق السياسة المسجَّلة في حدث الإبطال/الاستبدال، وتعيد التحقق عند الانتقال؛ على PostgreSQL تأخذ `FOR SHARE` على صف المستأجر.
- لا مسار كتابة للمستخدمين (جدار ساكن في `PartnerStatementVoidSupersedeApiTest`: لا ذِكر لـ`void_separation` في `app/Http` و`routes`، ولا `Settings::put('partner_statements', …)`).

### 6.2 مسار الكتابة الآمن المقترح

| الجانب | التصميم المقترح | المرجع في المشروع |
|---|---|---|
| الخدمة | `PartnerStatementPolicyService::update(User $actor, string $mode, string $reason)`: معاملة ← `Tenant::lockForUpdate()` (قراءة طازجة) ← مقارنة ← `Settings::put('partner_statements', ['void_separation' => …], $tenant)` ← حدث تدقيق في المعاملة نفسها؛ **لا كتابة إن لم يتغيّر شيء** | `AiActionTenantEnablementService::update` (النمط نفسه حرفياً) |
| ترتيب الأقفال | قفل صف المستأجر وحده ومعاملة قصيرة، دون أقفال استشارية/مِرساة ⇒ لا دورة مع مسار الإبطال (الذي يأخذ صف المستأجر `FOR SHARE`/المِرساة بعد أقفاله الاستشارية)؛ يُثبَّت باختبار سباق PostgreSQL (إبطال × تغيير السياسة) | سباق A3e الموثَّق (409 `void_policy_changed`) |

| المدخل | `mode ∈ {strict, flexible}` + `reason`؛ `rejectUnknown`؛ رفض أي مفتاح آخر | `AiActionTenantEnablementService` |
| التدقيق | جدول append-only `partner_statement_policy_events` (مستأجر، فاعل، من/إلى، سبب، وقت) — **يحتاج Migration (في A4d وبعد الموافقة)**؛ لا يوجد مدقّق عام للإعدادات (`AiAuditRecorder` للـAI حصراً) | سابقة `SalesChannelSettingEvent` (`CompanyWide`، مُلحق فقط) |
| القراءة | `GET` يعيد: السياسة الفعّالة، **هل هي مخزَّنة صراحةً أم افتراضية**، آخر تغيير (فاعل/وقت/سبب)، وعدّاد «نهائيات أُغلقت بواسطة المستخدم نفسه ضمن آخر X» اختياري (غير مطلوب) | |
| الجدار الساكن | يُعدَّل **عمداً** في A4d: يُسمح بمسار كتابة واحد فقط، من الخدمة الجديدة وحدها (اختبار ساكن يعدّ مواضع `Settings::put('partner_statements'`، ويُثبت أن المتحكّم الوحيد الذي يستدعيها هو الجديد) | تعديل صريح لشرط المالك في A3e §1.6 |
| الواجهة | `/settings/partner-statements` (بطاقة «فصل مهام الإبطال»): شرح بالمخاطر؛ تبديل `flexible` بحوار تحذير + سبب؛ شارة «افتراضي/مخصَّص»؛ سجل التغييرات | قياس على شاشات الإعدادات القائمة (`finance-settings`, `accounting-settings`) |

**ما لا يفعله A4d:** لا يضيف سياسات جديدة (مثلاً الاعتماد الجماعي) إلا بقرار — وفق CLAUDE.md قاعدة 6 ووثيقة Policy Charter. إن قُرِّر أن الاعتماد الجماعي سياسة، فمفتاحه يُضاف في المجموعة نفسها `partner_statements` عبر `Settings::DEFAULTS` (لا Registry موازٍ) — انظر D-A4-04.

#### عقد الاعتماد الجماعي الذرّي (D-A4-04 — مُحسَم الذرّية؛ الإذن بالتنفيذ ما زال معلّقاً)

**1. الذرّية (قرار مُقرَّر).** الدفعة كلها ذرّية. عند **قِدَم التشغيلة، أو انحراف الأهلية، أو قرار متعارض، أو أي خطأ تحقق**: تُحفظ **صفر** قرارات من المحاولة (تراجع كامل للمعاملة) وتُعاد أخطاء قابلة للتنفيذ؛ ممنوع إعلان نجاح جزئي أو «n من m»، وممنوع الرفض الجزئي المُعلَن. استجابة الفشل تحمل `persisted: 0`.

**2. أهلية السطر (تُعاد كاملةً على الخادم داخل المعاملة، لا تُصدَّق من العميل ولا من المعاينة):** نتيجة المحرّك في هذه التشغيلة `matched` · `unit_key` موجود · الصافي المالي المحسوب بـ`planConfirm`/`net()` يساوي **صفراً** (لا اعتماد على `difference_minor` المخزَّن وحده) · `warnings` فارغة · لا قرار فعّال على السطر في هذه التشغيلة (وإلا `bulk_line_already_decided`، ولا يُستبدل قرار موجود) · الجهة ضمن نطاق الفاعل. لا `accept_difference` ولا `reason` في الطلب (يُرفضان: المعاملات المجهولة 422)، ولا `override/dismiss/link_pair/clear` — **`confirm` فقط**.

**3. صيغتان لتحديد المجموعة (يُفرَّق بينهما صراحةً):**

| | معرّفات صريحة | `filter:'exact'` |
|---|---|---|
| الإدخال | `line_ids[]` (≤ **200**) | لا معرّفات؛ الخادم يحسب المجموعة = كل سطور الكشف الأهلة وغير المحسومة في التشغيلة |
| السقف | 200 (حجم الحمولة وقائمة أخطاء لكل معرّف قابلة للقراءة) | **2000** = `PartnerStatementImportService::MAX_ROWS` (سقف سطور الكشف نفسه ⇒ المجموعة محدودة بطبيعتها؛ لا حاجة لتقسيم) |
| الاستعمال | اختيار يدوي من الجدول | «اعتماد كل المطابقات الدقيقة» (حالة الـ1500 سطر) |
| سطر غير أهل | يُرفض **كل** الطلب (`bulk_line_not_eligible` + قائمة) | ليس خطأً بحد ذاته (خارج المجموعة)؛ لكن أي انحراف بين ما عاينه المستخدم وما يحسبه الخادم لحظة الحفظ ⇒ `bulk_set_changed` ورفض كل الطلب |

الحالة المفروضة بقاعدة المالك: **لا تقسيم** إلى طلبات/commits مستقلة يجوز نجاح بعضها. 1500 سطر = طلب واحد ومعاملة واحدة بوضع `filter:'exact'`؛ وضع المعرّفات (≤200) لا يُستعمل لتفريغ كشف كبير على دفعات.

**4. ربط التأكيد البشري بما يُحفظ فعلاً.** `GET …/decisions/bulk-preview?run_id=` (قراءة فقط، لا كتابة) يعيد `count`، `expected_digest` (بصمة مرتّبة بمعرّفات السطور + معرّفات وحدات الدفتر + بصمة الدفتر والتشغيلة)، وعيّنة. الواجهة تعرضها وتطلب تأكيداً صريحاً، ثم يُرسل `expected_count` و`expected_digest` مع الطلب؛ الخادم يعيد الحساب داخل القفل ويرفض عند أي اختلاف (`bulk_set_changed`). لا مسار تأكيد تلقائي، ولا استدعاء للخدمة إلا من المتحكّم (جدار ساكن).

**5. التزامن وعدم التكرار (Idempotency).**
- القفل نفسه الذي يأخذه `decide`: القفل الاستشاري للمقارنة ثم `FOR UPDATE` على صف المقارنة — **مرة واحدة للدفعة** لا لكل سطر، فتتسلسل مع القرارات الفردية و`match` و`review`/`reopen`/`close`.
- إعادة التحقق من الحداثة (`assertFresh`: المحرّك · السياسة · النطاق · بصمة الدفتر · بصمة الكشف) **مرة واحدة داخل القفل** قبل أي كتابة؛ لا مِرساة مستأجر (كما `decide`: الحماية من ترحيل لاحق بالبصمة ثم إعادة فحص عند `review`).
- إعادة إرسال الطلب نفسه بعد نجاحه ⇒ `200 replayed` بلا سجلات جديدة (يعتمد آلية إعادة التشغيل المتماثلة القائمة في `decide`: كل سطر عنده قرار `confirm` مطابق لنفس الوحدة/التشغيلة)، وطلب مختلف بعد ذلك ⇒ 409. تُحسم في A4b0 بقرار فرعي **D-A4-04د**: هل يُضاف وسم دفعة (`batch_id`، عمود nullable إضافي ⇒ **Migration يحتاج موافقة صريحة**) لتجميع سجلات الدفعة في التدقيق، أم يُكتفى بلا وسم؟ التوصية: وسم إضافي nullable. **لا Migration في هذه الوثيقة.**

**6. التدقيق.** سجل واحد **لكل سطر** في جدول القرارات القائم (append-only، فاعل، وقت، تشغيلة، بصمة الدفتر، وحدات الدفتر المطالَب بها `claim_entry_ids`) — بالقيم نفسها التي يكتبها `decide` الفردي، لا ملخص مجمَّع يحلّ محلها. المصدر الجماعي يظهر في الملخص/الوسم فقط ولا يغيّر مضمون القرار.

**7. حجم المعاملة والأداء.** معاملة واحدة بإدراج مُجزَّأ (نمط `INSERT_CHUNK`=500 داخل المعاملة نفسها، لا commits وسيطة) وقراءة واحدة لمصدر الدفتر والتشغيلة (لا استعلام لكل سطر). قبل الإذن بالتنفيذ يُقاس على **PostgreSQL حقيقي** (لا SQLite): مدة المعاملة وزمن حجز القفل وعدد الاستعلامات عند 200 و1500 و2000 سطر، ويُوثَّق في تقرير A4b0 مع عتبة يعتمدها المالك؛ تجاوزها يوقف الشريحة ولا يُحلّ بالتقسيم. Throttle مخصَّص منخفض للمسار (قيمته تُحسم في A4b0) ولا يمس حد القرار الفردي (60/د).

**8. ما لا يتغيّر (ثوابت).** لا اعتماد تلقائي أبداً · لا توسيع للصلاحيات (`reconcile`+`view` وبوابة القدرة ورؤية الطرف/الفرع كما هي) · المُغلِق ≠ المراجِع (D-PS-17) ثابت منفصل لا يمسّه هذا المسار (الاعتماد الجماعي لا ينقل الحالة إلى `reviewed`، ولا يجعل أحداً «مراجِعاً» — ذلك بفعل `review` الصريح) · قاعدة السبب D-PS-16 لا تُعطَّل ولا تُخفَّف (السطور ذات الفرق خارج الدفعة بحكم التعريف) · لا قيد/مستند/رصيد/ZATCA.

**اختبارات الاعتماد الجماعي (مُلزِمة لقبول A4b0):**
- **مكافئة:** نتيجة الدفعة = نتيجة `confirm` الفردي سطراً سطراً (الحقول، الصافي، `claim_entry_ids`، النسخة/revision) على بيانات متطابقة.
- **ذرّية بحقن فشل:** فشل مُحقَن عند السطر k، وعند آخر سطر، وعند الإدراج المُجزَّأ الثاني ⇒ عدد صفوف القرارات بعد الطلب = قبله؛ وكذلك: تشغيلة قديمة، انحراف أهلية (سطر صار فرقه غير صفري/ظهر تحذير)، قرار متعارض موجود، `expected_count/digest` مغاير، حالة `reviewed`، خطأ تحقق — كلها `persisted: 0` وأخطاء قابلة للتنفيذ.
- **حدود:** 200 مقبول و201 مرفوض؛ `filter:'exact'` عند 2000 مقبول؛ سقف الاستيراد يمنع تجاوزه.
- **تزامن PostgreSQL (`pcntl_fork`، يفشل ولا يُتخطى):** دفعة × قرار فردي على سطر منها · دفعة × دفعة · دفعة × `match` · دفعة × `review`/`reopen` · دفعة × ترحيل قيد (تظهر `run_stale` أو تنجح بتشغيلة سليمة، بلا قرارات على بصمة قديمة) · لا توقف متبادل · invariant: لا سطر بقرارين فعّالين.
- **أداء/قفل على PostgreSQL:** قياس 200/1500/2000 (الفقرة 7) وتثبيت عدد الاستعلامات.
- **Idempotency:** إعادة إرسال الطلب نفسه بعد نجاحه ⇒ `replayed` بلا سجلات جديدة؛ طلب مختلف على سطور محسومة ⇒ 409 `bulk_line_already_decided` بلا كتابة.
- **صلاحيات وعزل:** بلا `reconcile` ⇒ 403؛ قدرة موقوفة/معطّلة ⇒ منع؛ مستأجر آخر/مقيَّد بفرع/شريك مخفي ⇒ `PARTNER_UNAVAILABLE`؛ لا ثغرة تتجاوز فصل المهام.
- **جدار ساكن:** لا استدعاء لـ`decideBulk` إلا من المتحكّم؛ لا مجدول/Job/Listener؛ لا `LedgerService` ولا كتابة محاسبية؛ المسار لا يكتب `confirm` بلا إقرار صريح (`expected_digest` إلزامي).
- **Mutation (كل واحدة يجب أن تُسقط اختباراً):** إزالة شرط الصافي الصفري · إزالة شرط «بلا تحذيرات» · إزالة شرط `matched` · تعطيل مقارنة `expected_digest/count` · commit وسيط/تجاوز التراجع (نجاح جزئي) · إزالة `assertFresh` · إزالة فحص الصلاحية · قبول `reason`/`accept_difference` · إزالة فحص «قرار قائم».

## 8. Test Strategy

**مبادئ ثابتة (من تقاليد A1–A3e):** كل شريحة تُثبت بالاختبار عدم الأثر المالي حيث تمسّ الخلفية؛ اختبارات PostgreSQL الحقيقية للتزامن تفشل ولا تُتخطى؛ تجارب تحوير (Mutation) على القواعد الحرجة؛ جدران ساكنة للحدود.

| الطبقة | الأدوات | ما يُغطّى |
|---|---|---|
| خلفية — ميزة | PHPUnit/Pest على SQLite + PostgreSQL (CI) | العقود الجديدة (N1–N7)، RBAC الكامل، عزل المستأجر/الفرع/الشريك (مستخدم مقيَّد بفرع، شريك مخفي)، عدم تسريب العدّادات، عدد الاستعلامات |
| خلفية — تزامن | `pcntl_fork` على PostgreSQL | N5 (جماعي × فردي، جماعي × جماعي، جماعي × match/review/ترحيل — انظر عقد A4b0)، N7 (سياسة × إبطال)، لا انحدار على سباقات A3d/A3e |
| خلفية — جدران ساكنة | اختبارات ملفات | قراءة فقط لـN1–N4/N6؛ لا `LedgerService` كتابة؛ N7 المسار الوحيد للسياسة |
| واجهة — وحدة | Vitest | عقود وأخطاء ar/en (كل `reason` له ترجمة)، منطق الإتاحة والسبب الإلزامي، طابور القرارات، تحويل هللات↔ريال، أرقام 0–9 |
| واجهة — مكوّنات | RTL | الحالات (تحميل/فراغ/خطأ/موقوفة/معطّلة)، الحوارات، الإقرار الحرفي، تعطيل بسببه |
| واجهة — E2E | Playwright (RTL/LTR + جوال + dark/light) | المسارات الكاملة بمستخدمين متعدّدين (مراجِع ≠ مُغلِق)، بيانات اصطناعية فقط |
| بصري/قابلية الوصول | لقطات + فحص a11y (حسب سابقة Commerce) | تباين الشارات، ترتيب التركيز، أهداف اللمس |
| انحدار | الحزمة الكاملة | `php artisan test` كاملاً قبل أي PR خلفي؛ `npm run build` + `npm test` لواجهة |

بروتوكول ما قبل PR (CLAUDE.md): لا قيود محاسبية جديدة في PS-A4 — يكفي في وصف كل PR ذكر «لا قيد/مستند/رصيد/ZATCA» مع الدليل الساكن بدل جدول القيود.

### A.3 قواعد التصنيف المقترحة للجرد

1. **ثابت** (محاسبي/أمني/RBAC/بوابة تفعيل) ← لا يُعرَض كخيار مستأجر.
2. **سياسة عمل** لها >1 طريقة صحيحة ← تُجرَد، بافتراض يحمي القائم (قاعدة 6).
