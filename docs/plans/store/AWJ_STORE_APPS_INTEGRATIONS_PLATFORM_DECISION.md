# AWJ Store — Apps & Integrations Platform Decision

**الحالة:** قرار معماري/منتج معتمد
**التاريخ:** 2026-09-11
**النطاق:** ربط التطبيقات بمتجر أَوْج + تجربة إدارة التطبيقات والتكاملات

## 1. القرار

**التطبيقات والتكاملات تتصل بمنصة API أَوْج، وليس بـ Spree كمنصة خلفية أو بوابة تكامل.**

Spree Storefront هو أساس واجهة متجر الويب الموجهة للمشتري، لكنه ليس مصدر الحقيقة، وليس طبقة التكامل المركزية، وليس المنصة التي يجب أن تعتمد عليها تطبيقات الجوال أو التطبيقات الخارجية.

المسار المستهدف:

```text
Web Store (Spree-derived UI) ─┐
Mobile Store App             ├──→ AWJ API / Developer Platform ──→ AWJ Commerce Core
External Apps                ┤
Future Channels              ┘
```

وبالنسبة إلى متجر الويب:

```text
Spree-derived Storefront UI
        ↓
AWJ Store adapter / actions
        ↓
AWJ API
        ↓
AWJ Commerce Core
```

لا يعتمد المسار التالي:

```text
Mobile / External App → Spree Backend → AWJ
```

## 2. مصدر الحقيقة

أَوْج يبقى مصدر الحقيقة للقدرات المشتركة والتجارية، ومنها بحسب العقود المعتمدة ومراحل التنفيذ:

- Tenant / Store / Sales Channel context.
- المنتجات والنشر التجاري.
- الأسعار.
- التوفر والمخزون والحجوزات.
- هوية العميل.
- السلة وإتمام الشراء عند تنفيذها.
- CommerceOrder.
- الدفع.
- الشحن والتنفيذ.
- الفواتير.
- المحاسبة وZATCA.

لا تنشأ نسخة Spree وسيطة يجب مزامنتها ثم تستهلكها التطبيقات.

## 3. القنوات

تستخدم القنوات المختلفة نفس Commerce Truth مع الحفاظ على هوية القناة، مثل:

- Web Store.
- Mobile Store App.
- POS حيث تنطبق عقود Commerce.
- External integrations.
- قنوات مستقبلية.

وجود قناة مختلفة لا يبرر إنشاء منطق تسعير/طلب/مخزون مستقل خارج أَوْج. يمكن أن تختلف تجربة المستخدم أو سياسات القناة المعتمدة، لكن السلطة النهائية تبقى في الخادم وعقود أَوْج.

## 4. قرار إدارة التطبيقات والتكاملات

تعتمد مساحة إدارة متجر أَوْج قسمًا مخصصًا باسم مفاهيمي مثل:

**التطبيقات والتكاملات**

هذا القسم جزء من تجربة إدارة المتجر، لكنه يستخدم **AWJ Developer Platform / AWJ API** تحت الغطاء.

الهدف: يشعر التاجر أنه يدير تكاملات متجره من مكانه الطبيعي داخل Commerce Workspace، بينما تبقى المصادقة والصلاحيات والمفاتيح والأحداث والعزل تحت منصة أَوْج المركزية.

## 5. ماذا تعرض مساحة «التطبيقات والتكاملات»

النطاق المستهدف تدريجيًا يشمل:

- التطبيقات المرتبطة بالمتجر.
- التكاملات المتاحة للتثبيت/الربط.
- حالة كل تكامل: متصل، يحتاج إعدادًا، متوقف، به خطأ.
- الصلاحيات التي طلبها التطبيق بصورة مفهومة للتاجر.
- تاريخ الربط وآخر نشاط ذي معنى عند توفره.
- إعدادات التكامل الخاصة بالمتجر/القناة.
- فصل/إلغاء وصول التطبيق.
- إعادة التفويض عند تغير الصلاحيات.
- webhooks/events المرتبطة بالتكامل عند الحاجة.
- سجل مبسط للمشكلات/المحاولات المهمة دون كشف أسرار.
- روابط إلى التوثيق أو الدعم الخاص بالتطبيق.

لا يعني هذا أن Commerce Workspace يعيد بناء Developer Platform. هو واجهة سياقية فوق قدراتها.

## 6. طبقتان للمستخدمين

يجب التفريق بين تجربتين:

### أ. التاجر داخل إدارة المتجر

يرى تجربة بسيطة ومفهومة:

```text
إدارة المتجر
  → التطبيقات والتكاملات
      → تطبيق X
          → ربط
          → الصلاحيات
          → الإعدادات
          → الحالة
          → فصل
```

لا يحتاج التاجر للتعامل مع مفاتيح تقنية خام إلا إذا كانت طبيعة التكامل تتطلب ذلك.

### ب. المطور / الشريك

يستخدم Developer Platform لإدارة الجوانب التقنية مثل:

- تعريف التطبيق.
- بيانات الاعتماد المناسبة.
- الصلاحيات/scopes.
- webhooks.
- بيئات التطوير/الإنتاج عند اعتمادها.
- التوثيق.
- مراقبة الأخطاء/الاستخدام وفق ما توفره المنصة.

يمكن ربط التجربتين دون تكرار مصدر الحقيقة.

## 7. نموذج الصلاحيات

التطبيق لا يحصل على صلاحية عامة للمستأجر لمجرد أنه «مثبت في المتجر».

يجب أن تكون الصلاحيات:

- محددة وقابلة للمراجعة.
- أقل قدر ممكن.
- مرتبطة بالـTenant الصحيح.
- مرتبطة بالمتجر/القناة عندما تكون القدرة store-scoped أو channel-scoped.
- قابلة للإلغاء.
- مفروضة في الخادم.

مثال مفاهيمي:

```text
read:store_catalog
read:commerce_orders
write:commerce_orders
read:customers
manage:store_content
```

الأسماء النهائية لا تعتمد بهذه الوثيقة؛ يجب أن تتوافق مع نظام Developer Platform/RBAC الحالي بعد فحصه.

## 8. Tenant Isolation والأمن

- لا يختار التطبيق `tenant_id` بحرية ويصبح ذلك سلطة.
- بيانات الاعتماد/التفويض تحدد النطاق المسموح به server-side.
- لا يسمح لتطبيق مثبت لدى Tenant A بقراءة/تعديل Tenant B.
- store/channel context لا يتجاوز tenant ownership.
- الأسرار لا تعرض مجددًا بلا حاجة ولا تسجل في logs.
- إلغاء التطبيق يجب أن يوقف وصوله بصورة قابلة للتحقق.
- تغيير صلاحيات التطبيق يحتاج تدفق إعادة موافقة عندما يوسع الوصول.
- العمليات المالية/المخزنية الحساسة لا تتجاوز خدمات أَوْج وقواعدها حتى لو كان مصدر الطلب تطبيقًا خارجيًا.

## 9. Webhooks والأحداث

يستفاد من Outbound Webhooks / Developer Platform الموجودين في أَوْج بدل إنشاء نظام أحداث خاص بـSpree.

التطبيقات الخارجية يمكن أن تستهلك أحداث أَوْج المعتمدة، مثل أحداث التجارة المناسبة عند تنفيذها، مع الحفاظ على:

- tenant scoping.
- التوقيع/التحقق.
- retries/idempotency وفق عقود المنصة.
- عدم تسريب payloads بين المستأجرين.

إذا احتاج Commerce أحداثًا جديدة، تضاف إلى منصة أَوْج الحالية ضمن PRs مستقلة ومراجعة، ولا تنشأ قناة webhooks موازية داخل storefront.

## 10. Spree Admin كمصدر أفكار فقط

يمكن دراسة تجربة Spree Admin في integrations/apps والاستفادة من:

- تنظيم صفحة التكاملات.
- بطاقات الحالة.
- onboarding والربط.
- وضوح الإعدادات.
- تجربة الفصل/إعادة الاتصال.

لكن التنفيذ الخلفي لا يعتمد Spree Admin API ولا Spree credentials.

**نقتبس تجربة ناجحة، ولا ننقل سلطة المنصة من أَوْج إلى Spree.**

## 11. العلاقة بقرار Commerce Workspace

هذا القرار يكمل `AWJ_COMMERCE_ADMIN_NAVIGATION_DECISION.md`:

- القدرات الموجودة في ERP لا تُكرر داخل Commerce Workspace.
- التطبيقات والتكاملات تظهر داخل Commerce Workspace لأنها جزء طبيعي من رحلة إدارة المتجر.
- عند الحاجة إلى إدارة تقنية متقدمة، يمكن الانتقال سياقيًا إلى Developer Platform ثم العودة إلى المتجر.

مثال:

```text
إدارة المتجر
 → التطبيقات والتكاملات
 → تطبيق الشحن
 → إعداد/تفويض
 → إعدادات متقدمة (Developer Platform عند الحاجة)
 → العودة إلى إدارة المتجر
```

## 12. أثر القرار على تطبيق متجر الجوال

تطبيق متجر أَوْج للجوال لا يُبنى كعميل لـSpree Backend.

يستهلك نفس عقود AWJ Commerce API المستخدمة للويب حيث تكون العقود مشتركة، مع تجربة جوال مستقلة عند الحاجة.

هذا يحقق:

- مصدر حقيقة واحد.
- عدم مزامنة AWJ → Spree → Mobile.
- إمكانية تطوير الويب والجوال بصورة مستقلة.
- إمكانية إضافة قنوات جديدة دون جعل Spree dependency إلزاميًا.

## 13. أثر القرار على COM-7

عند تنفيذ COM-7 Public/Mobile Commerce API يجب تصميم العقود باعتبارها **عقود منصة أَوْج** وليست endpoints خاصة بواجهة Spree فقط.

Spree Storefront يصبح أول مستهلك رئيسي لها، وليس مالكها.

يجب تجنب API contracts التي تعكس أسماء أو state machine خاصة بـSpree إذا لم تكن جزءًا من Domain أَوْج.

## 14. ما يؤجل

لا تحسم هذه الوثيقة الآن:

- Marketplace عام لتطبيقات الطرف الثالث.
- نموذج مراجعة/اعتماد التطبيقات قبل النشر.
- التسعير أو مشاركة الإيرادات مع المطورين.
- public app listing/catalog النهائي.
- OAuth flow النهائي إن تقرر استخدامه.
- قائمة scopes النهائية.
- شكل شاشة integrations النهائي.
- sandbox developer environment النهائي.

هذه مراحل لاحقة، لكن البنية الحالية يجب ألا تمنعها.

## 15. المبدأ النهائي

> **Spree يشغّل أساس تجربة متجر الويب، أما أَوْج فيشغّل منصة التجارة والتطبيقات والتكاملات.**

و:

> **Commerce Workspace يعرض للتاجر تجربة إدارة التطبيقات والتكاملات في سياق متجره، بينما AWJ Developer Platform تبقى السلطة التقنية المركزية للتفويض والصلاحيات والأحداث والواجهات البرمجية.**
