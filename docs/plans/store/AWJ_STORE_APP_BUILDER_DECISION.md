# AWJ Store — Store App Builder Decision

**الحالة:** قرار اتجاه منتج/معمارية معتمد
**التاريخ:** 2026-09-11
**النطاق:** إنشاء تطبيق جوال خاص بمتجر التاجر

## 1. القرار

يعتمد أَوْج مسارًا مستقلًا باسم مفاهيمي **منشئ تطبيق المتجر (Store App Builder)** لتمكين التاجر مستقبلًا من إنشاء وإدارة تطبيق جوال حقيقي لمتجره، باسم المتجر وهويته وتجربته، دون جعل Spree Backend أو Spree Admin منصة تشغيل التطبيق.

منشئ تطبيق المتجر يختلف عن قسم **التطبيقات والتكاملات**:

- **منشئ تطبيق المتجر:** يصنع للتاجر تطبيقًا موجهًا لعملائه للتسوق من متجره.
- **التطبيقات والتكاملات:** تربط متجر التاجر بخدمات وتطبيقات أخرى مثل الشحن والتسويق والتحليلات والأنظمة الخارجية.

يجب ألا يختلط المساران في المنتج أو المعمارية.

## 2. البنية المستهدفة

متجر الويب وتطبيق الجوال قناتان مختلفتان فوق نفس Commerce Truth:

```text
                 AWJ Commerce Core
                       │
                 AWJ Commerce API
                 ┌─────┴─────┐
                 │           │
          Web Store       Store App
        Spree-derived     Mobile experience
                 │           │
                 └─────┬─────┘
                       │
                Same commerce truth
```

أَوْج يبقى مصدر الحقيقة للمنتجات والعملاء والأسعار والمخزون والحجوزات والطلبات والدفع والشحن والفواتير وفق مراحل التنفيذ المعتمدة.

لا يعتمد التطبيق على المسار:

```text
Mobile App → Spree Backend → AWJ
```

بل يتصل بعقود AWJ Commerce API مباشرة.

## 3. تجربة إدارة المتجر

التصور المفاهيمي لمساحة إدارة المتجر:

```text
إدارة المتجر
├── متجر الويب
│   ├── التصميم والمظهر
│   ├── الصفحات والمحتوى
│   └── النطاق
│
├── تطبيق الجوال
│   ├── إنشاء التطبيق
│   ├── الهوية والتصميم
│   ├── الصفحة الرئيسية
│   ├── التنقل
│   ├── الإشعارات
│   ├── المعاينة
│   ├── إعدادات القناة
│   └── النشر والتحديثات
│
└── التطبيقات والتكاملات
    ├── التطبيقات المرتبطة
    ├── الشحن
    ├── التسويق
    ├── التحليلات
    └── خدمات الطرف الثالث
```

الأسماء والتنقل النهائيان يخضعان لاحقًا لتصميم Commerce Workspace، لكن الفصل المفاهيمي معتمد.

## 4. التطبيق الناتج

الهدف ليس WebView بسيطًا أو تغليف موقع الويب داخل تطبيق.

يجب أن يكون الناتج تطبيق متجر حقيقي بمستوى تجاري، مع تجربة جوال مناسبة وقدرات يمكن أن تشمل تدريجيًا:

- تصفح المنتجات والتصنيفات.
- البحث والفلاتر.
- صفحة المنتج والصور.
- السلة وإتمام الشراء.
- تسجيل الدخول وحساب العميل.
- الطلبات وتتبع حالتها.
- الدفع وفق بوابات أَوْج المعتمدة.
- الشحن/الاستلام وفق Commerce.
- الإشعارات.
- الروابط العميقة إلى المنتجات والطلبات والعروض.
- مشاركة المنتجات.
- تجربة تنقل جوال أصلية وعالية الجودة.

التفاصيل النهائية لكل منصة لا تعتمد في هذه الوثيقة.

## 5. التخصيص بدون برمجة

يهدف App Builder إلى تمكين التاجر من تخصيص تطبيقه من داخل أَوْج دون بناء تطبيق مخصص من الصفر.

قد تشمل طبقة التخصيص:

- اسم التطبيق.
- الشعار والأيقونة.
- شاشة البداية.
- الألوان.
- الخطوط.
- الصفحة الرئيسية وأقسامها.
- البنرات.
- ترتيب الأقسام.
- شريط التنقل.
- إظهار/إخفاء بعض الأسطح.
- إعدادات الإشعارات.
- روابط التواصل والسياسات.

يجب أن تعتمد هذه التخصيصات على configuration/tokens منظمة لا على نسخ كود منفصل لكل متجر كلما أمكن.

## 6. Shared Commerce Truth وليس Shared UI بالضرورة

متجر الويب وتطبيق الجوال يشتركان في:

- العقود التجارية.
- البيانات الأساسية.
- قواعد التسعير.
- التوفر.
- الطلبات.
- العميل.
- الدفع والشحن عند تنفيذها.

لكن لا يشترطان واجهة واحدة أو تنقلًا واحدًا.

**الويب والجوال قناتان من الدرجة الأولى، ولكل قناة تجربة مناسبة لها.**

لا يتم إجبار التطبيق على تقليد Spree UI حرفيًا، ولا إجبار متجر الويب على تبني أنماط تطبيق الجوال.

## 7. العلاقة مع SalesChannel

يجب أن يستطيع Commerce تمييز مصدر الطلب والقناة مثل Web وMobile وفق `SalesChannel` وعقود أَوْج الحالية، دون إنشاء مصدر حقيقة مستقل لكل قناة.

يمكن لاحقًا وجود إعدادات خاصة بقناة التطبيق، لكن channel context لا يتجاوز Tenant Isolation أو صلاحيات أَوْج.

## 8. العلاقة مع Spree

Spree Storefront يبقى أساس واجهة متجر الويب.

يمكن الاستفادة من مفاهيم وتجارب Spree في التجارة، لكن:

- Spree ليس App Builder.
- Spree Backend ليس backend لتطبيقات المتاجر.
- لا تصبح Spree APIs عقدًا عامًا لتطبيق الجوال.
- لا يُربط نشر التطبيق بدورة حياة Spree.

منشئ التطبيقات منتج مملوك لأَوْج فوق AWJ Commerce API.

## 9. العلاقة مع «التطبيقات والتكاملات»

`AWJ_STORE_APPS_INTEGRATIONS_PLATFORM_DECISION.md` يحكم التطبيقات التي **تتصل بالمتجر**.

هذه الوثيقة تحكم التطبيق الذي **يمثل المتجر أمام عملائه**.

قد يستهلك تطبيق المتجر نفسه خدمات من قسم التكاملات — مثل بوابة دفع أو شحن أو تحليلات — لكن هذا لا يدمج المفهومين إداريًا أو معماريًا.

## 10. أثر القرار على COM-7

عقود Public/Mobile Commerce API لا تُصمم باعتبار Spree العميل الوحيد.

منذ البداية يجب أن تسمح البنية بأن يكون:

- Web Store مستهلكًا.
- Store Mobile App مستهلكًا.
- قنوات مستقبلية مستهلكة.

دون تكرار قواعد التجارة في كل قناة.

هذا لا يعني تنفيذ App Builder ضمن COM-7. المطلوب فقط ألا يغلق COM-7 الطريق أمامه أو يربط Commerce عقائديًا بـSpree.

## 11. النشر ومتاجر التطبيقات

النشر الفعلي إلى App Store / Google Play مرحلة مستقلة لاحقة وتحتاج خطة تشغيلية خاصة، مثل:

- ملكية حسابات النشر: أَوْج أم التاجر أم نماذج متعددة.
- إدارة الشهادات والتوقيع.
- الحزم/المعرفات.
- الإصدارات والتحديثات.
- مراجعات متاجر التطبيقات.
- سياسات Apple/Google.
- الخصوصية والموافقات.
- الإشعارات والشهادات الخاصة بها.

لا تحسم هذه الوثيقة النموذج التشغيلي النهائي، لكنها تمنع افتراض أن «إنشاء التطبيق» يساوي مجرد إنشاء واجهة.

## 12. ما لم يُحسم بعد

يؤجل البحث/القرار في:

- التقنية النهائية لبناء تطبيقات iOS/Android.
- تطبيق واحد متعدد المتاجر مقابل binary مستقل لكل تاجر أو نموذج هجين.
- نموذج النشر وحسابات Apple/Google.
- حدود التخصيص في الإصدار الأول.
- التسعير والباقات.
- هل يكون App Builder إضافة مدفوعة مستقلة.
- آلية المعاينة الحية.
- OTA/update strategy إذا سمحت التقنية والسياسات.
- Push notification provider النهائي.

هذه قرارات لاحقة ولا يجب اختراعها أثناء COM-7-P0.

## 13. المبدأ النهائي

> **أَوْج لا يبني مجرد موقع متجر؛ يبني Commerce Platform تستطيع تشغيل متجر ويب وتطبيق متجر وقنوات أخرى من نفس الحقيقة التجارية.**

و:

> **Store App Builder يصنع تجربة جوال حقيقية لعلامة التاجر، بينما Apps & Integrations تربط هذه التجارة بالخدمات والأنظمة الأخرى.**
