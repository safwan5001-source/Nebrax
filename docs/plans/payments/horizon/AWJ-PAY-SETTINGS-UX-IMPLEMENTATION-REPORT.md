# AWJ-PAY-SETTINGS-UX — صفحة إعدادات المدفوعات الموحّدة (الطريقة 3)

الإعدادات ← المالية ← المدفوعات: صفحة واحدة بتبويبين — **وسائل الدفع** (ما يراه العميل) و**بوابات الدفع** (الاتصالات والإعدادات التقنية المتقدمة داخل كل بوابة). واجهة متكاملة مربوطة بواجهات حقيقية، لا نموذج شكلي.

## 1) قرارات AWJ (وما لم يُتبنَّ)

| البند | القرار | السبب |
|---|---|---|
| معنى «تفعيل» الوسيلة | **إظهار للعميل** مشروط بجاهزية محسوبة في الخادم، لا «تقييد القبول» | واجهة فاتورة ميسّر المستضافة لا تتيح تقييد الوسائل؛ القبول يُضبط في لوحة المزوّد. التصميم يعلن ذلك صراحةً بدل مفتاحٍ يوحي بسيطرة غير موجودة |
| البوابة الافتراضية لكل وسيلة | **محسوبة وللعرض فقط** («تلقائي: {اسم}») | لا توجيه متعدد البوابات (H2-04) ولا تحويل تلقائي بين البوابات (منعاً لتكرار الخصم)؛ لا قيمة مخزَّنة ولا قائمة اختيار وهمية. عند وجود أكثر من بوابة مؤهلة يُشرح الحدّ نصاً |
| Apple Pay | **«تحتاج إعدادًا» دائماً** ولا تُفعَّل من أَوْج | يتطلب تسجيل نطاق لدى المزوّد/Apple لا يستطيع أَوْج التحقق منه (EXT-10) |
| أماكن الاستخدام | الفواتير (رابط الدفع) ✓، المتجر الإلكتروني «غير متاح بعد» | H4 غير مبني؛ لا ادّعاء |
| الشعارات | نص فقط | كل شعارات السجل `pending` (لا أصل رسمي موثَّق) |
| إعدادات متقدمة بلا إعداد حقيقي (سياسة التقاط/تسوية/مقاصة، مزامنة يدوية) | تُعلَن «غير متاحة/قواعد ثابتة» بلا مفتاح | عدم المحاكاة |
| مصدر الحقيقة | الاتصالات في `/payment-gateways` وحدها؛ الوسائل تقرأ جاهزيتها المحسوبة منها | لا مفاتيح ولا إعدادات مكرّرة بين التبويبين |

مرفوض / لم يُعتمد: failover تلقائي بين البوابات · تخزين بوابة افتراضية قبل H2-04 · أي Live أو تفعيل مزوّد حقيقي · شعارات غير رسمية · عرض أي سرّ.

## 2) ما نُفِّذ

**Backend (إضافي، متوافق رجعياً):** `OnlinePaymentMethodCatalog`، قدرات `methods`/`methodsRequiringProviderSetup` على `PaymentGatewayCapabilities` ومحوّلَي ميسّر/Fake، جدولا `online_payment_method_settings` + أحداثها (append-only، CompanyWide)، `OnlinePaymentMethodSettingsService`، `GET/PUT /online-payment-methods` (`payments.view` / `payment_gateways.manage`)، `provider_capabilities` في `PaymentGatewayResource`، و`payment_methods` في استجابة رابط الدفع العام (مفاتيح مدعومة ومفعَّلة وجاهزة فقط).

**Web:**
- `finance-settings/payments/page.tsx`: قشرة بتبويبين (`Tabs` WAI-ARIA)، التبويب في `?tab=` ويُزامَن عبر `history.replaceState`، حالة الرفض موحّدة، لا طلبات قبل الاستيعاب (`hydrated`).
- `modules/payments/methods/OnlineMethodsPanel.tsx` + `contract.ts`: بطاقة لكل وسيلة (الحالة، السبب المانع والخطوة المطلوبة مع زر للانتقال لتبويب البوابات، مفتاح «إظهار للعميل»، البوابة الافتراضية للقراءة، أماكن الاستخدام، الاتصالات المؤهلة)، تحميل/خطأ+إعادة محاولة/فارغ، رفض الخادم يعيد قراءة الحالة الحقيقية (لا تفاؤل كاذب).
- `modules/payments/gateways/GatewaysPanel.tsx` (الصفحة القديمة منقولة كما هي سلوكاً) + `GatewayDetailSheet.tsx`: لوح تفاصيل بستة أقسام (عام/المفاتيح والتحقق/دعم الوسائل الفعلي/Webhooks والأحداث/الالتقاط والاستردادات والتسويات/الأمان والتدوير والسجل). عنوان استقبال webhook لمن يملك `payment_gateways.manage` فقط، الأفعال تعود للصفحة الأم فتستعمل الحوارات والمسارات القائمة ذاتها.
- `PayLinkPage`: صفّ «وسائل الدفع المقبولة» من قائمة الخادم فقط (فارغ/غائب ⇒ لا عرض).
- رسائل ar/en متطابقة المفاتيح (`paymentSettings`, `onlinePaymentMethods`, `paymentGateways.detail`)؛ بطاقة مركز المالية صارت «المدفوعات».

## 3) الأمان والعزل
لا سرّ في أي استجابة أو واجهة (مؤشرات «محفوظ» فقط) · RBAC: القراءة `payments.view`، التعديل `payment_gateways.manage` (الواجهة تعكسه والخادم هو الحاسم) · عزل المستأجر عبر `BaseModel`/`TenantScope`/نماذج CompanyWide مع اختبار عزل · لا أثر محاسبي ولا قيد ولا تعديل لإعدادات تاريخية.

## 4) الاختبارات
- PHP: `OnlinePaymentMethodSettingsTest` (6) + امتداد `PublicPaymentLinkTest` — SQLite وPostgreSQL.
- Web (vitest): contract (6) · OnlineMethodsPanel (6×لغتين) · قشرة الصفحة (4×لغتين) · لوح التفاصيل (3×لغتين) ضمن اختبارات الصفحة المعدَّلة · رابط الدفع (+1×لغتين).
- Playwright (المسح البصري، API مُعترَض): الحالات الجديدة `payment-methods-tab` (16 تركيبة 390/768/1280/1440 × ar/en × فاتح/داكن) · `gateway-detail-sheet` (16) · toggle/viewer/load-failure/no-adapter/tab-switch · `paylink-open` يتحقق من الصف دون شعارات.

**نتائج التشغيل (الفرع المحلي):** vitest كامل 719 ملفاً / 8614 اختباراً أخضر · `npm run build` ناجح · Playwright مسح المدفوعات كاملاً 212 اختباراً أخضر (يشمل الحالات القديمة بلا انحدار) + إعادة تشغيل حالات الوسائل بعد آخر تعديل (28 أخضر). لقطات الجوال/سطح المكتب بـRTL وLTR وفاتح/داكن روجعت بصرياً (≥6). CI على الفرع المرفوع هو الحَكَم النهائي.

## 5) المخاطر والمتبقي
- «إظهار للعميل» لا يغيّر ما تقبله صفحة ميسّر المستضافة — موثَّق في الواجهة. التقييد الفعلي يحتاج دفعاً مدمجاً (Payments API/Elements) = خارج النطاق ويحتاج قراراً.
- اختيار بوابة مختلفة لكل وسيلة مؤجَّل إلى H2-04 (توجيه متعدد البوابات)؛ لا failover تلقائي.
- شعارات رسمية لمدى/فيزا/ماستركارد/Apple Pay بانتظار أصول موثَّقة (سجل العلامات).
- التحقق الحي مع ميسّر Sandbox (EXT-01) ما زال معلّقاً؛ لا Live ولا Deploy ولا هجرة إنتاج.
- تحذير «N Issues» في لقطات Playwright من شريط تطوير Next (dev overlay) وليس من الواجهة؛ INVALID_KEY لـ`appBuilder.*` سابق لهذا العمل.
