# PAY-H6-02 — Implementation Report

STATUS: **IN REVIEW** (PR مفتوح) · DATE: 2026-10-22
المرجع: R-30 (موافقة جهاز يتيمة)، AC-S08. **صفر قيد محاسبي جديد:** الطبقة تدير دورة الموافقة على الجهاز فقط؛ البيع نفسه يمر بـ`PosService::checkout` (A11/A12 من H6-01) عبر `PaymentService` القائم.

## Outcome

- جهاز دفع بطاقة معزول بالفرع (`pos_payment_terminals`) وطلب دفع على الجهاز (`pos_terminal_requests`): `created → sent → approved → consumed` أو `voided`/`compensation_required → voided|compensated`.
- **لا بيع بلا موافقة مؤكدة:** وسيلة دفع قد **تشترط** موافقة جهاز (`payment_methods.pos_terminal_required`، افتراضي مطفأ). البيع يستهلك الموافقة عبر `terminal_request_id` في وسيلة الدفع، فيتحقق الخادم: مؤكدة · نفس الجلسة · نفس الوسيلة · **نفس المبلغ تماماً** · لم تُستهلك · ليست قيد الإلغاء.
- **لا موافقة يتيمة دون تعويض:** فشل البيع بعد موافقة (المعاملة تتراجع كاملة) ⇒ إلغاء آلي على الجهاز؛ تعذّر الإلغاء ⇒ `compensation_required` **يمنع إقفال الجلسة** حتى يُحلّ (إعادة إلغاء ناجحة أو إقرار مدير بملاحظة). مجدول `pos:sweep-terminals` كل 5 دقائق يلغي الموافقات اليتيمة (> 10 دقائق) ويُنهي المعلّق القديم ويعيد محاولة التعويض.
- مراجع الموافقة (RRN/رمز الموافقة/آخر 4) تأتي **من الجهاز لا من العميل** وتُخزَّن على السند (`reference`/`payment_details`)؛ ولا يُقبل جمعها مع مراجع يدوية.
- **FakeTerminalAdapter** لـlocal/testing فقط؛ لا مزوّد حقيقي قبل H6-03 (الإنتاج: لا جهاز قابل للإنشاء).

## Design

| القرار | السبب |
|---|---|
| استدعاءات الجهاز **خارج** معاملات القاعدة؛ إيجار `compensating_until` (90ث) لكل عملية إلغاء | لا شبكة داخل معاملة؛ مُعوِّضان متزامنان لا يلغيان مرتين؛ إيجار حي يمنع استهلاك الموافقة أثناء إلغائها |
| الاستهلاك: `lockForUpdate` على صف الطلب داخل معاملة البيع + `consumed_payment_id` فريد | موافقة واحدة ⇒ بيع واحد مهما تزامنت الطلبات؛ الخاسر **لا يلغي** موافقة مستهلكة (التعويض يعيد فحص الحالة تحت القفل) |
| التعويض الآلي بعد فشل البيع يخص فقط الموافقات التي **اجتازت كل فحوص هذا البيع** (تُجمع بالمرجع أثناء `claimApprovals`) وبحالة `approved` تحت القفل | موافقة صالحة رُفض استعمالها لخلل في الطلب (وسيلة/جلسة/مبلغ خاطئ أو مراجع يدوية) لا تُلغى — يلغيها الكاشير أو المجدول (ملاحظة مراجعة P1) |
| استثناء المحوّل عند `start()` = نتيجة **غامضة**: الطلب يبقى `sent` بعلامة `start_unconfirmed` ويحجز الجهاز؛ الفشل القاطع فقط يعيده المحوّل `ERROR` | رد ضائع بعد موافقة لا يُحرّر الجهاز لخصم ثانٍ ولا يُترك يتيماً (ملاحظة مراجعة P1) |
| سباق مفتاح idempotency يعيد الفائز كـreplay **بعد** فحص تطابق المحتوى | محتوى مختلف بنفس المفتاح ⇒ `idempotency_conflict` لا 200 (ملاحظة مراجعة P2) |
| مبلغ يوافق عليه الجهاز يخالف المطلوب ⇒ إلغاء فوري ولا يُستهلك أبداً | المال محتجز بمبلغ لا يقابل بيعاً |
| طلب نشط واحد لكل جهاز (فهرس جزئي) | يمنع خلط موافقات عميلين على جهاز واحد |
| حد القاعدة: مبلغ > 0 وحالة معروفة (PostgreSQL قيد CHECK، SQLite مُشغّلان) + حارس النموذج للانتقالات الرتيبة وثبات الهوية وعدم الحذف | دفاع متعدد الطبقات |
| صلاحيات: الأجهزة `company.manage` (كأجهزة POS)، الطلبات `invoices.manage`، الحل اليدوي `pos.variance.approve` | لا صلاحية جديدة؛ المعتمِد نفسه الذي يقرّ فروق الإقفال |
| `pos_terminal_required` للطرق البنكية فقط، افتراضي مطفأ | سياسة تُضبط ولا تُفرض (قاعدة 6) |

## مراجعة Codex (رأس d603c58)

ثلاث ملاحظات صحيحة عولجت في الدفعة نفسها بدل الدمج: P1 تعويض موافقة لم تُتحقق (الآن: المُجتازة فقط) · P2 سباق المفتاح بلا فحص تطابق (الآن: يُفحص) · P1 استثناء `start()` غامض يُحرّر الجهاز (الآن: `sent/start_unconfirmed`). كل ملاحظة لها اختبار.

**الجولة الثانية (رأس 43baf32) — أربع ملاحظات صحيحة أخرى عولجت:** P1 ملكية الجلسة (عرض/إلغاء/void/قائمة الجلسة لكاشير الجلسة أو معتمد `pos.variance.approve` فقط) · P2 ربط الجهاز بجهاز POS (جهاز مخصَّص لا يخدم جلسة جهاز آخر؛ غير المخصَّص متاح) · P2 حذف طريقة دفع لها عمليات أجهزة ⇒ 422 لا 500 · P1 الحل اليدوي مرفوض أثناء إيجار إلغاء حيّ (`compensation_in_progress`) منعاً لرد مزدوج. لكل منها اختبار.

**الجولة الثالثة (رأس a923e7a) — ثلاث ملاحظات صحيحة عولجت:** P2 عدالة المجدول (الترتيب بـ`updated_at` الأقدم أولاً وصفٌ يفشل يُحرَّك إلى آخر الدور، فلا يجوّع الموافقات اليتيمة) · P2 تفرّد اسم/رمز الجهاز يعود 422 بدل 500 · P1 عمليات المزوّد (إنشاء/استعلام/إلغاء/انتهاء) متسلسلة بإيجار على الطلب (`operation_in_progress` ⇒ 409) فلا تُحفظ موافقة بينما ألغاها المزوّد. لكل منها اختبار (واحد على PostgreSQL للتزامن).

**الجولة الرابعة (رأس 828a1df) — ملاحظتان صحيحتان:** P1 إيجار المزوّد بلا مالك ⇒ أُضيف `lease_token` (رمز ملكية)؛ `apply()` وتحرير الاستثناء يتحققان منه، فنتيجة مالك انتهى إيجاره وأخذه غيره **لا تُطبَّق** ولا تمسّ إيجار المالك الحالي · P2 تُحفظ القيمة المقصوصة نفسها التي فُحص تفرّدها. اختباران.

**الجولة الخامسة (رأس 508a507) — ملاحظتان صحيحتان:** P1 تعويض `void` بلا ملكية إيجار ⇒ `compensate()` يأخذ `lease_token` ويتحقق منه عند الإنهاء (نتيجة مالك منتهٍ لا تُنهي الحالة ولا تحرّر إيجار الحالي، فيبقى الحلّ اليدوي مرفوضاً) · P2 إعادة الطلب بالمفتاح نفسه (العادية وسباق المفتاح) تتحقق من ملكية الجلسة كالإنشاء فلا يكشف كاشيرٌ آخر مراجع الموافقة. اختباران.

**الجولة السادسة (رأس 4ede8c6) — ثلاث ملاحظات صحيحة:** P1 تراكب نداءات المزوّد بعد انتهاء الإيجار ⇒ (أ) عقد مهلة صلبة في `TerminalAdapter` والإيجار ≥ 3× `provider_timeout_seconds`، (ب) `lease_op`: بعد إيجار إلغاء منتهٍ لم يتأكد لا يخلفه إلا إلغاء (لا استعلام يسجّل موافقة سيعكسها الإلغاء المعلّق) · P1 موافقة يحمل `void` رمز إيجارها ⇒ غير متاحة للاستهلاك ولا للحلّ اليدوي حتى بعد انتهاء المدة (`hasOutstandingLease`) ويستلمها إعادة المحاولة/المجدول · P2 حذف الفرع لا يحوّل جهازه إلى «بلا فرع»: FK مقيِّد + رفض 422 صريح في حذف الفرع. **قيد معلن:** أمان التراكب المطلق مع مزوّد حقيقي يعتمد على التزام المحوّل بالمهلة (يُتحقَّق منه في شريحة المحوّل الحقيقي H6-03). ثلاثة اختبارات.

**الجولة السابعة (رأس 6f26c90) — أربع ملاحظات صحيحة:** P2 إعدادات وسائل الدفع في POS تُطبَّق قبل بدء طلب الجهاز (`PosSettings::allowsPaymentMethod`) · P2 `down()` لا يُسقط مُشغّلات SQLite على PostgreSQL (مُتحقَّق بتشغيله على PG) · P1 استثناء `cancel` غامض يُبقي علامة الإلغاء (لا يخلفه إلا إلغاء، والاستعلام يعيد الصف بلا نداء) · P1 استثناء `void` غامض يُبقي رمز الإيجار ⇒ لا حلّ يدوي ولا استهلاك حتى تنجح إعادة إلغاء؛ الرفض الصريح من المزوّد (قاطع) يبقى قابلاً للحلّ اليدوي. **قرار مفتوح للمالك:** مخرج الحلّ اليدوي عند تعذّر المزوّد دائماً (انظر ملخص الجولة).
