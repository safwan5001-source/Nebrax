## 2. ماذا يفعل كل مسار

| المسار | التغيير |
|---|---|
| `FuelSaleService::collectPayment` | تحت الأساس `receiving_shift_receipts`: يقفل وردية المحطة المفتوحة `FOR SHARE`، يرفض النقدي بلا وردية (`FUEL_CASH_RECEIPT_NO_OPEN_SHIFT`) ولبيع بعقد شركة (`FUEL_CASH_CORPORATE_SETTLEMENT_UNDECIDED`)، يتحقق من نطاق الفاعل (فرع/مخزن)، ويختم الإيصال (`fuel_shift_id`، `settlement_type`، `amount_minor`، `cash_account_id`، `received_by_user_id`) ويكتب حدث `official_cash_payment_recorded` على **وردية الاستلام** (`comparison_only=false`). مغلقاً: بلا أي تغيير |
| `FuelShiftService::recordCashMovement` | الحد = `FuelShiftCashExpectationService::live()['expected']` (يشمل R تحت الأساس الجديد). تسليم الخزنة: `purpose=treasury_handover` + `received_by_user_id` + `evidence.proof_reference`؛ مستلم نشط ≠ المسلِّم يملك `fuel.shift.approve` أو `fuel.shift.cash_variance_review` ضمن فرع/مخزن المحطة؛ مقارنة حمولة عند إعادة الإرسال |
| `FuelShiftService::close` | يحسب المتوقع بالدالة نفسها تحت `FOR UPDATE` ويجمّد المكوّنات في `fuel_shift_cash_variances` (+`official_cash_basis`, `expectation_complete`, `incompleteness`) |
| `PaymentReversalService` | خطّافان: قفل مشترك على وردية الإيصال النقدي المختوم **أولاً**، ثم بعد العكس حدث `post_close_cash_adjustment` إن كانت الوردية مغلقة. لا يمسّ الفرق المجمَّد |
| `GET fuel-stations/shifts/{id}` (+ردود الـPOST) | حقل `cash_summary` (حيّ للمفتوحة، مجمَّد للمغلقة). مكوّنات المبيعات تتطلب `fuel.sale.view` وإلا `available:false, reason:'permission'` |
| واجهة `/fuel-stations/ops/shifts/[id]` | قسم «ملخص النقد» (قراءة فقط) |

## 3. الإعداد والبوابة

`shift_expected_cash_basis` (`movements_only` الافتراضي | `receiving_shift_receipts`) لكل مؤسسة/محطة عبر آلية إعدادات الوقود القائمة. البوابة `config('fuel_stations.shift_cash_receipts_enabled')` مغلقة ⇒ الأساس الفعّال `movements_only` ويرفض `PUT` الإعدادات القيمة الجديدة.

### شروط فتح البوابة (لا تُفتح ضمن هذا PR)
1. دمج إصلاح #2016 (نطاق محطة/مخزن `FuelSaleController`: القائمة/العرض/الإنشاء/الإنهاء/التحصيل/طرق الدفع/الأسعار) باختباراته — **غير مدموج وقت كتابة التقرير**. دفاع الفاعل داخل `collectPayment` هنا دفاع في العمق وليس بديلاً عن حارس HTTP.
2. QA مستقل + اختبار Safari/iPhone حقيقي.
3. قرار تنسيق مع #2013 (UI-2) — انظر §7.
4. قرار تفعيل منسّق مستقل، ثم ضبط الأساس للمحطة (يُنصح بوردية جديدة بعد الضبط لتفادي إيصالات غير منسوبة).

## 5. متى تكتب العملية محاسبياً؟ (القيود الناتجة لكل عملية)

| العملية في هذه المهمة | قيد/سند جديد | ملاحظة |
|---|---|---|
| ختم الإيصال بالوردية (تحصيل نقدي) | **لا** | عمود على `fuel_sale_payment_receipts`؛ السند نفسه قائم |
| تحصيل نقدي/شبكة (قائم، لم يتغير) | سند قبض عبر `PaymentService::post`: **مدين** حساب نقد/بنك الوسيلة · **دائن** 1130 العملاء | بلا تغيير؛ تغيّر فقط تصنيف الوردية |
| `close` + تجميد اللقطة | **لا** | الفرق `pending_review` ولا يُسوّى |
| تسليم للخزنة (D5) | **لا** | سجل تشغيلي موثّق؛ قيد/تحويل خزينة = قرار D5b مستقل |
| حدث ما بعد الإغلاق (عكس سند) | **لا** من هذه المهمة | العكس نفسه (قيد عكسي واحد عبر `LedgerService::reverse`) هو سلوك قائم لخدمة العكس العامة |

لا كتابة مباشرة في `journal_lines`/`journal_entries`؛ لا مفتاح أجنبي على `commerce_orders`؛ لا مساس بـZATCA.

## 8. المخاطر المتبقية (مُعلَنة)

1. **R1:** بائع يسجّل نقد البيع كـ`cash_in` يدوياً فيُضاعف المتوقع — لا كشف خادمي ممكن؛ التخفيف عنونة الواجهة وعرض R منفصلاً.
2. إيصالات ما قبل التفعيل تجعل وردية التحوّل غير مكتملة (مقصود، لا Backfill).
3. D8 (بعد دمج #2025): عند فتح البوابة تُخفى الحقول القديمة (`expected_operational_cash_minor`, `cash_variance_minor`…) وحمولات الأحداث عمّن لا يملك `fuel.sale.view`، وفي `cash_summary` يُخفى كذلك مكوّن المبيعات والفرق (لأن المعدود − الفرق = المتوقع الكامل) — يثبّته اختبار API. مع البوابة المغلقة (الافتراضي) لا مبيعات في المتوقع أصلاً فلا تسريب.
4. `FuelSale.paid_minor` لا يتحدّث عند عكس سند من الخدمة العامة (فجوة قائمة خارج النطاق).
5. اختبار Safari/iPhone حقيقي لم يُجرَ؛ QA مستقل مطلوب قبل التشغيل.
