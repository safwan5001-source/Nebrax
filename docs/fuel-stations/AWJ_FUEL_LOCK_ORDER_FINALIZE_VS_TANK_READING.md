# تعارض ترتيب الأقفال: إنهاء البيع (وأشباهه) مقابل قراءة الخزان — تحليل وإصلاح مقترح

> **الحالة:** تحليل + إصلاح **مُجرَّب في بيئة معزولة** (PostgreSQL حقيقي) ولم يُطبَّق على المستودع بعد — ينتظر اعتماد المالك. موجود على `main` قبل أي تعديل؛ **يجب إصلاحه قبل تنفيذ تسوية الوردية** (§5).
> لا مساس بالإنتاج ولا ببيانات محطة حقيقية. كل القياسات على قاعدة مؤقتة ببيانات `E2E_TEST`.

## 1. الأعراض (مُثبَتة بتجربة)
معاملة «شبيهة بقراءة خزان» (عملية `psql` منفصلة): `BEGIN; SELECT … FROM fuel_tanks … FOR UPDATE; pg_sleep(1.5); SELECT … FROM fuel_stations … FOR KEY SHARE;` تتقاطع مع الفاعل:

| الفاعل (المحطة `FOR UPDATE` أولاً) | قبل الإصلاح | بعد الإصلاح المقترح |
|---|---|---|
| `FuelSaleService::createDraft` | **جمود 40P01** (القراءة ضحية) | ✅ لا جمود |
| `FuelSaleService::finalize` | **جمود 40P01** (البيع ضحية: خطأ 500/422 للمستخدم) | ✅ لا جمود |
| `FuelOpeningBalanceService::post` | **جمود 40P01** (القراءة ضحية) | ✅ لا جمود |
| `FuelShiftService::open` | ✅ لا جمود (لا يلمس صفوف الخزان) | ✅ |

## 2. السبب الجذري
نمط قفل الصف في PostgreSQL: **`FOR UPDATE` يتعارض مع `FOR KEY SHARE`** (الذي يأخذه أي `INSERT` يملك مفتاحاً أجنبياً إلى الصف).
- المسار A (البيع/الرصيد الافتتاحي): `FuelStation … FOR UPDATE` ← ثم يحتاج الخزان (إدراج صف الدفتر التشغيلي/البيع بمفتاح أجنبي إلى `fuel_tanks` = `KEY SHARE`، أو قفل `FOR UPDATE` صريح كما في الرصيد الافتتاحي).
- المسار B (`FuelReconciliationService::recordReading`، `FuelTankReadingRequestService`، `updateTank`): `FuelTank … FOR UPDATE` ← ثم إدراج صف بمفتاح أجنبي إلى المحطة (`fuel_tank_readings.fuel_station_id`) = `KEY SHARE` على المحطة.
- A ينتظر B (الخزان)، وB ينتظر A (المحطة) ⇒ دورة. الاختلاف في الاتجاه: **محطة→خزان** مقابل **خزان→محطة**.

## 3. الإصلاح المقترح (الأقل مساساً)
**قفل المحطة بنمط `FOR NO KEY UPDATE` بدل `FOR UPDATE` في مسارات «التشغيل» التي تلمس الخزان لاحقاً.**
`FOR NO KEY UPDATE` **لا يتعارض مع `KEY SHARE`** فلا ينتظر B المحطة أبداً ⇒ تنكسر الدورة (يبقى اتجاه واحد A→B). ويبقى متعارضاً مع نفسه ومع `FOR UPDATE` فيستمر التسلسل بين مسارات المحطة المتنافسة.

```diff
--- a/app/Services/FuelSaleService.php   (الموضعان: createDraft وfinalize)
-    $station = FuelStation::lockForUpdate()->findOrFail($stationId);
+    $station = FuelStation::query()->lock('for no key update')->findOrFail($stationId);
--- a/app/Services/FuelOpeningBalanceService.php   (post)
-    $station = FuelStation::lockForUpdate()->findOrFail($document->fuel_station_id);
+    $station = FuelStation::query()->lock('for no key update')->findOrFail($document->fuel_station_id);
```
- لا تغيير مخطط/واجهة/صلاحية. SQLite يتجاهل نمط القفل (لا أثر).
- **المقايضة:** إدراج صف بمفتاح أجنبي إلى المحطة (قراءة خزان، حركة…) لم يعد ينتظر نهاية إنهاء بيع جارٍ؛ قراءة الخزان قد تُسجَّل «في منتصف» إنهاء بيع. القراءة تشغيلية بلا أثر مخزني/محاسبي (موثَّق في CLAUDE.md)، فلا ثابت يُكسر.
- **لماذا لا بدائل:** (أ) قفل المحطة داخل `recordReading` يسلسل كل القراءات مع كل بيع (تنافس أعلى بكثير)؛ (ب) تغيير ترتيب الأقفال في `finalize` إلى «خزان أولاً» يعاكس ترتيب الرصيد الافتتاحي (محطة→خزان) فينقل الدورة بدل أن يزيلها؛ (ج) إعادة المحاولة عند 40P01 تخفي المشكلة وتُرهق المستخدم.

## 4. أدلة التحقق (على PostgreSQL 16)
- **المصفوفة:** قبل: `{"create_draft": قراءة=ضحية, "finalize": بيع=40P01, "opening_post": قراءة=ضحية}`؛ بعد: كلها `ok`.
- **الانحدار:** حزم الوقود المرتبطة (`FuelSale|FuelShift|FuelApproval|FuelTankReading|FuelReconciliation|FuelEffective|FuelStationScope`) **216 نجاح / 0 فشل**؛ `FuelOpening|FuelAvi` **56 نجاح / 0 فشل** مع التعديل.
- المجسّات في بيئة معزولة (`proc_open` + `psql` يحاكي معاملة القراءة)؛ تُحوَّل إلى اختبار PostgreSQL دائم عند التنفيذ (§6).

## 5. شرط مسبق مهم لتسوية الوردية (انقلاب ثانٍ مُثبَت)
التسوية المقترحة تعمل داخل `FuelShiftService::approve` الذي **يقفل الوردية `FOR UPDATE` أولاً** ثم تستدعي `finalize` الذي يقفل **المحطة ثم الوردية** (`assertFinalizationShift`). تجربة: معاملة «وردية ← محطة» مقابل `finalize` ⇒ **جمود 40P01 (ضحية التسوية)**؛ و«محطة ← وردية» ⇒ ✅ بلا جمود.
**القاعدة الملزمة للتسوية (وتنطبق على `close` إن نُفِّذت التسوية داخله، §4.2b في وثيقة التصميم؛ و`close` اليوم يقفل الوردية أولاً فيُعاد ترتيبه):** تأخذ قفل **المحطة (`NO KEY UPDATE`) أولاً ثم الوردية**: يقرأ المنسّق `fuel_station_id` من الوردية بقراءة عادية، يقفل المحطة، ثم الوردية (`FOR UPDATE`) — لا تُستدعى `finalize` وفي المعاملة قفل وردية سابق على المحطة. والترتيب الكامل المعتمد:
```
البيع/الوثيقة → المحطة (NO KEY UPDATE) → الفوهة → الوردية → [الخزان/المخزون/القيد كما هو]
```
ويُضاف حارس معماري ساكن (§6).

### 5.1 التحصيل على بيع قائم (انقلاب ثالث يجب إصلاحه قبل التسوية)
`FuelSaleService::collectPayment` يقفل **البيع ← الفاتورة ← الوردية (FOR SHARE)** بلا قفل محطة، والتسوية داخل الإغلاق تقفل **الوردية ← البيع** (لتسديد فاتورة ERP قائمة) ⇒ دورة محصِّل↔إغلاق. الترتيب الموحَّد المطلوب: **`[المحطة NO KEY UPDATE] ← الوردية ← البيع ← الفاتورة ← السند ← مِرساة المستأجر`**، ولذلك:
- يُعدَّل `collectPayment`: قراءة عادية للبيع (محطة/وردية) ثم قفل الوردية `FOR SHARE` **قبل** قفل البيع والفاتورة.
- يبقى `PaymentReversalService` كما هو (سند ← وردية FOR SHARE ← فاتورة ← مِرساة، موثَّق في عقد D1/D2) لأنه لا يقفل البيع؛ ويُراجَع في اختبار المصفوفة.
- `finalize` (بيع ← محطة ← فوهة ← وردية) لا يتعارض لأن الإغلاق يأخذ المحطة أولاً (تسلسل على المحطة نفسها) ولأن `finalize` على بيع منتهٍ يعود فور قراءة حالته؛ يُثبَّت باختبار.
- اختبار PostgreSQL إلزامي: **إغلاق مع تسوية مقابل `collectPayment` على البيع نفسه** (عمليات متوازية) بلا 40P01.

## 6. خطة التنفيذ المقترحة (بعد الاعتماد، PR مستقل صغير)
1. تعديل الموضعين المذكورين (+ `FuelAviAuthorizationService` وأي موضع آخر يقفل المحطة ثم يلمس الخزان إن كشفه الجرد).
2. **اختبار PostgreSQL دائم** (`FuelLockOrderPostgresTest`): المصفوفة أعلاه (مسودة/إنهاء/رصيد افتتاحي ضد قارئ الخزان) تؤكد «لا 40P01 ولا ضحية»؛ يفشل على `main` الحالي.
3. **حارس معماري ساكن:** يمنع `FuelStation::lockForUpdate()` في خدمات الوقود (يُسمح فقط بـ`lock('for no key update')`)، ويوثّق الترتيب أعلاه.
4. اختبار تسوية مستقبلي يثبت «محطة ← وردية».
5. تشغيل حزم PostgreSQL للوقود كاملة + CI.
