# TANKER-PR6B-2 — حالة الترحيل وسلامة قاعدة البيانات

> **النطاق:** تجهيز بنية قاعدة البيانات لانتقال سند تعبئة الصهريج `pending_integration → posted → reversed` مستقبلاً، **مع ضمان ألا يكتب أي مسار هذه الحالات الآن.**
> المبدأ: تجهيز القاعدة لاستقبال عمليات مستقبلية دون تنفيذها. **لا دمج ولا نشر ولا فتح بوابة.**

## 1) ما أُنجز (وما لم يُنجز عمداً)

| البند | الحالة |
|---|---|
| مُشغّلات/قيود انتقال الحالة على `fuel_tanker_fills` (PostgreSQL + SQLite) | ✅ هجرة `2027_01_28_010000_add_fuel_tanker_fill_posting_state_guards` |
| مزامنة حالة السند مع جدول الترحيل داخل القاعدة نفسها | ✅ مُشغّلا `AFTER INSERT/UPDATE` على جدول الترحيل |
| منع إلغاء سند `posted` (قيد + مُشغّل + خدمة + نموذج) وتسلسل السباق | ✅ |
| ربط حركات المخزون/التكلفة بالترحيل، وحدّ الكمية 32 بت | ✅ |
| نوعا الدفتر التشغيلي `tanker_fill` / `tanker_fill_reversal` على الدفتر **القائم** | ✅ ثابتان + حارس إدراج + فهرس فريد جزئي (لا دفتر موازٍ، **لا صف يُنشأ**) |
| جدول `fuel_tanker_fill_inventory_posting_attempts` (append-only) | ✅ هجرة `2027_01_29_010000_…` — **فارغ بلا كاتب** + نموذج يرفض كل كتابة |
| `post()` / `reverse()` مالي، خصم/إضافة مخزون، قيد، تعديل مجمّع التكلفة | ⛔ غير منفَّذ (PR-6B-3) |
| فاتورة/ضريبة/ذمة/تحصيل، ترحيل سندات تاريخية، أي API، بيانات Railway، البوابة `FUEL_TANKER_INVENTORY_POSTING_ENABLED` | ⛔ لم تُمسّ |

**لا صف جديد في أي جدول، ولا سند قائم يتغيّر:** كل السندات الحالية تبقى `pending_integration` (يثبته اختبار التراجع/إعادة التطبيق بمقارنة لقطة كاملة للسندات).

## 2) ضمانات القاعدة (تُفرض على PostgreSQL وSQLite لا في التحقق البرمجي وحده)

### أ) الانتقال
- المسموح فقط: `pending_integration → posted → reversed`. أي قفز (`pending → reversed`) أو رجوع (`posted → pending`، `reversed → posted/pending`) أو قيمة مجهولة مرفوض.
- **`posted` لا يتحقق إلا بصف ترحيل مطابق بحالة `posted`؛ `reversed` لا يتحقق إلا بصف ترحيل بحالة `reversed`.** الحالة **تتبع جدول الترحيل بمُشغّل متزامن** (إدراج ترحيل ⇒ السند `posted`؛ تحويله `reversed` ⇒ السند `reversed`)، فلا يختلف الاثنان، وتحديث مباشر للسند يُقبل فقط إن وُجد الترحيل المقابل (وإلا فالمُشغّل يرفض). اخترنا المزامنة بمُشغّل بعد الإدراج لأن SQLite بلا مُشغّلات مؤجَّلة.
- السند لا يُنشأ إلا `pending_integration` (مُشغّل إدراج جديد على PostgreSQL؛ مُشغّل SQLite القائم يكفي).
- قيد CHECK على PostgreSQL: `NOT (status = 'voided' AND inventory_status = 'posted')`.

### ب) الإلغاء (void) والعكس عمليتان منفصلتان
- سند `posted` لا يُلغى: **409 `fill_inventory_posted`** من الخدمة (بعد قفل صف السند، يقرأ آخر حالة ملتزَمة)، و`LogicException` من النموذج، وخطأ قاعدة من المُشغّل/القيد لو وصل إليه كود آخر.
- بعد العكس (`reversed`) يصير الإلغاء ممكناً (المخزون عاد)؛ الإلغاء المتكرر idempotent كما كان.
- **التزامن:** حارس إدراج الترحيل يأخذ `FOR NO KEY UPDATE` على صف السند (في عبارة منفصلة ثم يعيد الفحص على آخر حالة ملتزَمة) فيتسلسل مع `lockForUpdate` في `FuelTankerFillService::void`. أيّهما سبق حسم الآخر، بلا جمود.

### ج) ربط الحركات (حارس الإدراج على الترحيل)
- السند: `recorded` و`pending_integration` ومن المؤسسة/الفرع/المحطة/المنتج/الكمية نفسها.
- المخزن = مخزن المحطة؛ حركة المخزون: المؤسسة نفسها، **المخزن نفسه، نوع `out`، الكمية نفسها، منتج الوقود نفسه**؛ حركة التكلفة: المؤسسة/المخزن/المنتج، **تتبع حركة المخزون نفسها، `issue`، الكمية نفسها، التكلفة التاريخية نفسها (`posted_cost_minor`)**.
- حركة عكس لا تُعاد كحركة ترحيل لآخر.
- **عند العكس:** حركة مخزون `in|adjustment` بالمخزن والمنتج والكمية نفسها؛ حركة تكلفة تتبعها بالكمية **والتكلفة الأصلية (لا إعادة تسعير)**؛ مختلفتان عن حركتي الأصل (CHECK) ولا تنتميان لترحيل آخر.
- **سقف الكمية:** `quantity_milliliters ≤ 2,147,483,647` (CHECK على PostgreSQL، مُشغّل على SQLite) لأن `stock_movements.quantity` عدد صحيح 32 بت.

### د) الدفتر التشغيلي (القائم)
`FuelOperationalLedger::TYPE_TANKER_FILL` و`TYPE_TANKER_FILL_REVERSAL` (ثابتان فقط؛ العمود نص حرّ بلا CHECK فلا هجرة نوع). حارس إدراج في القاعدة: لا يُدرج النوعان إلا بمصدر `FuelTankerFill` ومقابل ترحيل مطابق (المحطة/المنتج/المخزن/الخزان/الحركة الرسمية نفسها؛ كمية **سالبة** للصرف و**موجبة** للعكس، والعكس يتطلب ترحيلاً معكوساً بحركة العكس نفسها)، وفهرس فريد جزئي: صف واحد لكل (سند، نوع). الأنواع القائمة لا تتأثر.

### هـ) جدول المحاولات `fuel_tanker_fill_inventory_posting_attempts`
append-only (UPDATE مرفوض، DELETE مرفوض ما دام المستأجر موجوداً). الأعمدة: السند والمحطة والفرع والمؤسسة (مطابقة السند إلزامية)، `operation_type` (`post|reverse`)، `outcome` (`succeeded|rejected|failed`)، `reason_code` (إلزامي لغير الناجحة ومحظور للناجحة)، `idempotency_key` اختياري، `actor_id`، `attempted_at`، `posting_id` (إلزامي للناجحة، محظور لغيرها). **الناجحة تشترط ترحيلاً مطابقاً للسند (وللعكس ترحيلاً معكوساً).** فهرسان فريدان جزئيان: نجاح واحد لكل (سند، عملية)، ونجاح واحد لكل (مؤسسة، عملية، مفتاح). المحاولات الفاشلة المتكررة بالمفتاح نفسه مسموحة (سجل لا قيد). النموذج `FuelTankerFillInventoryPostingAttempt` (`BranchScoped`) يرفض كل كتابة حتى PR-6B-3.

## 3) مراجعة ضوابط PR-6A (بند «هـ»)

| الضابط | حالة 6A | بعد 6B-2 |
|---|---|---|
| ترحيل نشط واحد لكل سند | فهرس فريد على `fuel_tanker_fill_id` | + مزامنة الحالة، ومنع ترحيل ثانٍ لسند ليس `pending_integration` |
| لا تكرار حركة مخزون/تكلفة | فهارس فريدة على الحركتين | + حركة عكس لا تُستعمل كحركة ترحيل لآخر وبالعكس |
| عكس واحد | فهرسا حركتي العكس + ثبات `reversed` | + مختلفتان عن الأصل، وبالكمية/التكلفة الأصليتين |
| سلامة مفاتيح الربط | الإدراج يطابق السند فقط — **ثغرة:** الحركتان غير مربوطتين بالمخزن/المنتج/النوع/الكمية | **أُغلقت** (القسم 2-ج) |
| ثبات التكلفة التاريخية | `IMMUTABLE` تشمل الكمية والتكلفة | + مطابقتها لحركة التكلفة عند الإدراج والعكس |
| حدود أعمدة الكمية | **ثغرة:** `stock_movements.quantity` 32 بت، والترحيل `bigint` | **أُغلقت** بسقف 2,147,483,647 |
| حالة السند مقابل الترحيل | **ثغرة:** منفصلتان بلا ربط | **أُغلقت** بمُشغّلات المزامنة |
| إلغاء سند مرحَّل | **ثغرة:** لا حماية | **أُغلقت** |
| `down()` مع بيانات | يرفض إن وُجد صف ترحيل | يرفض إن وُجد سند غير `pending_integration` أو أي ترحيل أو صف دفتر من النوعين أو أي محاولة؛ ثم يعيد حراس PR-4/6A حرفياً (مثبت باختبار) |

اختبارات 6A المعدَّلة: فقط **تثبيتات** (fixtures) صارت تنشئ حركات مطابقة للكمية والتكلفة؛ وأُعيدت تسمية اختبار «pending_integration هي الحالة الوحيدة» إلى «لا انتقال بلا ترحيل مطابق»، وفحص الكتّاب الساكن يسمح بنموذجَي (الترحيل ومحاولاته) فقط.

## 4) حدود معلنة

1. سند حجمه > 2,147,483,647 مل يمكن تسجيله (PR-4) لكنه **لن يُرحَّل أبداً**؛ يلزم مانع جاهزية صريح في PR-6B-3 (لم يُضف هنا لأنه تعديل على الجاهزية خارج هذه الشريحة).
2. حركة عكس المخزون تقبل `in` أو `adjustment` عمداً: بدائية العكس (D-6B-3) **غير معتمدة** بعد، فلم نثبّت نوعاً أضيق. يُشدَّد بهجرة لاحقة إن اعتُمد خلافه.
3. لا ربط لـ`stock_movements.total_cost` بالتكلفة التاريخية (طريقة تسجيل التكلفة في الحركة قرار PR-6B-3)؛ المربوط هو `fuel_inventory_cost_movements.posted_cost_minor`.
4. الدفتر التشغيلي ثابت برمجياً فقط (لا مُشغّل UPDATE/DELETE عليه في القاعدة) — **سلوك قائم من قبل** وخارج هذه الشريحة؛ هذه الهجرة تحمي الإدراج لنوعين جديدين فقط.
5. اختبارات التزامن هنا تغطي **سباق الإلغاء↔إدراج الترحيل وترحيلين لسند واحد** فقط؛ اختبارات الترحيل المالي المتزامن (خصم/قيد/مجمّع) تخص PR-6B-3.
6. الفحص CHECK `reversal_*_id <> *_id` طبقة دفاع إضافية: حارس العكس يرفضه أصلاً لأن حركة الأصل `out`.

## 5) الاختبارات

- `FuelTankerFillPostingStateTest` (18 اختباراً): الانتقالات الصالحة، كل الانتقالات الممنوعة، الإنشاء المباشر `posted/reversed`، كل حالات عدم تطابق الحركات، الكمية السقف، العكس بالكمية/التكلفة/الحركات، الإلغاء (API/خدمة/نموذج/SQL) وفصل العكس عن الإلغاء، الدفتر التشغيلي (بلا ترحيل/كمية/حركة/مصدر/خزان/مخزن/تكرار/عكس)، المحاولات (الشكل، العزل، append-only، النجاح الوحيد)، نموذجا الترحيل والمحاولات يرفضان الكتابة، التراجع وإعادة التطبيق **بلا تغيير في أي سند** ولا أثر مخزني/مالي، استعادة حراس PR-4/6A، رفض التراجع مع سجل حقيقي، وفحص ساكن بعدم وجود مسار كتابة (خدمة/متحكّم/مسار/أمر).

- بقاء اختبارات 6A/6B-0/6B-1 وبقية وحدات الوقود خضراء على SQLite وPostgreSQL.
