# TANKER-PR8 — مطابقة قراءات الفوهات والورديات ومنع الخصم المزدوج

> الحالة: Beta/Development. **لا بوابة فُتحت، لا منح صلاحيات، لا نشر ولا دمج، لا بيانات إنتاجية، ولا بدء PR-9 أو التسويات.**
> التحليل الذي سبق التنفيذ: `PR8_ANALYSIS_AND_PLAN.md` (المسارات القائمة، التعارض، خطة الإصلاح، القرارات المعلّقة).

## 1. الخلاصة

| الهدف | ما نُفِّذ |
|---|---|
| مطابقة كل فوهة عند الإغلاق | لقطة مجمَّدة لكل فوهة: **M = D + T + U** (فرق العدّاد = مبيعات مباشرة نهائية + سندات تعبئة صهاريج مسجَّلة + غير مفسَّر) خلف بوابة جديدة **مغلقة** `FUEL_SHIFT_METER_RECONCILIATION_ENABLED` |
| فصل التعبئة عن المبيعات | عمود مستقل للتعبئة؛ **لا فاتورة ولا تحصيل ولا قيد ولا حركة مخزون** من التسجيل أو المطابقة (يحرسه اختبار بعدّ الصفوف) |
| التعارض `post_on_close` ↔ ترحيل السند | سببه مثبَّت في الكود (§2)؛ عولج **من الجذر** باستبعاد لترات التعبئة من بقية التسوية، وحلّ مانع دقيق محل المانع الكلّي |
| منع الخصم المزدوج | اللتر يُخصم مرة واحدة من المسار الذي سُجِّل به؛ مُثبَت بالترتيبين (تسوية ← ترحيل، ترحيل ← تسوية) بمطابقة المخزن والمجمّع لقراءة العدّاد |
| تصنيف الفروق ومراجعتها | سجل مراجعة ثابت لكل فرق، بـ`fuel.shift.meter_variance_review`، **تصنيف وصفي بلا أثر محاسبي**، شرط للاعتماد (البوابة مفتوحة فقط) |
| شاشة المراجعة والإغلاق | قسم «مطابقة العدّادات» في شاشتَي التسليم (حيّ) والمراجعة (مجمَّد)، جوال/RTL/LTR |
| التاريخي والتدقيق | لا تعديل لأي قيد/قراءة/تسوية مرحَّلة؛ اللقطات والمراجعات إلحاقية بحراس قاعدة بيانات؛ أحداث الوردية `meter_reconciliation_frozen|meter_variance_reviewed` |

## 2. لماذا كان الخصم مزدوجاً (التعارض C-1)

`FuelShiftSettlementPreviewService` و`FuelShiftSettlementEvaluator` كانا يحسبان بقية التسوية `= قراءة العدّاد − مبيعات ERP النهائية` ولا يطرحان تعبئات الصهاريج. تحت `post_on_close`:

1. لترات التعبئة تبقى في البقية ⇒ التسوية تُنشئ لها **فاتورة بيع آجلة** (تعامل التعبئة بيعاً — مخالف لقرار «لا فاتورة/إيراد/ضريبة/ذمة تلقائياً عند التعبئة»).
2. التسوية تخصم المخزون والمجمّع وتقيّد تكلفة البضاعة لها.
3. ترحيل سند التعبئة (PR-6B-3) يخصم **الكمية نفسها** ثانيةً ⇒ نقص مضاعف في المخزن والمجمّع وحساب المخزون.

حاجز PR-6B-0 (`settlement_mode_conflict`) كان يمنع **كل** ترحيل في محطة بهذا الوضع: حاجز كلّي لا يعالج السبب ولا يغطي تسوية سبقت الترحيل. كذلك اكتُشف **موضع ثانٍ** لمعاملة التعبئة كمبيعات: مطابقة إقرار التحصيل (`FuelShiftCollectionService`) كانت تتوقع من الموظف إقرار نقد/شبكة عن **كل** لترات العدّاد بما فيها التعبئة.

## 3. كيف مُنع الخصم المزدوج

| الطبقة | الآلية |
|---|---|
| **مصدر واحد للترات** | `FuelShiftNozzleLiters`: `direct` (مبيعات نهائية `source=station`) و`tanker` (سندات `recorded`، الملغاة مستبعدة) — تستعمله المعاينة والمُقيِّم والمطابقة |
| **التسوية** | `residual = metered − erp − tanker`. التعبئة تُخصم بترحيل سندها وحده فلا تدخل البقية ولا فاتورة لها. `residual < 0` ⇒ المانع القائم `FUEL_SETTLEMENT_ERP_EXCEEDS_METER` |
| **وسم التسوية** | أسطر التسوية الجديدة تكتب `tanker_milliliters`، والرأس `policy_snapshot.tanker_exclusion = true`. **NULL = تسوية سابقة لم تستبعد** (لا Backfill) |
| **مانع الترحيل الدقيق** | `settlement_covers_fill` (يحل محل الكلّي): يُحجب فقط سند سبقته تسوية لم تستبعد التعبئات (سطر فوهته `tanker_milliliters IS NULL`). الفحص ضمن الجاهزية نفسها التي يعيد الترحيل تقييمها **تحت الأقفال** |
| **ثبات المجموعة** | تسجيل/إلغاء السند يتطلب وردية مفتوحة (قفل `FOR SHARE`) والإغلاق `FOR UPDATE` ⇒ **مجموعة التعبئات ثابتة عند الإغلاق**؛ لا سباق بين السندات والتسوية |
| **idempotency** | ترحيل السند: مفتاح حتمي + ترحيل واحد لكل سند؛ التسوية: رأس واحد لكل وردية. الإعادة بلا أثر |
| **مطابقة إقرار التحصيل** | `FuelShiftSalesCalculator::compute(..., excludeTankerFills: true)` يطرح لترات التعبئة من «مبيعات العدّاد» المتوقعة (نقد/شبكة)؛ بقية المستهلكين (تقارير) افتراضياً كما كانوا |

**الإثبات (اختبارات):** `FuelShiftSettlementPostingTest`

- عدّاد 20 L + تعبئة 8 L ⇒ فاتورة التسوية لـ12 L فقط (27.60) والمخزن نقص 12 L، وسند التعبئة `pending_integration`.
- **تسوية ثم ترحيل السند:** المخزن ↓ 20 L بالضبط = قراءة العدّاد، والمجمّع = المخزن، والإعادة بلا أثر.
- **ترحيل السند ثم تسوية:** نتيجة مطابقة (8 ثم 12).
- بيع مباشر 15 + تعبئة 10 > عدّاد 20 ⇒ حجب بلا أي كتابة.
- `FuelTankerFillInventory{Readiness,Posting}Test`: محطة `post_on_close` تُرحِّل بلا مانع كلّي، وتسوية سابقة (`tanker_milliliters IS NULL`) تحجب ذلك السند وحده بـ`settlement_covers_fill` دون أي أثر.

## 4. المطابقة (M = D + T + U)

| الحالة | الشرط |
|---|---|
| `balanced` | U = 0 |
| `within_tolerance` | 0 < |U| ≤ `shift_meter_tolerance_milliliters` (الإعداد القائم، كان بلا مستهلك؛ الافتراضي 0) |
| `variance` | |U| > التفاوت — **U > 0** لترات بلا تسجيل · **U < 0** المسجَّل أكثر من العدّاد |
| `incomplete` | قراءة ناقصة أو إغلاق < افتتاح (لا يُحسب فرق) |

مبيعات `draft` معلومة (`draft_sale_milliliters`) لا تدخل المجاميع. الصرف الداخلي غير مبني (يُعلَن في `not_checked`). قيد قاعدة بيانات يفرض `U = M − D − T` عند الإدراج (PostgreSQL وSQLite).

**التصنيفات** (قائمة ثابتة وصفية، حسب نوع الفرق): فائض `{unrecorded_direct_sale, unrecorded_tanker_fill, reading_error, calibration_test, internal_use, loss_or_leak, other}` · مسجَّل أكثر `{over_recorded_entry, reading_error, other}` · ناقصة `{reading_error, other}`. `other` يتطلب ملاحظة. **لا أثر محاسبي أو مخزني أو تصحيح قراءة** (D-8-3).

## 5. البنية والواجهات

- **الهجرة** `2027_01_30_010000`: جدولان (`fuel_shift_nozzle_reconciliations`، `fuel_shift_meter_variance_reviews`) + عمود `fuel_shift_settlement_lines.tanker_milliliters`. حراس: لا UPDATE أبداً، لا DELETE ما دام المستأجر موجوداً، قيود شكل. التراجع يرفض متى وُجدت صفوف.
- **الخدمة** `FuelShiftMeterReconciliationService` (الكاتب الوحيد): `freezeAtClose` داخل معاملة الإغلاق تحت قفل الوردية · `view` · `review` (قفل الوردية ثم اللقطة، قرار واحد idempotent) · `assertApprovable`.
- **API:** `GET fuel-stations/shifts/{id}/meter-reconciliation` (`fuel.shift.view`) · `POST …/meter-reconciliation/review` (`fuel.shift.meter_variance_review`، مستقلة عن `cash_variance_review`). 404 والبوابة مغلقة؛ نطاق المحطة 404 موحَّد؛ الجسم: `nozzle_id` + `classification` + `note` فقط، ومفتاح مجهول مرفوض.
- **الاعتماد:** البوابة مفتوحة ⇒ فرق/ناقصة بلا مراجعة ⇒ `FUEL_METER_VARIANCE_REVIEW_REQUIRED`. وردية بلا لقطة (أُغلقت قبل الفتح) لا تُحجب. **الإغلاق لا يُحجب بفرق العدّاد** (تسجيل فقط، كنمط فرق النقد).
- **الواجهة** (`web/src/modules/station-ops/`): `MeterReconciliationSection` في شاشتَي التسليم (أرقام حيّة تُجمَّد عند الإغلاق) والمراجعة (لقطة مجمَّدة + نموذج التصنيف لمن يعلن الخادم `can_review`). كل رقم وحالة من الخادم؛ لا إعادة إرسال تلقائية (نتيجة غير مؤكدة ⇒ إعادة قراءة)؛ أهداف لمس ≥ 44px؛ خصائص منطقية؛ ar/en بلا مصطلحات محاسبية (حارس `app-only`). مفاتيح الرفض الجديدة ومحاذاة رسائل الجاهزية (`settlement_covers_fill`).

## 6. قائمة جلسة PIN — توسّع واحد موثَّق (D-8-7)

أُضيف مسار **كتابة واحد** إلى `StationSessionBoundary`: `POST shifts/{id}/meter-reconciliation/review` (إلى جانب `collection/review` و`cash-variance/review` القائمتين). القراءة `GET shifts/{id}/meter-reconciliation` تغطيها بادئة `shifts` القائمة. **لا منح صلاحيات:** `fuel.shift.meter_variance_review` تبقى لـowner/admin عبر `*` فقط (لا `MATRIX` ولا قالب ولا دور مخزَّن)، فجلسة PIN لموظف عادي لا تصل. **تحتاج اعتماد المالك**؛ إزالتها بسطر واحد دون أثر على بقية الميزة.
