# Cycle 6 — تصميم عقود الشركات والائتمان والأسطول وبطاقات الوقود

**الحالة:** منفذ على فرع Cycle 6 وقابل للمراجعة؛ لم يُدمج بعد.
**القرار التجاري:** عقد شركات مؤرخ، إنفاذ خادمي عند `FuelSale` finalization، وحد ائتماني صلب من الذمم الرسمية، وفاتورة مستقلة لكل بيع، وبطاقة وقود منطقية بلا RFID أو AVI.

> لا يضيف Cycle 6 محرك فاتورة أو ذمم أو دفع موازياً. يبقى المسار الرسمي: `FuelSale → InvoiceService → PaymentService`، ويضيف Cycle 6 قرار تفويض قبل أن ينشأ أي أثر نهائي.

## النطاق والحدود

ينشئ Cycle 6 طبقة تجارية فوق Cycle 5 لعملاء الشركات. لا يغير معنى سعر المحطة، ولا يعيد تفسير فاتورة أو بيع أو تحصيل سابق. يكون البيع المؤسسي خياراً صريحاً عبر عقد أو بطاقة منطقية، ويمنع الخادم finalization قبل إنشاء الفاتورة أو صرف المخزون أو COGS إن فشل العقد أو الأسطول أو البطاقة أو الائتمان.

| داخل النطاق | مؤجل صراحةً |
|---|---|
| عقد وقود مستقل ومؤرخ للعميل | فاتورة شهرية موحدة للشركات |
| تسعير عقدي صريح ومؤرخ لكل منتج وقود | RFID وAVI وفتح المضخة تلقائياً |
| حد ائتماني صلب من حساب العملاء الرسمي | مزود بطاقة خارجي أو clearing مستقل |
| مركبات وسائقون وبطاقات منطقية وسياسات حدود | workflow لتجاوز الائتمان أو موافقته |
| سعر وفاتورة منفصلان لكل FuelSale | تغيير نقطة الاعتراف بالإيراد أو ZATCA |

## نموذج البيانات والعزل

كل كيان عقدي أو أسطولي **CompanyWide** ضمن المستأجر، لأن العميل والعقد والمركبة والبطاقة قد تستخدم في أكثر من فرع/محطة. يبقى `FuelSale` و`Invoice` مقيدين بالفرع كما في Cycle 5، ويحفظان مراجع CompanyWide كلقطات تاريخية. لا يوجد استعلام يتجاوز `TenantScope`.

| الجدول/الكيان | الغرض | قيود تاريخية وعزل |
|---|---|---|
| `corporate_fuel_contracts` | العقد الأساسي للعميل، الفعالية، الحالة، الائتمان، الشروط والسياسات | CompanyWide؛ `draft/active/suspended/expired/cancelled`؛ العقد النشط لا يعدل مادياً بلا حدث/نسخة مؤرخة. |
| `corporate_fuel_contract_prices` | سعر لتر عقدي صريح، منتج، نمط VAT، فعالية ومراجع التدقيق | CompanyWide؛ لا تداخل نشط لنفس العقد/المنتج؛ immutable بعد الإنشاء. |
| قيود العقد station/fuel | `restriction_mode=all|selected` مع قوائم محطة/منتج | CompanyWide؛ `all` صريح، فلا تفسر قائمة فارغة بتخمين. |
| `corporate_fuel_credit_locks` | صف قفل واحد لكل `partner_id` مؤسسي | CompanyWide؛ يمنع سباق مبيعات العقد المتزامنة على حد العميل. |
| `fuel_fleet_vehicles` | مركبة أسطول مستقلة، مع customer/contract اختياريين | CompanyWide؛ `active/suspended/inactive`؛ لا حذف للتاريخ. |
| `fuel_fleet_drivers` | سائق مستقل مع `employee_id` اختياري | CompanyWide؛ العميل/العقد اختياريان لحالة الأسطول الداخلي. |
| `fuel_cards` | هوية تفويض أعمال منطقية، لا جهاز RFID | CompanyWide؛ public identifier، hash داخلي، customer/contract وvehicle/driver اختياريون، وحالة فعالية. |
| قيود البطاقة station/fuel | station/fuel modes وقوائم مسموحة | CompanyWide؛ دلالة `all|selected` صريحة. |
| `fuel_card_usages` | استهلاك بطاقة معتمد مربوط بـFuelSale | CompanyWide؛ append-only وunique على FuelSale، مصدر حدود اليوم/الأسبوع/الشهر. |
| أحداث العقد/الأسطول/البطاقة | before/after، actor، وقت وسبب | CompanyWide؛ append-only لتغييرات الائتمان، السعر، الحالة والقيود. |

تضاف إلى `fuel_sales` مراجع اللقطات: `corporate_fuel_contract_id`، و`corporate_fuel_contract_price_id`، و`fuel_card_id`، و`fuel_fleet_vehicle_id`، و`fuel_fleet_driver_id`، و`corporate_price_source`، و`contract_payment_terms_days`. لا تسمح حماية السجل النهائي بتعديلها بعد finalization.

## دورة العقد والتسعير

ينشأ العقد مسودة، ثم ينشط ضمن نافذة فعالية محددة. لا يصرح `draft` بالبيع. يرفض `suspended` و`expired` و`cancelled` أي تفويض ائتماني جديد مع بقاء AR والفواتير والتحصيلات والسجل التاريخي دون تعديل. يمنع النظام تداخل عقدين نشطين لنفس العميل في وقت واحد حتى لا يصبح حل العقد والسقف الائتماني ملتبساً.

| ترتيب القرار | النتيجة |
|---|---|
| سعر عقدي فعال للمنتج | يستخدم سعره ونمط VAT المحفوظين على نسخة السعر نفسها. |
| لا سعر عقدي فعال | يستدعي resolver Cycle 5 نفسه: محطة ثم tenant default ثم `FUEL_PRICE_NOT_CONFIGURED`. |
| لا عقد/بطاقة مسار مؤسسي | يبقى بيع Cycle 5 العادي كما هو. |

لا يرث سعر العقد `fuel_price_tax_mode` ديناميكياً؛ يملك `tax_mode` محفوظاً (`tax_inclusive|tax_exclusive`) لحظة إنشائه. تحفظ `FuelSale` السعر والنمط والمصدر ومرجع نسخة السعر، وتثبت `Invoice.tax_inclusive` النمط المستعمل. يبقى الحساب النسبي نفسه: `mL × minor/L ÷ 1000` ثم half-up مرة واحدة في `InvoiceLinePrecision`.

## الإنفاذ والائتمان

يطلب `FuelSale` المؤسسي صراحةً معرف عقد أو بطاقة. داخل معاملة finalization، وبعد قفل البيع والمحطة والفوهة، تحل خدمة التفويض العقد والبطاقة/المركبة/السائق والسعر ونمط الضريبة، ثم تبني فاتورة Nebrax مسودة فقط لحساب إجماليها المشتق. لا ينشأ قيد أو صرف مخزون في هذه المرحلة. تقفل الخدمة صف الائتمان الخاص بالعميل، وتحسب exposure من **رصيد 1130 العملاء الرسمي الموسوم بنفس Partner** (`Σ debit - Σ credit`، مع عدم نزول التعرض عن صفر)، فيشمل كل فواتير المبيعات والقبوض والإشعارات الدائنة الرسمية عبر Nebrax.

```
projected exposure = max(0, official AR balance) + new invoice total
projected exposure <= contract credit_limit_minor
```

إذا تجاوزت القيمة السقف تفشل المعاملة بالرمز `CORPORATE_CREDIT_LIMIT_EXCEEDED`. لا يوجد warning-only أو override يدوي أو رفع تلقائي أو fallback إلى فاتورة غير مغطاة. قفل صف الائتمان نفسه يسلسل مبيعات العقد المتزامنة للعميل؛ وتُقفل البطاقة قبل حساب حدود استخدامها. بعد اجتياز التفويض فقط تستدعي الخدمة `InvoiceService::post()` ومسار Cycle 5 للمخزون وCOGS، ثم تسجل usage البطاقة وتحدث `FuelSale` بلقطاتها.

## الأسطول والبطاقة

المركبة والسائق كيانات مستقلة لا تفترض أنها موظف Nebrax أو تخص عميلاً دائماً. في بيع مؤسسي، إن كانت المركبة أو السائق مرتبطة بعميل أو عقد فيجب أن تطابق العميل والعقد المحلولين؛ وإن كانت `suspended` أو `inactive` تفشل العملية. يمكن للبطاقة ربط مركبة أو سائق؛ عند وجود الربط يصبح تقديم المعرف المطابق إلزامياً.

| سياسة البطاقة | وحدة القياس | الإنفاذ |
|---|---:|---|
| الحد لكل معاملة | mL / هللة | قبل finalization، بعد حساب إجمالي الفاتورة المتوقع. |
| اليوم/الأسبوع/الشهر | mL / هللة | مجموع `fuel_card_usages` في منطقة وقت المحطة التشغيلي. |
| عدد المعاملات اليومي | عدد صحيح | مجموع usage اليومية. |
| قيود محطة/منتج | معرفات محطات/منتجات | `all|selected` صريح؛ لا دلالة مخفية للقائمة الفارغة. |
| النوافذ الزمنية | قواعد محلية مدققة | تقارن وقت المحطة في `operating_timezone`؛ خارج النافذة يرفض. |

استخدام البطاقة ليس سند قبض ولا ينشئ clearing account أو يحرك النقد. الفاتورة تظل AR على العميل وفق العقد.

## الشروط والـodometer والإعدادات

تضيف إعدادات Fuel Stations سياسة صريحة بميراث `Tenant → Station → Contract` حيث يملك العقد override محدداً:

| المفتاح | الافتراض الحامي | الملاحظة |
|---|---|---|
| `corporate_credit_enabled` | `false` | لا يغير مبيعات Cycle 5 القائمة. |
| `require_active_contract` | `true` للمسار المؤسسي | يمنع عقداً مسودة/منتهياً من التفويض. |
| `odometer_policy` | `optional` | `disabled|optional|required`؛ العقد يستطيع فرض قيمة أشد. |
| `driver_required` | `false` | يطبق في المسار المؤسسي فقط. |
| `vehicle_required` | `false` | يطبق في المسار المؤسسي فقط. |
| `fuel_card_required` | `false` | يطبق في المسار المؤسسي فقط. |

شروط الدفع من العقد (`payment_terms_days`) تحسب `Invoice.due_date` وقت finalization؛ لا يغير تعديل العقد فاتورة تاريخية. سجل odometer مستقل ومؤرخ، ولا يسمح بقراءة تنخفض عن آخر قراءة معتمدة للمركبة؛ لا تدخل قواعد fraud تلقائية في Cycle 6.

## الفوترة المجمعة المؤجلة

`consolidated_monthly` غير قابل للتفعيل في Cycle 6. لا تتولد فاتورة موحدة فوق فواتير كل بيع، ولا يتحول بيع Cycle 5 إلى استعمال غير مفوتر. يحتاج المستقبل إلى `unbilled corporate usage → period close → consolidated Invoice → AR/VAT/ZATCA مرة واحدة` في دورة مستقلة، لذلك يوثق كحالة `DEFERRED` فقط.

## واجهات API وRTL والتحقق

تخضع كل نقاط Cycle 6 لبوابة `fuel_stations.core` التجارية ولصلاحية RBAC مستقلة؛ لا ترث إدارة المحطة سلطة العقد أو الائتمان أو البطاقة. تغطي API إدارة مسودة العقد وتفعيلها وتعليقها وسعرها المؤرخ وقراءة exposure، إضافة إلى قوائم/إنشاء المركبات والسائقين والبطاقات. لا يخرج مورد البطاقة `credential_hash` أبداً.

تضيف الواجهة العربية/RTL صفحة `/fuel-stations/corporate-contracts` لمسودة العقد والتفعيل وقائمة الحالة، ورابطاً صريحاً من مساحة عمل المحطات. تبقى إدارة تفصيل الأسطول والبطاقة المتقدمة عبر API في هذا الإصدار؛ لا تدّعي واجهة العقد أنها تفتح مضخة أو تنفذ RFID/AVI.

| التحقق | النتيجة في فرع Cycle 6 |
|---|---|
| PHP / SQLite كامل | `1321 passed`، `7852 assertions`، و`1 skipped` |
| PostgreSQL | هجرة `000113` من الصفر نجحت، واختبار `FuelSaleServiceTest` نجح: `5 passed / 68 assertions` |
| الواجهة | `42` ملف اختبار و`183` اختباراً ناجحاً، وبناء Next.js ناجح |

> تصحيح توافق PostgreSQL: لا يضيف `replaces_fuel_card_id` FK ذاتياً، لأن نموذج Nebrax متعدد المستأجرين لا يضمن فهرس `id` منفرداً صالحاً لذلك القيد في كل محرك. يبقى الحقل مفهرساً ويُتحقق منه خادمياً داخل `FuelCardService` ضمن المستأجر والعقد، ولا يسمح مسار الاستبدال بتوسيع قيود البطاقة أو حدودها بصمت.
