## 1. P1-2 — لماذا تظهر «زيادة» وهمية في نقد الدرج

### 1.1 المعادلة الحالية (من الكود: `FuelShiftCashExpectationService::live`)

```
E (المتوقع) = O + R_basis + I − U − X          حيث R_basis = Σ إيصالات النقد المختومة بالوردية   إذا الأساس receiving_shift_receipts
                                                           = 0                                       إذا الأساس movements_only (الافتراضي)
V (الفرق)   = C − E                             (C = النقد المعدود)
```

| الرمز | المعنى | مصدره |
|---|---|---|
| O | عهدة الافتتاح | إدخال البائع |
| R | نقد مبيعات **مسجَّل رسمياً** | `fuel_sale_payment_receipts` — يُكتب فقط من `collectPayment` (مسار ERP) وخلف بوابة `FUEL_SHIFT_CASH_RECEIPTS_ENABLED` المغلقة |
| I / U / X | نقد وارد / صادر (يشمل التسليم) / مصروف | حركات نقد يدوية |
| C | المعدود | إدخال البائع عند التسليم |

### 1.2 السبب الجذري (مُثبَت)

**معادلة E لا ترى نقد المبيعات إلا عبر مسار ERP، بينما تطبيق الجوال يبيع بلا ERP.** وردية الجوال: عدّادات + إقرار تحصيل + عدّ نقد — لا إيصالات R، ولا `cash_in` (لا يجوز أن يكون نقد مبيعات). لذلك:

> **V = C − (O + 0 + 0) = نقد المبيعات المحصَّل بالضبط**، في **كل** وردية نقدية سليمة.

| الدليل | القياس |
|---|---|
| S02 (API، افتراضي) | بيع 20 لتر نقداً: E=200.00، C=246.00 ⇒ V=**+46.00**، `pending_review`، `approve`⇒422 |
| S08 (عدّادات فقط) | نفس الرقم؛ و`drawer.implied_sales_cash=46.00`، `declared_difference=0` ⇒ **النظام يعرف أن الدرج سليم** لكنه يصنّفه فرقاً |
| UI وردية 1 (حقيقي) | عهدة 500.00، معدود 546.00 ⇒ «زيادة 46.00» |
| UI وردية 2 (إقرار تحصيل مفعّل) | مبيعات العدّادات 69.00 = تحصيل 69.00 (فرق التحصيل 0، بلا مراجعة)، **ومع ذلك** نقد الدرج «زيادة 40.00» (= نقد الإقرار) |
| `s01` (مسار ERP + الأساس `receiving_shift_receipts`) | E=246.00، V=0 ✅ — **المعادلة صحيحة حين يمرّ البيع عبر ERP** |

الخلاصة: **المعادلة ليست «خاطئة»؛ مصدر نقد المبيعات فيها ناقص لمسار الجوال.** وثّقه العقد نفسه (§6 من عقد الإقرار: «قد يُظهر زيادة تساوي نقد المبيعات؛ فرق التقاطع يفسّره»). النتيجة العملية: كل وردية نقدية تحتاج مراجعة مشرف (`FUEL_CASH_VARIANCE_REVIEW_REQUIRED`) فتضيع إشارة العجز الحقيقي وسط ضوضاء ثابتة.

### 1.3 ما يملكه النظام اليوم لتصحيحه (بلا بيانات جديدة)

الفرق **الصحيح** محسوب أصلاً في `FuelShiftCollectionService::drawer`:
```
implied_sales_cash = C − O − I + U + X          (نقد المبيعات الذي يدلّ عليه الدرج)
cash_cross_difference = D_cash − implied_sales_cash      (D_cash = النقد المُقَرّ به في الإقرار)
```
و`cash_cross_difference ≡ −(C − (O + D_cash + I − U − X))`؛ أي هو **V مع E المصحَّح**. المطلوب إذن ليس معادلة جديدة بل **ربط بوابة المراجعة/الاعتماد بالفرق الصحيح** وعدم اختراع مصدر ثانٍ.

## 2. منع الاحتساب المزدوج — مصفوفة المصادر

أربعة مصادر قد تحمل «النقد نفسه» في وردية واحدة:

| المصدر | يمثّل | طبيعته |
|---|---|---|
| **R** | إيصالات `collectPayment` المختومة | رسمي (سند + قيد)، لكل بيع ERP |
| **D_cash** | النقد المُقَرّ به في إقرار التحصيل | **إجمالي الوردية** (بيع ERP + غير ERP)، تصريح البائع، تشغيلي |
| **I** (`cash_in`) | وارد من غير مبيعات الوقود | يدوي؛ إدخال نقد بيع هنا يضاعفه (خطر R1 الموثَّق) |
| **S_meter** | مبيعات العدّادات × السعر الفعّال | تقدير مستقل للنظام (لا تصريح بشري) |

**الحالات الخطرة:** `E = O + R + D_cash` يعدّ نقد مبيعات ERP مرتين (مرة R ومرة داخل D_cash).

**القاعدة المقترحة (ملزمة، لا جمع بين مصدرين):**
1. النقد المتوقع من **مصدر واحد بالأولوية**: **(أ)** إقرار التحصيل المجمَّد إن وُجد ← **(ب)** إيصالات R إن فُعّل الأساس ← **(ج)** الحركات فقط (السلوك الحالي).
2. D_cash **إجمالي** يضمّ R (جزء منه)، فلا يُضاف R إلى D_cash أبداً؛ يُستعمل R **تحقّقاً**: `D_cash ≥ R_cash` وإلا إشارة `declared_cash_below_recorded_receipts`.
3. `cash_in` يبقى «غير مبيعات» ولا يدخل D_cash؛ حارس واجهة/تحذير (لا كشف خادمي ممكن — R1).
4. الشبكة لا تدخل نقد الدرج في أي مصدر.

```
E_declared = O + D_cash + I − U − X          V = C − E_declared      (يعادل −cash_cross_difference)
```

**الضابطان المستقلان معاً (لا يُغني أحدهما عن الآخر):**
- **ضابط التصريح:** `D_total − S_meter` (يكشف إخفاء مبيعات: يقارن تصريح البائع بالعدّاد المستقل).
- **ضابط الدرج:** `V = C − E_declared` (يكشف نقداً ناقصاً بعد التصريح الصحيح).
بائع يصرّح بأقل ⇒ الضابط الأول؛ يصرّح صحيحاً ويأخذ النقد ⇒ الثاني. ولو كان E يعتمد على D فقط دون الضابط الأول لصار V=0 دائماً بإقرار ذاتي — لذلك الضابطان إلزاميان معاً.

### 2.1 الحواف (تُحسم قبل التنفيذ)
| الحالة | الاقتراح |
|---|---|
| بيع آجل (على الحساب) | مستبعد من الإقرار اليوم (`credit_sales_excluded`) فيظهر كعجز كاذب في ضابط التصريح؛ **يلزم سطر «آجل» في الإقرار أو خصم بيع ERP الآجل من S_meter** (قرار D-C) |
| تغيّر سعر أثناء الوردية | S_meter=`null` (سلوك آمن قائم)؛ ضابط التصريح غير نهائي، وضابط الدرج يعمل (لا يحتاج السعر) |
| تسليم للخزنة | داخل U (قائم)، بلا تغيير |
| وردية بلا إقرار | يبقى الأساس القائم كما هو (لا تغيير لمن لا يفعّل) |
| إقرار + إيصالات R | E من الإقرار فقط؛ R تحقّق (قاعدة 2) |
| الإقرار يُجمَّد عند الإغلاق | E_declared يُجمَّد في لقطة `fuel_shift_cash_variances` (حقل أساس جديد `declared_collection`) |

### 2.2 التنفيذ المقترح لـP1-2 (بعد الموافقة)
- **فصل «وسم الإيصالات» عن «مصدر النقد المتوقع» (إلزامي):** اليوم `FuelSaleService::collectPayment` يختم الإيصال بالوردية فقط حين `effectiveBasis === receiving_shift_receipts`. لو أُضيفت القيمة الجديدة دون تعديل هذا الشرط لما عاد يُختم أي إيصال ERP تحت `declared_collection`، فيختفي `R_m` من الوردية ويُرحَّله التسوية (§4) مرة ثانية عبر `U_m = D_m − R_m`. مثال: 23 حُصِّلت عبر ERP، بقية قيمتها 69، إقرار 50 ⇒ المطلوب سند 27 لا 50. لذلك تُفصل الدالتان: **أهلية ختم الإيصالات** = بوابة `shift_cash_receipts_enabled` مفتوحة **و** الأساس ∈ {`receiving_shift_receipts`، `declared_collection`}، بغضّ النظر عن المصدر الذي يغذّي E. ويُشترط للتسوية: لا إيصالات غير مختومة (`unattributed_cash_receipts`) في نافذة الوردية، وإلا تُحجب (`FUEL_SETTLEMENT_UNATTRIBUTED_RECEIPTS`) منعاً للترحيل المزدوج. **تبعية معلنة:** التسوية تتطلب فتح بوابة ختم الإيصالات (مغلقة اليوم بقرار المالك) — تُضاف لشروط التفعيل.
- قيمة ثالثة للسياسة القائمة `shift_expected_cash_basis` = `declared_collection` (سياسة تُضبط لا تُفرض؛ الافتراضي يبقى `movements_only` فلا يتغيّر مستأجر قائم).
- تغيير نقطة واحدة: `FuelShiftCashExpectationService::live` تقبل مصدر الإقرار؛ كل من `close` والحارس والعرض يستعملها (قاعدة «دالة مشتركة واحدة»، §2-4 من العقد).
- هجرة إضافية nullable (`documented_declared_cash_minor`) + اختبارات: V=0 للوردية السليمة، عجز/زيادة حقيقية تظهر، **عدم الاحتساب المزدوج** (إقرار + R)، تغيّر السعر، تسليم الخزنة، تحصيل مختلط.
- بوابة الاعتماد `FUEL_CASH_VARIANCE_REVIEW_REQUIRED` تعمل فقط حين V≠0 (تنتهي مراجعة كل وردية).
- نص واجهة البائع: «فرق غير نهائي/مطابق/عجز/زيادة» من V الجديد (لا «زيادة» لدرج سليم).

### 3.2 الصلة بين المسارين (لا يوجد ربط)
- `FuelShiftService` و`FuelShiftSalesCalculator` و`FuelShiftCollectionService` **لا تقرأ `fuel_sales` إطلاقاً** (grep مُثبَت). الربط الوحيد عرضي: `fuel_sales.fuel_shift_id` (اختياري) وختم الإيصال بالوردية.
- مدى العدّاد في البيع (`meter_start/end`) اختياري ولا يُقارن بعدّادات الوردية ولا يُمنع تداخله.
- **النتيجة:** محطة بالتطبيق وحده ⇒ خزان دفتري ثابت، إيراد صفر، لا فواتير. محطة تجمع المسارين ⇒ لا ما يمنع **ازدواج** نفس اللترات (تُدخل كبيع ERP وتبقى في العدّاد) ولا ما يكشف **الفجوة** سوى فرق التحصيل (S08b: 5 لتر غير موثّقة ⇒ −11.50 عجز تحصيل، دون أثر مخزني).

## 4. التصميم الموحَّد المقترح: «تسوية الوردية» (Shift Settlement)

### 4.1 المبدأ
**العدّاد هو الحقيقة المادية الوحيدة للكمية؛ وثائق ERP تثبّت جزءاً منها؛ والباقي يُرحَّل مرة واحدة بوثيقة تسوية عبر المسار المحاسبي نفسه.** لا مسار ترحيل ثانٍ: التسوية تستدعي `FuelSaleService` (فاتورة + COGS + مخزون + دفتر تشغيلي) و`PaymentService` (سندات) كما هي.

```
لكل فوهة في الوردية:
  M      = إغلاق − افتتاح                          (مل، من العدّادات)
  Q_erp  = Σ كميات FuelSale النهائية لهذه الفوهة والوردية
  Q_res  = M − Q_erp                               (البقية غير الموثَّقة؛ إن كان < 0 ⇒ بيع ERP يفوق العدّاد = شذوذ يمنع التسوية ويُحال للمشرف)
```

### 4.2 التدفق
1. **أثناء الوردية:** الجوال يسجل عدّادات/نقد/إقراراً (لا تغيير). وثائق ERP تبقى اختيارية (آجل/شركات/أسطول).
2. **الإغلاق:** يُجمَّد M وQ_erp وإقرار التحصيل D (قائم).
3. **الاعتماد (المشرف)** — نقطة الترحيل الوحيدة (بعد المراجعات): خدمة `FuelShiftSettlementService::settle(shift)` داخل معاملة الاعتماد وتحت قفل الوردية:
   - لكل فوهة Q_res>0: تنشئ `FuelSale` بنوع `shift_settlement` وتُنهيه عبر `FuelSaleService::finalize` (وضع تسوية يسمح بوردية مغلقة-غير-معتمدة) ⇒ فاتورة للعميل النقدي الافتراضي للمحطة + COGS + خصم مخزون + سطر دفتر.
   - المدفوعات من الإقرار: `U_m = D_m − R_m` لكل طريقة دفع (نقد/شبكة/…): سند `PaymentService` واحد لكل طريقة بمبلغ `U_m` (يدعم **الكاش والشبكة والمختلط** بنفس الآلية: سطر لكل طريقة)، والنقد يُختم بالوردية (يدخل R آلياً ⇒ E متّسق).
   - **التسعير مجمَّد وقت الإغلاق لا وقت الاعتماد (إلزامي):** `FuelSaleService::finalize` يحلّ السعر بـ`now()` (لحظة الإنهاء)، فتأخير الاعتماد بعد تغيّر السعر كان سيقيّم اللترات بسعر خاطئ ويصنع رصيداً مفتوحاً أو دفعاً زائداً مصطنعاً. لذلك تُضاف لـ`finalize` معاملة تسوية صريحة `pricing_snapshot` (`price_per_liter_minor`، `tax_mode`، `source`، لحظة السريان) تُؤخذ **من لقطة الإقرار المجمَّدة عند الإغلاق** (`fuel_shift_collection_declarations` تحفظ المنتج والسعر والنمط)، وتُستعمل بدل الحلّ الحيّ؛ وتاريخ الفاتورة/القيد = يوم تشغيل الوردية (بتقويم المحطة) لا يوم الاعتماد، ويمرّ بحارس الفترة المحاسبية.
   - **وردية بأكثر من سعر ⇒ تُحجب التسوية** برمز `FUEL_SETTLEMENT_PRICE_SPANS_SHIFT` (هي نفسها حالة `price_changed_during_shift` القائمة التي تجعل مبيعات العدّاد `null`): لا تُطبَّق «آخر سعر» ولا يُوزَّع بالتخمين؛ تُحلّ بإدخال بيع ERP لكل شريحة سعرية قبل الإغلاق (يُخصم من `Q_res`) أو بقرار مشرف صريح موثَّق لاحقاً (خارج الشريحة الأولى). الاعتماد نفسه لا يُحجب بل تبقى التسوية `pending_pricing` ظاهرة للمشرف.
   - **الفرق بين قيمة البقية والمُحصَّل:**
     - **عجز** (`Σ U_m < V_res_value`): تُسدَّد الفاتورة بقدر المُحصَّل وتبقى **مفتوحة جزئياً ظاهرة** (الافتراضي)، أو يُرحَّل الفرق لحساب «عجز النقد» إن فعّل المالك السياسة (قرار D-E).
     - **فائض** (`Σ U_m > V_res_value`): لا يُدفع للفاتورة أكثر من متبقّيها — `PaymentService` يرفض التخصيص الزائد. تُخصَّص المدفوعات بأولوية ثابتة (**الشبكة أولاً حتى سقف الفاتورة ثم النقد**) ويبقى لكل طريقة `Surplus_m = U_m − paid_m` **منسوباً إلى طريقته هي** لا إلى النقد: فائض من الشبكة يبقى فائضاً مصرفياً (لا يدخل الدرج)، وفائض نقدي يبقى في الدرج. الفاتورة تُغلق بحدّها، والفائض **غير مرحَّل** ومعلَّم «زيادة» بحسب الطريقة في المراجعة (الفرق مراجَع بالفعل بشرط الاعتماد). عند تفعيل السياسة (D-E) يُرحَّل كل فائض بحساب طريقته: نقد `Dr 1110`، شبكة `Dr 1120` (أو حساب تسوية الشبكة المعيَّن) مقابل `Cr` حساب «زيادة/غير مطابَق» يعيّنه المحاسب. **النقد المتوقع لا يتأثر** لأنه يُحسب من الإقرار D (يشمل فائض النقد) لا من سندات التسوية، وفائض الشبكة لا يدخله أصلاً.
4. **بعد الاعتماد:** الوردية مقفلة؛ لا إنهاء بيع ولا تحصيل عليها (حارس قائم).

**دفع مختلط** (100 لتر = 230.00: نقد 100.00 + شبكة 130.00): نفس الفاتورة، وسندان: `Dr 1110 100.00 / Cr 1130 100.00` و`Dr 1120 130.00 / Cr 1130 130.00`. **شبكة فقط:** `Dr 1120 / Cr 1130`. **عجز تحصيل 3.00** (صرّح 20.00 من 23.00): السند 20.00 والفاتورة تبقى 3.00 مفتوحة (الافتراضي) — أو قيد عجز إن فُعّلت السياسة. **فائض 1.00** (صرّح 24.00 من 23.00): السند 23.00 فقط والفاتورة تُغلق، والـ1.00 يبقى زيادة غير مرحَّلة **منسوبة إلى طريقتها** — شبكة فقط 24.00 ⇒ فائض 1.00 مصرفي (`Dr 1120` عند تفعيل السياسة)، ونقد فقط 24.00 ⇒ فائض 1.00 نقدي (`Dr 1110`)، ومختلط (شبكة 10 + نقد 14 من 23) ⇒ الشبكة 10 والنقد 13 والفائض 1.00 نقدي. لا قيد خارج `LedgerService::post`.

### 4.4 ضمانات عدم الازدواج (يحرسها الخادم والقاعدة)

| الخطر | الضمان |
|---|---|
| تسوية الوردية مرتين | فهرس فريد `(tenant, fuel_shift_id, fuel_nozzle_id)` لوثائق `shift_settlement` + مفتاح `shift-settle:{shift}:{nozzle}` + قفل الوردية + إعادة الاستدعاء تُعيد الأثر الأول |
| نفس اللترات كبيع ERP وكتسوية | التسوية تحسب `Q_res = M − Q_erp` بعد قفل الوردية؛ ERP يُمنع بعد الإغلاق (حارس قائم)؛ مدى العدّاد في البيع يُفرض عدم تداخله داخل الفوهة |
| تحصيل نقدي مضاعف (R + D) | قاعدة §2: E من مصدر واحد؛ مدفوعات التسوية = `D_m − R_m` لا D_m |
| فترة محاسبية مقفلة | تفشل التسوية قبل أي أثر (تراجع كامل)؛ الاعتماد يبقى معلَّقاً برمز `FUEL_SETTLEMENT_PERIOD_LOCKED` (لا تغيير تاريخ تلقائياً) |
| تأخر الاعتماد بعد تغيّر السعر | التسعير من لقطة الإقرار المجمَّدة عند الإغلاق (لا `now()`) ويُحجب التسوية عند أكثر من سعر في الوردية (`FUEL_SETTLEMENT_PRICE_SPANS_SHIFT`) |
| جمود الأقفال (وردية ↔ محطة، محطة ↔ خزان) | ترتيب ملزم **البيع/الوثيقة ← المحطة (`NO KEY UPDATE`) ← الفوهة ← الوردية**؛ التسوية تقفل المحطة قبل الوردية (تجربة PostgreSQL: العكس يُنتج 40P01) — انظر `AWJ_FUEL_LOCK_ORDER_FINALIZE_VS_TANK_READING.md` |
| تعديل بعد التسوية | لا تعديل؛ التصحيح بإشعار دائن/عكس عبر المسارات العامة (خارج النطاق الأول) |
| تسرب بين المستأجرين/الفروع | `BaseModel` + نطاق المحطة كما هو؛ بلا استعلام يدوي |

### 4.5 التكوين والنشر (سياسة تُضبط لا تُفرض)
- إعداد محطة `shift_sales_settlement_policy`: **`none` (الافتراضي = السلوك الحالي حرفياً)** · `post_on_approval`.
- بوابة نشر `FUEL_SHIFT_SETTLEMENT_ENABLED` (`false`)؛ مغلقة ⇒ لا تسوية ولا أثر. لا تُفتح لمستأجر دون قرار تفعيل منسّق.
- شروط مسبقة لكل محطة قبل التفعيل: عميل نقدي افتراضي، طرق الدفع المسموحة، سعر ساري، نمط ضريبة محدد، **سياسة النقد `declared_collection`** (P1-2).

## 7. المخاطر المعلنة
1. التصريح الذاتي D قد يتطابق مع المعدود دائماً ⇒ الضابط المستقل (D مقابل العدّاد) إلزامي، لا يُلغى.
2. البيع الآجل غير مُمثَّل في الإقرار اليوم (قرار D-C) وإلا يظهر عجز كاذب.
3. العميل النقدي الافتراضي يجمع مبيعات التجزئة في ذمة واحدة (يُسدَّد فوراً؛ المتبقي من العجز يلوّثها ما لم تُفعَّل سياسة D-E).
4. تأخر الاعتماد يترك الأرقام المحاسبية معلَّقة بين الإغلاق والاعتماد؛ التسعير المجمَّد وتاريخ يوم التشغيل يمنعان انحرافها، لكن فترة محاسبية قد تُقفل قبل الاعتماد (تفشل التسوية ولا يُغيَّر التاريخ تلقائياً).
5. الاعتماد يصبح نقطة ترحيل فيزداد حمله (معاملة أطول) ⇒ اختبار أداء/تزامن PostgreSQL.
