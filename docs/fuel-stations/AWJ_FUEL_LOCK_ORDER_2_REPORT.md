# FUEL-LOCK-ORDER-2 — توحيد ترتيب الأقفال بين مسارات المجمّع وERP

> **لا تغيير** في القيود المحاسبية ولا حركات المخزون ولا قواعد الصلاحيات. لا نشر ولا تعديل لبيانات dominah. PR مستقل عن #2070 (تسوية الورديات).

## 1. المشكلة (من تدقيق P1-3a)
ترتيب ERP الفعلي لإنهاء بيع الوقود (`InvoiceService::post`): **مِرساة المستأجر ← رصيد المخزن ← حالة التكلفة**. ثلاثة مسارات تعاكسه (تقفل المجمّع ثم تنتظر المِرساة عند القيد) فتتشابك مع بيع على **أي محطة تشترك في المجمّع (مخزن × منتج)** — وعلى المحطة نفسها لأنها لا تقفل المحطة:

| المسار | قبل | بعد |
|---|---|---|
| اعتماد استلام الوقود `FuelSupplyReceivingService::approveDelivery` | الاستلام ← حالة التكلفة ← رصيد/حالة المنتج ← **المِرساة** | الاستلام ← **المِرساة** ← حالة التكلفة ← الرصيد |
| اعتماد تسوية الخزان `FuelReconciliationService::approve` | التسوية ← المنتج ← الرصيد ← حالة التكلفة ← **المِرساة** | التسوية ← **المِرساة** ← المنتج ← الرصيد ← حالة التكلفة |
| الرصيد الافتتاحي `FuelOpeningBalanceService::post` | المستند ← المحطة ← حالة التكلفة ← … ← **المِرساة** | المستند ← المحطة ← **المِرساة** ← حالة التكلفة ← … |
| إنهاء بيع ERP `FuelSaleService::finalize` (المرجع) | المحطة ← الوردية ← … ← **المِرساة** ← الرصيد ← حالة التكلفة | **بلا تغيير** |

هذه الأربعة هي **كل** كتّاب حالة تكلفة الوقود (`grep costBasis->`)؛ وحركات مخزون الوقود تُحرس بـ`assertNotFuelPoolManaged` فلا كاتب خامس.

## 2. الإصلاح (صغير ومحصور)
- `AccountingDateGuard::lockLedgerAnchor()`: يأخذ **صف المستأجر `FOR UPDATE` نفسه** الذي يأخذه `LedgerService::post` لاحقاً (`lockAnchor` الخاص). إعادة أخذه داخل المعاملة نفسها لا أثر لها، فلا يتغيّر القيد ولا مبلغه ولا توقيته.
- يُستدعى في المسارات الثلاثة **قبل أي قفل مجمّع** وبعد فحوص القراءة البحتة. بما أن كل كاتب مجمّع صار يأخذ المِرساة أولاً (وERP يأخذها قبل المجمّع)، تتسلسل الكاتبات عندها فلا ترتيب داخلي متعاكس ممكن (حالة التكلفة/الرصيد/المنتج).
- لا تعديل لـ`FuelSaleService` ولا `InvoiceService` ولا `LedgerService` ولا الصلاحيات.
- **الأثر على الأداء:** تمسك المسارات الثلاثة صف المستأجر مدة أطول قليلاً (من بداية مرحلة المجمّع لا من القيد). هي عمليات إدارية نادرة (اعتماد استلام/جرد/رصيد افتتاحي) وERP يمسكه أصلاً طوال إنهاء البيع؛ ولا قراءة تتأثر (قفل صف لا قراءات).

## 3. الأدلة (PostgreSQL 16)
`FuelLockOrder2PostgresTest` (5 اختبارات) + `FuelLockOrder2StaticTest` (4، تعمل على SQLite أيضاً):

| الاختبار | ما يثبته |
|---|---|
| استنساخ الدورة القديمة | جلستا `psql` بالترتيبين المتعاكسين ⇒ `deadlock detected` (يثبت أن الأدوات تلتقط الدورة) |
| اعتماد الاستلام / اعتماد تسوية الخزان / ترحيل الافتتاحي (3 اختبارات حتمية) | جلسة `psql` تحاكي ترتيب ERP (مِرساة ← نوم ← رصيد ← حالة التكلفة) والمسار **الحقيقي** يعمل بينها: ينتظر المِرساة (>0.6 ث) ثم يكتمل، والمحاكاة لا تكون ضحية جمود |
| تزاحم فعلي (8 جولات، 3 عمليات حقيقية معاً بترتيب متبدّل) | إنهاء بيع ERP + اعتماد استلام + اعتماد تسوية خزان على المجمّع نفسه ⇒ كلها تكتمل؛ الدفتر التشغيلي = الرصيد الرسمي = كمية حالة التكلفة؛ قيود ≥ 3 لكل جولة |
| حارس ساكن | المِرساة تسبق أول قفل مجمّع في المصدر لكل مسار، وطريقة الحارس هي نفس قفل `lockAnchor` |

**قبل الإصلاح (الاختبارات نفسها على الكود القديم، موثَّق):** الاختبارات الأربعة الحقيقية الفاشلة — الثلاثة الحتمية (`ERROR: deadlock detected` في جلسة ERP المحاكاة) **والتزاحم الفعلي بالكود الحقيقي: `DeadlockException SQLSTATE[40P01]`** — ثم **كلها خضراء بعد الإصلاح**. أي أن الجمود حدث في الكود الإنتاجي نفسه لا بالمحاكاة وحدها.

اختبارات الوقود الأخرى على الاستلام والرصيد الافتتاحي والتسوية وأقفال البيع والإقرار والتحصيل (SQLite وPostgreSQL) تمرّ دون تعديل (انظر وصف الـPR).

## 4. أثره على تسوية الورديات (#2070 / P1-3b)
تصميم التسوية (§4.2) يتبع ترتيب ERP: المحطة ← الوردية ← فواتير ERP ← **المِرساة** ← المجمّع. بهذا الإصلاح صار الترتيب نفسه عبر كل كتّاب المجمّع، فلا تعارض متوارث. وشرط القبول المتبقي في P1-3b (إغلاق بتسوية مقابل `finalize` ERP على محطة تشاركه المجمّع) صار قابلاً للكتابة بالأدوات نفسها.

## 5. حدود معلنة
- لم تُراجَع مسارات POS/المخزون العام لأنها لا تكتب حالة تكلفة الوقود (محروسة).
- ترتيب الأقفال **الداخلي** بين المنتج والرصيد وحالة التكلفة داخل المسار الواحد لم يُوحَّد (غير لازم بعد أن تسلسلت الكاتبات عند المِرساة).
- التراجع: حذف استدعاءات `lockLedgerAnchor()` الثلاثة والدالة؛ لا مخطط ولا بيانات.
