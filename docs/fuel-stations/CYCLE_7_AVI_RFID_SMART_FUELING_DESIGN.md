# Cycle 7 — AVI / RFID Smart Fueling Design

**الحالة:** قيد التنفيذ على فرع `fuel-stations-cycle-7-avi-rfid`، المبني من `main` عند `8b737d452d93c60cffc04db7ec51f7bcf07fd585`.

## القرار المعماري

> **هوية الوسم ليست بطاقة وقود، وتفويض AVI/RFID ليس دفعة ولا فاتورة ولا أمراً لمضخة.**

تبني هذه الدورة طبقة محايدة عن المورد تفصل بين: **الوسم أو وسيلة الهوية**، ثم **قرار التفويض الصريح القابل للتدقيق**، ثم **إعادة استخدام** الفحص التجاري الموجود في Cycle 6، ثم مسار البيع الرسمي في Cycle 5. لذلك يبقى المسار المحاسبي والتشغيلي النهائي كما هو:

```text
Identity / Tag
→ AVI/RFID authorization decision
→ Corporate contract / fuel card / vehicle / driver checks
→ station / fuel / limits
→ FuelSale
→ InvoiceService
→ PaymentService
```

لا تستقبل هذه الدورة payload قارئ RFID أو تتصل بمضخة أو controller أو ATG أو terminal، ولا تنشئ adapter أو driver أو credential لجهاز فعلي. يبقى إدخال الأحداث من جهاز وربط vendor-specific من نطاق Cycle 8، مع بقاء نتائج Cycle 7 صالحة ليستهلكها ذلك الإدخال لاحقاً.

## ما يعاد استخدامه ولا يعاد بناؤه

| العقد القائم | استخدام Cycle 7 |
|---|---|
| `FuelSaleService` | يظل المالك الوحيد لمسودة البيع وإنهائه وتسلسل الفاتورة/المخزون/COGS. |
| `CorporateFuelAuthorizationService` | يظل المصدر الوحيد لفحص العقد والسعر والبطاقة والمنشأة والسائق والعداد والائتمان وحدود البطاقة. |
| `InvoiceService` و`PaymentService` و`LedgerService` | لا تستدعيها طبقة AVI/RFID ولا تنشئ مساراً مالياً موازياً. |
| `FuelStationSettingsService` | يظل نقطة القرار الوحيدة لسياسات المحطة والمستأجر والتدقيق. |

## نموذج المجال المقترح

### 1. وسيلة هوية ذكية: `FuelAviIdentityTag`

وسم مؤسسي مشترك `CompanyWide`، لا يختزن قيمة RFID أو البطاقة الذكية أو PIN أو QR الخام. يخزن فقط:

| الحقل/السلوك | القرار |
|---|---|
| `public_identifier` | اسم إداري مرئي وفريد داخل المستأجر. |
| `credential_hash` | `sha256` للقيمة التي قُدمت عند القراءة؛ فريد داخل المستأجر ولا يخرج في Resource أو audit. |
| `identity_type` | `vehicle_rfid` أو `driver_card` أو `qr` أو `pin`، مع عدم افتراض مورد أو بروتوكول. |
| الربط | الوسم يربط إما مركبة أو سائقاً بحسب نوع الهوية، ومعه العميل والعقد والبطاقة المنطقية اختيارياً. |
| الحالة | `active`, `suspended`, `lost`, `blacklisted`, `expired`, `cancelled`, `replaced`؛ لا حذف حفاظاً على الأثر. |
| التاريخ | نطاق فعالية واستبدال موثق، مع منع تعديل credential أو العميل أو العقد أو هدف الهوية على الوسم القائم. |
| العزل | `BaseModel implements CompanyWide`؛ كل lookup يمر عبر `TenantScope`. |

تتحقق الخدمة عند الإنشاء والاستبدال من أن العميل والعقد صالحان ضمن المستأجر، وأن المركبة أو السائق يخص العميل/العقد عند وجود ربط، وأن النوع يطابق الهدف. تمنع فهارس `(tenant_id, credential_hash)` و`(tenant_id, public_identifier)` تكرار الوسم في المؤسسة، وتمنع الخدمة التكرار أو الازدواج بين مستأجرين من دون تخزين السر الخام.

### 2. سجل قرار التفويض: `FuelAviAuthorization`

قرار تشغيلي `BranchScoped` append-only يمثل محاولة تفويض قبل أي بيع رسمي. يسجل المحطة والفرع والفوهة والمنتج والكمية المطلوبة، الوسوم التي حُلّت، العميل/العقد/البطاقة/المركبة/السائق الناتجة، نتيجة `approved` أو `denied`، رمز السبب الصريح، إشارات الاشتباه الآمنة، correlation/idempotency key، ووقت القرار وانتهاء صلاحيته.

القرار ليس فاتورة ولا حركة مخزون ولا استخدام بطاقة ولا قيد. يظل قرار الرفض محفوظاً بدلاً من فقدانه داخل استثناء HTTP، ويعيد طلب idempotency نفسه القرار السابق عندما تتطابق حمولة الطلب. يحظر حذف السجل أو تعديل النتيجة؛ ويرتبط `FuelSale` المقبول به عبر مفتاح فريد حتى لا يستعمل قرار واحد لإنشاء أكثر من بيع.

## محرك التفويض

تضيف `FuelAviAuthorizationService` مرحلتين منفصلتين:

1. **`authorize()`** يحل القيم الخام المقدمة إلى وسوم hash فقط، ويتحقق من حالة الوسم وفعاليته، وعدم التكرار، وتطابق هوية المركبة/السائق والعقد والعميل والبطاقة. ثم يستدعي منطق Cycle 6 القائم للتحقق من العقد والمركبة والسائق والعداد والمحطة والوقود والبطاقة. كما يتحقق من السعة المنطقية للخزان إن فُعلت السياسة، ومن أقل مهلة بين التزويد، ومن محاولات الرفض المتكررة. يعيد دائماً نتيجة صريحة آمنة للاستهلاك؛ لا تعني الموافقة بيعاً أو تحصيلاً.
2. **`assertUsableForSale()` و`assertFinalizationAllowed()`** يربطان القرار الموافق بمسودة مطابقة للمحطة/الفوهة/الكمية ويعيدان التحقق من صلاحية الوسوم وانتهاء التفويض قبل إنشاء الأثر الرسمي. بعد ذلك فقط يستدعى `CorporateFuelAuthorizationService` في `FuelSaleService::finalize()` كما هو، كي تبقى حدود الائتمان والاستخدام الحسابي محكومة بمعاملة الإنهاء الرسمية.

لا تحفظ رسالة الرفض credential أو hash أو أي قيمة قراءة خام. تكون الأسباب رموزاً مستقرة مثل `AVI_TAG_NOT_FOUND` و`AVI_TAG_NOT_ACTIVE` و`AVI_IDENTITY_MISMATCH` و`AVI_DUAL_IDENTITY_REQUIRED` و`AVI_REFILL_INTERVAL_RESTRICTED` و`AVI_VEHICLE_CAPACITY_EXCEEDED` و`AVI_REPEATED_DENIAL_PATTERN`، إضافة إلى أسباب Cycle 6 التجارية القائمة عند انطباقها.

## السياسات والإشارات

تضاف مفاتيح سياسات واضحة في `Settings::DEFAULTS['fuel_stations']` وتقرأ حصراً من `FuelStationSettingsService`، مع audit عند تعديل المستأجر أو المحطة ومنع override على مستوى جهاز لا يوجد له عقد جهاز بعد:

| المفتاح | الدلالة | الافتراض الحامي |
|---|---|---|
| `avi_rfid_enabled` | فتح طبقة الهوية والتفويض للمحطة/المستأجر | `false` حتى لا يتغير مسار البيع القائم. |
| `avi_driver_identity_required` | طلب وسيلة هوية سائق إضافية مع وسيلة المركبة | `false`؛ يبقى العقد قادراً على فرض السائق عبر سياسة Cycle 6. |
| `avi_min_refill_interval_seconds` | أقل مهلة بين تفويضين مقبولين للمركبة | `0` لتعطيل الحد صراحةً. |
| `avi_enforce_vehicle_tank_capacity` | منع كمية تتجاوز سعة المركبة المعروفة | `true` لأن تجاوز السعة طلب غير معقول وليس خيار تسعير. |
| `avi_denial_window_seconds` | نافذة اكتشاف رفضات متكررة | `900`. |
| `avi_repeated_denial_threshold` | عدد الرفضات الذي يوسم المحاولة بالاشتباه | `3`. |
| `avi_authorization_ttl_seconds` | زمن صلاحية قرار الموافقة قبل ربطه أو إنهائه | `120`. |

إشارات الاشتباه محفوظة في قرار التفويض، لا تغير النتيجة المحاسبية ولا تتصل بجهاز. تشمل: معرف مكرر (يحاربه الفهرس أيضاً)، وقود غير مسموح، إعادة تعبئة مبكرة، كمية فوق السعة، عداد مشبوه عبر فحص Cycle 6، استخدام محطة مشبوه خارج العقد، ونمط رفض متكرر.

## API والصلاحيات والاستحقاق

تستعمل دورة 7 القدرة التقنية `fuel_stations.avi` بعد تحويلها إلى `built`، مع الاعتماد على `fuel_stations.core`. لا تُنشأ حالة تجارية أو entitlement أو تفعيل لمستأجر إنتاجي. يبقى إصدار المنتج التجاري المنشور immutable؛ إعداد وإصدار نسخة تجارية جديدة تضم `core + avi` ومنحها لاحقاً قرار منصة صريح خارج هذا التغيير.

| السطح | الحماية | الغرض |
|---|---|---|
| إدارة الوسوم | `fuel.avi.view` / `fuel.avi.manage` + `fuel_stations.avi` | قائمة/إنشاء/تعديل حالة/استبدال، من دون credential خام في الاستجابة. |
| قرارات التفويض | `fuel.avi.authorize` + `fuel_stations.avi` | إنشاء قرار صريح من هوية المركبة والسائق، وإرجاع السبب أو الموافقة. |
| تاريخ القرارات | `fuel.avi.view` + `fuel_stations.avi` | رؤية قرارات المحطة المخولة فقط. |
| إنشاء المسودة من قرار | صلاحية البيع القائمة + `fuel_stations.core`، مع تحقق داخلي من قرار AVI إذا مُرّر مرجعه | لا يسمح للطلب بتبديل العميل أو العقد أو المركبة المشتقة من القرار. |

لا يُدخل أي route قارئاً أو مصدر جهاز أو secret. تضاف فقط مفردات أحداث مستقبلية `vehicle.identified` و`fuel.authorization.approved` و`fuel.authorization.denied` إلى العقد المعياري، من دون adapter أو producer خارجي في هذه الدورة.

## واجهة المستخدم

تضاف شاشة عربية RTL لمساحة العمل عند `/fuel-stations/avi-rfid`، محمية بحالة الاستحقاق والصلاحيات ولا تظهر كملاحة مكسورة. تستخدم DataTable لإدارة الوسوم وسجل القرارات، وحواراً لإصدار أو استبدال وسم، وحالات تحميل/فراغ/خطأ وصلاحية واضحة. لا تعرض القيم الخام للوسم أو hash مطلقاً. يظل إدخال بيع Cycle 5 منفصلاً، مع دعم اختيار مرجع قرار AVI/RFID الموافق بدلاً من جعل الصفحة تدّعي فتح مضخة.

## التحقق المطلوب

يشمل التنفيذ اختبارات خدمة وAPI لعزل المستأجر والفرع، صلاحيات العرض/الإدارة/التفويض، تكرار hash، حالة blacklist/suspension، تطابق عقد/عميل/مركبة/سائق، فرض الهوية الثنائية، حدود السعة والفاصل الزمني ونمط الرفض، idempotency، صلاحية القرار وربطه الأحادي بـFuelSale، استمرار دورة invoice/inventory/COGS بلا مسار موازٍ، وحراس الكتالوج والترجمة. تظل اختبارات SQLite وPostgreSQL ومجموعة الواجهة والبناء الكاملة شرطاً قبل طلب الدمج.
