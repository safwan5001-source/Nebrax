# الجزء ب — بوابات الدقة المالية

## ب-1) لماذا (الحادثة)

اختبار باشت أظهر خطأً في عرض إجماليات كشف حساب **مورد** مع أن بيانات الـAPI صحيحة. **النتائج الميدانية المُبلَّغ بها مسجّلة في ب-7**، وهي تُظهر خطأ **مقياس** (1900 بدل 19000 ريال) لا خطأ إشارة. فحص الكود يبيّن ثلاث فجوات في **العقد** (لا في المحاسبة) تجعل خطأ كهذا ممكناً، وتبقى فجوة الاتجاه خطراً كامناً للأرصدة غير الصفرية:

| الفجوة | الدليل | الأثر المحتمل |
|---|---|---|
| لا إجماليات ولا عدد حركات في الاستجابة | `PublicPartnerStatementController::show` يعيد `rows` + رصيدين فقط | الوكيل يجمع الأعمدة بنفسه (حساب لغوي) |
| اتجاه الرصيد غير معلن | الرصيد الجاري = `debit − credit` لكل الأدوار (`ReportService::partnerStatement`)؛ موجب = الطرف مدين لنا | رصيد المورد **سالب** عندما نحن المدينون؛ واجهة أَوْج تعرضه **مطلقاً** (`displayBalance` مع `creditBalance`) → اختلاف بين شاشة أَوْج وما يقوله الوكيل |
| لا نص عرض جاهز | الاستجابة أعداد صحيحة بالهللات فقط | الوكيل يحوّل ويقرّب بنفسه (÷100، فاصلة، إشارة) |

> **مثال (مورد):** شراء 1,150.00 ر.س ثم دفع 500.00:
> الصف 1: `debit=0 credit=115000 balance=-115000` — الصف 2: `debit=50000 credit=0 balance=-65000`.
> الإجماليات الصحيحة: مدين 50000، دائن 115000، صافي −65000، الرصيد الختامي −65000 ⇒ **نحن مدينون للمورد بـ650.00 ر.س** (مستحق). وكيل يجمع عمود الرصيد، أو يقرأ −65000 "رصيداً للمورد لدينا"، أو يخلط مدين/دائن، سيعرض رقماً مختلفاً عن الشاشة.

**المبدأ:** الخادم يحسب ويتحقق ويُنسّق؛ الوكيل **يقتبس** ولا يحسب.

## ب-2) المواصفة: الغلاف المتحقَّق (Verified Report Envelope) — إضافي لا كاسر

يُضاف إلى كشف الحساب أولاً ثم يُعمَّم على كل تقرير (`financials:read`/`reports:read`). كل الحقول **إضافية**؛ الحقول الحالية (`opening_balance_minor`, `rows`, `closing_balance_minor`…) تبقى حرفياً.

```jsonc
{
  "data": {
    "partner": {...}, "currency": "SAR", "from": "2026-01-01", "to": "2026-03-31",
    "opening_balance_minor": 0,
    "rows": [ { "date":"…","number":"…","description":"…","debit_minor":0,"credit_minor":115000,"balance_minor":-115000,"source":{...} } ],
    "closing_balance_minor": -65000,

    "role": "supplier",                              // الدور المطلوب (أو null = كل الأدوار)
    "balance_convention": {                          // يُعلَن دائماً — لا افتراض
      "formula": "debit_minus_credit",
      "positive_means": "partner_owes_us",
      "negative_means": "we_owe_partner"
    },
    "totals": {                                      // من الخادم، بحساب صحيح
      "row_count": 2,
      "debit_minor": 50000,
      "credit_minor": 115000,
      "net_minor": -65000                            // debit − credit
    },
    "position": {                                    // الاتجاه بلغة الأعمال
      "opening": { "side": "settled",  "amount_minor": 0 },
      "closing": { "side": "payable",  "amount_minor": 65000 }   // payable | receivable | settled
    },
    "display": {                                     // نصوص جاهزة — الوكيل ينقلها حرفياً
      "currency": "SAR", "minor_unit_exponent": 2,
      "opening": "0.00", "debit": "500.00", "credit": "1150.00",
      "net": "-650.00", "closing": "650.00", "closing_side": "payable"
    },
    "completeness": { "complete": true, "page": 1, "has_more": false, "truncated": false },
    "integrity": {
      "status": "verified",                          // verified | failed
      "checks": [
        { "id": "running_balance_chain",        "passed": true },
        { "id": "closing_equals_opening_plus_net", "passed": true },
        { "id": "row_count_matches_rows",       "passed": true },
        { "id": "minor_units_are_integers",     "passed": true },
        { "id": "role_filter_applied",          "passed": true }
      ],
      "data_checksum": "sha256:…"                    // على JSON قانوني للصفوف + الأرصدة
    },
    "report_status": "final",                        // final | partial | unverified
    "as_of": "2026-04-01T08:00:00Z"
  }
}
```

**قواعد الحساب (إلزامية في الخادم):**
1. كل المبالغ `int` (PHP int64)؛ الجمع بأعداد صحيحة؛ التنسيق بـ`App\Support\Money::toRiyal` (`intdiv`/`%`) — لا `float` ولا `number_format` على عدد عشري ولا `round`.
2. `display.*` يُشتق من `*_minor` **بعد** التحقق بصيغة `Money::toRiyal` حرفياً (بلا فاصل آلاف، نقطة عشرية، أرقام 0–9 فقط، إشارة `-` للسالب). أي تجميع آلاف يُضاف لاحقاً في الخادم بأعداد صحيحة لا في الوكيل.
3. `position.side`: `net<0 ⇒ payable` (نحن مدينون)، `net>0 ⇒ receivable`، `0 ⇒ settled` — لكن **حسب الرصيد الختامي لا الدور**: عميل برصيد دائن يظهر `payable` مع تنبيه `opposite_sign=true`.
4. `minor_unit_exponent`: يُحسم قبل بدء AIA-0.1 (**D-12 شرط بدء**): `tenants.currency` عمود `string(3)` و`UpdateCompanyRequest` يقبل أي 3 خانات، و`Money::toRiyal` يقسم على 100 دائماً. الخياران: (أ) تقييد الغلاف لمنزلتين وفشل مغلق لغيرها، (ب) جدول ISO-4217 مدمج. لا يُنفَّذ أيٌّ منهما قبل قرارك.
5. حدّ الدقة: `|minor| ≤ 2^53−1` (JS `Number.MAX_SAFE_INTEGER`)؛ أكبر من ذلك ⇒ `integrity.failed` (وكيل JS سيفقد الدقة). يمكن إضافة `*_minor_str` لاحقاً.

## ب-3) فحوص السلامة (تُنفَّذ في الخادم قبل الاستجابة)

| المعرّف | الفحص | يفشل عند |
|---|---|---|
| `running_balance_chain` | `balance[0] = opening + (debit[0]−credit[0])` و`balance[i] = balance[i−1] + (debit[i]−credit[i])` | أي كسر في السلسلة |
| `closing_equals_opening_plus_net` | `closing = opening + Σdebit − Σcredit` | اختلاف |
| `row_count_matches_rows` | `totals.row_count = count(rows)` ويطابق `count` المُرسَل عبر الصفحات | اختلاف/اقتطاع |
| `minor_units_are_integers` | كل `*_minor` عدد صحيح في النطاق الآمن | كسر/تجاوز |
| `role_filter_applied` | الدور المطلوب مطابق لما طُبِّق؛ لا تسرّب سطور دور آخر | اختلاف |
| `page_chain` (مع الترقيم) | `page_opening = previous.page_closing` وآخر صفحة `closing = closing_balance` | كسر بين الصفحات |
| `report_total_ties` (لتقارير أخرى) | ميزان: Σمدين=Σدائن؛ ميزانية: أصول = خصوم + ملكية + صافي الدخل؛ دخل: صافي = إيراد − مصروف؛ أعمار: Σشرائح = الإجمالي؛ مركز ذمم = Σ الأرصدة | عدم تطابق |

**السلوك عند الفشل:** إن فشل فحص **اشتقاقي من الخادم** (خطأ برمجي) ⇒ `500 report_integrity_failed` برقم طلب، **بلا بيانات** (فشل مغلق، لا تقرير جزئي مضلّل). الحالات المتوقعة (تجاوز السقف) تبقى `422`.

## ب-4) الترقيم والنتائج الجزئية

اليوم: غير مرقَّم، سقف 2000 حركة ⇒ `422` (لا اقتطاع صامت) — **سلوك جيد يُحفظ**.
المقترح (D-02، اختياري صراحةً `?cursor=`):

- `?limit=` (≤ 500) و`?cursor=`؛ كل صفحة تحمل `page_opening_balance_minor` و`page_closing_balance_minor` و`has_more` و`next_cursor`.
- `totals` الكلية للكشف (كل الصفحات) تُحسب في الخادم وتأتي في **كل** صفحة، و`integrity.page_chain` يربط الصفحات.
- `report_status = final` فقط حين `complete=true` (آخر صفحة وصلت) **وكل** الفحوص ناجحة. صفحة وسطى ⇒ `partial`.
- المؤشر مربوط بلقطة (آخر `entry_id` + `as_of`)؛ قيد جديد أثناء التصفح لا يغيّر الصفحات السابقة (أو ينتهي المؤشر `409 cursor_stale`).
- الوكيل ملزم بعرض كلمة "جزئي" لأي مخرج `partial`/`unverified`، ويمنع وسم "نهائي".

## ب-5) على جانب الوكيل (حتمي لا لغوي)

1. **الأساسي:** نقل `display.*` و`position` و`integrity` كما هي. ممنوع حساب أو تقريب أو إعادة ترتيب.
2. **ثانوي:** مُتحقِّق غير متصل (BigInt) في `docs/integrations/basht/scripts/verify-envelope.mjs` يعيد فحص الغلاف (الجمع، السلسلة، العدد، النص مقابل الهللات). **قدرة الوكيل على تشغيله غير متحقَّق منها** — لذلك الأساس هو الخادم.
3. المهارة (v2): تمنع كلمة "نهائي" بلا `report_status=final`؛ تعرض الاتجاه (`payable/receivable`)؛ تذكر عدد الحركات؛ عند `422` تطلب تضييق الفترة؛ تعرض `as_of`.
4. التصدير يقرأ من الغلاف نفسه ويضيف سطر/ورقة تحقق (عدد، إجماليات، بصمة).

## ب-6) مصفوفة الاختبارات الآلية (يجب أن تُكتب قبل كل تعميم)

**وحدة (Unit)** — `MinorUnits/Money`:
| الحالة | المتوقع |
|---|---|
| 0، 1، 9، 10، 99، 100، 101، 123456789 | `0.00`, `0.01`, `0.09`, `0.10`, `0.99`, `1.00`, `1.01`, `1234567.89` |
| سالب: −1، −99، −100، −65000 | `-0.01`, `-0.99`, `-1.00`, `-650.00` |
| `PHP_INT_MAX` وما فوق 2^53 | فشل سلامة صريح (لا تقريب) |
| إدخال عشري (115.00 مكان 11500) | رفض `minor_units_are_integers` |
| عملة بمنازل ≠ 2 | فشل مغلق (خيار أ) أو تنسيق صحيح لكل منزلة (خيار ب) — بحسب قرار D-12 |

**ميزات (Feature)** — `PublicApiStatementIntegrityTest`:
- كشف مورد: المثال أعلاه ⇒ `net=-65000`, `position.closing=payable 65000`, `display.closing="650.00"`, و`report_status=final`.
- كشف عميل: إشارة موجبة ⇒ `receivable`.
- طرف ثنائي الدور: كل دور بمفرده يطابق مجموع القيود المنسوبة له؛ جمع الدورين = الكشف بلا دور (حيث ينطبق).
- رصيد افتتاحي بفلتر `from`: `opening` = مجموع ما قبل `from`؛ `closing = opening + net`.
- فلتر `to`: ما بعد `to` مستبعد من الصفوف والإجماليات والرصيد الختامي.
- كشف فارغ: `row_count=0`, `settled`, `report_status=final`.
- حدود السقف: 2000 ✔، 2001 ⇒ `422` بلا بيانات جزئية.
- ترقيم: صفحات متعددة ⇒ سلسلة الصفحات متصلة؛ مجموع صفحات الإجماليات = الكلي؛ قيد جديد بين الطلبين لا يكسر؛ مؤشر منتهٍ ⇒ 409.
- **حقن عدم اتساق (اختبار سلبي):** عبر Fake/Spy لـ`ReportService` يعيد صفوفاً بسلسلة مكسورة أو `closing` خاطئ ⇒ استجابة `500 report_integrity_failed` وليس `200`.
- **اختلاف الوحدات:** مدخل مختلط (ريال/هللة) في أداة الوكيل ⇒ رفض.
- عزل مستأجر: طرف مستأجر آخر ⇒ 404؛ مجاميع لا تتسرب.
- بوابة scopes: بلا `statements:read` ⇒ 403.

**تصدير** — `PublicApiExportIntegrityTest`:
- CSV/XLSX: إجماليات الملف = إجماليات JSON بالهللة؛ عدد الصفوف يطابق `row_count`؛ ورقة `Verification` تحمل البصمة نفسها.
- PDF (عند وجوده): استخراج النص بـ`pdftotext` ⇒ الإجماليات المعروضة = `display.*`.
- حقن صيغ: خلية `=HYPERLINK(...)` في وصف قيد ⇒ تُحيَّد.
- مسودة ⇒ علامة "مسودة" ولا `final`.

**عقد (Contract):** `PublicApiOpenApiContractTest` يغطي الحقول الجديدة؛ اختبار انجراف يضمن أن الحقول القديمة لم تتغير.

**مقارنة مع الواجهة:** اختبار يقارن `display.closing` لكشف مورد بنص شاشة أَوْج (`displayBalance` مع `creditBalance`) عند البيانات نفسها.

## ب-7) نتائج اختبار باشت الميداني — **مُبلَّغ بها، وليست تحققاً مستقلاً**

> **مصدر الأدلة:** أبلغ المالك بهذه النتائج عن تنفيذ باشت. لم أنفّذ أي استدعاء مصادَق، ولم أتحقق من قاعدة البيانات ولا من واجهة أَوْج، ولم أرَ ناتج الوكيل الخام. تُعامل كمدخل لحالات اختبار، لا كدليل محاسبي.

| البند | القيمة المُبلَّغ بها |
|---|---|
| الطرف | مورد: «شركة نجم المناجم» |
| الفترة | `2026-01-01` إلى `2026-11-06` |
| الاستجابة | HTTP 200 |
| عدد الحركات | 6 |
| المبالغ بالهللات | 586086 و608511 و705403 — **كل مبلغ يظهر مرة مديناً ومرة دائناً** |
| مجموع المدين | 1,900,000 هللة |
| مجموع الدائن | 1,900,000 هللة |
| الرصيد الافتتاحي / الختامي | 0 / 0 |
| خطأ العرض الأول | **1,900 ريال بدل 19,000 ريال** |

**مطابقة حسابية (أجريتُها أنا على الأرقام المُبلَّغة فقط):**

| فحص | الحساب | النتيجة |
|---|---|---|
| مجموع المبالغ الثلاثة | 586086 + 608511 + 705403 | **1,900,000** ✔ (يطابق المُبلَّغ) |
| مجموع المدين = مجموع الدائن | كل مبلغ مرة في كل جهة ⇒ 1,900,000 = 1,900,000 | ✔ صافي 0 |
| الرصيد الختامي | افتتاحي 0 + صافي 0 | 0 ✔ (يطابق المُبلَّغ) |
| التحويل الصحيح | 1,900,000 ÷ 100 | **19,000.00 ر.س** (`Money::toRiyal` ⇒ `"19000.00"`) |
| العرض الخاطئ | 1,900 | = 1,900,000 ÷ **1000** (أو سقوط خانة) — **انحراف بعامل 10** |

**التفسير (حدوده):**
1. الأرقام الخام في الاستجابة **متسقة داخلياً** (الجمع والرصيد صحيحان)، فالخطأ **بعد** الـAPI: تحويل/عرض الوكيل. هذا يؤيد المبدأ «الخادم يحسب وينسّق والوكيل يقتبس».
2. الخطأ **عامل مقياس 10 لا إشارة**. لذلك فرضيتي السابقة (أن سبب الحادثة فرق إشارة رصيد المورد عن شاشة أَوْج) **غير مدعومة بهذه الحالة** — الأرصدة كلها صفر والإجماليات موجبة. تبقى فجوة اتجاه الرصيد (ب-1) مخاطرة حقيقية لكشوف غير صفرية، لكنها **ليست** مثبتة كسبب هذه الحادثة.
3. **السبب الجذري الدقيق داخل الوكيل غير معروف** (÷1000؟ اقتطاع؟ تنسيق؟). لا أدّعي أكثر من «انحراف بعامل 10 بعد الـAPI».
4. ملاحظة: `to=2026-11-06` بعد تاريخ هذه الجلسة بيوم؛ قد يكون فرق منطقة زمنية أو اختيار الوكيل. لا أثر على الحساب، لكن حقل `as_of` المقترح يحسمه.
5. نمط «كل مبلغ مرة مديناً ومرة دائناً» يوحي بمستند وعكسه أو بمستند وتسوية كاملة؛ **لم أتحقق** من الأصل (فاتورة شراء + دفع؟ إشعار؟). لا يُبنى عليه استنتاج محاسبي.
