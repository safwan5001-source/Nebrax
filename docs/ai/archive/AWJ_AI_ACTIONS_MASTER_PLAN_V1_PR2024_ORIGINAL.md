# AWJ AI Actions — الخطة الرئيسية المعتمدة للتنفيذ التدريجي

**المشروع:** أَوْج | AWJ ERP  
**نوع المستند:** Master Plan / Architecture & Delivery Roadmap  
**الإصدار:** 1.0  
**التاريخ:** 2026-11-05  
**الحالة:** خطة مستهدفة — **ليست تقريرًا بأن الميزات نُفذت**  
**المالك:** مشروع أَوْج

---

## 1. ملخص القرار

إنشاء قدرة موحدة وآمنة داخل **Backend أَوْج** تتيح لوكلاء الذكاء الاصطناعي المصرّح لهم استخدام وظائف ERP الحالية من خلال API: الاستعلام، وإنشاء المسودات والسجلات، وتنفيذ الإجراءات المسموح بها، مع درجات موافقة مناسبة للمخاطر.

**ليست الفكرة بناء نظام ERP آخر، أو نقل منطق المحاسبة إلى الوكيل، أو اشتراط تشغيل مساعد أَوْج الداخلي.** جميع العمليات الفعلية يجب أن تمر عبر قواعد أَوْج وخدماته وصلاحياته، ويظل أَوْج مصدر الحقيقة الوحيد للبيانات المالية والتجارية.

**مبدأ التنفيذ:** نتيجة عملية صغيرة مبكرًا، ثم توسع تدريجي حسب الوظائف الجاهزة. لا Gateway مستقل ولا MCP Server ولا واجهة جديدة ولا إعادة هيكلة واسعة في المرحلة الأولى ما لم يكشف فحص الكود عن ضرورة واضحة.

## 2. التجربة النهائية المطلوبة

يمكن للمستخدم مخاطبة مساعد أَوْج أو باشت أو ChatGPT أو Claude أو تطبيق خارجي مُرخّص باللغة الطبيعية (نص/صوت/صورة/PDF/Excel بحسب قدرات القناة)، مثل:

- «ابحث عن منتج الديزل وبيّن سعره ورصيده في الفرع المحدد».
- «أضف هذه المنتجات من ملف Excel، مع التصنيف والوحدة والـSKU والصور، وأظهر نتيجة كل صف».
- «أنشئ عرض سعر لشركة كيفير واحفظه مسودة».
- «أنشئ فاتورة مبيعات مسودة من المستند المرفق».
- «اعرض كشف حساب العميل والمتأخرات حتى تاريخ محدد».
- «جهّز فاتورة مشتريات أو أمر شراء للمورد».
- «حضّر مصروفًا أو سند قبض أو سند صرف، واعرض تفاصيله للموافقة قبل التنفيذ».
- «استخرج تقرير المبيعات والأرباح والمخزون وملخص الورديات».

يُرجع النظام نتيجة موثوقة: الحالة، المعرّفات/الروابط، العمليات المنفذة، الفاشلة، وما يحتاج مراجعة. **لا يدّعي الوكيل نجاح عملية إلا بناءً على استجابة مؤكدة من أَوْج.**

## 3. نطاق الوحدات المستهدف

| المجال | أمثلة القدرات المستهدفة |
|---|---|
| المنتجات والكتالوج | بحث، إنشاء وتحديث، SKU/باركود، وحدات، تصنيفات، سمات ومتغيرات، قوائم أسعار، صور، استيراد جماعي، ربط قناة المتجر |
| العملاء | بحث، إنشاء وتحديث، بيانات الاتصال، أرصدة، كشف حساب، مديونيات |
| الموردون | بحث، إنشاء وتحديث، كشوف حساب ومستحقات |
| المبيعات | عروض أسعار، فواتير، مرتجعات وإشعارات حسب ما يدعمه أَوْج، متابعة الحالة |
| المشتريات | طلبات/أوامر شراء، فواتير مشتريات، مرتجعات، مطابقة الموردين |
| التحصيل والسداد | سندات قبض وصرف، تسوية مستحقات، دفعات جزئية، ربط الحسابات البنكية/النقدية حسب صلاحياتها |
| المصروفات | إنشاء مسودة مصروف، تحديد الحساب والفرع والمرفقات، موافقات وترحيل وفق السياسات |
| المحاسبة والتقارير | كشوف الحساب، دفتر الأستاذ، ميزان المراجعة، الأرباح والخسائر، تقارير الذمم والتحليل |
| المخزون | استعلام عن الأرصدة والحركات، نقل وجرد وتسويات ضمن الموافقات والصلاحيات |
| المتجر الإلكتروني | تصنيف وعرض منتجات القناة، إتاحة المنتجات، صورها وأسعارها، حسب عقود المتجر الحالية |
| محطات الوقود | تقارير المنتجات والخزانات والمضخات والفوهات والورديات والمبيعات والتحصيل؛ أي كتابة أو ترحيل يخضع لعقود الوحدة |
| الإدارة | استعلامات الإعدادات المصرّح بها؛ التغييرات الإدارية الحساسة تتطلب ضوابط منفصلة |

**هذه قائمة هدف وليست إثباتًا لوجود API مكتمل لكل وظيفة.** التوافر الفعلي يحدده فحص المستودع والاختبارات.

## 4. أين تقع المكونات؟

```text
المستخدم
  │
  ├─ مساعد أَوْج الداخلي (اختياري)
  ├─ باشت / واتساب / صوت (اختياري)
  ├─ ChatGPT / Claude (بعد توصيل آمن)
  └─ تطبيقات خارجية مصرّح بها
  │
  ▼
طبقة تكامل الوكيل (مصادقة وتحديد هوية المستخدم/المستأجر)
  │
  ▼
AWJ AI Actions — واجهات/أدوات مُقيّدة ومُوثّقة
  │  التحقق من المدخلات، الصلاحيات، حدود العمليات، الموافقات،
  │  Idempotency، منع التكرار، Audit، نتيجة مؤكدة
  ▼
خدمات أَوْج الحالية وقواعد الأعمال/API الموجودة
  │
  ▼
قاعدة بيانات أَوْج الحالية (دون وصول مباشر للوكيل)
```

في النسخة الأولية قد تكون «AWJ AI Actions» مجرد **تغليف محدود لمسارات API الحالية**، لا خدمة منفصلة. لا نفترض أن الاسم يعني منتجًا جديدًا أو خادمًا إضافيًا.

## 5. العلاقة مع مساعد أَوْج

- **تشغيل مساعد أَوْج الداخلي ليس شرطًا** لربط وكيل خارجي بوظائف API.
- يجب فصل **إظهار/تشغيل واجهة المساعد الداخلي** عن **السماح بتكاملات AI API الخارجية**.
- إيقاف المساعد الداخلي لا يعني إيقاف جميع التكاملات الخارجية تلقائيًا، والعكس صحيح، مع احترام سياسة المشرف.
- لا توجد موافقة مسبقة على جعل API عامًا أو فتحه دون مصادقة؛ كل تكامل يحتاج هوية وصلاحيات محددة.

## 6. درجات الإجراءات والموافقات

| المستوى | أمثلة | السلوك المستهدف |
|---|---|---|
| A — قراءة | بحث، كشف حساب، تقارير | تنفيذ فوري ضمن الصلاحيات، مع تسجيل مناسب وعدم تجاوز نطاق الفرع/المستودع |
| B — كتابة غير مُرحّلة | عميل، منتج، عرض سعر، فاتورة مسودة | تحقق من المدخلات، معاينة عند الغموض/التعديل الجماعي، تأكيد وفق سياسة المستأجر |
| C — أثر مالي/مخزني أو إجراء حساس | ترحيل، قبض، صرف، سداد، إلغاء مُرحّل، تسوية، تغيير سعر جماعي عالي الأثر | تفاصيل واضحة وموافقة بشرية صريحة قبل التنفيذ، ثم تحقق وسجل تدقيق |

**لا يسمح للوكيل بتجاوز قيود الترحيل أو الضرائب أو الأرصدة أو الصلاحيات أو التسلسل المحاسبي.** لا تُعامل موافقة محادثة عامة على أنها موافقة صالحة لعملية لاحقة غير محددة.

## 7. متطلبات الأمان والجودة غير القابلة للتفاوض

1. **Tenant Isolation:** سياق المستأجر يُستمد من مصادقة موثوقة، وليس من معرّف يختاره النموذج بحرية؛ اختبارات منع الوصول العابر بين المستأجرين.
2. **RBAC وActor Scope:** جميع قواعد الفروع والمستودعات والحسابات النقدية/البنكية تُطبّق كما في واجهة أَوْج، دون امتيازات إضافية للوكيل.
3. **مصادقة مؤهّلة للوكلاء:** رموز محدودة النطاق والقابلية للإلغاء والدوران؛ لا استخدام بريد/كلمة مرور المالك كاعتماد دائم؛ لا أسرار في الكود أو سجلات الطلبات.
4. **خدمات الأعمال مصدر الحقيقة:** لا SQL أو وصول مباشر لقاعدة البيانات من وكلاء الذكاء الاصطناعي، ولا احتساب مالي نهائي خارج خدمات أَوْج.
5. **Idempotency وDuplicate Prevention:** خصوصًا في المدفوعات، المستندات، والاستيراد الجماعي؛ إعادة المحاولة لا تنشئ ازدواجًا.
6. **Validation:** تحقق من العميل/المورد، المنتجات، الوحدات، الضريبة، العملة، الأسعار، الفرع، المستودع، الفترات المحاسبية والحسابات المرتبطة قبل الحفظ.
7. **Approval & Audit:** من طلب؟ في أي مستأجر؟ ما البيانات الملخّصة؟ من وافق؟ ما الذي تغير؟ لا تسجل بيانات حساسة غير لازمة.
8. **Least privilege وRate Limits:** حدود العمليات والحجم والوقت، والقدرة على تعطيل الوكيل أو إلغاء اعتماده فورًا.
9. **Backward Compatibility:** عدم كسر مسارات API الحالية أو العقود أو سلوك الواجهة.
10. **Fail safe:** الطلب غير المكتمل أو الملتبس أو ذو المرجع غير المحدد يتوقف للمراجعة؛ لا تخمين للأرقام والحسابات.
11. **محتوى غير موثوق:** نص المستندات والروابط والصور بيانات تُحلّل، وليست تعليمات مخوّلة تتجاوز قواعد المنصة.
12. **اختبار مالي وأمني فعلي:** لا تُختصر اختبارات العزل أو الصلاحيات أو العمليات المحاسبية بسبب كون البيئة Beta.

## 8. مسار التنفيذ — تسليم سريع دون تعقيد

### المرحلة 0 — فحص موجّه وقصير + تنفيذ أول شريحة (المهمة الجارية مع Claude Code)

**أولوية قصوى.** فحص مسارات API والخدمات والاختبارات ذات الصلة فقط. الهدف توفير تكامل خارجي موثوق بأقل تغيير عبر أربع قدرات:

1. البحث عن العملاء والمنتجات.
2. إنشاء منتج.
3. إنشاء فاتورة مبيعات **مسودة**.
4. استخراج كشف حساب عميل.

**معيار الإنجاز:** اختبار نداء من وكيل/عميل API مصرح به على مستأجر تجريبي ينتج استجابة موثّقة من أَوْج؛ مثل إضافة «باقة ورد أحمر» ثم ظهور معرّف المنتج ورابطه. إذا كانت قدرة تتطلب إعادة تصميم كبيرة، تُوثَّق وتؤجّل بدل تعطيل ما يمكن تسليمه.

**غير مشمول:** الترحيل، السداد، إنشاء خادم MCP، لوحة AI جديدة، إعادة بناء المساعد الداخلي، النشر والدمج التلقائي.

### المرحلة 1 — تثبيت الأساس القابل للتكرار

- تعريف عقود أفعال بسيطة (اسم الفعل، المدخلات، التحقق، الصلاحية، الاستجابة، أخطاء معروفة).
- توحيد المصادقة الخارجية والتفويض وتحديد المستأجر والفاعل.
- سجل تنفيذ وتتبّع للطلبات، ومنع التكرار ومعالجة إعادة المحاولة.
- اختبارات أمنية وعقود API ونتائج أداء أساسية.
- لا تُستحدث طبقة/سيرفر مستقل إلا إذا أصبحت حاجة مثبتة.

### المرحلة 2 — توسعة العمليات اليومية ذات الأثر السريع

- المنتجات: تعديل، تصنيفات، سمات، وحدات، صور، استيراد Excel/CSV، دفعات منظمة مع معاينة Dry Run.
- العملاء والموردون.
- عروض الأسعار، أوامر الشراء، فواتير المشتريات كمسودات حسب العقود الحالية.
- تقارير وكشوفات حساب متعددة، مع روابط تنزيل قابلة للصلاحيات.
- نتائج جزئية واضحة لعمليات Bulk (ناجح/مرفوض/مكرر/يحتاج مراجعة).

### المرحلة 3 — العمليات المالية والمخزنية الحساسة

- تصميم موافقات مرتبطة بالعملية وبالطلب وبمدة صلاحية محددة.
- تحصيل وسداد، مصروفات، تسوية، ترحيل وإلغاء وفق قواعد أَوْج وإجراءات التدقيق.
- حسابات بنكية ونقدية وActor Scopes واختبارات صلاحيات/تطابق مالي عالية التغطية.
- التعامل مع الفشل والرجوع الآمن: **لا Rollback اعتباطيًا للحركات المُرحّلة**؛ تُستخدم آليات العكس النظامية المتاحة.

### المرحلة 4 — القنوات والتوسع

- دمج مساعد أَوْج الداخلي عند الرغبة.
- ربط باشت وواتساب والمحادثة الصوتية عند جاهزية قنواتها ومصادقتها.
- موصلات ChatGPT/Claude وتغليف MCP إن ثبتت فائدته، فوق نفس عقود الأفعال.
- تغطية وحدات إضافية (المتجر الإلكتروني، محطات الوقود، ...)، دون نسخ المنطق.

> ترتيب المراحل حسب القيمة والمخاطر، وليس جدولًا زمنيًا ملزمًا. لا نؤخر إنجاز المرحلة الأولى حتى اكتمال تصميم المنصة النهائية.

## 9. استراتيجية المنتجات والاستيراد

- المطابقة أولًا بالمعرّفات المستقرة (SKU/باركود عند وجوده) وبقواعد واضحة؛ الأسماء وحدها قد لا تكفي.
- وضع **Dry Run** يعرض المتوقع: إضافة/تحديث/تكرار/خطأ قبل تنفيذ الاستيراد الجماعي.
- صور المنتج: مراعاة صلاحيات المصدر وسياسات الوسائط وقيود الحجم والصيغة، وفشل رفع الصورة لا يُموّه على أنه نجاح.
- التحقق من العلاقة بين التصنيفات وقوالب الوحدات والسمات والمتجر قبل التحديث.
- ترقية أسعار جماعية تتطلب معاينة فرق السعر والسجلات المتأثرة، والموافقة حسب مستوى التأثير.
- سجل لكل صف، واستكمال آمن عند انقطاع الاتصال بدل إعادة استيراد كل الصفوف.

## 10. استراتيجية التقارير والمستندات

- استخرج البيانات من تقارير أَوْج المعتمدة بدل أن يحسب النموذج أرصدة وضرائب من تلقاء نفسه.
- اعرض نطاق التقرير بدقة: المستأجر، الفرع، الفترة، العملة، حالة المستندات.
- وضّح إن كانت المخرجات بيانات شاشة أو PDF أو Excel حسب القدرات المتوفرة فعلًا.
- روابط التنزيل يجب أن تكون مصرحًا بها ومحدودة الوصول؛ لا تسرّب مستندات لعميل أو مستأجر آخر.

## 11. سياسة بناء التكاملات والتكلفة

- **البدء:** استخدام API الحالي مباشرة عند كفايته، مع طبقة أفعال خفيفة إذا لزم.
- **لا حاجة افتراضية لخادم إضافي أو MCP في البداية.** قد يصبح MCP خيارًا لتعدد العملاء والقنوات، لكنه ليس أساس التنفيذ.
- لا نحتاج تشغيل مساعد أَوْج أو شراء نموذج جديد لإتاحة وظائف API، لكن استخدام نموذج خارجي/قناة اتصال قد يترتب عليه استهلاك منفصل.
- نعتمد اختبارات صغيرة متتابعة، وفرع/PR مستقل لكل توسعة واضحة.
- **الأداة المفضلة:** Claude Code للأعمال متعددة الملفات؛ ChatGPT للتخطيط ومراجعة تقارير التنفيذ؛ Cursor للإصلاحات المحددة. لا يُستهلك Work/Codex إلا إذا احتاجت المهمة قدراتهما فعليًا.

## 12. ضوابط العمل في بيئة Beta

- أَوْج حاليًا Beta ويستخدم حسابات/مستأجرين تجريبيين؛ هذا يسمح بتجربة التكامل بأمان أكبر، **ولا يلغي** العزل، الصلاحيات، الدقة المحاسبية أو الاختبارات.
- اختيار المستأجر التجريبي والهوية المُصرّح لها قبل أي كتابة فعلية.
- لا Merge أو Deploy أو Production Release دون موافقة المالك الصريحة.
- لا تغيير لقواعد مالية أو API أو قاعدة بيانات خارج نطاق المهمة دون تفويض واضح.

## 13. معايير القبول العامة

يُعتبر كل فعل «جاهزًا» فقط إذا:

1. يعمل من API بهوية مخوّلة، ويُرفض عند غياب الصلاحية أو عند تجاوز المستأجر.
2. يستخدم خدمات أَوْج الحالية ويتصرف مثل العملية المقابلة من الواجهة.
3. يتحقق من البيانات ولا يختلق معرّفات أو أسعارًا أو مبالغ.
4. يعيد نتيجة مؤكدة قابلة للتتبّع، مع رسائل خطأ مفهومة.
5. لديه اختبارات مرتبطة بالنطاق، تشمل الحالات السلبية، ومعايير منع التكرار عند الحاجة.
6. يملك توثيق استخدام بسيطًا وأمثلة استدعاء **من دون أسرار**.
7. اجتاز المراجعة وCI الملائم، ثم الدمج/النشر والتحقق عند التصريح بذلك؛ **الاختبارات المحلية وحدها لا تعني أنه منشور.**

## 14. التسليمات المطلوبة من Claude Code / Cursor

تقرير Markdown نهائي لكل شريحة يتضمن:

- ما تم فعليًا، وما لم يُنفّذ.
- الوظائف والـEndpoints المستخدمة أو المضافة.
- الملفات المتغيرة.
- الاختبارات ونتائجها، وBuild/CI.
- نتائج تجربة API (مع تعمية البيانات والأسرار).
- اعتبارات Tenant Isolation وRBAC والدقة المحاسبية والتوافق.
- المخاطر والعوائق والقرارات المطلوبة.
- Branch / PR / Base SHA / Head SHA إن توفرت.
- **الخطوة التالية الواحدة ذات الأولوية**.

## 15. النطاق الحالي مقابل الخطة الكبرى

| البند | الآن | لاحقًا |
|---|---|---|
| بحث العملاء والمنتجات | نعم | تحسين البحث |
| إنشاء منتج | نعم | استيراد وتحديث جماعي وصور ومتغيرات |
| إنشاء فاتورة مبيعات | مسودة فقط | بقية دورة المستندات والترحيل بموافقة |
| كشف حساب عميل | نعم إذا تدعمه API الحالية أو يمكن توفيره بتغيير صغير | بقية التقارير |
| عروض الأسعار والمشتريات | ليس ضمن المهمة الأولى | المرحلة 2 |
| السداد والتحصيل والمصروفات المرحلة المالية | لا | المرحلة 3 بضوابط صريحة |
| باشت/واتساب/الصوت | ليس شرطًا لنجاح البداية | المرحلة 4 |
| مساعد أَوْج الداخلي | لا يحتاج تفعيلًا | ربط اختياري |

## 16. القرارات التي لا نتخذها قبل الفحص

- هل المسارات الحالية تكفي أم تحتاج Actions/Endpoints جديدة؟
- ما آلية المصادقة الآمنة المتاحة في المستودع فعلًا؟
- هل توجد خدمة موافقات/Idempotency قابلة لإعادة الاستخدام؟
- ما حدود التقارير والإصدارات المتاحة من API؟
- هل يحتاج أي تكامل لاحق MCP أم يبقى REST مباشرًا؟

الإجابة على هذه الأسئلة تأتي من **الكود والتقارير والاختبارات**، لا من افتراضات الخطة.
