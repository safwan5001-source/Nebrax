### 1.1b D-08 — خيارات أمر CLI `public-api:create-client` (للقرار — **لا خيار معتمد**)

**الواقع (قراءة كود):** الأمر يعمل من الخادم بلا مستخدم، يستدعي `ApiClientKeyService::issueKey` بأي scopes معروفة، **ولا يكتب أي أثر تدقيق للإصدار**. لا يستعمله أي اختبار في المستودع، ولا يُذكر إلا مثالاً في تقرير #2026. docblock يصفه «إدارة عبر CLI خادمية موثوقة». المفتاح الذي استعمله باشت صدر من واجهة `/developer/keys` لا من CLI.
**نقطة التمييز:** مستخدم المستأجر المحدود لا يصل إلى CLI (وصول الخادم)، فالتصعيد المُثبَت في §1.1 هو عبر الواجهة/REST. CLI «مسار تجاوز» لأنه بلا سقف ولا تدقيق، لا لأن مستخدماً محدوداً يستعمله.

| المعيار | **A — ربط الإصدار بمستخدم مخوّل** | **B — إصدار إداري موثوق مستقل بقيود وتدقيق** | **C — توافق الأوامر الحالية بلا مسار تصعيد** |
|---|---|---|---|
| الفكرة | `--issuer=<email>` **إلزامي**؛ السقف يُطبَّق على صلاحيات ذلك المستخدم كما في الواجهة | وضع صريح `--operator --reason="…"` (منفصل عن الاستعمال العادي): عمل منصة لا مستخدم مستأجر | الأمر بلا خيارات يعمل كما اليوم **خلال فترة انتقال** ثم يتحول إلى A أو B |
| سقف الصلاحيات | نعم، مطابق للواجهة | لا سقف مستخدم؛ **قيود بديلة**: `--reason` إلزامي، `--expires-days` إلزامي (≤ 90)، قائمة scopes ضمن حدّ أعلى معلن، بوابة بيئة (`PUBLIC_API_OPERATOR_ISSUANCE_ENABLED`) | لا سقف خلال الانتقال |
| التدقيق | الفاعل = المستخدم | **حدث تدقيق إلزامي** (مشغّل/سبب/scopes/مستأجر/انتهاء) — يحتاج مخزن تدقيق (الموجود لا يغطي؛ يرتبط بتصميم AIA-0.6a أو سجل قائم) | سطر تحذير + سجل «legacy» |
| كسر التوافق | **نعم**: كل استدعاء بلا `--issuer` يفشل | جزئي: الاستدعاء بلا `--operator` يفشل بعد الانتقال | **لا** خلال الانتقال؛ كسر مؤجل |
| مسار تصعيد متبقٍ | لا | لا يوجد مسار **صامت**؛ يبقى تجاوز مُعلن ومُدقَّق لموظفي المنصة | **نعم خلال الانتقال** (يُحدَّد سقف زمني) |
| ملاءمة | عمليات يومية لمستأجر | حالات تشغيل المنصة/الطوارئ/التهيئة الأولى | هجرة سلسة لمن يملك سكربتات |
| الجهد | صغير | متوسط (مخزن تدقيق + بوابة) | صغير + قرار موعد الإلغاء |

**التوصية (غير معتمدة):** **A كقاعدة + B كاستثناء مُدقَّق، مع C كجسر محدود المدة:**
1. الأمر الافتراضي يتطلب `--issuer` (A) ويطبّق السقف نفسه؛
2. `--operator --reason` لإصدار منصة موثوق مُدقَّق (B)، معطَّل في الإنتاج افتراضياً ببوابة بيئة؛
3. الاستدعاء القديم (بلا أي منهما) يعمل **إصداراً واحداً فقط** بتحذير صريح ثم يُغلق (C)، فلا يبقى مسار صامت.
**شرط يسبق B:** وجود مخزن تدقيق لإصدار المفاتيح (لا أضيف هجرة ضمنياً؛ يُقرَّر في 0.6a). حتى ذلك الحين يبقى A فقط ويُرفض الوضع التشغيلي.
**ما لا يتغير في أي خيار:** مفاتيح قائمة لا تُبطَل ولا تُعدَّل؛ `EnsureApiScope` كما هو؛ لا هجرة.

### 1.2 D-02 — التوافق الخلفي وحالات الدقة

**التوافق الخلفي (شروط الاعتماد):**
1. كل الحقول الحالية تبقى بأسمائها وأنواعها وقيمها: `partner`, `currency`, `from`, `to`, `opening_balance_minor`, `rows[]` (وحقول كل صف), `closing_balance_minor`. اختبار انجراف يقارن استجابة قبل/بعد على بيانات ثابتة.
2. الحقول الجديدة **إضافية فقط** (`balance_convention`, `totals`, `position`, `display`, `completeness`, `integrity`, `report_status`, `as_of`)؛ مستهلك صارم للمخطط يُوثَّق تأثيره في OpenAPI (`additionalProperties`).
3. سلوك السقف يبقى: أكثر من 2000 حركة ⇒ `422` بلا اقتطاع. الترقيم **اختياري** (`?cursor=`) ولا يغيّر الطلب الافتراضي.
4. الإشارة الخام تبقى `debit − credit` لكل الأدوار؛ **لا نقلب الإشارة للمورد في الحقول القديمة**. الاتجاه يُعلَن في `balance_convention` و`position` فقط.
5. الفشل الجديد `500 report_integrity_failed` يُفعَّل بعلم نشر مغلق افتراضياً في الإصدار الأول (يُسجَّل ولا يُرفض) حتى يُراجَع على بيانات حقيقية؛ فتح الرفض قرار لاحق.

**حالات الدقة المالية المطلوبة (كشف المورد أولاً):** تُغطى بمصفوفة الجزء ب-6 من وثيقة البوابات، ويُلزَم منها قبل الدمج على الأقل:

| الحالة | المتوقع |
|---|---|
| مورد: شراء 115000 ثم دفع 50000 | صافي −65000؛ `position.closing = payable 65000`؛ `display.closing = "650.00"` |
| مورد بلا حركات | `row_count=0`, `settled`, `final` |
| مورد دفعنا له أكثر (رصيد مدين) | `receivable` مع `opposite_sign=true` |
| طرف ثنائي الدور بفلتر `role` | كل دور يطابق قيوده؛ لا تسرّب بين الدورين |
| رصيد افتتاحي بفلتر `from` وحدّ `to` | افتتاحي = ما قبل `from`؛ ما بعد `to` خارج الصفوف والإجماليات والختامي |
| قيد معكوس لمستند مورد | يتبع دور الأصل (سلوك `ReportService` القائم) |
| 2000 / 2001 حركة | يمر / `422` بلا بيانات |
| سلسلة رصيد مكسورة (حقن) | لا `final`؛ فشل مغلق |
| ما يطابق شاشة أَوْج (`displayBalance`) | `display.closing` = القيمة المطلقة التي تعرضها الشاشة، مع اتجاه صريح |
| تغطية `role=supplier` عبر Public (ثغرة P2-0) | اختبار مضاف |

### 1.3 D-12 — شرط بدء غلاف السلامة المالية

> **مسار مستقل عن D-08:** تحليل العملات **منفصل تماماً** عن إصلاح AIA-0.4 (PR مختلف، شريحة مختلفة، لا اعتماد متبادل). **اتجاه التصميم المعتمد: ISO 4217** كمرجع للمنازل العشرية. **لا تغيير** في `Money::toRiyal` ولا في عقود المبالغ الحالية (هللات صحيحة + `currency` منفصل)، **ولا أي تغيير في تفسير العملات أو القيم قبل تحليل أثر** مكتوب ومراجَع. التحليل نفسه لم يُكتب بعد وسيُسلَّم مستقلاً قبل AIA-0.1.


**أدلة (قراءة كود):** `tenants.currency` عمود `string(3)` افتراضيه `SAR`، و`UpdateCompanyRequest` يقبل أي نص من 3 خانات (`'currency' => ['nullable','string','size:3']`) دون قائمة. `Money::toRiyal` يقسم على 100 دائماً. إذن **لا ضمان** أن كل المستأجرين بمنزلتين عشريتين.
**شرط البدء:** لا يبدأ AIA-0.1 قبل حسم أحد الخيارين:
- (أ) **تقييد**: غلاف التقرير يعمل لعملات منزلتين فقط، ويفشل مغلقاً (`unsupported_currency_exponent`) لغيرها؛ ويُسجَّل أي مستأجر حالي مخالف.
- (ب) **جدول منازل ISO-4217** مُدمَج (KWD/BHD/OMR=3، JPY=0…) وتنسيق مُدرك بالعملة، مع اختبارات لكل منزلة.
**مطلوب منك:** اختيار (أ) أو (ب)، ونتيجة استعلام قراءة على الإنتاج لعدد المستأجرين بعملة ≠ SAR (أنفّذه أنا أو باشت بإذنك؛ لم أنفّذه).

### 1.5 D-04 — شروط كل نوع مستند قبل الكتابة

لا يُفتح مسار كتابة لنوع إلا بعد ورقة نوع تحدد: الحقول المقبولة (قائمة بيضاء) والمرفوضة صراحةً (`status`, `number`, الإجماليات…)؛ الحدود (أقصى عدد سطور، أقصى مبلغ للسطر/المستند، فترة التاريخ المقبولة، منع التواريخ في فترة مقفلة)؛ اعتماد القدرة (`EnsureApplicationActive`) وحد الخطة؛ اختبارات: إنشاء ناجح بلا قيد/ICV/حركة مخزون، رفض الحقول المحظورة، تكرار المفتاح، 403 لـscope ناقص، 404 لمستأجر آخر، سقوف الحدود، **مسودة فقط حتى بعد قراءتها**؛ تقرير أثر محاسبي = "لا قيود". ترتيب الشرائح لا يعني التفويض: كل نوع بموافقة مستقلة.

### 1.6 D-10 — حدود التصدير: مقترحات قابلة للقياس

القيم التالية **فرضيات تُقاس قبل التثبيت**، وتُضبط عبر إعدادات لا ثوابت:

| الحد | المقترح الابتدائي | كيف يُقاس |
|---|---|---|
| متزامن | ≤ 5,000 صف / ≤ 2 MB | زمن p95 وذروة ذاكرة PHP على PostgreSQL بحجم إنتاجي ضمن حد زمن الطلب (Apache prefork) |
| سقف الصف | 50,000 | يطابق تصدير المنتجات؛ يُراجع بعد القياس |
| احتفاظ الملف | 24 ساعة | تكلفة التخزين + حاجة إعادة التنزيل |
| حد المعدّل | أشد من القراءة العادية | استهلاك CPU للتصدير في ساعات الذروة |
تُنفَّذ كاختبارات أداء (CI `pg-perf` كنمط) وتقرير قياس في AIA-2.1b قبل تثبيت أي رقم.

### 1.7 D-03 — Headless Chromium غير معتمد

`P-B` **مرشَّح للقياس فقط**. لا اعتماد ولا بناء قبل: سبايك AIA-5.0 (تكلفة/زمن/ذاكرة/خطوط/استضافة) **و**مقارنة عملية مع P-D (تشغيل مولّدات jsPDF في Node) و P-C (رابط عميق) على نفس الفواتير النموذجية بتقرير أدلة (تطابق RTL ضد الواجهة، `pdftotext` ↔ JSON). القرار بعدها لك.

### 6.3 شروط الدمج التلقائي (كلها معاً)
1. نطاق الـPR داخل شريحة معتمدة، وقائمة ملفاتها ضمن المتوقع (حرس الانحراف: ملف خارج المتوقع ⇒ توقف).
2. **CI أخضر بالكامل** على الرأس النهائي: sqlite + pgsql + `CI Gate` + بناء الويب إن لُمس.
3. `php artisan test` كامل أخضر محلياً؛ لا اختبار معطَّل/متخطَّى جديد.
4. **مراجعة مستقلة** بوكيل منفصل يقرأ الـdiff (لا ملخص المؤلف) بقائمة الأمان + الدقة المالية، **بلا ملاحظة حرجة/عالية مفتوحة**.
5. بوابات الدقة (الجزء ب) وG-S1…S5 ناجحة بأدلة في التقرير.
6. لا تعارض ولا تغيير في عقد API غير الإضافي؛ اختبار الانجراف أخضر.
7. لا تعليقات مراجعة بشرية مفتوحة؛ لا اعتراض من المالك.
8. تقرير الشريحة مكتمل ومرفق.
