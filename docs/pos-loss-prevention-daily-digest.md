# POS Loss Prevention — Phase 3: Daily LP Digest

> **مؤشرات المراجعة والاستثناءات تساعد في ترتيب أولوية التحقيق، ولا تُثبت وحدها وجود مخالفة.**

الملخص الرقابي اليومي منتج بيانات مشتقّ حتمي فوق Phase 1/2/3 القائمة: يلخّص الفترة
التشغيلية السابقة (يوم واحد بتوقيت المؤسسة) — استثناءات جديدة، قضايا جديدة، مبلغ قيد
المراجعة، قضايا عالية الأولوية غير محسومة، نتائج خسارة مؤكدة/خلل رقابي، وجلسات بفروق إغلاق
جوهرية — ويربط كل رقم بمصدره (معرّفات استثناءات/قضايا)، دون اتهام ودون ازدواج.

## 1) لماذا صفّ واحد لكل (مستأجر، تاريخ) لا لكل فرع

المهمة تطلب معاً: فلترة بالفرع في الواجهة (`branch filter`)، توليداً idempotent لنفس
`(tenant, date, scope)`، وعدم ازدواج AUR. توليد صفّ منفصل لكل فرع كان سيضاعف مخاطر الازدواج
عند إعادة الحساب — خصوصاً أن استثناءات بلا فرع صريح (`branch_id IS NULL`) مشتركة بطبيعتها.
**القرار: صفّ واحد لكل `(tenant_id, digest_date)`**، يحمل `branch_breakdown`/`payload` JSON
مفصَّلاً بالفرع؛ فلتر الفرع في الواجهة يُصفّي هذا الـJSON محلياً بلا إعادة استعلام أو إعادة
توليد — يبقى مفتاح idempotency بسيطاً (`unique(tenant_id, digest_date)`).

## 2) حدود اليوم التشغيلي والمنطقة الزمنية

`PosLpDigestService::generate()` يقرأ `Tenant.timezone` (الافتراض `Asia/Riyadh` إن كان
فارغاً) ويحسب حدود اليوم المُلخَّص بتوقيت المؤسسة:

```php
$localDay = Carbon::now($timezone)->subDay()->startOfDay();   // أمس افتراضياً
$periodStart = $localDay->copy()->setTimezone('UTC');
$periodEnd   = $localDay->copy()->addDay()->setTimezone('UTC');
```

كل الاستعلامات (`detected_at`, `opened_at`, `resolved_at`) تُصفَّى بـ `whereBetween`
على هذا المدى بتوقيت UTC المخزَّن فعلياً — لا انزياح صامت لحدود اليوم.

## 3) idempotency

`PosLpDigest::updateOrCreate(['tenant_id' => ..., 'digest_date' => ...], [...])` — نفس
`(المستأجر، التاريخ)` يُحدَّث لا يتكرر أبداً، بفهرس فريد `unique(tenant_id, digest_date)`.
إعادة التوليد اليدوي (`POST pos/lp-digests/generate`) تعيد حساب اليوم المطلوب من الأدلة
الحيّة فتُحدِّث الصفّ ذاته؛ **الأيام السابقة لا تتأثر إطلاقاً** — كل يوم صفّه المستقل، فالتاريخ
يبقى محفوظاً حتى بعد تغيّر إعداد قاعدة كشف أو ترحيل قضايا لاحقاً (مُختبَر صراحة).

> ملاحظة فنية: `digest_date` مصنَّف بصيغة `date:Y-m-d` صراحةً في النموذج — الصيغة الافتراضية
> لِـ Eloquent تُسلسِل تاريخ/وقت كاملَين عند الكتابة رغم القراءة كتاريخ فقط، مما يُفشل مطابقة
> `updateOrCreate`/`where('digest_date', ...)` بسلسلة نصية خام. وثّقناها هنا لأنها مصدر خطأ
> صامت شائع في Eloquent، لا لأنها تخصّ منطق العمل.

## 4) المقاييس وحساب "الفرق الجوهري"

| المقياس | المصدر | ملاحظة |
|---|---|---|
| استثناءات جديدة / بأولوية مراجعة | `PosException.detected_at` ضمن اليوم | عدّ مباشر |
| المبلغ قيد المراجعة | اتحاد `amount_event_ids` لاستثناءات اليوم | **نفس دالة إزالة الازدواج** في `PosLossPreventionController`/`PosInvestigationCaseService`، لا حساب موازٍ |
| قضايا جديدة | `PosInvestigationCase.opened_at` ضمن اليوم | — |
| قضايا عالية الأولوية غير محسومة | لقطة حيّة (لا محصورة باليوم): `status ∈ {open, investigating, awaiting_information}` و`priority ∈ {high, critical}` | مؤشر تراكمي متعمَّد |
| خسارة مؤكدة / خلل رقابي | `outcome` + `resolved_at` ضمن اليوم | يعكس قرارات **حُسمت** خلال اليوم، لا فتحت خلاله |
| **جلسات بفروق إغلاق جوهرية** | استثناءات `closing_variance_magnitude`/`closing_variance_frequency` ضمن اليوم، `pos_session_id` المتمايز | **إعادة استخدام تعريف "الجوهري" من Phase 2** (وزن/عتبة القاعدة القابلة للضبط) — لا عتبة مادية جديدة موازية تُخترع هنا |

## 5) كفاية البيانات (Data Sufficiency Caveats)

مصفوفة `data_sufficiency_caveats` (رموز ثابتة، تُترجَم في الواجهة):

- `no_activity` — لا استثناءات ولا قضايا جديدة خلال اليوم (يمنع عرض أصفار مضلِّلة كأنها
  "يوم آمن مؤكَّد" بدل "لا نشاط رقابي يُذكر").
- `insufficient_sample_some_exceptions` — بعض استثناءات اليوم مصدرها عينة دون الحد الأدنى
  (`explanation.sample_sufficient = false` الموروثة من Phase 2).

## 6) الربط بالمصدر (لا أرقام مجرَّدة)

`payload` JSON يحمل `exception_ids`, `case_ids`, `confirmed_loss_case_ids`,
`rule_breakdown` (تكرار كل قاعدة كشف)، و`performer_approver_concentration` (أزواج منفّذ/معتمِد
موسومة). الواجهة تعرض هذه المعرّفات كروابط قابلة للنقر تفتح القضية/الاستثناء مباشرة —
لا رقم بلا مرجع قابل للتحقق.

## 7) التوليد الآلي — بلا Redis/عامل خلفية جديد

`pos:generate-lp-digest` أمر كونسول (نمط `finance:scan-controls` نفسه حرفياً: يلفّ كل
مستأجر، يضبط `TenantContext`، يستدعي الخدمة، لا كتابة مالية). مجدوَل يومياً في
`routes/console.php` (`dailyAt('01:00')`, `withoutOverlapping`, `onOneServer`).
الإنتاج يعمل بـ `QUEUE_CONNECTION=sync`؛ لا حاجة لعامل طوابير حقيقي لأن التوليد اليومي خفيف
(تجميع مُفهرَس، لا مسح كامل).

## 8) API/UI

- `GET pos/lp-digests` — قائمة مرقَّمة (أحدث أولاً).
- `GET pos/lp-digests/latest` — أحدث ملخص.
- `GET pos/lp-digests/{date}` — تفصيل يوم محدَّد.
- `POST pos/lp-digests/generate` — توليد/إعادة توليد يدوي (`pos.investigations.manage`)،
  يسجّل `generated_by` (فارغ = توليد آلي عبر الأمر المجدوَل).
- تبويب **الملخص اليومي** داخل `/pos/audit` (لا صفحة منفصلة): منتقي تاريخ، بطاقات مؤشرات
  كثيفة، جدول توزيع بالفرع، قضايا مرتبطة قابلة للنقر، وتحذيرات كفاية البيانات — بلا لوحة
  زخرفية.

## 9) نقاط امتداد مؤجَّلة صراحةً

**تسليم القنوات الخارجية (بريد/واتساب/Slack) غير مبنيّ في هذا الطور** — لا بنية إشعار عامة
قابلة لإعادة الاستخدام دون توسعة نطاق حقيقية اليوم؛ `payload` JSON المُهيكل بالفعل هو نقطة
الامتداد المحفوظة لأي قناة تُبنى لاحقاً. تصدير PDF لملخص القضية/اليوم كذلك مؤجَّل (لا محرّك
PDF جديد يُبنى حسب توجيه المهمة).
