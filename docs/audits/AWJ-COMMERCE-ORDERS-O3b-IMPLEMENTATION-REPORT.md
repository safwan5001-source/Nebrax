**المرجع:** `docs/plans/store/ADR-28-COMMERCE-ORDER-LIFECYCLE.md` (§5.1، §8). **فوق:** O3a-2b (#1777، Merge `799d09e3f97e1f5c0dab968547632ac94a3850a6`).
**الطبيعة:** واجهة إلغاء الطلب فوق API القائم، **بلا منطق إلغاء موازٍ**، مع عقد قراءة صغير آمن للبوابة. **لا** تفعيل للبوابة، **لا** تغيير في الدفع/المخزون/الترحيل، **لا** تعديل لعقد المشتري (O3c)، **لا** Merge/Deploy.

## 1. نقطة التكامل: كيف تعرف الواجهة حالة البوابة؟

الفحص: الواجهة لا تملك وسيلة آمنة لقراءة `commerce.order_cancellation_enabled` (إعداد خادم؛ لا يجوز `NEXT_PUBLIC_*` ولا `process.env` في المتصفح — يحرسه اختبار ساكن). لا مسار «قدرات» عام يحمله.
**أصغر عقد قراءة (ضمن هذا الـPR):** يضيف `GET commerce/orders/{id}` (الموجود) المفتاح:

```json
"cancel_action": { "available": true, "blocked_reason": null }
```

- **يغيب كلياً** (لا مفتاح) حين البوابة مغلقة **أو** لا صلاحية `commerce.orders.cancel` ⇒ لا يُكشف وجود بوابة ولا حالتها ولا سبب الغياب. البوابة مغلقة افتراضياً فتبقى الواجهة كما كانت.
- حين يحضر: `available` و`blocked_reason` ∈ رموز المصفوفة الآمنة نفسها (`already_cancelled`، `not_confirmed`، `already_posted`، `payment_paid`، `payment_collected`، `payment_captured`، `payment_authorized`) — لا إعداد ولا اسم بوابة ولا بيانات مالية.
- **لا نسخة ثانية للقواعد:** `CommerceOrderLifecycleService::cancellationBlocker` قراءة SELECT بلا أقفال تعيد استعمال `assertCancellable` نفسها. **استرشادي:** قد يتغيّر الوضع بين القراءة والنقر؛ `cancel()` تحت الأقفال يبقى المرجع (409 ⇒ تحديث الحالة).
- القائمة لا تحمل العقد. المقيَّد بمخازن 403 كالقراءة. التفاصيل ما زالت تمرّ بـTenantScope (404 موحَّد).

## 5.1 مراجعة Codex P2 — قفل الحوار بعد خطأ شبكة ثم تحديث يؤكد الأهلية

**الملاحظة:** بعد انقطاع شبكة (إلغاء غير مؤكَّد) يقفل الحوار تأكيده ويحدّث الطلب؛ فإن بقي مؤهلاً وأُعيد فتح الحوار بقي القفل والحقول المعطَّلة لأن الحوار كان يظل مركَّباً ما دام `canCancel` صحيحاً — فلا تُعاد المحاولة إلا بإعادة تحميل الصفحة.
**المعالجة (واجهة فقط):** `CancelOrderDialog` يُركَّب عند كل فتح ويُفكّ عند الإغلاق (`cancelOpen` وحده)، فتبدأ كل محاولة جديدة بحالة نظيفة (قفل/خطأ/حقول) بعد أن تكون الأهلية حُدِّثت، بينما يبقى القفل لمحاولة الفتح الجارية (يحمي من إعادة الإرسال على حالة قديمة) ويبقى الحوار مركَّباً طوال فتحه حتى لو اختفى الإجراء (سباق 409) فلا تضيع رسالة الرفض.
**الدليل:** اختبار `reopening after an inconclusive failure starts clean…` (شبكة ← قفل ← تحديث مؤهل ← إغلاق ← فتح: الحقول والتأكيد مفعَّلان والخطأ زال والحقول فارغة، ثم نجاح الإلغاء بطلب ثانٍ). الطفرة (الإبقاء على الإرساء القديم `canCancel || cancelOpen`) تُفشله. 95 اختباراً لوحدة الطلبات خضراء، وTypeScript نظيف.
