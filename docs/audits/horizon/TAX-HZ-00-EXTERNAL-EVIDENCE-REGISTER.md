## 2.4 Error, retry and duplicate semantics (summary)

| HTTP | Meaning in official text | Document state at ZATCA | What the EGS should do |
|---|---|---|---|
| 200 | Successful | stored (clearance: stamped and QR added) | record accepted; store cleared invoice (clearance) |
| 202 | Accepted with warnings | stored | do not resubmit; log and route warnings for correction (D5 p.79) |
| 208 | **Clearance duplicate hash within 24 h** (FORUM 6859/7954, prod 6 Aug 2025) | already stored | treat as accepted; reply carries the cleared invoice; investigate why it was resent |
| 303 | Clearance switched off | not stored | resend to Reporting API (no stamp/QR returned) |
| 400 | Rejected (validation errors) | hash recorded, document not accepted | do not resend the same bytes; build a **new** document (new UUID, ICV, hash, timestamp); keep chain |
| 401 | Unauthorized | not received | check CSID/secret/revocation, then resubmit |
| 409 | **Reporting duplicate hash within 24 h** (FORUM, prod 6 Aug 2025) | already reported | treat as success; investigate cause of the resend |
| 413 | Payload too large (about 10 MB) | not received | cannot be fixed by resending the same bytes |
| 429 | Too many requests | not received | resend later; no published limit or Retry-After rule (NV) |
| 500 / 503 / 504 | Server error / unavailable / timeout | not received | resend; indicative intervals ~5 min then ~15 min "timing TBC" (D4 §10) |

Other rules: a duplicate older than the 24-hour hash window is not rejected by the front-end check and "ZATCA will consider the Invoice only once based on … UUID and hash" (D5 FAQ p.78). The 24-hour reporting deadline keeps running while retrying, so keep per-attempt evidence (D4 p.46) and notify through the failure-notification form if reporting cannot be completed (D4 pp.48–52). Planned API downtime windows exist (7 Aug 2026, 03:00–11:00): hold and resume.

## 2.5 Decision packets and ambiguities

**DP-T1 Curve / key length.** D3 says "Key length shall be 256" and shows P-256; every SDK artefact (CSR, dummy certificate, key) is secp256k1, and the Java-16+ SunEC gap is a symptom of that. Options: (A) follow the SDK/CA behaviour, secp256k1 (recommended; evidence-based); (B) P-256 per the PDF text (unproven against the CA); (C) obtain written confirmation from `sp_support@zatca.gov.sa` (named in staff posts) before production. Recommend A with C. Not a Saudi tax-policy decision.

**DP-T2 `uuid` in the request body.** D6 step lists and the sandbox Release-2 note require it; the D6 FAQ example (Release 1) has two keys. Options: (A) send three keys (recommended); (B) keep two. Live enforcement not verified; confirm in a sanctioned simulation run only after separate owner approval.

**DP-T3 Duplicate semantics.** Older FAQ (D4 p.60, D5 p.78): a duplicate "will not be rejected". Staff announcements (Aug 2025, in production): 208 and 409 within 24 h. Options: (A) implement the announcements and keep UUID+hash idempotency (recommended); (B) wait for a formal guideline update. The Detailed Guidelines were not updated after May 2023, so no formal document carries the change.

**DP-T4 Compliance-check set for a `1100` unit.** D5 lists three documents for `1000` and for `0100`, not for `1100`; a non-staff error text names simplified step ids. Options: (A) plan six documents for `1100` (recommended planning assumption); (B) onboard B2B and B2C as separate EGS units (`1000`, `0100`), which also gives separate chains but doubles certificates; (C) verify in simulation later. This is an AWJ design choice with a regulatory unknown.

**DP-T5 Renewal call sequence and HTTP method.** Register: `/production/csids` with OTP (method PATCH recalled). Sandbox list: "Compliance CSID API (for Renewal)" plus "Production CSID API (for Renewal)". Options: model renewal as the whole onboarding sequence with a flag (recommended), method behind a constant until Swagger is read.

**DP-T6 SDK baseline for CI.** Stable 3.4.8 needs Java 11–15; Beta 4.0.0 uses Java 21 but carries older rules. Options: (A) pin 3.4.8 + JDK 11 (recommended); (B) test with both and treat the Beta as informative only; (C) wait for stable 4.x. Re-baseline when the portal's version history changes.

**DP-T7 SDK licence and fixtures.** The zip ships an LGPL-3.0 licence text; whether copying jar or samples into the repo is acceptable is a legal question, not answered here. Options: download in CI with pinned sha256 (no redistribution); vendor only after counsel review.

**DP-T8 Data residency and cybersecurity scope.** No ZATCA technical standard prescribes a hosting region; VAT IR Art. 66(3) (R1-191) requires KSA location or KSA access; D4 allows cloud with Authority access. Options: relocate storage to KSA; keep region and provide a KSA terminal/access; obtain a legal opinion. Needs owner decision (also NCA applicability). Ties to REM-00A.

**DP-T9 Key custody model for a multi-tenant SaaS.** Options: (A) software keys wrapped per tenant/EGS by a managed KMS (acceptable only if "non-exportable" is interpreted as not exportable from the application); (B) KMS/HSM key generated and used inside the module (closest to "non-exportable"; signing latency and cost); (C) tenant-side signing agent (key never leaves the tenant; operational burden). Recommend B where available, A as interim with written risk acceptance. Policy-bearing: owner decision (CLAUDE.md rule 6).

**DP-T10 Retry policy numbers.** Official text gives only indicative "~5 min / ~15 min (timing TBC)". Make interval, ceiling and jitter settings (per tenant default conservative) rather than constants.

**DP-T11 Rate limits unknown.** No official figure. Options: one in-flight request per EGS chain (needed anyway for ICV/PIH order), global concurrency cap, honour 429 with exponential back-off. Ask ZATCA support for quotas before enabling bulk replays.

**DP-T12 Compliance CSID lifetime.** 24 h appears only in a non-staff forum post. Design onboarding to complete in one session regardless; treat the number as unverified.

**DP-T13 Directory listing / certification.** Listing is voluntary and non-binding; no active certification scheme was found. Decide whether to apply after SDK-passing output exists; avoid compliance claims until then.

**DP-T14 Header and JSON names not in official documents.** `OTP` header, `csr` key, `Clearance-Status`, `compliance_request_id`, `requestID`, `validationResults.*`, `clearedInvoice`, status strings. Options: read the Swagger files through a normal Developer Portal login by an authorised person (documentation, not an API call; the gateway download is the only route found) and store them under `docs/`; or keep everything behind constants flagged UNVERIFIED. Owner to decide who downloads.
