## 1.2 Topic checklist

Status vocabulary: IMPLEMENTED / PARTIAL / MISSING / DISABLED. Risk is stated in terms of AWJ's own pipeline.

### 1.2.1 EGS-unit-specific credentials and onboarding

- **Status: MISSING (onboarding), PARTIAL (credential storage).**
- **Onboarding code.** There is no CSR generation, no compliance CSID call, no production CSID call, no OTP handling, no compliance-check submissions, no renewal and no revocation. `grep -rniE "csr|compliance_csid|otp.*zatca|openssl_csr_new" app routes` finds only `ZatcaService.php` (an unrelated hit on the word in a comment or string). The only input path is a manual `PUT /api/zatca-credentials/{environment}` with `binary_security_token`, `secret`, `private_key` and an unused `request_id` (`UpdateZatcaCredentialRequest.php:23-32`; `ZatcaCredentialService.php:75-86`). This is the same finding as AUDIT-1 PH2-09, and I did not find any change. `openssl_csr_new` occurs only in tests.
- **EGS granularity.** One credential per `(tenant_id, environment)` (`migrations/…000131:25`). There is no EGS unit, device or branch dimension, and no overlap window for rotation. `ZatcaCredentialService::store` overwrites in place.
- **Binding.** `ZatcaCredentialMaterialValidator` checks: key↔certificate match, secp256k1 and 256-bit on both, chain to a per-environment trust-anchor bundle (`ZATCA_*_CA_BUNDLE`, path outside the repo), `CA:FALSE`, `digitalSignature`, `clientAuth` EKU, and validity window. A grep for `vat|subject|serial|template|TSTZATCA|organizationIdentifier` in it returns nothing, so the certificate subject, VAT number (versus `tenants.vat_number`) and certificate template (TST/PRE/prod) are not checked. A certificate of another taxpayer, or a test-template certificate stored under `production`, is accepted if it chains to the configured bundle.
- **Risk:** High for go-live. Onboarding is a manual, out-of-band process with no guard against wrong-taxpayer or wrong-template material.

### 1.2.2 Tenant and taxpayer isolation of credentials

- **Status: IMPLEMENTED for tenant isolation; PARTIAL for taxpayer isolation.**
- `ZatcaCredential extends BaseModel implements CompanyWide` (`Models/ZatcaCredential.php`), so the tenant scope applies. Both resolvers also filter `tenant_id` explicitly (`ZatcaSigningCredentialResolver.php`, `ZatcaTransportCredentialResolver.php:~30`) and refuse to run without a tenant context. `SendZatcaSubmission` sets and clears the tenant and branch context around the dispatch.
- Test: `ZatcaCredentialTest::credential_lists_are_isolated_between_tenants`, plus `ZatcaNotificationBridgeTest::tenant_isolation_keeps_zatca_notifications_separate`.
- Taxpayer isolation: no binding between the certificate subject and the tenant's VAT number (see 2.1). `ZatcaIcvScope::branch` is blocked because there is no `branches.vat_number` and no branch-inclusive unique index on `zatca_icv` (`ZatcaIcvScope.php:~70-100`; `ZatcaIcvScopeTest::branch_scope_is_unavailable…`, `…enabling_branch_scope_over_the_api_is_rejected`).
- **Risk:** Medium. Tenant isolation is tested; taxpayer binding is absent.

### 1.2.3 CSID and private-key storage

- **Status: PARTIAL.**
- The whole payload (token, secret, private key, derived public key, chain, `request_id`) is stored in one column cast `encrypted:array` (`Models/ZatcaCredential.php:20`; `migrations/…000131:18`), so it is encrypted with the application `APP_KEY`. The column is `$hidden`. The API returns only booleans, curve, chain length, fingerprint and dates (`ZatcaCredentialService::publicMetadata`). Writes need the user's current password (`:31`), the `company.manage` permission and `throttle:5,1` (`routes/api.php:1620-1623`). Tested in `ZatcaCredentialTest::credentials_are_encrypted_and_only_safe_metadata_is_returned`, `…changing_credentials_requires_the_current_password`.
- Not present: per-tenant or per-key envelope encryption (one `APP_KEY` protects every tenant's key), KMS/HSM wrapping, server-side key generation (keys are pasted in from outside, so the key has already left whatever generated it), any audit-log event on credential or `active_environment` change (grep for `audit` in `ZatcaCredentialService`, the controller and `Settings.php` finds nothing; only `updated_by` is stored). Whether production holds `APP_PREVIOUS_KEYS` handling for key rotation is NOT VERIFIED.
- **Risk:** Medium to high. A DB dump plus `APP_KEY` yields all tenants' signing keys.

### 1.2.4 Rotation and revocation

- **Status: MISSING.**
- Rotation is "PUT a new complete set". A change of stage or token requires the full new set (`ZatcaCredentialService.php:61-73`; `ZatcaCredentialTest::changing_csid_stage_requires_a_complete_new_credential_set`). There is no overlap, no history of previous certificates, no expiry warning, and no certificate fingerprint recorded on invoices or attempts (the attempt table has no certificate or environment column).
- No delete or disable endpoint exists for credentials (routes: GET and PUT only). No CRL or OCSP check (`grep -niE "crl|ocsp|revoc"` on `Zatca*.php` is empty).
- **Risk:** High (operational). Expiry halts signing for the whole tenant (see 2.18).

### 1.2.5 Canonicalisation

- **Status: IMPLEMENTED as C14N 1.1 inclusive via external `xmllint`; hash step matched official samples in the AUDIT-1 one-off run.**
- `ZatcaXmlCanonicalizer::ALGORITHM = http://www.w3.org/2006/12/xml-c14n11` and the command is `xmllint --nonet --c14n11` (`ZatcaXmlCanonicalizer.php:11, 36`). It is not exclusive C14N. The SignedInfo builder declares the same algorithm for CanonicalizationMethod and for the transforms (`ZatcaXmlDsigSignedInfoBuilder.php:47, 70, 80, 114`).
- Subprocess design: temp file with mode 0600, DTD rejected, `--nonet`. The tenant anchor row stays locked across the `xmllint` and `openssl` calls during posting (`ZatcaService.php:63-64` then signing), as in SEC-09/PH2-15. `xmllint` is a runtime dependency; the Docker image has `libxml2-utils` (`Dockerfile:8`).
- Evidence in CI: `ZatcaInvoiceHasherTest`, `ZatcaXmlCanonicalizerContextTest`. These do not compare against the official sample hashes. AUDIT-1 PC-1 recorded 19/19 sample matches in a one-off SDK run.
- **Risk:** Low for the hash step. High for the dependent signature (2.9).

### 1.2.6 Invoice immutability after posting / freeze

- **Status: PARTIAL.**
- Service guards only (rows 10 and 11 in §1). I found no model-level or DB-level protection (trigger, `updating` hook) for `zatca_xml`, `zatca_hash`, `zatca_icv`, `zatca_previous_hash`, `zatca_qr`. The dispatcher re-checks `sha256(zatca_xml)` against the attempt's `request_hash` and the document type before sending (`ZatcaSubmissionDispatcher.php:84-96`, tested), which detects drift but does not prevent it.
- No seller or buyer snapshot: both are read live, so reprints can change after a rename (AUDIT-1 PH1-02; no `seller_snapshot` or `buyer_snapshot` anywhere in `app` or migrations).
- **Risk:** Medium. Any code path or tinker/SQL session can change a frozen XML without the DB noticing.

### 1.2.7 Idempotency

- **Status: IMPLEMENTED at the attempt-creation level; MISSING at the ZATCA-request level.**
- Client idempotency key (required header, ≤128 chars, stored as sha256, unique per tenant): same key and same invoice returns the same attempt; same key for another invoice returns 409 (`ZatcaSubmissionAttemptTest::the_same_idempotency_key_returns_the_same_attempt`, `…cannot_be_reused_for_another_invoice`). A race on the same key is resolved after the unique-violation (`ZatcaSubmissionService.php:84-95`).
- One open attempt per invoice and "no attempt after acceptance" are enforced by the invoice row lock only (`:52-58`). The schema has only `(invoice_id, attempt_number)` and the key unique index, so there is no partial unique index for one open attempt (SUB-13, unchanged). Tested serially only.
- No request id or `uuid` is sent to ZATCA, and no gateway request id is captured. Duplicate prevention at ZATCA's side rests on the same signed XML (same hash and UUID) being resent.
- Job uniqueness (`ShouldBeUnique`, 300 s) expires at the same time as the 5-minute re-queue guard, so a duplicate job for one pending attempt is possible after 5 minutes (SEC-10). The uniqueness lock uses the cache store, and `Dockerfile:56` sets `CACHE_STORE=file`, which is not shared between instances (see §4, N4).
- **Risk:** Medium.

### 1.2.8 Retries, backoff, failure recovery, in-doubt handling

- **Status: PARTIAL / largely MISSING.**
- The job never retries (`tries=1`), by design: a retry is a new manual attempt (`ZatcaSubmissionAttemptTest::a_failed_attempt_can_be_retried_manually_with_the_next_number`). There is no backoff, scheduler or sweep. A job that dies or times out leaves the attempt `pending`; a person must call `POST …/dispatch` after 5 minutes (`ZatcaSubmissionRecoveryTest::a_pending_attempt_can_be_requeued_after_readiness_is_fixed`). No `failed()` hook exists.
- A `ConnectionException` (including a timeout after the request was sent) is recorded as `failed`, `retryable=true` (`ZatcaHttpTransport.php:44-56`). There is no `unknown` or in-doubt state and no reconcile step, so the next manual attempt resends the same document, which is consistent with the documented ZATCA duplicate behaviour but is not tested against any real or simulated gateway.
- The HTTP call runs inside an open DB transaction holding a row lock for up to 35 seconds (`ZatcaSubmissionDispatcher.php:23, 32`). If the connection is lost afterwards, ZATCA may hold an accepted document while AWJ's attempt is still `pending` or rolled back (SUB-09, unchanged).
- **Risk:** High for any future live use.

### 1.2.9 Submission status state machine and audit events

- **Status: PARTIAL.**
- Actual machine: `pending → accepted | rejected | failed` (enforced in `ZatcaSubmissionAttempt::booted`, `:69-96`). `queue_count` and `queued_at` may change while still pending. A failed or rejected attempt does not reopen: a new attempt row is created with the next number. There is no invoice-level e-invoice lifecycle state (posted → cleared / reported / rejected); `invoices.status` stays `posted` irrespective of ZATCA outcome (SUB-01).
- Audit events: the attempt rows themselves (permanent, `restrictOnDelete` FK) plus the in-app notification. No event log, no structured logs, no metrics (§1 row 17).
- **Risk:** Medium to high. "Posted" is not distinguishable from "cleared" for a standard invoice.

### 1.2.10 Response parsing (`reportingStatus` / `clearanceStatus` / warnings / errors)

- **Status: PARTIAL, weak.**
- Acceptance is by HTTP status only (200 or 202). The body's `clearanceStatus`/`reportingStatus` is copied into `response_code` but never gates acceptance, so a 200 with `NOT_CLEARED` or `REJECTED` in the body is recorded as `accepted` (`ZatcaHttpTransport.php:83-92`). HTTP redirects are not disabled, and a non-JSON 200 is accepted for reporting (`json()` returns null → `[]`). Statuses 401, 403, 404, 409, 413, 422 and 303 map to `rejected` (so notifications read "ZATCA rejected this invoice"). Warnings and validation errors are kept only inside the sanitised JSON payload; there is no extraction into fields. For clearance, a 200 without a parseable cleared `<Invoice>` is downgraded to `failed / invalid_clearance_response` (`ZatcaSubmissionDispatcher.php:40-50`). This is the single place where the body is consulted, and it is tested (`clearance_xml_is_saved_separately…`).
- Cleared XML is stored but never used: the printed and displayed QR remains the locally generated one (SUB-04). Cleared XML is not checked for DOCTYPE or integrity (SEC-11).
- **Risk:** High. A wrong "accepted" is the worst failure here.

### 1.2.11 Security controls

- **Log redaction.** No `Log::` call in the ZATCA classes except `ZatcaNotificationBridge` (`Log::error('zatca_submission_notification_failed', …, 'message' => $e->getMessage())`). The dispatcher swallows every `Throwable` without logging, so there is nothing sensitive in logs, but also nothing diagnostic (see §4, N1). Transport payload sanitising is a key blocklist (`ZatcaHttpTransport::sanitize`) and is unit-tested only through the happy path. Request-body logging for `PUT zatca-credentials` was not examined (NOT VERIFIED).
- **Permissions.** There is no `zatca.submit` permission. Submitting and dispatching use `invoices.manage` (`routes/api.php:691-694`), viewing the full XML and hash uses `zatca.view` (`:688`), credentials and settings writes use `company.manage` (`:1620-1625`), and `GET zatca-settings` (which includes readiness metadata) uses `invoices.view`. `Rbac` contains only `zatca.view` (`Support/Rbac.php:36, 43, 84`). Separation of duties is absent (SEC-07).
- **Application gating.** Routes carry `EnsureApplicationActive:compliance.zatca`, which is optional and off for post-cutover tenants (`ApplicationCatalog.php:91-96`). Posting artefacts are generated regardless, and signing and transmission ignore the toggle (SEC-08).
- **Readiness gates / fail-closed.** `ZatcaSigningReadiness` and `ZatcaTransportReadiness` (`inspect()`) return stable blocker codes without secrets. Dispatch needs `dispatch_enabled === true`, a non-sync queue, a production-stage unexpired CSID, and an endpoint that matches the pinned host and path. Posting fails closed (and rolls back the ledger) once any credential row exists and the active environment has no valid credential or policy (`ZatcaSignedInvoicePostingTest`). Readiness is evaluated at enqueue and at the settings call, not continuously.
- **Error text.** `ApiController::domain` returns `RuntimeException::getMessage()` as the 422 body (`ApiController.php:34-36`); `ZatcaXmlCanonicalizer` embeds `xmllint` stderr, which can include temp paths, in its exception text (`:55-61`) (SEC-13).
- **Risk:** Medium.

## 1.4 Incidental new findings

Labelled N1…N8. Each is based on the current code. None is a regulatory conclusion.

- **N1 — The dispatcher discards every exception without logging.** `catch (Throwable)` at `ZatcaSubmissionDispatcher.php:63-71` stores a generic `submission_preflight_failed` with `retryable=false` and no log line. Operators cannot tell a bad snapshot from a bad credential, a network class error or a DB error. This is wider than SUB-06/OPS-02 (which describe missing observability); here a cause is actively dropped. It also runs inside the open transaction, so a DB error caught here can leave the transaction aborted before `complete()` runs (PostgreSQL behaviour; UNTESTED, listed as a hypothesis).
- **N2 — A clearance 200 with an unusable cleared XML is recorded `failed`, retryable, although ZATCA has already answered 200.** `ZatcaSubmissionDispatcher.php:40-50` rewrites an accepted response to `failed / invalid_clearance_response` with `retryable=true`. A manual retry then resends a document that the gateway may already hold. This is the same family as SUB-06 but a distinct trigger (a parsing failure, not a transport failure), and no test covers a retry after it.
- **N3 — The `submission_mode=automatic` setting is accepted, stored and shown in the web settings page, but nothing reads it.** `Support/Settings.php:258` and `UpdateZatcaSettingsRequest.php:21` define it, `web/src/app/(app)/sales-settings/einvoice/page.tsx:140` writes it, and no service consumes it. The model allows `source='automatic'` (`ZatcaSubmissionAttempt.php:63`), but no code creates such an attempt. A user can choose "automatic" and nothing happens. This is not covered by the SUB-05 text as a UI-expectation risk.
- **N4 — Job uniqueness depends on a cache store that is `file` in the shipped image.** `SendZatcaSubmission` is `ShouldBeUnique` (`:17, :23`) and `Dockerfile:56` sets `CACHE_STORE=file`. A file cache is not shared between instances, so uniqueness would not hold across more than one app or worker container. Related to SEC-10 but about the lock store, not the window.
- **N5 — No `ZATCA_*` setting exists in any deployment manifest.** `render.yaml`, `Dockerfile`, `deploy/` set none of `ZATCA_*_CA_BUNDLE`, `ZATCA_SIGNATURE_POLICY_*` or `ZATCA_SUBMISSION_*`. Consequence: credential storage fails at the trust-anchor check ("حزمة ثقة ... غير مهيأة"), signing cannot be configured, and dispatch stays off. This is fail-closed and matches the plan's intent, but it means the production configuration path for these values is undocumented in the repo.
- **N6 — Credential `request_id` is stored encrypted but never used.** It is accepted by the request, kept in `SECRET_FIELDS` (`ZatcaCredentialService.php:20`) and surfaced only as a boolean. Harmless today; it will matter for REM-19.
- **N7 — No audit trail for credential and environment changes.** Neither `ZatcaCredentialService::store`, the controller nor `Settings::put('zatca', …)` writes an audit event (only `updated_by` on the credential row). Switching `active_environment` changes which credential signs and sends, with no record of who did it or when. Close to SEC-06/SUB-12 but about the missing log rather than the missing validation.
- **N8 — The test suite itself is internally consistent and green (171/171), but several tests pin the non-conformant behaviour.** Examples: the genesis test asserts the raw-hash form, and the transport test asserts the two-field body. This is PH2-14 re-observed. REM-16/17/21 will have to change these tests deliberately and not "fix" them as regressions.

## 2.2 Per-task notes (non-obvious points only)

- **REM-01 / REM-02 "done" scope.** "Done" means the card's acceptance criteria are covered by merged code and tests that pass on SQLite here. PostgreSQL-only tests (concurrency, lock order) could not be run; CI results quoted in the reports (sqlite, pgsql, web green on the PR heads) were not re-observed. Production state and Finance's review of historical returns/credit notes (plan gate G1) are not verified.
- **REM-02 and ADR-E.** The card's "Decisions: ADR-E" is satisfied in substance by an owner decision recorded in the PR and report (Option A: source invoice required by default; standalone via setting), but no ADR file exists. The plan's Definition of Done (§7) asks for ADRs to be referenced; this remains a documentation gap, not a code gap.
- **REM-02 residual open path for VAT-02.** Migration `2026_11_04_030000_pin_standalone_credit_notes_for_existing_tenants` pins `allow_standalone_credit_notes=true` for tenants that existed at migration time (explicit values untouched). For such tenants a standalone note has no source and therefore no cap (service docblock `CreditNoteService.php:43-44`). The Pre-Production Data Policy would have allowed defaulting them to `false`; whether any such tenant exists in production is not verified.
- **REM-03.** The audit's claim that `post` is reachable cross-branch is slightly softened on main by `assertWarehouseAllowed`, but the acceptance criterion (404 for foreign-branch PUT/DELETE/POST post/classification and no revisions visibility) is not met. Returns and quotes show the same bare-`findOrFail` pattern, so the card's "review quotes/credit-notes/returns" scope is confirmed for returns and quotes; credit notes are already fixed.
- **REM-04.** The REM-01/02 work added `lockForUpdate` on the source row for returns/notes/POS and a PostgreSQL lock-order test for those paths. That is a different lock chain from `InvoiceService::post` (partner row before tenant anchor), which the audit reproduced with a concurrent payment creator. Nothing on main addresses that chain.
- **REM-09.** The card cites `DeliveryNoteSalesInvoiceDraftBuilder::checkedMultiply` as the model; `ReturnSourceAllocator::mulDiv` (REM-01) is a second, independent overflow-safe helper. Consolidating them is part of this task's design choice; no code uses both.
- **REM-10 vs REM-02.** `CreditNoteService` now takes its default rate from settings, which removes one `?? 15` site (VAT-10) but not the card's other items.
- **REM-20.** Because `InvoiceService::post` builds QR/ICV/XML for every posted invoice regardless of the capability, the missing-QR symptom (PH1-03) is a read-path/UX gate on the invoice page plus the catalog flag, not a missing-generation defect. Which tenants have the capability on in any real environment is not verified.
- **REM-34.** PRINT-01 is credited only for the rate-aware credit-note VAT label; the card's other four findings are unchanged on main as far as grep/code-read shows. Web tests were not run to confirm rendering.
- **REM-36.** The card's PH1-16 evidence (365-day default, local disk) is still true in `render.yaml`, which is a repository blueprint, not proof of production configuration.
