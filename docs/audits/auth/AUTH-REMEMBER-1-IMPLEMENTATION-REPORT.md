# AUTH-REMEMBER-1 — Persistent login + Remember Me

Issue: #1752 · Base SHA: `4789b2e` (origin/main) · Branch: `claude/persistent-login-remember-me-mwymez`

## Confirmed root cause (against current code)

| Finding | Status |
|---|---|
| Bearer token in `localStorage` (`token`, `user`) | Confirmed — survives browser restart (it is not session storage). |
| `/login` never checks an existing session | **Confirmed — the defect.** `LoginPage` always rendered the form; a valid token was ignored. Opening `/login` (bookmark, history, address-bar autocomplete, login link on `/`) showed the form although the session was valid. |
| Token lifetime 7 days, no `remember` field | Confirmed (`AuthController::TOKEN_TTL_DAYS`, `LoginRequest`). `config/sanctum.php` is not committed (generated by `setup.sh`; package default `expiration = null`), so the per-token `expires_at` is the only lifetime control and Sanctum's guard enforces it. |
| Any 401 clears credentials | Confirmed, plus a latent race: a *late* 401 for an old token wiped a token from a newer login. Fixed. |

Differential for the reported symptom:
1. **/login with valid token** — the primary, code-confirmed cause (fixed).
2. Missing storage (private mode / "clear on exit" / Safari ITP) — cannot be fixed client-side; not reproducible here.
3. Expired/revoked token (>7 days, password reset, logout elsewhere) — correct behaviour; Remember Me extends to 30 days.
4. 401 from tenant context — `/me` on a wrong-tenant host returns non-401 or 401; only a true 401 clears.
5. Hostname/origin change — `localStorage` is per-origin, so `app.` vs `{slug}.` vs `www.` do not share a session. **By design** (tenant isolation); not changed.

**Not verified in a real browser/production.** The original problem must not be considered resolved in production until checked after deployment (desktop + Safari/iOS).

## Changes
- `AuthController::login` honours optional boolean `remember` → 30-day token (`REMEMBER_TOKEN_TTL_DAYS`); default stays 7. Register/handoff unchanged (7). Always an explicit `expires_at`; never non-expiring.
- `LoginRequest`: `remember` => `sometimes|boolean`.
- `auth.ts`: `login(email, password, remember)`, `landingPathFor(role)`, `checkStoredSession()` (verifies via `/me`; role taken from `/me`, never from cached user).
- `login/page.tsx`: on mount with a saved token (not demo) verify via `/me` → redirect `/dashboard` or `/me` (`self_service`); invalid → form; network/5xx/403 → form **without clearing the token**. Any user interaction (submit/demo) invalidates the pending result (no redirect loops/races). Localized "Remember me" checkbox + restoring state.
- `api.ts`: a 401 clears only the token that was sent.
- Messages `login.remember`, `login.restoring` (ar/en).
- Unchanged: logout revokes current token; password reset still deletes all tokens (`AuthRecoveryService`); passwords never stored; Demo Mode untouched.

## Risks / remaining
- 30-day tokens in `localStorage` widen the XSS-theft window (inherent to the existing design; httpOnly cookies would be a separate project). Token is tenant-bound by SetTenant/hostname checks.
- Tokens issued before deploy keep their 7-day expiry.
- `/me` is called on `/login` only when a token exists; a hostname-mismatched token shows the form and keeps the token.
- Repo-wide `tsc` has pre-existing errors in unrelated test files (none in touched files).

## Hardening round (PR review)

Two race conditions found in review, both fixed:

1. **`api.ts` — stale 401 redirected the browser.** The first revision only guarded `clearToken()`; the redirect to `/login` still fired for a 401 belonging to an old token. A shared `handleUnauthorized(sentToken)` now does *both* the clear and the redirect only if `getToken() === sentToken`. The same flaw existed in `fetchPrivateFileUrl` (unconditional clear + redirect) and is fixed through the same helper. A 401 for the current token still clears it and redirects once (not when already on `/login`).
2. **`checkStoredSession()` — stale `/me` could persist a user.** It now captures the token before the request and, after it settles, returns the new `superseded` status (no `persistUser`, no redirect) if the token changed, was removed (logout), or Demo Mode started meanwhile (so the demo user is never overwritten). A 401 for the unchanged current token (which `api` itself clears) is still reported `invalid`. The login page treats `superseded` as "show the form" (no navigation).

### Tests (new: `web/src/lib/auth-session-race.test.ts`, 9 cases)
