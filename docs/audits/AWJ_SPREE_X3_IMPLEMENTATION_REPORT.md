## 1) العقود المصدرية (مُتحقَّق منها من متحكمات Laravel، لا مفترضة)
| المصدر | العقد |
|---|---|
| `GET store/v1/products` | منتجات `is_active` ذات `CommerceListing.is_published` على قناة المضيف فقط · `per_page` ≤ 100 · `meta.pagination.total/last_page` · ترتيب مستقر (`name` ثم `id` تنازلياً) · القائمة تحمل `updated_at` و`thumbnail_url` **ولا تحمل** المعرض (`media` في التفصيل فقط) |
| `GET store/v1/categories` | شجرة واحدة غير مُرقَّمة، النشطة **والمنشورة** فقط، بعمق 3 مستويات، بلا تواريخ |
| المضيف = سلطة المستأجر | `storefrontFetch()` يمرّر `X-Storefront-Forwarded-Host`؛ الباكند يحسم المستأجر والقناة منه |
| صيغة الروابط | `/{country}/{locale}/products/{id}` و`/c/{id}` (الـslug/permalink = UUID في AWJ) |
| الأسواق | سوق AWJ ثابت واحد (`getMarkets()`)، اللغتان `ar`/`en`، اللغة الافتراضية من إعداد المتجر |

لم يُخترع أي endpoint. ما لا تدعمه الواجهات الحالية (معرض الصور، `lastmod` للتصنيفات، تصنيفات أعمق من 3 مستويات) مذكور في §7.

## 2) قبل / بعد
| | قبل | بعد |
|---|---|---|
| مصدر البيانات | `getClient()` من Spree (أسواق/عدّ/صفحات) + `"use cache: remote"` | `storefrontFetch` على `store/v1` فقط، بلا ذاكرة مؤقتة عابرة للطلبات |

| قراءات الكتالوج | لكل سوق×لغة: استدعاء عدّ + صفحة أولى مكرّرة، وشريحة 10k رابط قد تتطلب ~100 طلب | ملف sitemap بتكلفة **ثابتة معروفة سلفاً** (§10): 5 صفحات منتجات؛ الكتالوج يُقرأ مرة لكل طلب ويُشارَك بين اللغتين؛ الفهرس يقرأ صفاً واحداً (`per_page=1`) |

| فشل الـAPI | `200` فارغ أو ناقص (المنتجات تُسقَط بصمت) | تسجيل خادمي (حالة/رمز فقط) + خطأ عام 5xx؛ الفهرس وrobots.txt يتراجعان إلى `sitemap/0.xml` |
| الإجمالي فوق الحد (100k) | اقتطاع صامت | `console.warn` معلن |
| صفحة قصيرة (الكتالوج تغيّر أثناء القراءة) | غير مرصود | تحذير معلن |
| صورة المنتج | معرض كامل (Spree) | الصورة الرئيسية فقط، رابطها مطلق على المضيف عبر وكيل الوسائط |
| `lastmod` | `updated_at` | `updated_at` للمنتجات إن صحّ؛ التاريخ غير الصالح يُحذف لا يُختلق |

## 5) قرارات التصميم المهمة
1. **الفشل يرمي لا يُرجع فارغاً:** خطة X3 تطلب «503/فارغ مُعلَن»؛ مسارات metadata في Next لا تضبط الحالة، فيُرمى خطأ عام (5xx) ليعيد الزاحف المحاولة وتراه المراقبة. لا نصف-sitemap (إسقاط المنتجات مع إبقاء التصنيفات) كما كان.
2. **أساس الرابط من المضيف:** أي أساس ثابت يجعل مستأجراً يعلن نطاق آخر. مضيف بصيغة غير صالحة يُتجاهل.
3. **بلا ذاكرة مؤقتة:** `"use cache"` لا يجتمع مع `headers()` وأي مفتاح بلا المضيف يعبر المستأجرين (شرط قبول H0).
4. **إزالة `/c`** تصحيح لمدخل 404 لا تغيير «اصطلاح».

## 10) إصلاح Codex P1 — ميزانية معدّل الطلبات (`EnforcePublicApiRateLimit:unauth`)
**الحقائق من الباكند** (`app/Http/Middleware/EnforcePublicApiRateLimit.php`, `app/Support/PublicApiRateLimits.php`, `routes/api_storefront.php`):
- مسارات `store/v1` (`products`، `categories`، `storefront`…) كلها خلف `unauth`: **30 طلباً / نافذة ثابتة 60 ث**.
- المفتاح `pubapi:unauth:ip:sha1(IP)` — أي **IP خادم Next.js**، لا المستأجر ولا المضيف: الميزانية **مشتركة بين كل المستأجرين وكل قراءات المتجر الحيّة**. كل طلب يُحتسب (بما فيها 404)، والتجاوز يعيد 429 + `Retry-After` ولا يمدّ النافذة. العدّاد على `file` cache بنسخة واحدة (وثّق الباكند أن التوسّع الأفقي يضعف الحدّ).
- الحدّ الأقصى 100 منتج/صفحة ⇒ سقف نظري **3,000 منتج/دقيقة** لكل الخادم، قبل خصم حركة المتجر. لا يغيّر التجميع أو التوازي شيئاً.

**الخلل:** شريحة بـ10k رابط كانت تصل إلى ~100 طلب منتجات (وفي متجر 3,000+ منتج تتجاوز 30)، فتفشل الشريحة ويُستهلك سقف المتجر الحيّ.

**التصميم المنفَّذ (بلا endpoint جديد):**
1. **ملفات sitemap بتكلفة ثابتة:** الملف 0 = الصفحات الثابتة + كل التصنيفات + صفحات المنتجات 1–5؛ الملف k = الصفحات 5k+1…5k+5 (500 منتج لكل لغة). تكلفة الملف ≤ **7 طلبات** (0) أو **6** (k>0)، والفهرس **2**. متجر 100 ألف منتج = 200 ملف.
2. **حجز مسبق + ميزانية:** كل استدعاء يحجز تكلفته قبل أي طلب؛ الحدّ الافتراضي **15 من 30 لكل 60 ث** لكل عملية (`SITEMAP_UPSTREAM_BUDGET_PER_MINUTE`). فوق الميزانية ⇒ فشل مغلق **بلا أي نداء للـAPI** (خطأ عام + سجل «retry after Ns»).
3. **429:** يُلتقط `Retry-After` في `StorefrontApiError`، وتبدأ فترة تبريد (مسقوفة بنافذة واحدة) لا تُجرى فيها أي طلبات. **لا إعادة محاولة** في الخادم؛ الزاحف هو حلقة الإعادة. السجل لا يتضمن رسالة الـAPI.
4. **العزل:** لا بيانات كتالوج محفوظة بين الطلبات؛ العدّادات فقط. التبريد والميزانية عالميان عمداً لأن حدّ الـAPI نفسه لكل IP.
5. فهرس/robots.txt: تكلفته 2، وعند نفاد الميزانية يتراجع لملف واحد (سجل معلن).

**ما يبقى حداً معمارياً (blocker للمتاجر الكبيرة):** السقف الفعلي = ميزانية الـsitemap (15/دقيقة) ≈ ملفان/دقيقة ≈ 1,000 منتج/دقيقة؛ متجر 100 ألف منتج يحتاج ~100 دقيقة زحف وهو مقبول للزاحف لكنه يعتمد على إعادته للمحاولة بعد 5xx. وحركة المتجر الحيّة التي تتجاوز ~15 طلب/دقيقة من الـIP نفسه ما زالت قادرة على إشعال 429 للـsitemap (يُعالَج بالتبريد، لكن الحارس لا يرى حركة العمليات الأخرى). الحل الجذري يتطلب تغييراً في الباكند (خارج نطاق X3 وبلا اختلاق): (أ) فئة حدّ/endpoint مخصّص للـsitemap بمعرّفات خفيفة ومؤشر (cursor) وصفحات أكبر ومفتاح حدّ لكل مستأجر لا IP مشترك، أو (ب) توليد الـsitemap خلفياً وتخزينه (R2/Redis) وخدمته ساكناً. يوصى بفتح شريحة منفصلة.

**تغيير التخطيط:** الملفات صارت بحسب صفحات المنتجات لا 10k رابط؛ ترتيب الروابط داخل الملف 0 لكل لغة: ثابتة ← تصنيفات ← منتجات.

**اختبارات الميزانية** (`sitemap.rate-limit.test.ts`، باكند وهمي يطابق المحدِّد: نافذة ثابتة، مفتاح IP واحد، 429 + Retry-After، ساعة مزيّفة): تكلفة الملف ≤ 7 لكتالوج 100k؛ زحف كتالوج 100,000 منتج كاملاً عبر 200 ملف بلا تكرار وبـ**صفر 429 من الـAPI**؛ لا يزيد أي نطاق 60 ث عن 15 طلباً؛ رفض فوق الميزانية بلا نداء ثم تعافٍ؛ التراجع المحسوب للفهرس؛ تبريد 429 بلا نداءات ثم استئناف وملف كامل؛ سقف Retry-After؛ مشاركة التبريد بين المضيفين؛ عزل المستأجرين. طفرات (حذف الحجز، حذف التبريد، 10 صفحات/ملف) كُشفت.
