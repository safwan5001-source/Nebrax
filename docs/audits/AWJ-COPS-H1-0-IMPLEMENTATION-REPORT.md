## 2. قرارات تصميمية ثبّتها ADR-29 ضمن حدود الموافقة (للمراجعة)

1. **`acceptance_mode` لقطة على الطلب لا قراءة حيّة** — حتى لا يعيد تغيير إعداد المتجر تفسير طلبات قائمة (مبدأ ADR-01 §5). `NULL` = تلقائي، فالبوابة المغلقة ⇒ مسار الإنشاء بلا أي كتابة جديدة.
2. **الرفض متاح فقط مع فتح بوابتي القبول والإلغاء معاً** — لأن الرفض إلغاء (R-3)، فلا يصبح القبول اليدوي طريقاً خلفياً لإلغاء بوابته مغلقة. هذا قيد محافظ مشتق من R-3/R-6b، لا قرار جديد.
3. **صف رأس مخصص `commerce_order_feed_heads`** بدل صف `tenants` كي لا يتسع تنازع مِرساة الترقيم/الأستاذ.
4. **ترتيب الأقفال:** ADR-29 لا يعيد ترتيب أي قفل قائم؛ يضيف قاعدة واحدة — الرأس آخراً — ويدرج التنفيذ (H2) بعد الطلب.
5. **حد التصعيد للأداء** (p95 إضافي > 50ms تحت 20 كاتباً، أو أي جمود) — يجعل شرط R-2 قابلاً للقياس.
6. **اكتشاف مسبق مُسجَّل لـH1-1:** `completeCaptured` له 5 مستدعين، وقد يُستدعى داخل معاملة خارجية؛ إن ثبت ذلك فإفراغ الأحداث يُؤجَّل إلى المالك الخارجي، وإلا تتوقف الشريحة وتُصعَّد.

- لا تغيير سلوكي ⇒ لا أثر على العزل أو RBAC أو المحاسبة أو المخزون.
- **القيود المحاسبية الناتجة: لا شيء** (شريحة توثيق).
- ADR-29 يثبّت للشرائح القادمة: `commerce.orders.manage` و`commerce.orders.cancel` لـowner/admin عبر `*` فقط بلا زرع؛ 404 موحَّد لعزل المستأجر؛ رفض المقيَّد بمخازن حتى H2-2؛ لا PII في الأحداث.
