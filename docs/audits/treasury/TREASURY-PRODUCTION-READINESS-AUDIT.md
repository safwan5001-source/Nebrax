## 0. الملخّص التنفيذي

| | |
|---|---|

## 3. فحوص الإنتاج الجاهزة (لم تُشغَّل على الإنتاج)

الملف: `docs/audits/treasury/sql/treasury-readiness-scans.sql` — **معاملة `READ ONLY` ثم `ROLLBACK`**، مهلة 60ث، مخرجاتها أعداد (ومعرّفات مستأجرين فقط في Q03b). **التحقق المحلي:** شُغِّلت الاستعلامات الستة عشر على PostgreSQL 16 بسيناريو مُصطنع يحوي حالة واحدة من كل نوع، فعادت كل الأعداد المتوقعة (رئيسية ≠1110 = 1، مسودة بحساب = 1، جلسة غير مثبّتة = 1، مرجع جلسة عابر للمستأجر = 1، طريقة دفع خارج 1110 = 1، عدم تطابق تحصيل POS = 1، مرتجع مستقل = 1، مرتجع/إشعار آجل = 1، عملة أجنبية = 1، قيود غير متوازنة = 0، ردود خارج 1110 = 0).

| الفحص | يجيب عن | معيار القبول |
|---|---|---|
| Q01 | السياسة المخزَّنة | **كلها legacy/غير مضبوطة** (وإلا: شذوذ يُحقَّق فيه قبل أي شيء) |
| Q02، Q03، Q03b | T4-أ: مستأجرون بلا رئيسية صالحة، أو رئيسيتهم ≠1110، أو عملة/حساب غير صالح | لا يمنع التفعيل العام؛ **يحدد أهلية كل مستأجر** (المستأجر غير الصالح لا يُفعَّل له) |
| Q04 | T4-ب: مسودات فاتورة نقدية تحمل `cash_account_id` | تُراجَع قبل تفعيل مستأجرها (تصير فعّالة عند التفعيل) |
| Q05، Q05b | T6-أ: جلسات POS المفتوحة بلا خزينة مثبّتة، أو مثبّتة على حساب غائب/عابر/معطّل | **Q05b = 0 إلزامي**؛ Q05 تُغلق جلساته قبل تفعيل مستأجرها |
| Q06 | T6-ب: طرق دفع نقدية فعّالة مرتبطة بغير 1110 | مستأجرو `linked_not_1110` تتغير قيود رد POS عندهم عند التفعيل (إخطار + قبول) |
| Q07، Q07b | أثر D-T5-2/D-T6-2: مرتجعات/إشعارات نقدية آخر 90 يوماً بمصدر مستقل أو آجل | معلومة تشغيلية: هذه العمليات **سترفض** عند التفعيل؛ يلزم تدريب على «رصيد ثم سند صرف» |
| Q08 | T6: فواتير POS حُصِّل نقدها خارج خزينة جلستها | سيرفض ردها النقدي (`refund_treasury_mismatch`)؛ معلومة |
| Q09 | عزل المستأجر: مراجع عابرة للمستأجر | **كلها 0 إلزامي** |
| Q10 | خزائن بعملة غير عملة المستأجر | تُستبعد من أهلية مستأجرها |
| Q11 | قيود غير متوازنة | **0 إلزامي** |
| Q12 | ردود (مرتجع/إشعار/استبدال) دائنة لخزينة غير 1110 منذ نشر T6 | **0 إلزامي** (البوابة مغلقة) — يثبت عدم وجود تغيير محاسبي غير مقصود |

## 5. خطة التفعيل التدريجي (بعد موافقتك، وكل مرحلة بموافقة صريحة)

**المرحلة 0 — ما قبل التفعيل (قراءة فقط):**
1. تأكيد أن الإصدار المنشور = `cc8b1a4b6` (أو لاحق يحتوي T6)، وأن الخدمات الثلاث سليمة، وأن قيمة البوابة `false`.
2. تأكيد نسخة احتياطية/PITR حديثة، وتشغيل ملف الفحوص على نسخة قراءة.
3. تقييم النتائج بمعايير §6؛ بناء قائمة المستأجرين المؤهلين (Q02/Q03/Q10 نظيفة، Q05 مغلقة الجلسات، Q04 مراجَعة).

**المرحلة 1 — فتح البوابة بلا أثر:** ضبط `TREASURY_CASH_SALE_ROUTING_ENABLED=true` وإعادة تشغيل API. كل المستأجرين ما زالوا `legacy` فلا يتغير أي قيد. التحقق: Q12 = 0، اختبار دخان للمبيعات النقدية والمرتجعات، وسجلات بلا أخطاء جديدة.

**المرحلة 2 — مستأجر داخلي/تجريبي:** `PUT /sales-settings` بالسياسة `main` لمستأجر داخلي. سيناريو دخان مكتوب: بيع نقدي، مرتجع عام، إشعار دائن نقدي، رد POS، استبدال بفائض نقدي، وحالات الرفض (مستقل، آجل، عدم تطابق). مقارنة القيود بجداول تقارير T4–T6.

**المرحلة 3 — تجريبي محدود (1–3 مستأجرين مؤهلين، 3–7 أيام):** إخطار مسبق (W2/W3)، مراقبة يومية: Q11، Q12 (متوقع الآن ردود خارج 1110 للمستأجرين المفعَّلين فقط)، عدد رفوض 422 بحسب السبب في السجلات.

**المرحلة 4 — دفعات:** مستأجرون مؤهلون على دفعات مع نفس المراقبة. `explicit_required` عند الطلب فقط.
