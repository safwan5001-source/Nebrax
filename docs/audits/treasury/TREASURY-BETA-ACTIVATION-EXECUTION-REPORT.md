## 5. بنود معلّقة ومخاطر متبقية

| البند | الحالة / الأثر |
|---|---|
| ⚠️ **حذف `tmp-treasury-scan`** | **معلّق.** أداة `delete-service` طلبت تأكيداً منك ولم يصلها جواب خلال 60 ثانية، فلم يُحذف. الخدمة الآن بوضع **قراءة فقط** (`default_transaction_read_only=on`) وتنتهي حاويتها تلقائياً خلال ~ساعة (restart=NEVER)، لكنها تحمل مراجع اتصال بالقاعدة وصلاحية المستخدم الأعلى. **يجب حذفها**: أجِب على مطالبة Railway، أو أخبرني لأعيد المحاولة، أو احذفها من لوحة Railway |
| بيانات اختبارية قليلة | لا فواتير نقدية مرحَّلة أصلاً؛ **أول مسار نقدي حقيقي سيمر عبر المنطق الجديد لأول مرة**، فأوصي بتجربة يدوية قصيرة (بيع نقدي → مرتجع → إشعار دائن → POS) على مستأجر تجريبي |
| تغيير سلوكي مقصود | إشعار دائن/مرتجع نقدي **مستقل أو لفاتورة آجلة/POS-مدفوعة** يُرفض بـ`refund_source_required` (البديل: إشعار `credit` + سند صرف). ردّ POS النقدي يخرج من خزينة الجلسة ويُرفض عند اختلاف خزينة التحصيل أو جلسة بلا خزينة |
| `awj-scheduler` | **لا يتأثر**: لا أمر مجدول يستدعي خدمات الترحيل الموجَّهة بالعلم، وترحيل المتجر الإلكتروني فواتيره `credit`. لم يُغيَّر |
| بيئة Railway اسمها `production` | البيئة الوحيدة؛ التفعيل نُفِّذ على أساس أنها Beta كما أكّدتَ |
| مخارج 1110 المرمَّزة (أصول، رواتب، مصروفات، مشتريات) | بقيت (خارج النطاق): تخرج من 1110 لا من الرئيسية؛ لا أثر على سلامة الدفتر |
| ترتيب JSON | تحويل `settings` عبر `jsonb` أعاد ترتيب المفاتيح وأزال تكرارها؛ لا أثر دلالي (القراءة بالمفتاح) |
| نشر `main` الجديد | `nibras-api` ينشر تلقائياً من `main`؛ أي دمج لاحق يعيد النشر والعلم يبقى مضبوطاً كمتغير بيئة |

## 6. التراجع

| المستوى | الإجراء |
|---|---|
| لمستأجر | `PUT /sales-settings` ← `cash_sale_treasury_policy: "legacy"` (فوري) |
| لكل المستأجرين | حذف/ضبط `TREASURY_CASH_SALE_ROUTING_ENABLED=false` على `nibras-api` (إعادة نشر واحدة) فيعودون إلى `legacy` مهما خُزِّن |
| القيود المرحَّلة | لا تُعاد كتابتها. بيع حُصِّل في غير 1110 أثناء التفعيل لا يُردّ نقداً بعد التراجع (`CashSaleRefundGuard`) بل عبر إشعار `credit` + سند صرف |
