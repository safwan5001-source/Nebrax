# ADR-010 — Delivery Notes to Sales Invoice Draft

- **Status:** Accepted
- **Scope:** PR-10
- **Decision owner:** Sales, Inventory, and Intelligent Document Center domains

## Context

يعالج PR-9 إثبات التسليم التشغيلي فقط ولا ينشئ فاتورة أو تخصيصاً أو أثراً مالياً. يحتاج Nebrax الآن إلى تحويل مجموعة من سندات التسليم **المؤكدة والمتوافقة** إلى مسودة فاتورة مبيعات واحدة، مع حفظ مصدر كل سطر وقطع إعادة فوترة السند نفسه. لا يجوز أن يتحول هذا المسار إلى قناة ثانية لإنشاء الفواتير أو إلى ترحيل ضمني؛ لأن `InvoiceService::create()` و`InvoiceService::post()` يملكان مسؤوليتين منفصلتين في المجال القائم.

> إنشاء المسودة لا يساوي ترحيلها: **لا قيد** عند إنشاء مسودة من سندات التسليم.

## Decision

ينشئ `DeliveryNoteSalesInvoiceDraftBuilder` مسودة فاتورة مبيعات واحدة فقط من خلال استدعاء `InvoiceService::create()` مرة واحدة داخل معاملة قاعدة بيانات. لا ينشئ الباني `Invoice` أو `InvoiceLine` مباشرة. تبقى `InvoiceService::post()` وحدها مالكة لترحيل الفاتورة والقيد وحركة المخزون والتكلفة وفق الدورة الحالية.

| البند | القرار الملزم |
|---|---|
| نطاق المصدر | سند واحد كامل أو أكثر، كلها `confirmed`، غير ملغاة، غير مرتبطة سابقاً، ومن المستأجر والفرع النشطين نفسيهما. |
| التوافق | كل السندات المختارة تشترك في العميل والمستودع؛ لا يسمح MVP بالخلط أو إعادة التوزيع. |
| التخصيص | `delivery_note_invoice_allocations` يربط رأس كل سند بفاتورة واحدة؛ لا تخصيص جزئي ولا كمية متبقية. |
| تتبع السطور | `delivery_note_line_invoice_links` يسجل كل سطر مصدر إلى سطر فاتورة مع الكمية الدقيقة والبسط/المقام والوحدة والعامل. |
| الكمية النسبية والمخزون | لا يرحّل الباني؛ وعند ترحيل الفاتورة لاحقاً يحوّل `baseQuantity()` البسط/المقام مع عامل الوحدة إلى عدد صحيح من وحدات المخزون. يرفض التحويل غير القابل للتمثيل عددياً بدلاً من خصم كمية خاطئة. |
| إنشاء الفاتورة | `InvoiceService::create()` مرة واحدة؛ الإجماليات والسطور تظل مشتقة عبر خدمة الفواتير. |
| التسعير | كل قرار سطر صريح بالهللات الصحيحة (`unit_price` و`discount` و`tax_rate`). الاختيار الصريح لقائمة السعر، أو القائمة الافتراضية النشطة للعميل عند غيابه، يعاد التحقق منهما في المعاينة والبناء. |
| التجميع | يدمج الباني السطور المتطابقة في المنتج/الوحدة/العامل/السعر/الضريبة/سبب تجاوز الحد، ويجمع خصم **كل سطر مصدر** بأعداد صحيحة محكومة. |
| حالة الفاتورة | الفاتورة الناتجة `draft` فقط؛ لا يوجد زر أو استدعاء post في هذا المسار. |

## Trusted scope, idempotency, and concurrency

تأتي هوية المستأجر والفرع من `TenantContext` و`BranchContext`، وتأتي `actor_id` من المستخدم المصادق عليه فقط؛ تمنع Form Request تمريره من جسم الطلب. لا يقبل المسار tenant أو branch أو invoice أو إجماليات أو دفع أو قيد أو مخزون أو مزود. المعاينة غير كاتبة وتعيد فقط إسقاطات المصدر المؤهلة وقرارات السعر المقترحة الآمنة.

يفرض البناء ترتيب UUID حتمياً. داخل المعاملة يقفل مرساة الفرع أولاً، ثم سجل idempotency، ثم سندات التسليم والسطور والتخصيصات بترتيب ثابت. سجل `delivery_note_invoice_draft_builds` فريد في `(tenant, branch, idempotency_key)` ويحفظ checksum لقرار البناء. يعبّر checksum عن الحمولة الدلالية: إذا حذف العميل `invoice_date`، يحفظ الإنشاء الجديد تاريخ اليوم في المسودة لكن يبقى حقل checksum `null` ثابتاً، فيعيد الطلب نفسه بعد تغير اليوم المسودة ذاتها؛ أما تغيير حمولة دلالية فيبقى تعارضاً. يُفحص حد خطة الفواتير **بعد** اكتشاف replay المطابق وداخل بناء الطلب الجديد فقط؛ لذلك لا يحجب retry الآمن بعد استهلاك آخر حصة، بينما يرفض إنشاءاً جديداً عند بلوغ الحد. تضيف القيود الفريدة على رأس السند وسطره طبقة قاعدة بيانات تمنع إعادة الفوترة حتى في السباق.

## Immutability and audit

الجداول الثلاثة الجديدة immutable ومرتبطة بمراجع UUID مقيّدة (`restrict`). بعد ربط المصدر لا يمكن تعديل أو حذف أو نسخ مسودة الفاتورة المرتبطة عبر مسارات الفاتورة العامة، ولا حذف أو تعديل سطرها مباشرة، ولا إلغاء سند التسليم المصدر. يسجل الباني حدثاً append-only باسم `sales_invoice_draft_created` لكل سند، مع رقم ومعرّف الفاتورة والتخصيص وبصمة طلب idempotency والسبب الذي أدخله المستخدم.

هذه سياسة حماية لا سياسة تصحيح. لا يوجد unlink أو rebuild أو تحرير يدوي للتخصيص في PR-10. أي مسار تصحيح لاحق يحتاج ADR وعقد تدقيق وقيود عكس واضحة قبل أن يفتح رابطاً محمياً.

## Explicitly excluded effects

لا يستدعي الباني `InvoiceService::post()` أو `LedgerService` أو `InventoryService` أو `PaymentService`. لا يكتب `JournalEntry` أو `JournalLine` أو `Payment` أو `StockMovement` ولا ينشئ Partner أو Product أو Unit أو Warehouse أو CostCenter. لا يفعّل AI أو شبكة مزود أو تخزين دائم أو Redis أو Worker أو ClamAV أو Render أو قنوات، ولا يغير `provider_network_enabled=false`، ولا ينشر أو يشغل migrations إنتاجية.

## Access and user interface

تتطلب المعاينة والبناء `delivery_notes.invoice`، بالإضافة إلى فصل الاستحقاق التجاري `sales.invoicing`: المعاينة تحت `read` والبناء تحت `write` وحد الخطة `invoices`. لا تمنح الواجهة الصلاحية؛ فهي تخفي الإجراءات عند غيابها، بينما يبقى الإنفاذ في API إلزامياً. تُبكفأ صلاحية المحاسب النظامي للمستأجرين القائمين بهجرة idempotent تحفظ قائمة صلاحيات الدور كما هي ولا تمس الأدوار المخصصة؛ التسجيلات الجديدة تأخذها من المصفوفة الحالية.

المعالج المشترك يبدأ من اختيار قائمة سندات التسليم أو من اختصار مسمى في نموذج فاتورة جديد. يعرض السندات المؤكدة فقط، حالة الرابط الموجودة وأسباب التعطيل، معاينة التوافق، التسعير الصريح لكل سطر، سبب القرار، مفتاح idempotency داخلي، ورابط المسودة الناتجة. يطبق `MAX_SOURCE_LINES` المركزي نفسه في preview وbuild وForm Request: تعيد المعاينة عدد المصدر والحد وسبب عدم أهلية واضحاً قبل التسعير، ويرفض البناء العدد نفسه تحت القفل. يحمل فهرس السندات روابط التخصيص والفاتورة دفعة واحدة كي يظهر السند المرتبط غير متاح قبل الاختيار. لا يشترط المعالج `invoices.view`: إذا منع دورٌ محدود قراءة قوائم الأسعار، يظهر خطأ الوصول وتظل السندات والمعاينة متاحتين بقائمة العميل الافتراضية؛ ولا يظهر رابط الفاتورة العام أو رابط تفاصيل السند لذلك الدور، مع بقاء حالة الارتباط مرئية لمنع إعادة الفوترة. لا يستخدم نموذج الفاتورة العام كمسار استيراد صامت، ولا يعرض الترحيل أو الدفع. العرض متاح بالعربية والإنجليزية، RTL وLTR، الوضعين الفاتح والداكن والجوال، مع fixture محلية موسومة للعرض فقط.

## Rejected alternatives and deferrals

| البديل المرفوض أو المؤجل | سبب القرار |
|---|---|
| إنشاء `Invoice` و`InvoiceLine` مباشرة من الباني | يتجاوز حساب الإجماليات وملكية دورة الفاتورة التي يوفرها `InvoiceService::create()`. |
| ترحيل الفاتورة عند بناء المسودة | يخلط قرار التجميع بالمحاسبة والمخزون والدفع ويخالف فصل `create()` عن `post()`. |
| تخصيص جزئي أو كميات متبقية | يحتاج سياسة دقيقة للباقي والعكس والخصومات والضرائب؛ خارج MVP. |
| unlink أو rebuild لمسودة مرتبطة | يقطع سلسلة التدقيق ويفتح مسار تصحيح غير معتمد. |
| تحديث مسودة مرتبطة عبر نموذج الفاتورة العام | قد يعيد بناء السطور ويفقد أثر المصدر؛ تحظره حواجز الخادم. |
| استنتاج سعر وحدة بديلة | قائمة الأسعار تعتمد سعراً صريحاً لكل وحدة؛ لا يوجد تحويل سعري صامت. |
| توقيت مخزون جديد عند تأكيد التسليم | سيصطدم بملكية `InvoiceService::post()` الحالية وقد يخصم المخزون مرتين. |
| المرتجعات أو القنوات أو التكاملات | لكل منها مصدر وحركة عكس ودليل خاص، وتحتاج قراراً مستقلاً. |

## Verification

تغطي الاختبارات إنشاء مسودة من عدة سندات، الروابط والأحداث، الكميات النسبية وجمع الخصم، وترحيل نصف عبوة بمعامل 10 إلى خمس وحدات مخزون أساس فقط، وقائمة السعر الصريحة والافتراضية، idempotency، replay بعد حد الخطة، وreplay لتاريخ فاتورة محذوف بعد تغير اليوم، وحدود 499/500/501 لسطر المصدر، ونسخة السند، والعزل، وRBAC والاستحقاق وحقول spoofing، وحواجز تعديل/حذف/نسخ الفاتورة أو إلغاء المصدر. يثبت اختبار API إسقاط السند المرتبط وغير المرتبط في القائمة، واختبار الدور المخصص أن `delivery_notes.view` و`delivery_notes.invoice` يكفيان للبناء من دون `invoices.view`. يثبت اختبار الهجرة المستأجر القديم والجديد والدور المخصص وidempotency وrollback. يعد الاختبار الجداول المحاسبية والمخزون والدفع قبل وبعد البناء لإثبات انعدام الأثر. تخضع الهجرة لاختبارات SQLite محلياً وتغطي CI SQLite وPostgreSQL. تغطي الواجهة Vitest وPlaywright fixture محلية موسومة لرسالة حد المصدر وتعطيل الإنشاء، وحالة الرابط في تفاصيل السند للدورين المقيّد والمخوّل، وحالة السند المرتبط والمتاح، والمسودة المتوافقة والخطأ المختلط وRTL/LTR والجوال؛ وهي ليست بيانات إنتاج أو معاينة منشورة.
