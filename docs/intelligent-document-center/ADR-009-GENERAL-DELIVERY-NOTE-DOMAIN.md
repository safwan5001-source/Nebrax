# ADR-009 — General Delivery Note Domain

- **Status:** Accepted
- **Scope:** PR-9
- **Decision owner:** Sales, Inventory, and Intelligent Document Center domains

## Context

يحتاج Nebrax إلى إثبات تشغيلي عام لتسليم مبيعات يمكن إنشاؤه يدويًا اليوم ويصبح مصدرًا موثوقًا لاحقًا لبناء **مسودة فاتورة مبيعات واحدة من عدة سندات**. هذا الإثبات ليس ملفًا مستخرجًا ولا عملية محطة وقود ولا مستند شراء، ولذلك لا يملك `DocumentCenter` أو نطاق الوقود أو `ProcurementDocument` دورة حياته العامة.

أظهر تدقيق دورة المبيعات أن `InvoiceService::post()` هو موضع الأثر الحالي للفواتير: فهو يرحّل القيد عبر `LedgerService` ثم يطلب من `InventoryService` تسجيل تكلفة المبيعات وحركة المخزون. إن إنشاء `StockMovement` عند تأكيد السند الآن سيجعل دورة الفاتورة اللاحقة تخصم الكمية للمرة الثانية. كما أن إنشاء Invoice أو InvoiceLine في هذه المرحلة يخلط دليل التسليم مع قرار الفوترة والتسعير والضريبة الذي يملكه PR-10.

> سند التسليم في PR-9 هو **إثبات تشغيلي للتسليم وقاعدة للفوترة اللاحقة**، بينما تبقى الحركة المخزنية الحالية مملوكة لدورة الفاتورة إلى أن يُعتمد تصميم موحد يمنع الخصم المزدوج.

## Decision

ينشئ PR-9 نطاقًا عامًا مستقلًا داخل الـModular Monolith يتكون من `DeliveryNote` و`DeliveryNoteLine` و`DeliveryNoteEvent` و`DeliveryNoteService`. جميع النماذج تحمل UUID و`tenant_id` و`branch_id` صريحين وتستخدم تصنيف الفرع التشغيلي. السطر والحدث لا يعتمدان على علاقة الرأس وحدها في العزل، بل يخزنان نطاقهما أيضًا؛ ويتحقق حدث السجل عند الإضافة من تطابق نطاقه مع الرأس في سياق موثوق.

| البند | القرار الملزم |
|---|---|
| النطاق | وحدة مبيعات عامة خارج `DocumentCenter` وFuel وProcurement؛ لا توجد تسمية مزود أو استخراج أو قناة. |
| الرأس | رقم داخلي، مرجع خارجي اختياري غير فريد عالميًا، عميل، مستودع، تاريخ تسليم، ملاحظات، حالة ونسخة optimistic. |
| السطور | منتج ووحدة وكمية ووصف اختياري ولقطات اسم/رمز المنتج والوحدة فقط؛ لا سعر أو ضريبة أو إجمالي أو JSON خام. |
| سجل الأحداث | append-only، لا يقبل تحديثًا أو حذفًا، وإضافته محروسة بممر خدمة المجال. |
| الحالة | `draft` و`confirmed` و`cancelled` فقط. الإلغاء انتقال محفوظ للتدقيق حتى للمسودة؛ لا حذف مادي للسند المؤكد. |
| نقطة الكتابة | `DeliveryNoteService` فقط للإنشاء والتعديل والتأكيد والإلغاء؛ يمنع النموذج تعديل الحالة أو النسخة أو حقول القرار خارج ممر الخدمة. |
| الترقيم | `GeneratesDocumentNumbers` مع مرساة قفل الفرع و`max()+1`، مسجل في `DocumentNumberingCatalog` تحت سلسلة `delivery_note` وبادئة مبيعات قابلة للضبط افتراضيها `DN`. |

## Trusted scope and references

السياق الموثوق يأتي من `TenantContext` و`BranchContext`، ولا يقبل service أو API المستأجر أو الفرع أو الرقم أو الحالة أو الممثلين أو الطوابع الزمنية من جسم الطلب. العميل يجب أن يكون نشطًا ومرئيًا من نوع `customer` أو `both`. المستودع يجب أن يكون نشطًا ومربوطًا بفرع السند أو مركزيًا وفق عقد المستودعات القائم. المنتج يجب أن يكون نشطًا ومرئيًا؛ وتحل الوحدة حصريًا بواسطة `UnitConversion`، لذلك ترفض الوحدة الشكلية أو غير المرتبطة بقالب المنتج.

الكمية الصحيحة العادية عدد صحيح موجب ومحدود. وعند وجود كمية نسبية دقيقة يحفظ السطر البسط والمقام الصحيحين معًا من دون `float` أو `double`، بالإضافة إلى لقطة الوحدة؛ وهذا يحفظ المقدار القابل للفوترة لـPR-10 من دون تقريب نقدي أو تحويل كمي مخفي. لا ينشئ السند Partner أو Product أو Unit أو Warehouse تلقائيًا.

## Lifecycle and concurrency

ينشئ `create` مسودة مع حدث `created`. ولا يسمح `update` إلا لمسودة محجوزة بـrow lock ومطابقة `expected_version`، ثم يعيد حل العميل والمستودع والمنتجات والوحدات والكمية ويستبدل السطور ضمن المعاملة نفسها ويكتب حدث `updated`. يؤكد `confirm` مسودة مقفلة فقط، ويعيد التحقق من كل مرجع تحت القفل، ويكتب حدث `confirmed` واحدًا. وتفشل إعادة التأكيد أو النسخة القديمة بخطأ مجال واضح من دون حدث مكرر أو تغيير جزئي.

يتطلب `cancel` سببًا محدودًا ومستخدمًا مخولًا ونسخة متوقعة. ويسمح بالانتقال من المسودة أو المؤكد إلى `cancelled` مرة واحدة مع حفظ الممثل والطابع والسبب والحدث. لا يعيد الإلغاء السند إلى مسودة ولا يعيد استخدام رقمه.

## Explicitly excluded effects

لا يستدعي هذا النطاق `InvoiceService::create()` أو ينشئ `Invoice` أو `InvoiceLine` أو تخصيص فاتورة. ولا يستدعي `InventoryService` ولا ينشئ `StockMovement`. ولا يستدعي `LedgerService` ولا ينشئ `JournalEntry` أو `JournalLine` أو `Payment`. هذه ليست قيود واجهة؛ فهي حدود داخل خدمة المجال ومثبتة باختبارات تعدّ هذه الجداول قبل وبعد create/update/confirm/cancel.

لا يفعّل PR-9 شبكة مزود أو ذكاء اصطناعي أو تخزين دائم أو S3/R2 أو Redis أو Worker أو ClamAV أو Render أو قنوات WhatsApp أو بريد، ولا يغير `provider_network_enabled=false`، ولا ينشر ولا ينفذ migration إنتاجي.

## Access and API/UI

تستخدم المسارات `sales.invoicing` الموجود مع تفريق read/write، وتفصل RBAC إلى `delivery_notes.view` و`delivery_notes.manage` و`delivery_notes.confirm` و`delivery_notes.cancel`. امتلاك الاستحقاق لا يتجاوز RBAC وامتلاك RBAC لا يتجاوز الاستحقاق. تعرض الواجهة القائمة والفلاتر والنموذج وصفحة التفاصيل وسجل الأحداث بالعربية والإنجليزية، RTL وLTR، والوضعين الفاتح والداكن. لا يظهر زر إنشاء فاتورة؛ السند المؤكد للقراءة فقط.

تغطي واجهة API `GET/POST /delivery-notes` و`GET/PUT /delivery-notes/{id}` و`POST /delivery-notes/{id}/confirm` و`POST /delivery-notes/{id}/cancel` عبر Form Requests وResources. البحث مقيد برقم السند والمرجع واسم العميل، والفلاتر والترتيب والصفحات معزولة تلقائيًا بالفرع.

## Consequences and deferrals

يمنح هذا القرار PR-10 مصدرًا موثقًا ودقيقًا للكمية والوحدة ودورة الإلغاء، لكنه **لا** يمنحه بعد جدول تخصيص أو رابط فاتورة أو سياسة منع إعادة فوترة. يملك PR-10 فقط قرار اختيار عدة سندات مؤكدة، التحقق من عدم تكرار تخصيصها، وإنشاء مسودة Invoice عبر خدمة المبيعات، ثم تنسيق ملكية أثر المخزون لمنع الخصم المزدوج.

| البديل المرفوض | سبب الرفض |
|---|---|
| إنشاء Invoice عند تأكيد السند | يخلط دليل التسليم بتسعير وضريبة وفاتورة مؤجلة إلى PR-10. |
| إنشاء حركة مخزون عند التأكيد الآن | يتعارض مع ملكية `InvoiceService::post()` الحالية ويهدد بخصم مزدوج. |
| إعادة استخدام FuelSale أو FuelShift | نطاق محطة وقود متخصص وله دلالات إغلاق ومحطة لا تطابق سند تسليم عام. |
| إعادة استخدام ProcurementDocument | مستند شراء ومورد واستلام، لا دليل تسليم مبيعات لعميل. |
| وضع السند داخل Document Center | المركز يملك دليل الاستخراج والمراجعة؛ السند معاملة مبيعات مستقلة ويمكن أن يكون مصدره يدويًا أو لاحقًا نتيجة مراجعة. |
| بناء جدول invoice allocation الآن | يسبق PR الذي يملك قرار عدة سندات إلى فاتورة ويضيف جدولًا مستقبليًا بلا مالك حالي. |

## Verification

يتحقق PR-9 من دورة المجال وRBAC والاستحقاق والعزل وحقول spoofing والمراجع والوحدات والكمية والنسخ والترقيم وسجل الأحداث وانعدام الأثر المالي والمخزني. تُختبر الهجرة صعودًا وهبوطًا محليًا على SQLite، بينما تغطي CI نفسها SQLite وPostgreSQL. واجهة الويب لها اختبارات Vitest وترجمة عربية/إنجليزية متطابقة وبناء Next.js، وتستخدم Playwright fixture محلية موسومة بوضوح للقطات RTL/LTR والجوال؛ وهي ليست بيانات إنتاجية ولا معاينة منشورة.
