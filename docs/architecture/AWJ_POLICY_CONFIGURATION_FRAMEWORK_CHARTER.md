# AWJ Policy & Configuration Framework
## ميثاق إطار السياسات والإعدادات الموحد — أَوْج ERP

**المعرّف:** `AWJ-POLICY-FRAMEWORK`  
**القرار:** معتمد معماريًا بتاريخ 2026-11-03.  
**الحالة التنفيذية:** **مؤجّل؛ توثيق فقط.** لا موافقة على بناء الإطار المركزي أو جرد POLICY-0 أو ترحيل الإعدادات أو النشر.  
**القاعدة السارية فورًا:** **Build for Policy Readiness** — تلتزم المهام الجديدة وتطوير الوظائف القائمة بمبادئ هذا الميثاق من الآن *ضمن Scope المهمة*، حتى قبل إنشاء الإطار المركزي.  
**المرجع السابق المتكامل:** `design-system/foundations/configurable-policies.md` (ما زال مُلزمًا، لا يُستبدل بهذا الميثاق).

## 1. القرار والنطاق

يعتمد أَوْج توجهًا معماريًا لتوحيد **تعريف السياسات والإعدادات وضوابطها** تدريجيًا، مع قابلية ضبط ما يصح ضبطه لكل شركة، ودون المساس بسلامة النظام. لا يعني ذلك وضع كل الإعدادات في شاشة واحدة أو تحويل كل ثابت إلى خيار للمستخدم.

**المبدأ:** `Preserve → Register → Unify → Enhance`.
- **Preserve:** الحفاظ على السلوك والعقود والبيانات وواجهات البرمجة والإعدادات الحالية.
- **Register:** تسجيل مالك كل سياسة ومصدرها ونطاقها وقيمها الافتراضية.
- **Unify:** توحيد التعريف والحوكمة والتقييم عند ثبوت أمان ذلك، دون استبدال مخازن الإعدادات بشكل جماعي.
- **Enhance:** تحسين التخصيص تدريجيًا بعد الاختبارات والموافقات.

**النطاق يشمل الكل، لا المستقبل فقط:** جميع الوظائف المبنية والمُدمجة سابقًا، والموجودة حاليًا، والجاري تطويرها، وما سيُبنى لاحقًا؛ ERP والمحاسبة والمبيعات والمشتريات والمخزون والموارد البشرية والوقود وPOS وCommerce وStorefront والمتاجر وStore Customizer وApp Builder وAI Actions والاستيراد والمنصة. التطبيقات السابقة لا تُستثنى من الجرد/التبنّي *عند إطلاق المشروع مستقبلًا*؛ ولا يتطلب اعتماد هذا الميثاق تغييرها الآن.

## 2. القرار النافذ فورًا — Build for Policy Readiness

هذه **قاعدة تصميم ومراجعة ملزمة لكل مهمة تطوير جديدة أو تعديل وظيفي**، وليست موافقة على تنفيذ الإطار المركزي. يتعين على المنفذ:

1. تمييز **System Invariants** (قواعد السلامة الإلزامية) عن **Business Policies** (خيارات صحيحة متعدّدة) وعن **RBAC** (من يملك الإجراء) وعن **Feature / Commercial Gates** (هل القدرة متاحة).
2. تحديد مالك السياسة ونطاقها، ومستويات تخصيصها المشروعة، والقيمة الافتراضية الآمنة، عند تعلق المهمة بسياسة.
3. استخدام `Settings` / `BranchSettings` أو آليات التطبيق القائمة الموثوقة عند الحاجة لإعداد حالي؛ **لا بناء Registry/Resolver/مخزن Key-Value موازي لمجرد الاستعداد المستقبلي**.
4. جعل معرّفات وخيارات السياسة واضحة ومستقرة، مع تحقق خادمي وقيم مسموحة محددة وصلاحيات تغيير مضبوطة، ليسهل دمجها لاحقًا دون كسر عقودها.
5. صون Tenant/Branch/Store Isolation وBackward Compatibility؛ لا تغيير صامت للسياسات الافتراضية أو توسيع صلاحيات المستخدم بسبب إعداد جديد.
6. تدقيق القرارات والتغييرات الحساسة (فاعل/وقت/سبب وعند الحاجة نسخة أو بصمة السياسة التي حكمت العملية).
7. اختبار القيمة الافتراضية والخيارات المتاحة والعزل والصلاحيات؛ وإضافة حماية قاعدة البيانات عند ضرورة ضمان سلامة مالية أو أمنية.
8. توضيح في تقرير PR كيف روعيت الجاهزية، أو سبب عدم انطباقها على المهمة؛ لا إعدادات شكلية لكل ثابت برمجي.

**حدود الملاءمة:** إذا لم تلمس المهمة سياسات أو إعدادات فلا تُنشأ تغييرات إضافية. وإذا استلزم هذا الالتزام تغييرًا ماليًا أو DB/API أو Refactoring واسعًا، يُرفع الأمر لقرار مستقل. لا تتوقف أي Feature في انتظار POLICY-0.

## 3. الضمانات غير القابلة للتخصيص

لا يمكن لأي إعداد تعطيل Tenant Isolation أو RBAC أو القيد المزدوج وسلامة المحاسبة أو سلامة المخزون أو قواعد ZATCA الإلزامية أو تدقيق العمليات أو منع IDOR أو متطلبات التزامن/الذرّية/الخصوصية. لا تخلط سياسة الفرع مع منح صلاحية الوصول إليه. معاملات المال بالهللات والعقود المحاسبية القائمة تبقى محفوظة.

حالة أَوْج الآن **Beta** وجميع المستأجرين والحسابات اختبارية؛ لا عملاء حقيقيين. هذا لا يخفف ضوابط الأمان والمحاسبة والتوافق.

## 4. أنماط السياسات ونطاقها

| النوع | الوصف |
|---|---|
| `Mandatory` | قاعدة إلزامية لا تُعرَض كخيار يعطّلها |
| `Configurable` | سياسة عمل مع عدة خيارات صحيحة وحدود وقيم معلومة |
| `Feature/Operational Gate` | إتاحة قدرة مكتملة أو حظرها تشغيليًا؛ لا تمنح الصلاحية بذاتها |

**طبقات مرجعية مقترحة، وليست عقد Resolver منفّذًا:** System Invariants ← Platform/Commercial Gates ← Tenant ← Application/Module ← Branch/Store/Sales Channel فقط حين تنص السياسة على ذلك. **لا أسبقية تلقائية للأضيق:** كل سياسة تعرف أي نطاق يستطيع تجاوز قيمة نطاق آخر، وشروط التقييد والفشل المغلق.

يُوثَّق لكل مفتاح عند بناء السجل لاحقًا: `id`، النسخة، المالك، المصدر الحالي، التصنيف، أنواع القيم، القيمة الافتراضية، النطاقات المسموحة، صلاحيات القراءة/التغيير، قواعد الأسبقية، التحقق الخادمي، سجلات التدقيق، أثر تعديل السياسة على العمليات الجارية والتوافق.

**موضع الإعداد:** الإعداد الوظيفي يظل في قسمه أو قسم تطبيقه كما ينص `configurable-policies.md`. قد يوفر مركز الإعدادات المستقبلي **فهرسة أو بحثًا أو حوكمة موحدة**، لكن لا يفرض نقل كل واجهات إعدادات الأقسام إلى شاشة عامة أو خلط ملكية التطبيقات.

## 5. التغطية المستقبلية — ليست وعدًا بوجود خيارات اليوم

| النطاق | أمثلة محتملة تخضع للجرد والاعتماد |
|---|---|
| المحاسبة/المالية/كشوف الأطراف | فصل المهام، الاعتماد، الإقفال، الإبطال والاستبدال |
| المبيعات والمشتريات | الخصومات، مستويات الموافقة، حدود الإنفاق |
| المخزون/المستودعات | سياسات التسويات والتحويل والرصد السالب عندما يصح |
| POS والوقود | خصومات الكاشير والمرتجعات والوردية وتسويات التشغيل |
| الموظفون والعملاء والموردون | سير الموافقات وضوابط الائتمان والإجازات |
| التجارة الإلكترونية والمتجر | الدفع والشحن والمرتجعات وقبول الطلبات والنشر |
| Store Customizer / App Builder | النشر، المسودات، الموافقات، إدارة الأدوار |
| AI Actions والاستيراد | بوابات التشغيل والتفويض والحدود والتدقيق |
| إدارة المنصة | الإتاحة والضوابط التجارية والتشغيلية |

الأمثلة **سياسات مرشحة للدراسة**، لا تعني أن كل قدرة أو إعداد موجود أو مناسب للتفعيل.

## 6. الحفاظ على السابق — لا تنفيذ حاليًا

عند اعتماد التنفيذ لاحقًا، يُجرى POLICY-0 لجرد **القديم والجديد معًا**: المصدر الفعلي (كود/DB/API/Env)، المالك والنطاق والافتراضات، أثر التشغيل، علاقتها مع `ApplicationCatalog` وRBAC والاشتراكات والبوابات، تدقيقها، وتصنيفها `Preserve/Register/Unify/Enhance/Exclude` بأدلة.

لا إعادة كتابة جماعية، ولا ترحيل تلقائي، ولا تغيير سلوك قائم. الميزات الجاري تطويرها لا يُوسّع نطاق PR الخاص بها لهذا الإطار.

## 7. مثال قائم — PS-A3e

- **PS-A3e / PR #1960** مستقل، ولا يُعاد تصميمه ضمن مبادرة الإطار.
- `D-PS-19`: الاستبدال الصريح، دون اشتراط التعارض، وبحد افتراضي موثّق ومراجعة نطاقه.
- `D-PS-20`: فصل مهام الإبطال سياسة قابلة للتخصيص للمستأجر؛ الافتراضي صارم، والوضع المرن يتطلب `partner_statements.void` ومسار تغيير مصرحًا به؛ لا منح تلقائي.
- سجل التدقيق والإفراج عن المطالبات والذرّية والفصل اللازم بين المراجع والمُغلِق وقواعد العزل والقيود المالية **غير قابلة للتجاوز**.
- يندمج تعريف هذه السياسة مع الإطار مستقبلاً دون تغيير نتيجة العمليات التاريخية أو فرض بناء الإطار الآن.

## 8. اتجاه تقني مؤجل

**مقترحات تدرس بعد الجرد، وليست مكونات قائمة أو موافقة على إنشائها:**
- `Policy Registry` لتعريف العقود، مع إعادة استخدام مخازن إعدادات التطبيقات.
- `Policy Resolver` موثوق على الخادم بقواعد أسبقية صريحة.
- سجل تغييرات ونسخ سياسات، وتثبيت النسخة/البصمة للأحداث الحساسة.
- واجهة لاحقة متوافقة مع نظام تصميم أَوْج، RTL/LTR وMobile-first، تحافظ على أماكن إعدادات الأقسام.

## 9. خارطة الطريق المؤجلة

| المرحلة | المخرج | الحالة |
|---|---|---|
| POLICY-0 | جرد قراءة فقط وسياسات فعلية ومصادرها وفجواتها | **مؤجل** |
| POLICY-1 | ADR للعقد، الأسبقية، الصلاحيات والتوافق | **مؤجل** |
| POLICY-2 | أساس مشترك صغير عند الحاجة بعد قرار مستقل | **مؤجل** |
| POLICY-3 | تكامل حالة مرجعية واحدة مع الموجود | **مؤجل** |
| POLICY-4 | تبنٍ تدريجي عبر ERP/POS/Commerce | **مؤجل** |
| POLICY-5 | واجهة بحث/إدارة/تدقيق ملائمة للأقسام | **مؤجل** |

أي ترتيب/تفصيل لاحق يتطلب موافقة مستقلة. لا يُبنى POLICY-0 الآن.

## 10. القرارات والحدود

**معتمد الآن:** الشمول الكامل للأنظمة السابقة والجديدة، منهج الحفاظ ثم التسجيل ثم التوحيد ثم التطوير، سلامة النظام، والالتزام الفوري بمبدأ Policy Readiness عند بناء أو تطوير أي وظيفة، مع Scope محدود.

**مؤجل وغير معتمد تنفيذه:** جرد POLICY-0، إنشاء Registry/Resolver، تغييرات Database/API وواجهة الإعدادات المركزية، أي ترحيل، تعديل الافتراضات الحالية، فتح صلاحيات جديدة، نشر أو تفعيل تشغيل.

**العلاقة بالمراجع الحالية:** هذا الميثاق يوسع المبدأ المؤسس في `design-system/foundations/configurable-policies.md` على كل المنتجات والقنوات، ولا ينسخ قاعدة «الإعداد في قسمه»، ولا يحل محل `CLAUDE.md` أو عقود Commerce أو ADRs المدموجة أو اختبارات النظام. عند التعارض مع واقع الكود أو عقد معتمد، تُرفع المسألة لمراجعة معمارية ولا يُغيّر السلوك بصمت.

**حدود هذا PR:** وثيقة ميثاق + مرجع في `CLAUDE.md` فقط. **لا كود، لا اختبارات تشغيلية مطلوبة، لا Migration، لا POLICY-0، لا Deploy.**
