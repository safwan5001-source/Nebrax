## 1. الخلاصة

1. **الحماية التقنية الوحيدة المُلزِمة غائبة:** `main` بلا Ruleset ولا Branch Protection؛ `CI Gate` معلوماتي. أي «تفويض» اليوم نصّ لا آلية. لذلك **لا منح فعلي قبل G3** (§7).
2. **النموذج:** أربع مناطق (A/B/C/P) تُحسب بدالة **max** على المسار والسلوك والسياق، ومجهول المسار = C. المنح سجلّ مقروء من `main` فقط، له سقف مدة وعدد ونطاق، ولا يتضمن أبداً قائمة استثناءات قابلة للإزالة (§3–4).
3. **العقدة الحرجة ليست الكود بل الأصالة:** بهوية GitHub واحدة لا يمكن تمييز «منح كتبه المالك» عن «منح كتبه وكيل». لذا V2-4 مشروط بقناة أصالة خارج متناول الجلسات (§4.6, D2).
4. **الأثر على الآفاق القائمة منخفض:** من آخر 40 commit على `main` كلها دُمجت عبر PR [تحقّقتُ]، فاشتراط PR لا يكسر نمط عملها؛ الأثر الفعلي عند اشتراط CI Gate (وقت الانتظار ~25–40 د) وعند حماية ملفات البوابة.
5. **عشر حالات dry-run** (§8) بمعيار PASS صارم: أي «أهلية خاطئة» = فشل كامل.

### 3.1 المناطق

| المنطقة | التعريف | التنفيذ الذاتي (فرع + PR + اختبارات) | الدمج الذاتي | الأدلة الإضافية قبل الدمج |
|---|---|---|---|---|
| **A** | تغييرات منخفضة المخاطر معزولة: توثيق غير حوكمي، نصوص/تسميات a11y، UI عرضي بحت دون مال/صلاحيات/إجراء تدميري، اختبارات فقط تُضيف ولا تُعدّل أصلاً | نعم | **مرشحة** لمنح محدود مستقبلاً (V2-4) | CI Gate PASS على SHA الدقيق + PRE_MERGE_REVIEW |

### 3.2 دالة التصنيف
```
zone(PR) = max( path_zone(كل ملف), behavior_zone(PR), context_zone(PR) )   # A < B < C < P
```
- **path_zone:** من جدول §3.3؛ مسار غير مطابق ⇒ **C** (default-deny). يُحسب من `pulls/{n}/files` شاملاً `previous_filename` (إعادة التسمية لا تُخفي).
- **behavior_zone:** يرفع فقط (لا يخفّض أبداً): لمس مبلغ/ضريبة/ترقيم مستند ⇒ C؛ كتابة/حذف/إجراء تدميري في UI ⇒ ≥B؛ عرض أرقام مالية ⇒ ≥B؛ استدعاء endpoint جديد ⇒ ≥B؛ تغيير عقد مشترك ثلاثي الطبقات (tokens/presentation) ⇒ ≥B.
- **context_zone:** تقاطع مع سطح مسجّل لأفق آخر (§6) ⇒ ≥B وتسلسل؛ فرع/PR لأفق غير مسجّل نشط على نفس الأسطح ⇒ توقف (§6.4).
- **ملاحظات تثبيت:** (1) الوكيل لا يخفّض تصنيفاً بنفسه؛ التخفيض يتطلب تعديل جدول المسارات (وهو C). (2) PR مختلط يُصنَّف بأعلى ملف؛ والأفضل تقسيمه. (3) الغموض ⇒ الأعلى.

## 4. مخطط المنح (Grant Schema)

### 4.1 الحقول

| الحقل | النوع | قاعدة |
|---|---|---|
| `schema_version` | int | يرفضه المُقيِّم إن لم يعرفه (fail-closed) |
| `grant_id` | `GR-YYYYMMDD-NNN` | فريد؛ يُسجَّل في كل PR مدموج |
| `status` | `draft\|active\|suspended\|revoked` | `expired/exhausted` تُحسب ولا تُخزَّن |
| `owner` | معرّف المالك | الجهة المخوِّلة؛ يُتحقق منها بقناة الأصالة §4.6 |
| `issued_at` · `not_before` · `expires_at` | UTC ISO | **سقف المدة:** A ≤ 7 أيام، B ≤ 48 ساعة، قابل للتجديد بمنح جديد لا بتعديل |
| `horizon_id` | string | أفق مسجَّل (§6) ومُسجَّل فيه `protocol_version: v2` |
| `approved_outcome` | نص | الهدف المعتمد؛ يُقارَن بعنوان/وصف المهمة |
| `repositories` · `base_branches` | قوائم | `safwan5001-source/Nebrax` · `main` فقط افتراضياً |
| `zones_allowed` | `["A"]` أو `["A","B"]` | C/P ممنوعان بنيوياً (يرفض المخطط أي قيمة أخرى) |
| `task_categories` | قائمة مغلقة من تعداد | مثل `docs-nongov`, `a11y-label`, `presentational-ui`, `isolated-bugfix` |
| `tasks_allowlist` | قائمة معرّفات | B: لا يُدمج إلا ما سُمّي |
| `paths_allow` / `paths_deny` | globs | `paths_deny` = اتحاد الاستثناءات الصلبة §3.4 + ما يضيفه المالك؛ لا يمكن حذف الصلب |
| `limits` | `max_merges`, `max_merges_per_day`, `max_files_per_pr`, `max_changed_lines`, `max_open_prs` | استنفاد أي سقف ⇒ `exhausted` |
| `agents` | قائمة `agent_id`/هوية | وكيل خارج القائمة ⇒ لا ينطبق |
| `required_checks` | `["CI Gate"]` + ما يحدده المانيفست | يُقرأ من `main` لا من الـPR |
| `review_requirements` | `PRE_MERGE_REVIEW`, Guardian، ومراجع مستقل عند B | بهوية واحدة لا يُعدّ «مستقلاً» |
| `conflict_policy` | `serialize\|stop` | افتراضي `stop` |
| `revocation` | قناة + kill-switch | §4.4 |
| `production_gated` | `true` ثابتة | لا قيمة أخرى |
| `audit` | مسار سجل الدمج | §4.5 |

### 4.2 خوارزمية التقييم (fail-closed، بالترتيب، أول فشل يوقف)
1. جلب المنح **من `main` الحالي** (طازجاً، لا ذاكرة) — منح موجود على فرع الـPR أو في وصفه **لا يُعتدّ به**.
2. أصالة المنح (§4.6) ⇒ وإلا `BLOCK`.
3. `status=active` ∧ `now ∈ [not_before, expires_at)` ∧ لا kill-switch ∧ الحدود غير مستنفدة.
4. الوكيل ∈ `agents`؛ المستودع/الفرع ضمن النطاق.
5. تصنيف الـPR (§3.2) ⇒ المنطقة ∈ `zones_allowed`؛ الفئة ∈ `task_categories`؛ B: المهمة ∈ `tasks_allowlist`.
6. كل الملفات ∈ `paths_allow` ∧ ∉ `paths_deny`؛ الحجم ضمن الحدود.
7. لا تعارض آفاق (§6.3).
8. على **head SHA الحالي**: PR مفتوح غير مسودة؛ `CI Gate` = success **لهذا SHA** وبعد آخر push؛ لا مراجعة لاحقة بطلب تغييرات؛ PRE_MERGE_REVIEW مسجّل لنفس SHA.
9. القاعدة: `base.sha` الحالي = المختبَر، أو أُعيد الاختبار بعد دمجها.
10. إعادة جلب المنح (kill-switch) **مباشرة قبل** الدمج، ثم `PUT /merge` مع `sha=<head المراجَع>` (409 عند عدم التطابق).
11. بعد الدمج: تحقق من merge SHA، سجل التدقيق، ثم فحص ما بعد الدمج.

الإخراج: `ELIGIBLE` · `ELIGIBLE_WITH_EXTRA_VERIFICATION` · `WAIT` · `BLOCK` · `STOP_OWNER_DECISION` — مع قائمة الأسباب والأدلة.

### 4.3 دورة حياة المنح
`draft → active → (suspended ↔ active) → revoked`؛ `expired`/`exhausted` حالتان محسوبتان. لا تمديد في مكانه: التجديد = منح جديد بمعرّف جديد. تغيّر هوية الوكيل أو سقوط الجلسة لا يمدّد شيئاً.

### 4.4 الإلغاء
- **kill-switch:** وجود ملف/حالة `revoked`/`suspended` على `main`، أو تعطيل الحماية/حذف البوابة ⇒ أي من هذا يوقف الدمج فوراً.
- **متى يُفحص:** عند كل خطوة دمج وقبل `PUT /merge` مباشرة، لا مرة واحدة في بداية الجلسة.
- **القناة السريعة:** قول المالك الصريح في الجلسة «أوقف الدمج» يوقف الوكيل ذاتياً، ويُسجَّل لاحقاً في المنح.
- الإلغاء لا يتراجع عن دمج سابق؛ التراجع = PR عكسي (fix-forward) بلا إعادة كتابة تاريخ.

### 4.5 سجل التدقيق (لكل دمج)
`grant_id` · `pr` · `head_sha_reviewed` · `base_sha` · `zone` + أسباب التصنيف · `checks` (أسماء + run ids + conclusions) · `ci_gate_run_id` · `review_verdicts` · `idempotency_key=(horizon,task,head_sha,action)` · `merge_sha` · `post_merge_checks` · `evaluated_at`. يُكتب تعليقاً على الـPR (علامة dedupe `<!-- awj-merge-record:key -->`) ويلحقه ملف الأفق. بلا أسرار ولا PII.

### 4.6 أصالة المنح — الفجوة المفتوحة
ما دامت كل الكتابات بهوية واحدة، **المنح الذي يكتبه وكيل لا يتميّز عن المنح الذي يكتبه المالك**. هذا يلغي قيمة كل بنود §4.2 إن لم يُعالَج. الخيارات (D2):

| الخيار | يحمي من | يتطلب | الحكم |
|---|---|---|---|
| أ) commit موقّع بمفتاح المالك (SSH/GPG لا يوجد في أي جلسة) + قاعدة «Require signed commits» + المُقيِّم يتحقق من التوقيع مقابل `allowed_signers` المثبّتة | تزوير الوكيل | حفظ المفتاح خارج الجلسات؛ أن لا يتغيّر `allowed_signers` إلا بتوقيع | **موصى به** كحدّ أدنى |
| ب) هوية Bot مستقلة للوكلاء + المالك هو الوحيد الذي يملك صلاحية كتابة ملفات المنح (CODEOWNERS + Code Owner review على مجلد المنح) | تزوير الوكيل، S12/S13 | GitHub App، قرار P3 | **الأقوى**، بعد أ |
| ج) إعلان المنح في محادثة المالك فقط | — | لا شيء | لا يصلح للأتمتة بلا حضور؛ يبقى كما هو اليوم (دمج بأمر المالك لكل PR) |

حتى يتحقق أ أو ب: **المُقيِّم يُرجِع `BLOCK` لأي منح غير موثَّق**، ويبقى الدمج بأمر المالك الصريح كما هو.

## 5. نموذج التهديدات (Threat Model)

افتراض الخصم: وكيل (أو محتوى يؤثر عليه) يتصرف خطأً أو خبيثاً بصلاحيات الجلسة (كتابة على فروعه، فتح PR، أداة الدمج)، دون سرّ المالك. ليس ضمن النطاق: اختراق حساب المالك أو GitHub نفسه.

مفتاح: **م** منع · **ك** كشف · **س** استرداد · **اختبار** = حالة dry-run في §8.

### T1 — تعديل CI Gate أو تعطيل فحوصها (S12/S13)
| | |
|---|---|

## 6. الآفاق المتوازية (Registry & Ownership)

مبدأ: **المرصود من GitHub يغلب المُبلَّغ**، والسجل تقريري/تدقيقي لا قفل؛ الإنفاذ الوحيد الملزم هو شروط GitHub نفسها (head SHA، الحماية). لا يُعدَّل أي أفق قائم ولا يُسجَّل بدلاً عنه.

### 6.1 السجل
- ملف لكل أفق: `docs/autonomous-engineering/registry/<horizon_id>.yml` (لا ملف مشترك كبير؛ `CURRENT-STATE.md` و`TASK-QUEUE.md` **ممنوعان** على V2 قبل التفعيل). **لا ينشأ في هذه المهمة.**
- الحقول: `horizon_id` · `protocol_version` (`v1|v2`) · `owner_agent` · `status_reported` · `status_observed` + `observed_at` (TTL قصير، يُعاد التحقق قبل الاعتماد) · `branches` (نمط) · `open_prs` · `surfaces` (مع الوضع) · `risk_zone` · `depends_on` · `last_verified_main_sha` · `checkpoint` · `grant_id?`.
- **الانضمام طوعي:** أفق غير مسجَّل = `v1` = يعمل بصلاحياته الحالية دون أي تغيير.

### 6.2 أسطح الدلالة (Surfaces) — أبعد من الملفات
كل مهمة تعلن الأسطح التي تلمسها وبأي وضع (`exclusive` كتابة / `shared-read` / `shared-write`):

| سطح | يشمل | سبب التعارض الدلالي |
|---|---|---|
| `S-LEDGER` | LedgerService، قيود، ترقيم المستندات | قاعدة القيد المزدوج |
| `S-FIN-CONTROLLERS` | Controllers: Invoice/Payment/Purchase/Return/Expense | سطح مالي مشترك (مثلاً Media S1 فوق TAX) |
| `S-ZATCA-ICV` | سلسلة ICV/PIH/UBL | عدّاد متسلسل غير قابل للتعايش |
| `S-ATTACH-STORAGE` | AttachmentStorage، R2، `config/attachments.php` | قرار R2 موحَّد (Media مقابل Cloudflare #1093) |
| `S-TOKENS-CONTRACT` | عقد global-tokens (PHP/web/storefront byte-identical) | كسر التوأمة |
| `S-PRESENTATION` | Commerce presentation/publish | #1089 مقابل CUST-HV |
| `S-DESIGN-TOKENS` | `globals.css`، `design-system/**` | أثر بصري عام + CODEOWNER |
| `S-MIGRATIONS` | `database/migrations/**` | **تصادم أرقام الترحيل** وترتيب التنفيذ |
| `S-ROUTES` | `routes/api.php` | مسارات مشتركة |
| `S-NAV-I18N` | sidebar، ملفات الترجمة | تعديل متزامن لملف مشترك |
| `S-RBAC-TENANT` | Rbac، Middleware، Tenancy | عزل/صلاحيات |
| `S-CI-GATE` | `.github/**`، `scripts/ci-gate/**` | S12/S13 |
| `S-GOV-DOCS` | ملفات الحوكمة والبروتوكول | سلطة الدمج |

مصفوفة: `exclusive` ↔ أي وضع آخر = تعارض؛ `shared-write` ↔ `shared-write` = تسلسل؛ `shared-read` متوافق مع الجميع عدا `exclusive`. الأسطح C (`S-LEDGER`, `S-ZATCA-ICV`, `S-RBAC-TENANT`, `S-CI-GATE`, `S-GOV-DOCS`) **دائماً `exclusive`**.

### 6.3 قواعد قبل الفتح/الدمج
1. **Claim:** اسم الفرع `<horizon>/<task>` + وسم PR `horizon:<id>` + كتلة `Horizon-Claim` في الوصف (horizon، task، surfaces، grant؟، generation).
2. **فحص حي** عند الـClaim وقبل الدمج: كل PR مفتوح وفروقه + commits main حديثة على أسطح المهمة. تقاطع `exclusive` ⇒ لا بدء؛ `shared-write` ⇒ تسلسل بترتيب الـClaim الأقدم (الأقدم يدمج أولاً وبتحقق فعلي من الدمج).
3. **الدمج الناجح لآخر يُبطل الافتراضات:** إعادة قراءة الأسطح المشتركة، دمج `main` في الفرع (لا rebase)، إعادة الفحوص والمراجعة.
4. **الـgeneration/fencing** في Claim استشاري؛ **المرجع الملزم** = `PUT /merge` بـ`sha` وحماية الفرع.
5. تعارض لا يُحسم بالتسلسل ⇒ `STOP_OWNER_DECISION`؛ يستمر العمل المستقل الآمن.

### 6.4 أفق غير مسجَّل أو غير معلوم
نفترض أنه يلمس **أقصى سطح** لمسارات PRs المفتوحة وفروعه: أي نشاط في آخر 30 دقيقة على فرع (أو بلا Claim واضح) = **ممنوع اللمس**، والعمل على فرع جديد. لا يُنسب مالك من اسم الفرع (`claude/` لا تعني Claude، تعلّمنا من #1328).

### 6.5 الأثر على الآفاق القائمة
لا تغيير. (TAX، Delivery المتوقف، Media Storage، Platform UX، CUST-HV، Growth، Cloudflare تبقى تحت بروتوكولها.) فرق الأسطح الأعلى حساسية اليوم [موثّق V2-0B §5]: TAX↔Delivery على Invoice/Payment، Media S1↔Controllers المالية، #1329/#1338/#1345↔عقد tokens/presentation، Cloudflare R2↔Media R2.

## 7. أساس أمان GitHub (خطة، **لا تنفيذ**)

**لا يُفعَّل أي إعداد في هذه المهمة.** الخطة قرارات للمالك ويُنفّذها هو أو بأمره الصريح.

### 7.1 الإعداد المستهدف (Ruleset واحد على `main`)
| القاعدة | القيمة المستهدفة | ملاحظة |
|---|---|---|
| Require pull request | مفعّل | آخر 40 commit كلها PR ⇒ لا كسر لنمط العمل [تحقّقتُ] |
| Required status check | `CI Gate` وحده (على أن يطابق `integration` = GitHub Actions) | يُقفل بعد استكمال شروط readiness §8 |
| Block force pushes · Restrict deletions | مفعّلان | |
| Require signed commits | مرشح لـD2-أ | يتطلب أن توقّع GitHub commits الدمج نفسها؛ **[غير مُتحقَّق]** تفاعله مع «Squash and merge» الحالي |
| Code owner review لـ`.github/**`, `scripts/ci-gate/**`, مجلد المنح/السجل | عند G4 | يتطلب هوية مراجع ≠ الكاتب |
| Restrict file paths | بديل محتمل لـG4 | **[غير مُتحقَّق]** توفره لمستودع شخصي عام |
| Require approvals (عدد) | 0 عند G3، ≥1 عند G4 | «Required reviewers» غير متاحة لمستودعات المستخدم (توثيق) |

| Require up to date | قرار D3 | الإلزام يضيف دورة CI (~35 د) لكل دمج |
| Auto-merge | **يبقى معطّلاً** | حتى V2-4 ومنح |

- **اشتراط CI Gate:** كل PR ينتظر البوابة (median 24 د، p90 38 د، max 114 د [موثّق]) — يتطلب إخطار الآفاق؛ PRs المفتوحة قبل التفعيل **لم تُشغِّل البوابة** وستظهر «Expected — Waiting» حتى push جديد: **خطر تعليق** لـ13 PR مفتوحة (معظمها قديمة)؛ يُعالَج بإغلاقها (D7) أو push يطلق البوابة.
- **#1345** (CUST-HV) وهي تدفع بكثافة: تخضع للبوابة؛ تُنبَّه قبل التفعيل.
- **Require up to date (D3):** كل دمج يتطلب تحديث الفرع ثم دورة CI؛ آفاق بدفعات كثيفة ستتأثر بشدة.
- **حماية ملفات الحوكمة (G4):** تعديل ملفات البروتوكول/الـworkflow يتطلب مراجعاً ثانياً؛ المسار المستقبلي لـV2-2 نفسه.
- **إعادة تشغيل البوابة بعد تغيّر main** لم تُختبر — شرط للإعلان الجاهز.

## 8. عقد الـDry-Run

**الغرض:** إثبات أن المُقيِّم (§4.2) يقرّر صحيحاً **دون أي دمج حقيقي**. يُنفَّذ في V2-3 كدالة نقية على fixtures (JSON للـPR/المنح/السجل/نتائج CI)؛ V2-1B تعرّف العقد فقط.

### 8.1 قواعد عامة
- **صفر كتابات:** المُقيِّم يعمل بأدوات قراءة؛ تُحجب `merge_pull_request`/`enable_pr_auto_merge`/`update_pull_request_branch` على مستوى الأداة. **PASS يتضمن** سجلاً يُثبت عدم استدعائها.
- المخرج لكل حالة: `DryRunDecision {case, decision, reasons[], evidence[], would_merge:false}`.
- **معيار شامل:** كل الحالات PASS **و«أهلية خاطئة» = 0** (أي ELIGIBLE حيث المتوقع غيره = فشل الخطة كلها، لا حالة واحدة).

### 8.2 الحالات

| # | السيناريو | المدخل | القرار المتوقع | PASS إذا | FAIL إذا | الدليل |
|---|---|---|---|---|---|---|
| DR-01 | Zone A مؤهل | PR docs غير حوكمي ٣ ملفات، منح A نشط، CI Gate success على head، PRE_MERGE_REVIEW على نفس SHA، لا تعارض | `ELIGIBLE` | القرار صحيح + `would_merge:false` + لا استدعاء merge + السجل يحوي كل حقول §4.5 | أي أهلية ناقصة الأدلة، أو استدعاء merge | decision JSON + سجل الأدوات |

### 8.3 تقارير الـDry-Run
جدول حالات (PASS/FAIL) + عدّاد false-eligible + مراجع الأدلة + SHA الذي قُيِّم + رقم نسخة المُقيِّم. تقرير لا يحمل SHA = غير صالح.

## 10. المراجعة والحدود

- لا تغيير على الكود أو قواعد البيانات أو APIs أو الـworkflows أو الصلاحيات أو أي فرع أفق آخر؛ لا Merge/Deploy؛ لا Ruleset/Protection/Auto-Merge؛ لا منح فعلي.
- لا عمليات مالية ⇒ لا قيود محاسبية ناتجة.
- كل ادعاء حي موسوم؛ ما لم يُتحقق منه صُنّف **[غير مُتحقَّق]** صراحةً.
- **الخطوة التالية:** قرارات المالك D1–D10 ← عندها فقط يُقيَّم V2-2. **V2-2/V2-3/V2-4 لا تبدأ.**
