# ADR-0006 — AWJ Payments: قرارات المالك لـH2-02 ومصفوفة قيود ترحيل الالتقاط

DATE: 2026-10-23
STATUS: **accepted** (D-16، D-24، D-26، وADR-0004 §3 — الأساس R1) · مصفوفة القيود أدناه **مقدَّمة للمراجعة قبل أي كود محاسبي**
DECIDED_BY: صفوان (المالك)، رسالة «AWJ Payments — Owner Decisions for H2-02» بتاريخ 2026-10-23
RELATED_TASKS: PAY-H2-02 (a…e) · الأفق: `docs/plans/payments/horizon/`
SUPERSEDES: ADR-0004 §3 (يحوّل حالة «proposed» إلى «accepted» بالحدود أدناه)

## القرارات المعتمدة

| ID | القرار | الترجمة التنفيذية |
|---|---|---|
| D-16 | الدفع الجزئي **ممنوع افتراضياً**، ويُفعَّل **لكل رابط على حدة**، مع منع تجاوز الرصيد المستحق | `invoice_payment_requests.allow_partial = false` افتراضياً؛ الطلب بلا تفعيل يُنشأ بالمتبقي كاملاً؛ مع التفعيل المبلغ المختار `1 ≤ مبلغ ≤ المتبقي` ويُعاد التحقق عند كل محاولة ومرة أخرى عند الترحيل |
| D-24 | الالتقاط الفوري هو الافتراضي؛ التفويض ثم الالتقاط فقط في مسار أعمال معتمد وبعد التحقق من دعم المزوّد | روابط الفواتير: فوري فقط. لا مسار تفويض/التقاط في H2-02. المحاولة `authorized` لا تُرحَّل ولا تنتج سنداً |
| D-26 | الدفعة الزائدة المؤكدة = **رصيد دائن غير مخصص يحتاج مراجعة**، لا إيراد إضافي؛ منع الازدواج؛ التخصيص/الاسترداد عبر الإجراءات المعتمدة | سند ثانٍ غير مخصص (مدين 1170 / دائن 1130 بالطرف) في المعاملة نفسها + علامة مراجعة `overpayment`؛ لا استرداد آلي (الاسترداد عبر `CustomerRefundService` القائم بقرار بشري) |
| ADR-0004 §3 | دفع مؤكد بتاريخ في فترة/سنة مقفلة: يُحفظ إثبات الدفع وحالته لدى المزوّد، والترحيل `blocked_period`؛ لا قيد في الفترة المقفلة ولا تغيير تاريخ تلقائي | الأساس **R1** (فتح رسمي ثم إعادة ترحيل بإجراء صريح). ما لم يُقرّه المالك: **R2 غير مبني** (يحتاج قرار `payments.closed_period_resolution`)، و**R3 مؤجَّل إلى H3-01** لأنه يعتمد استرداد المزوّد |

**تفسيرات ضمن القرارات (لا قرار جديد):** صلاحية المعالجة هي `payments.resolve_blocked` (owner/admin، كما اقتُرح في §3 ولم يُعترض)؛ `accounting_date` = تاريخ التقاط المزوّد بتوقيت الرياض؛ لا إعادة ترحيل تلقائية بعد فتح الفترة.

## مصفوفة القيود المتوقعة (A1…)

كل القيود تُنشأ **حصراً** بـ`PaymentService::create()` ثم `post()` ← `LedgerService::post` (لا كتابة مباشرة). الحسابات بالأدوار: `gateway_clearing` (1170 مستحقات بوابات الدفع (دور gateway_clearing)) و`accounts_receivable` (1130 العملاء + `partner_id`). المثال: فاتورة مرحَّلة 1,150.00 ر.س (115000 هللة). التاريخ المحاسبي = `accounting_date`. المصدر `source_type=Payment`.

| # | الحالة | الشرط | سندات تُنشأ (معاملة واحدة) | القيد | `paid_amount`/حالة الفاتورة | الحالة النهائية للمحاولة |
|---|---|---|---|---|---|---|
| **M1** | عادية | التقاط = مبلغ المحاولة = المتبقي، فترة مفتوحة | سند 1 مخصّص بالفاتورة | **مدين** 1170 1,150.00 · **دائن** 1130 + طرف 1,150.00 | `paid_amount += 1,150.00` ⇒ `paid` | `captured` / `posted` |
| **M2** | جزئية (D-16 مفعّل للرابط) | التقاط = مبلغ المحاولة = 500.00 ≤ المتبقي | سند 1 مخصّص بـ500.00 | مدين 1170 500.00 · دائن 1130 + طرف 500.00 | `paid_amount += 500.00` ⇒ `partial` | `captured` / `posted` |
| **M3** | زائدة (D-26) | التقاط = مبلغ المحاولة = 1,200.00 والمتبقي عند الترحيل 1,150.00 (انخفض بعد إنشاء الطلب) | سند 1 مخصّص بـ1,150.00 · سند 2 **غير مخصص** بـ50.00 | سند 1: مدين 1170 1,150.00 / دائن 1130 + طرف 1,150.00 · سند 2: مدين 1170 50.00 / دائن 1130 + طرف 50.00 | `paid_amount += 1,150.00` ⇒ `paid`؛ السند 2 بلا تخصيص (رصيد دائن للطرف) | `captured` / `posted` + مراجعة `overpayment` |
| **M3ب** | زائدة كلياً | المتبقي = 0 (سُدّدت بوسيلة أخرى/أُلغيت) | سند وحيد غير مخصص بكامل الملتقط | مدين 1170 المبلغ / دائن 1130 + طرف المبلغ | لا تغيير | `captured` / `posted` + مراجعة `overpayment` |
| **M4** | مكررة | الحدث/المطابقة تتكرر، أو انهيار بعد السند 1 وقبل السند 2 | **لا شيء جديد**: `UNIQUE(attempt_id, role)` + معاملة واحدة + فحص المجموعة داخل قفل المحاولة | لا قيد إضافي. الانهيار بين السندين يتراجع كلياً (معاملة واحدة) ثم تعيد الإعادةُ المجموعةَ كاملة | بلا تغيير مضاعف | `posted` (مرة واحدة) |
| **M5** | فترة/سنة مقفلة (ADR-0004 §3) | فحص قراءة `AccountingDateGuard` على `accounting_date` يرفض | **لا سند ولا قيد ولا تخصيص ولا تحديث `paid_amount`** | لا قيد. يُحفظ: المبلغ، المرجع، `accounting_date` المحسوب، سبب الحجب (فترة/سنة ومعرّفها)، الحدث الخام | لا تغيير | `captured` / `blocked_period` + تنبيه |
| **M5-R1** | معالجة المقفلة | مخوَّل (`payments.resolve_blocked`) فتح الفترة رسمياً ثم ضغط «إعادة الترحيل» | كما M1/M2/M3 بـ`accounting_date` الأصلي، idempotent | كما المناظرة | كما المناظرة | `posted` (+ حدث قرار غير قابل للتعديل: الفاعل/السبب) |
| **M6** | مبلغ/عملة مختلفان | الملتقط ≠ مبلغ المحاولة، أو عملة مختلفة | لا شيء (قائم: `requires_review`) | لا قيد | لا تغيير | `captured` / لا ترحيل + مراجعة |
| **M7** | فشل/تفويض فقط/إلغاء/انتهاء | `failed`/`authorized`/`cancelled`/`expired`/`voided` | لا شيء | لا قيد | لا تغيير | لا ترحيل |
| **M8** | التقاط متأخر (D-15) | المحاولة `expired`/`cancelled` محلياً ثم التقط المزوّد | كـM1/M3ب حسب المتبقي عندئذٍ + علامة `late_capture` | كما المناظرة | كما المناظرة | `posted` + مراجعة |
| **M9** | استرداد (خارج H2-02) | استرداد مؤكَّد من المزوّد لدفعة **مرحَّلة** | H3-01 (A5): `CustomerRefund method=gateway` بعد تأكيد المزوّد (D-03) | مدين 1130 + طرف / دائن 1170 | — | يُحدَّد في H3-01 |
| **M9-R3** | استرداد دفعة **غير مرحَّلة** (`blocked_period`) | R3 | لا سند (لم يُعترف بها) | لا قيد | — | مؤجَّل لـH3-01 (يحتاج استرداد المزوّد) |

**ثوابت لكل الحالات:** لا تعديل لقيد مرحَّل · لا مساس بضريبة الفاتورة ولا XML/QR/ICV/سلسلة ZATCA · لا رسوم/عمولة/ضريبة رسوم (مؤجَّلة H3-02/D-04) · لا قيد وهمي لفروقات · `branch_id` السند = لقطة المحاولة · أقفال: المحاولة ← الطلب ← الفاتورة ← السند ← مِرساة المستأجر.

**الخدمات المستخدمة:** `PaymentService` (إنشاء/ترحيل السندات وتخصيصها وتحديث السداد) ← `LedgerService` (القيد) ← `AccountingDateGuard` (فحص قراءة قبل الترحيل + داخل `LedgerService`). خدمة جديدة `PaymentAttemptPostingService` تنسّق فقط ولا تكتب قيداً بنفسها.

## تقسيم H2-02 (شرائح مستقلة، PR لكل واحدة، بلا تكديس)

| الشريحة | المحتوى | أثر محاسبي |
|---|---|---|
| H2-02a | مخطط إضافي: `invoice_payment_requests` (+`allow_partial`)، `payment_attempt_postings` (UNIQUE(attempt_id, role))، أعمدة `posting_status`/`accounting_date`/سبب الحجب على `payment_attempts`؛ نماذج وحراس | لا |
| H2-02b | `InvoicePayable` + إنشاء/إلغاء طلب دفع (`POST /invoices/{id}/payment-requests`) بصلاحية؛ D-16 | لا |
| H2-02c | `PaymentAttemptPostingService`: M1–M8 + ربطه بالمنسّق والمُطابِق | **نعم (A1/A3/A4)** |
| H2-02d | معالجة المقفلة R1 (`payments.resolve_blocked`) + تنبيه + سطر جاهزية الإقفال | إعادة ترحيل بالمسار نفسه |
| H2-02e | API عام `/pay/v1/*` + إلغاء تلقائي عند إقفال الفاتورة بإشعار دائن | لا |

لا تنفيذ لـR2 ولا R3 ولا أي تفويض/التقاط ولا رسوم: قرار جديد أو شريحة لاحقة.

## Rationale
الإبقاء على الحقيقة المؤكدة محفوظة دون اقتحام فترة مقفلة أو تغيير تاريخ، والترحيل idempotent بمجموعة ذرّية واحدة، والدفعة الزائدة رصيدٌ ظاهر لا إيراداً، والمسار المحاسبي الوحيد هو الخدمات القائمة.

## Consequences
- أعمدة وجداول إضافية فقط؛ لا تغيير لسلوك `PaymentService`/`LedgerService`.
- قد تبقى دفعات مؤكدة معلّقة الترحيل ما دامت الفترة مقفلة؛ تظهر في تنبيه وسطر جاهزية الإقفال (H2-02d).
- EXT-01 مفتوح: كل ما أعلاه يُختبر بالمحاكاة (`FakeAdapter`/Moyasar Fixtures)، والتحقق الفعلي في Sandbox لاحق.
