## Decision

1. **Introduce an immutable `issued_at` instant** that records when an invoice is legally issued, i.e. at the posting boundary inside the posting transaction. It is system-assigned, never accepted from a request, and never changed after posting.
2. **Draft `created_at` is not the legal issue time** and must not feed `IssueDate`, `IssueTime`, QR timestamps or printed issue time for newly issued documents.
3. **`invoice_date` keeps its present meaning** (accounting date / ledger `entry_date`). No journal behaviour, period lock, fiscal-close or report behaviour changes because of this ADR.
4. **One issuance instant, several representations.** XML, QR (Phase 1 and Phase 2) and printed/PDF output are all derived from the same stored `issued_at`. Each output may use the representation its official specification requires (for example date/time elements in XML, a different textual form in a QR tag, a localised display form in print). **This ADR does not assert that the XML and QR must contain identical literal timestamp strings.** What must be identical is the underlying instant.
5. **Preserve the original instant** on reprint, regeneration and resend. Re-producing an artefact for an already-issued document reads `issued_at`; it never re-reads the clock and never falls back to `created_at`.
6. **Existing issued documents are not rewritten.** Rows posted before the change keep their stored XML, hash and QR; any display of their time is read from what was actually issued, not re-derived.
7. **Credit and debit notes** (REM-18) follow the same principle when they are issued as ZATCA documents: each note has its own issuance instant, and carries a reference to the original document. No such artefact exists today (R10), so this is direction, not a present gap closure.

## Alternatives considered

| Option | Verdict |
|---|---|
| Keep `created_at` | Rejected: wrong instant for any draft not posted at creation; leaves three representations of the wrong instant. |
| `issued_at` derived from user-entered `invoice_date` | Rejected: lets the legal issue time be back-dated by input and breaks the reporting-window semantics. |
| Forbid every `invoice_date` ≠ posting date for ZATCA tenants | Not adopted here: blocks legitimate late entry; belongs to gate G-A4 as a configurable policy. |
| Mandate identical literal strings in XML and QR | Not adopted: not established by primary evidence (G-A2). |

## Rationale

The legal event is issuance, not drafting. A single stored instant removes the divergence between outputs, makes reprint/resend deterministic, and keeps the previous-invoice-hash chain valid because historical XML is never regenerated (R9). Separating the instant from its representation avoids hard-coding an unverified format contract.

## Consequences

- **Snapshot:** new immutable field on the invoice (nullable for historical rows).
- **XML / hash:** for newly issued documents the `IssueDate`/`IssueTime` source changes, so the hash input changes. Historical documents are unaffected. The Phase-2 chain is unaffected because the previous hash comes from stored XML.
- **Signing:** `SigningTime` remains an independent signing-moment value.
- **QR:** Phase 1 and Phase 2 read `issued_at`; their text form is subject to G-A1/G-A2.
- **Credit/debit notes:** direction only (see Decision 7).
- **Accounting:** none. No posting, amount, VAT rate or ledger change.

## Compatibility / migration impact

- Additive and nullable by design; **no backfill with guessed values**. Historical rows keep their stored artefacts.
- **A database migration adding `issued_at` is NOT YET AUTHORIZED.** It requires the owner's explicit approval at implementation time, together with a decision on G-A1.
- No API contract is removed. Whether `issued_at` is exposed in API resources is decided in REM-13a.
- Pre-Production Data Policy (`AWJ_PRE_PRODUCTION_DATA_POLICY.md`, owner-approved 2026-09-06) applies; production holdings of issued ZATCA documents are **NOT VERIFIED** (G-A6).

## Security / tenant / accounting impact

- Tenant isolation: `issued_at` lives on a `BaseModel`-derived invoice; no cross-tenant path is introduced.
- ICV scope (`ZatcaIcvScope`) and its lock are unchanged; the instant should be captured after the existing anchor lock so that issuance order and ICV order agree (to be proven in REM-13a with a concurrency test on PostgreSQL).
- No journal write path changes; `LedgerService::post/reverse` is untouched.
