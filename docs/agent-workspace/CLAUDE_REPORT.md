## ملخص تنفيذي

هذه مهمة **تصميم ومراجعة فقط** — لم أُنشئ أي GitHub Action، لم أُضف أي secret، لم أُنشئ dispatcher، ولم أُغيّر كود التطبيق، بحسب النطاق المحدد في `TASK.md`.

أهم نتيجة: **الافتراض المعماري الأساسي لتصميم ChatGPT — "GitHub Action يستدعي Claude Code Routine عبر HTTP" — غير دقيق بدليل مباشر من هذه الجلسة نفسها**، وليس بحثاً خارجياً غير مؤكَّد. هذه الجلسة تملك فعلياً أداة `subscribe_pr_activity` التي تُوقظ الجلسة تلقائياً عند نشاط PR (تعليق/CI/مراجعة) **بلا أي GitHub Action أو secret أو dispatcher جديد على الإطلاق**. هذا يبسّط V2 بشكل جوهري لجانب Claude، لكنه يكشف أيضاً أن الجزء الأصعب فعلياً هو **جانب المراجع الآلي من OpenAI**، والذي يحمل سؤال هوية/ثقة معماري لم يُحسم (انظر QUESTION أدناه) قبل أن يستحق أي تصميم أعمق.

## الأدلة (من واقع هذه الجلسة والمستودع، لا تخمين)

1. **قدرات هذه الجلسة الفعلية** (وليست "بحث خارجي يحتاج تحققاً" — هذه تعريفات الأدوات المتاحة لي حرفياً الآن):
   - `subscribe_pr_activity(owner, repo, pullNumber)`: تُسجّل الجلسة الحالية لتستقبل أحداث GitHub الفعلية على PR — تعليقات، فشل CI، ونجاح check-suite — كـ`<wake reason="external-event">`، **بلا GitHub Action، بلا secret، بلا كود جديد**. القيد الموثَّق: إن كانت جلسة أخرى ("PR Steward") تراقب نفس الـPR بالفعل، لا تصل الأحداث لهذه الجلسة حتى تُلغى مراقبة الأخرى.

2. **`.github/workflows/ci.yml` و`web-ci.yml` الحاليان لا يعلنان `permissions:` صراحة إطلاقاً** (تحقّق مباشر بـ`grep -n "permissions:"` — لا نتيجة في كليهما). هذه فجوة hygiene قائمة بالفعل بمعزل عن V2، ذات صلة مباشرة بسؤال 7 أدناه.

## إجابات الأسئلة الإلزامية

1. **هل GitHub Actions يمكنه تشغيل Claude Code رسمياً بالطريقة المقترحة؟** لا بالشكل المفترَض (dispatcher → HTTP → Claude Routine). الأصح: هذه الجلسة نفسها تملك آلية توقّظ مبنية أصلاً (`subscribe_pr_activity`) لا تحتاج GitHub Action مطلقاً لجانب Claude. `watch_url` موجود لكنه مخصص لخدمة أخرى وليس webhook عاماً.
2. **أفضل طريقة لتشغيل Reviewer آلي من OpenAI دون الادعاء أنه ChatGPT التفاعلي؟** لا أملك رؤية أو تحكماً بمنتجات OpenAI من هذه البيئة فلا يمكنني تحققاً مباشراً كما فعلت لجانب Claude. بالمعرفة العامة: OpenAI Responses API يدعم تشغيلاً خلفياً وwebhooks عند الاكتمال، وهذا يصلح تقنياً لبناء وكيل مراجعة عبر API. لكن هذا الوكيل **كيان مختلف تماماً** عن محادثة ChatGPT التفاعلية التي يتحدث معها صفوان اليوم — انظر QUESTION الحاسم أدناه.
3. **من هو الـsingle writer لكل ملف؟** `TASK.md`: المراجع/المالك فقط. `CLAUDE_REPORT.md`: Claude فقط. `REVIEW.md`: المراجع فقط. `DECISIONS.md`: إلحاق فقط بعد قرار معتمد من أي طرف. منع التعارض: كل كتابة تتحقق أولاً أن `EXPECTED_ACTOR`/`LAST_PROCESSED_SHA` المخزَّنين يطابقان من يكتب الآن، وإلا تتوقف وتُصعَّد بدل الكتابة فوق حالة غير متوقعة.
4. **كيف نضمن مراجعة الـSHA الصحيح؟** إضافة حقل `LAST_PROCESSED_SHA` صريح يذكره Claude في `CLAUDE_REPORT.md` عند كل `READY_FOR_REVIEW`. المراجع يرفض المراجعة إن اختلف رأس الفرع الحالي عن هذا الـSHA (يعني تدخلاً غير متوقعاً منذ التقرير).
5. **منع loop لا نهائي:** `MAX_ROUNDS` ثابت في `PROTOCOL.md` (وليس لكل مهمة) — أقترح 5. عداد `ROUND` في `TASK.md` يزداد مع كل `CHANGES_REQUESTED`؛ تجاوز الحد ينقل الحالة **إجبارياً** إلى `BLOCKED` مع تنبيه صفوان، بلا استمرار آلي بعده مهما كان.
6. **فشل الاستدعاء/الدفع/الـAction:** فشل آمن دائماً (fail-closed) إلى `BLOCKED` — لا إعادة محاولة صامتة غير محدودة. يُسجَّل السبب في تعليق PR أو `DECISIONS.md`، وينتظر تدخلاً يدوياً صريحاً.
7. **أقل `permissions`:** أي workflow جديد لـV2 (إن أُقر لاحقاً) يجب أن يُصرِّح `permissions:` صريحة أضيق ما يمكن (`contents: read` كحد أدنى، `pull-requests: write` فقط إن احتاج التعليق)، ولا يُشغَّل أبداً على `pull_request_target` مع أسرار. هذا يستحق إصلاحاً في `ci.yml`/`web-ci.yml` الحاليين أيضاً بمعزل عن V2 — فجوة قائمة فعلاً (دليل أعلاه)، أطرحها هنا كملاحظة لا كتنفيذ.
8. **fork/untrusted PRs:** لا توجد forks في تدفق AWJ الحالي. أي V2 مستقبلي يجب أن يرفض صراحة أي حدث مصدره fork، ولا يُشغِّل كوداً وارداً من fork بصلاحيات مرتفعة أبداً.
9. **حالات توقف automation فوراً:** فشل تحقق SHA، تجاوز `MAX_ROUNDS`، أي حدث من fork/مصدر غير موثوق، أي تعارض دمج، `ESCALATED_TO_OWNER`، أو `APPROVED_FOR_OWNER` — تُعيد الحالة لصفوان دون استثناء ودون استمرار آلي.
10. **dispatcher واحد أم workflows منفصلة؟** بدليل نقطة 1: **لا dispatcher خارجي إطلاقاً لجانب Claude** — استخدام `subscribe_pr_activity` المدمج يُلغي الحاجة كاملة. لجانب OpenAI (إن أُقر لاحقاً)، الأفضل workflow GitHub منفصل تماماً وضيق الصلاحيات، منفصل تماماً عن أي شيء يخص Claude.
11. **هل V2 غير مناسب الآن؟** لجانب Claude: لا — القدرة موجودة اليوم بلا تكلفة أو اعتمادية جديدة. لجانب OpenAI الآلي: نعم يستحق التريث حتى يُحسم سؤال الهوية/الثقة (QUESTION أدناه). Fallback: أبقِ جانب Claude آلياً عبر `subscribe_pr_activity`، وأبقِ مراجعة OpenAI كما هي اليوم (صفوان ينقل الطلب لمحادثة ChatGPT التفاعلية) حتى يُحسم ذلك السؤال.
12. **أصغر Prototype آمن لإثبات wake-up دون لمس كود AWJ:** Slice 0 بلا أي كود جديد: استدعاء `subscribe_pr_activity` على PR تجريبي، ثم يترك صفوان تعليقاً تجريبياً غير مرتبط بمحتوى AWJ، والتحقق أن هذه الجلسة تستيقظ فعلياً بـ`<wake reason="external-event">`. يثبت الآلية كاملة بلا أي تعديل ملف واحد.

## التصميم المعماري المقترح (بعد التحدي)

```
READY_FOR_CLAUDE
  → (Claude session مشترِكة مسبقاً في subscribe_pr_activity على PR AWJ)
  → Claude ينفّذ ويدفع CLAUDE_REPORT.md: READY_FOR_REVIEW + LAST_PROCESSED_SHA
  → [بلا dispatcher] المراجع (بشري اليوم، أو وكيل OpenAI مستقبلاً بعد حسم سؤال الهوية) يراجع
  → المراجع يكتب REVIEW.md ويترك تعليق/مراجعة فعلية على PR (لا commit صامت فقط) — هذا التعليق نفسه هو ما يوقظ Claude تلقائياً عبر subscribe_pr_activity
  → CHANGES_REQUESTED (ضمن MAX_ROUNDS) أو APPROVED_FOR_OWNER (يوقف كل أتمتة وينتظر صفوان)
```

**الفرق الجوهري عن تصميم ChatGPT:** لا حاجة لأي GitHub Action أو dispatcher أو secret لجانب Claude؛ الشرط الوحيد هو أن يترك المراجع **تعليقاً أو مراجعة فعلية على الـPR** (لا commit صامت فقط على الفرع) لأن `subscribe_pr_activity` يستيقظ على نشاط PR (تعليق/CI/مراجعة) لا على كل push.

## Question / Risk / Challenge

### QUESTION (الأهم في هذه الدورة) — هوية المراجع الآلي المقترح

### CHALLENGE — افتراض dispatcher/GitHub Action لجانب Claude غير دقيق
