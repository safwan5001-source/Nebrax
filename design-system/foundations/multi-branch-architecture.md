# معمارية تعدّد الفروع — قاعدة مُلزِمة

> **القاعدة الحاكمة:** كل كيان بيانات جديد يُنشأ في النظام **يُعزل بالفرع افتراضياً**،
> إلا إذا صُنِّف صراحةً كإعداد/بنية على مستوى المؤسسة.
>
> هذه ليست توصية — **حارس آلي في CI يُفشل البناء** إن أُضيف نموذج بلا تصنيف.

## لماذا

المؤسسة الواحدة قد تدير عدّة فروع. البيانات التشغيلية لفرعٍ **لا يجوز** أن تظهر
لفرع آخر افتراضياً. اكتشاف غياب العزل بعد بناء كل قسم مكلف ومتكرّر — فرفعناه إلى
قاعدة معمارية تُطبَّق من أول يوم لكل وحدة قادمة.

## طبقتا العزل — لا تخلطهما

| الطبقة | الأداة | الطبيعة |
|---|---|---|
| **المستأجر (Tenant)** | `TenantScope` عبر `BelongsToTenant` | **حاجز أمني صارم** — إجباري، لا يُتجاوز |
| **الفرع (Branch)** | `BranchScope` عبر `BranchScoped` | **عزل تشغيلي** — قابل للتجاوز المتعمَّد في التقارير المجمّعة |

الفرع **ليس** حاجز أمان بين مؤسستين؛ هو تقسيم داخلي لمؤسسة واحدة.

## التصنيفات الثلاثة (إلزامية)

كل نموذج يرث `BaseModel` **يجب** أن يعلن واحداً منها:

### ١. `BranchScoped` — الافتراضي للبيانات التشغيلية
```php
use App\Tenancy\BranchScoped;

class WorkOrder extends BaseModel
{
    use BranchScoped;   // وسم عند الإنشاء + عزل القراءة تلقائياً
}
```
يلزمه عمود `branch_id` nullable في الهجرة (مع فهرس `(tenant_id, branch_id)`).

**استخدمه لـ:** الفواتير · العملاء · المنتجات · المخزون · المصروفات · أوامر الشغل ·
الحجوزات · الشحنات — أي بيانات عمل يومية تخصّ فرعاً.

### ٢. `BelongsToBranch` — موسوم بالفرع، تصفيته صريحة
```php
use App\Tenancy\BelongsToBranch;

class JournalLine extends BaseModel
{
    use BelongsToBranch;   // يُوسم بالفرع، لكن **بلا** Scope عالمي
}
```
**استخدمه للبيانات المحاسبية حصراً.** السبب حاسم: لو صُفّيت سطور القيد تلقائياً
لانكسر **ميزان المراجعة المجمّع** (قيود تختفي صامتةً) ولتعطّل خيار «كل الفروع».
التصفية تتم صراحةً في `ReportService` عبر مرشّح `branch_id`.

### ٣. `CompanyWide` — مشترك بإقرار واعٍ
```php
use App\Tenancy\CompanyWide;

class Account extends BaseModel implements CompanyWide
{
}
```
**استخدمه لـ:** إعدادات المؤسسة وهويتها (الاسم، الشعار، الرقم الضريبي) · دليل
الحسابات وأرصدته · الفروع والمخازن · المستخدمون والصلاحيات · **سطور المستندات**
(تتبع فرع رأسها فلا تُعزل مستقلّةً).

## مفاتيح المشاركة الخمسة — استثناءات اختيارية

العزل هو الأصل. المستخدم قد يختار **مشاركة** أنواع محدّدة عبر «إعدادات الفروع»:
العملاء · المنتجات · الموردون · مراكز التكلفة · تخصيص الحسابات.
تُقرأ من `BranchSettings` ولا تُلغي القاعدة — بل تُرخّص استثناءً واعياً.

## سلوك `BranchScope` بدقّة

1. **لا يعمل إلا مع سياق فرع مضبوط** (`BranchContext`) — فأوامر artisan والمهام
   المجدولة واختبارات الوحدة لا تُصفّى.
2. **يشمل `branch_id IS NULL`** — البيانات المنشأة قبل الفروع تبقى مرئية للجميع،
   فلا تختفي بيانات قائمة عند تفعيل العزل.
3. **قابل للتجاوز المتعمَّد** حين يكون التجميع مقصوداً:
   ```php
   Invoice::withoutGlobalScope(BranchScope::class)->…   // تقرير عبر كل الفروع
   ```

## قائمة فحص لأي قسم/وحدة جديدة

- [ ] هل صُنِّف كل نموذج جديد؟ (`BranchScoped` / `BelongsToBranch` / `CompanyWide`)
- [ ] إن كان `BranchScoped`: هل الهجرة تضيف `branch_id` nullable + فهرس `(tenant_id, branch_id)`؟
- [ ] هل التقارير التي تجمع عبر الفروع تتجاوز الـ Scope صراحةً؟
- [ ] هل الشاشة توضّح للمستخدم أي فرع يعرض؟
- [ ] هل يوجد اختبار يثبت أن فرعاً لا يرى بيانات فرع آخر؟
- [ ] هل مرّ `BranchIsolationGuardTest`؟ (يعمل تلقائياً في CI)

## الحارس الآلي

`tests/Feature/BranchIsolationGuardTest.php` يمرّ على كل نماذج `BaseModel` ويُفشل
البناء عند وجود نموذج غير مصنَّف، برسالة تشرح الخيارات الثلاثة.

يحوي أيضاً **قائمة انتظار سقّاطة** (`PENDING_ISOLATION`) للنماذج التشغيلية التي
تنتظر عمود `branch_id`: **تنقص ولا تزيد**، واختبارٌ يمنع تضخّمها. أي نموذج جديد
يُصنَّف فوراً — لا يُضاف إليها.

## مراجع

- التنفيذ: `app/Tenancy/{BranchScope,BranchScoped,BelongsToBranch,CompanyWide,BranchContext}.php`
- الوسيط: `app/Http/Middleware/SetBranch.php` (يحلّ الفرع من `X-Branch-Id` أو الفرع الرئيسي)
- الفرع الرئيسي: عمود `branches.is_main` بفهرس فريد جزئي — يتغيّر من «إعدادات الفروع» حصراً
